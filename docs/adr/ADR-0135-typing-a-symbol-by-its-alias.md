# ADR-0135: 별칭으로 특수문자를 치고, 자동완성 후보를 창의 말로 옮긴다

## 맥락

특수문자를 넣는 길은 지금 하나다. `:symbols` 나 팔레트로 판을 열고, 이름으로 걸러서 격자에서 고르는 것이다(ADR-0056). 그 판은 「무엇이 있는지 모를 때 찾는」 자리로 잘 맞는다.

**아는 글자를 넣을 때는 그 길이 길다.** 👍 를 넣으려고 판을 열고 `엄지` 를 치고 격자에서 고르고 판을 닫는다. github 에서 `:+1:` 한 번에 되던 것이다. `docs/tasks.md` 에 「특수문자의 별칭 추가」와 「`:+1:` 을 입력하면 자동 완성으로 특수 문자 보여주기」가 두 항목으로 올라와 있었다.

붙일 자리는 이미 있다. insert 에서 뜨는 자동완성 목록이다(ADR-0066). 위아래로 고르고 `enter`·`tab` 으로 넣는 손이 이미 익어 있다.

**그 목록이 LSP 에 묶여 있다.** `completion.items` 가 `[]lsp.CompletionItem` 이고, 그리는 자리(`completionLabel`) 와 넣는 자리(`applyCompletion`) 가 그 타입을 직접 본다. 넣을 범위도 서버가 준 `TextEdit` 을 확정 시점에 UTF-16 에서 byte 로 옮겨 쓴다.

정할 것은 넷이다.

1. 별칭을 어디에 담을지
2. 후보를 지금 목록에 어떻게 얹을지
3. 언제 뜨고 어떻게 확정할지
4. 별칭 데이터를 어디서 얻을지

## 결정

### 1. `Symbol` 에 `Aliases` 를 둔다. `Keywords` 를 쓰지 않는다

`assets.Symbol` 에 필드가 하나 는다.

```go
Keywords string // 판에서 눈으로 찾을 때 걸리는 말
Aliases  string // `:+1:` 처럼 쳐서 넣는 이름
```

**두 몫이 다르다.** `Keywords` 는 특수문자 판에서 걸리는 말이라 한국어와 뜻이 넓은 말이 들어간다(`▲` 에 `세모`). 넓게 걸리는 것이 그쪽의 이득이다.

`Aliases` 는 치는 이름이다. `:` 뒤에 칠 수 있는 글자(ASCII 소문자·숫자·`+ - _`) 뿐이고 뜻이 하나로 좁아야 한다. `:s` 를 쳤을 때 `세모` 가 끌려오면 무엇이 뜬 것인지 종잡을 수 없다.

한 필드에 두 몫을 담으면 한쪽 규칙이 다른 쪽을 망친다. `Keywords` 에 `+1` 을 넣으면 판에서 `+1` 로 👍 를 찾을 수 있게 되는데, 그 대가로 별칭 쪽이 한국어와 공백 섞인 말을 걸러내야 한다.

### 2. 후보를 창의 말로 옮긴다. LSP 타입을 목록에서 뗀다

`completion.items` 가 `[]completionItem` 이 된다. core 의 타입이다.

```go
type completionItem struct {
	label  string
	detail string
	text   string
	start, end int // 이 줄에서 바꿀 범위. byte 열이고, 없으면 -1
}
```

**후보가 서버에서만 오지 않게 됐다는 것이 근거다.** 목록과 키와 그리는 자리가 갈래마다 나뉘면, 뜨는 자리와 고르는 키를 두 번 익히게 되고 그리는 코드가 둘로 갈린다. 창을 하나로 두려면 그 창이 보는 타입이 어느 한쪽 것이면 안 된다.

**옮기는 자리는 `finishCompletion` 하나다.** 서버 답을 받는 곳이다. 범위를 byte 로 옮기는 일도 여기로 왔다 — 예전에는 넣는 자리(`applyCompletion`) 에서 했는데, 그러면 `:별칭` 후보도 UTF-16 범위를 지어내야 한다. 옮기는 일은 서버의 말을 쓰는 쪽에 두는 것이 맞다(ADR-0125 가 「창은 서버를 모른다」로 정한 방향이다).

`lsp.CompletionItem` 의 `Kind`·`SortText` 는 옮기지 않는다. 그리는 쪽이 쓰지 않는다.

**대안: `lsp.CompletionItem` 을 우리 손으로 지어서 넣는다.** 변경이 가장 적다. 기각한 까닭은 `internal/lsp` 가 「규격을 담는 자리」라는 뜻을 잃기 때문이다. 그 패키지의 타입에 서버와 무관한 후보가 담기면, 다음 사람이 그 필드를 보고 규격을 짐작하게 된다.

**대안: 별도 후보 창을 둔다.** 기각한 까닭은 그리는 자리와 키 처리가 둘로 나뉘는 것이다. 창의 폭·밀기·「몇째/모두 몇」이 두 벌이 되고, 한쪽에 고친 것이 다른 쪽에 빠진다.

### 3. `:` 뒤 한 글자부터 뜨고, `enter`·`tab` 으로 확정한다

커서 앞이 `:별칭` 꼴이면 그 별칭으로 후보를 세운다. 닫는 `:` 까지 친 것도 같은 별칭으로 본다 — `:+1:` 를 끝까지 치는 사람과 목록에서 고르는 사람이 같은 답에 닿아야 한다.

**`:` 만 쳤을 때는 뜨지 않는다.** 산문과 yaml 에서 `:` 는 흔하고, 그 자리마다 목록이 뜨면 방해가 된다.

**한 글자부터 뜨는 것이 두 글자보다 낫다.** 목록의 값이 「보고 고르는」 것이라, 별칭을 거의 다 치고 나서 뜨면 그 값이 없다. `:s` 로 여럿이 걸리고 이어 치며 좁히는 것이 이 기능의 쓰임새다.

**걸리는 별칭이 없으면 뜨지 않는다.** 이것이 오탐을 좁히는 실제 장치다. 별칭이 손으로 적은 서른몇 개뿐이라 `:zzz` 같은 것은 아무것도 끌어오지 않는다.

**감수하는 것: `enter` 가 가로채인다.** 목록이 떠 있는 동안 `enter`·`tab` 은 넣기다(ADR-0066). `key:on` 처럼 `:` 뒤에 별칭과 겹치는 글자를 붙여 치고 줄을 바꾸면 이모지가 들어간다. `:` 뒤에 공백을 두는 산문에서는 나지 않고(공백에서 목록이 닫힌다), 겹치는 자리는 짧은 별칭(`:ok`·`:x`) 에 남는다. 대가로 얻는 것이 「친 손 그대로 확정」이라 그쪽을 골랐다.

**서버에 묻지 않는다.** 답이 우리 표에 있어서 기다릴 것이 없다. 그래서 LSP 가 붙지 않는 파일(markdown·평문) 에서도 뜬다 — 이모지를 치는 자리가 대개 그쪽이다.

커서가 `:별칭` 안에 있으면 그 갈래로 확정하고 서버는 보지 않는다. 「자리인가」와 「걸렸나」를 갈라 둔 까닭이 여기다. 자리이면서 아무것도 걸리지 않을 때(`:zz`) 목록을 닫아야 하는데, 그 둘이 한 답에 섞이면 좁히다 빈 목록이 화면에 붙어 있게 된다.

### 4. 별칭은 손으로 적는다

`assets.CuratedSymbols` 의 자주 쓰는 글자 서른다섯 개에 github 표기를 적었다. `+1`·`tada`·`rocket` 처럼 널리 굳은 것들이다. 이름이 길어 아무도 치지 않을 것에는 짧은 것을 같이 뒀다(`white_check_mark check`).

**`emoji-cheat-sheet` 같은 표를 받아 생성하지 않는다.** 수백 개가 한꺼번에 오면 목록이 그것으로 뒤덮이고, 밖에서 받은 낱말이 우리 표를 점령한다. 큐레이션 표가 손으로 적는 자리라는 것도 그대로다(ADR-0056). 표가 모자라면 한 줄이 는다.

**훑어서 얻은 글자에는 별칭이 없다.** `indexSymbols` 가 유니코드 전체에서 모으는 12000 여 개다(ADR-0056). 별칭은 사람이 이름을 정해 주는 것이라 훑어서 나올 것이 아니고, 후보를 그 목록에서 찾으면 걸러야 할 것이 400 배로 는다.

## 결과

- `:+1` 을 치면 목록이 뜨고 `enter` 로 👍 가 들어간다. 판을 열지 않는다
- 자동완성 창이 서버 후보와 별칭 후보를 같이 쓴다. 뜨는 자리와 고르는 키가 하나다
- LSP 가 붙지 않는 파일에서도 자동완성이 뜬다. 그 창이 처음으로 서버 없이 뜬다
- `completion` 이 `internal/lsp` 를 보지 않는다. 옮기는 자리가 `finishCompletion` 하나다
- `:` 뒤에 별칭과 겹치는 글자를 붙여 치고 `enter` 를 누르면 이모지가 들어간다. 짧은 별칭에 남는 대가다
