# ADR-0123: 창이 자기 크기를 든다. `width` 는 인자가 아니라 상태였다

## 맥락

ADR-0121 이 커서를 `viewport` 로 빼면서 「화면 폭(`width`) 인자가 아직 메서드 예순 남짓에 남아 있다. 화면 행 이동과 `desiredX` 가 줄바꿈에 걸려 있어서인데, 그 둘이 viewport 로 갔으므로 이 인자도 그쪽으로 모을 수 있다」고 적어 두었다.

세어 보니 이랬다.

| | 수 |
|---|---|
| `viewport` 메서드 | 90 |
| 그중 `width` 를 받는 것 | **71** |
| `height` 도 받는 것 | 8 |
| `e.contentWidth()` 를 넘기는 자리 | 112 |
| `width` 가 나오는 시험 줄 | 300 남짓 |

## 1. 71 개 중 52 개는 쓰지도 않았다

본문이 `width` 를 어떻게 쓰는지 갈라 보았다.

| | 메서드 |
|---|---|
| 아래로 넘기기만 한다 | **52** |
| 본문이 직접 쓴다 | 19 |

그 19 개도 13 개는 한 번 쓴다. **순수한 실꿰기였다.** `deleteRange(area, width)` 는 지우는 데 폭이 필요해서가 아니라 지운 뒤 커서를 놓는 자리가 그것을 필요로 해서 받는 것이고, 그 값은 세 겹 아래까지 그대로 내려간다.

## 2. 창은 이미 폭에서 나온 값을 들고 있었다

이것이 결정의 근거다.

- `viewTop.row` 는 「그 줄의 몇 번째 wrap 행」이다. 폭이 없으면 뜻이 없다
- `desiredX` 는 「화면 행 안에서 센 칸」이다(ADR-0108). 역시 폭이 없으면 뜻이 없다

**파생값은 안에 있는데 그것을 만든 값만 밖에 있었다.** 그래서 폭은 인자가 아니라 창의 상태다.

```go
// 편집 영역 전체다. 본문 앞 칸은 아직 안 뗐다
type viewSize struct {
	width  int
	height int
}
```

`viewport` 가 이것을 필드로 들고, `contentWidth()` 가 거기서 본문 앞 칸을 뗀다.

**처음에 `viewPane` 이라 지었다가 물렸다.** 짓기 전에 저장소를 안 찾아봤다.

찾아보니 `pane` 은 이미 두 자리에 있었고, **둘이 서로 다른 것을 가리킨다.**

| 있던 `pane` | 무엇 | 자리 |
|---|---|---|
| `paneHeight()` | 편집 영역 **+ 판(drawer)** 을 합친 세로 띠 | 함수 이름 하나 |
| 「pane 이 둘뿐이라」 | 편집 영역과 sidebar. `ctrl+w` 가 오가는 vim 의 window | 3 곳 |

새 type 은 판까지 뗀 나머지라 앞엣것과 **딱 `drawerHeight` 만큼 다르다.** 판이 닫혀 있는 동안은 우연히 같아서 어긋남이 안 보인다. 이것이 나쁜 쪽이다.

`col` 이 세 단위였던 것을 잡은 ADR-0122 바로 다음에 같은 짓을 할 뻔했다.

## 3. 폭이 아니라 **크기**를 든다

`contentWidth` 를 담지 않고 `size` 를 담는다. **본문 앞 칸의 폭이 이 파일의 줄 수에서 나오기 때문**이다(ADR-0086). 담아 두면 999 줄에서 1000 줄로 넘어가는 순간부터 조용히 한 칸 틀리고, 편집할 때마다 다시 밀어 넣어야 한다.

`size` 는 화면을 나누는 결정에서만 바뀐다. 줄 수는 창이 스스로 아는 것이라 `contentWidth()` 가 그때그때 잰다.

## 4. editor 가 민다. pubsub 이 아니다

「editor 가 event 를 발행하고 viewport 가 구독하는」 길을 재 봤다. 세 가지가 걸린다.

- **발행 자리가 안 줄어든다.** 문제는 전달 수단이 아니라 「폭이 바뀌는 자리가 흩어져 있다」다. 잊는 자리가 대입에서 발행으로 이름만 바뀐다
- **구독을 걸 주소가 없다.** `editor.buffers` 가 `[]viewport` 라 `slices.Insert`·`slices.Delete` 가 원소를 통째로 옮긴다. 구독자의 주소가 tab 하나 열 때마다 바뀐다. `[]*viewport` 로 가는 것은 화면 분할 때 하기로 미뤄 둔 결정이다(ADR-0121)
- **고리가 둘이 된다.** bubbletea 가 이미 메시지 고리다. 폭은 `Update` 안에서 바뀌고 같은 `Update` 안에서 쓰이는데(`e.drawerHeight = ...` 바로 다음 줄이 `e.scrollToCursor()` 다), 비동기 전달이 끼면 그 프레임이 틀린다. `internal/pubsub` 은 goroutine·context 물건이고 편집기가 한 곳도 안 쓴다

**대신 흩어진 대입을 setter 로 모았다.**

| | 전 | 후 |
|---|---|---|
| `e.drawerHeight = ...` | 13 곳 | `setDrawerHeight` 1 곳 |
| 창 크기 | 1 | `resize` 1 |
| sidebar 여닫기 | 2 | `toggleTree` 1 |
| 창을 새로 끼우기 | 3 | 3 (`newTab`·`openTab`·`editTab`) |

**18 → 6 이다.** 판들이 전부 `*editor` 를 embed 해서 `m.drawerHeight = ...` 이 `m.setDrawerHeight(...)` 로 승격 그대로 섰다.

## 5. 일곱 번째 자리가 실제로 있었다

여섯을 다 넣고 훑다가 `adopt`(다시 읽기) 에서 하나가 더 나왔다.

```go
*buf = buf.adopt(newBuffer(buf.path, data))
```

`newBuffer` 가 지은 새 창은 editor 를 지나오지 않아서 자기 크기를 모른다. `adopt` 이 커서와 `top` 은 이어받으면서 `size` 는 놓쳐서, **다시 읽는 순간 폭이 0 이 되어 본문이 사라진다.** 시험이 없어서 조용히 지나갔다.

`next.size = buf.size` 를 넣고 `TestBufferReloadKeepsPane` 으로 못 박았다. 그 줄을 빼면 시험이 걸리는 것을 확인했다.

**이것이 「밀어 넣기」의 값이자 대가다.** 크기가 필드가 되면 「누가 언제 그것을 넣는가」가 새로 생긴 짐이고, 그 짐은 pubsub 을 깔아도 그대로 남았을 것이다. 다만 이쪽은 값이 0 이라 **화면이 비는 것으로 곧바로 드러난다** — 잘못된 폭으로 그리는 것보다 낫다.

## 6. 어떻게 옮겼나

이름 하나가 여러 type 에 있어서(`scrollTo` 는 열세 type 이 가졌다) 글자로 고칠 수 없었다. 인자 개수와 `width` 의 자리를 선언에서 읽어 두고, **그 개수와 정확히 맞는 호출만** 고치는 도구를 썼다.

- 옮긴 선언 105 개 (`viewport` 70, motion 34, 그 밖 1)
- 남은 것은 컴파일러가 잡았다. 「declared and not used: width」 로 죽은 지역 변수 스물 남짓이 드러났고, 이름 없는 인자로 적힌 motion 넷(`span(viewport, int, int)`) 은 인터페이스 불일치로 걸렸다

**motion 도 같이 옮겼다.** `move(buf *viewport, count, width int)` 34 개가 같은 짐을 지고 있었다. 창을 인자로 받으면서 그 창의 폭을 따로 받던 자리다.

`Buffer` 의 `retreatRows`·`advanceRows` 둘은 그대로 `width` 를 받는다. `Buffer` 에는 자리가 없다 — 글만 드는 type 이라는 ADR-0121 의 가름이 여기서도 선다.

## 남는 것

- **`height`.** 여덟 개가 아직 인자로 받는다. `size.height` 가 이미 있으므로 같은 손으로 걷을 수 있는데, 화면 높이를 쓰는 자리가 판(drawer) 과 얽혀 있어 따로 본다
- **시험이 창을 직접 세우는 자리.** `setContentWidth` 라는 시험 전용 손을 두었다. 본문 폭을 정하고 싶어 하는 시험에 뗄 만큼을 도로 얹어 준다
- **화면 분할.** 그때 `layoutViews` 가 창마다 다른 크기를 배정하게 된다. 지금 전부 같은 값을 받는 것은 tab 이 화면을 나눠 쓰지 않기 때문이다(ADR-0121)

## 되짚은 것

**「18 곳을 어떻게 빠뜨리지 않을까」를 전달 수단으로 풀려 했던 것이 잘못이었다.** pubsub 이든 대입이든 발행은 사람이 부른다. 실제로 값을 낸 것은 **바뀌는 자리 자체를 줄인 것**이고(setter 로 13→1), 그러고도 남은 일곱 번째는 결국 훑어서 찾았다.

그리고 그 일곱 번째는 **인자였을 때는 있을 수 없던 버그**다. 인자는 부르는 쪽이 늘 지금 값을 넘기므로 낡을 수가 없다. 상태로 바꾼 값은 「누가 갱신하는가」를 새로 져야 한다. 그 짐을 지기로 한 근거가 §2 하나다. 창이 이미 그 폭에서 나온 값들을 들고 있었다는 것.

**낱말도 되짚었다.** 새 type 에 `pane` 이라 붙였다가 물렸다(§3). ADR-0122 가 「주석은 검사되지 않지만 type 은 검사된다」고 적었는데, **낱말이 겹치는 것은 type 도 안 잡아 준다** — `paneHeight()` 와 `pane.height` 는 값이 다른데 둘 다 `int` 라 둘 다 컴파일된다.

그러다 저장소의 낱말 둘을 세어 봤다.

- **「판」은 흔들리지 않았다.** drawer 를 쓰는 파일에 171 곳, 화면을 통째로 쓰는 파일에 4 곳이다. spec 도 30 줄 중 대부분이 drawer 를 「판」이라 부른다. 어긋난 것은 `spec.md` 의 **한 줄**뿐이었다(「경계는 `drawer 냐 판이냐` 하나다」). 175 대 1 이라 그 한 줄을 고쳤다
- **흔들린 쪽은 `pane` 이었다.** 자리가 넷뿐인데 그 안에서 두 가지를 가리킨다. 그래서 `paneHeight` 를 **`textAndDrawerHeight`** 로 바꿨다. 나눠 쓰는 둘을 이름에 다 적으면 「판을 안고 있나」를 물어볼 일이 없다. 남은 `pane` 은 `ctrl+w` 쪽 셋이고 그것은 vim 의 어휘라 그대로 둔다

**적게 쓰인 낱말이 더 위험했다.** 「판」은 175 번 쓰이며 뜻이 굳었고, `pane` 은 네 번 쓰이는 동안 아무도 그것이 무엇인지 정하지 않았다.
