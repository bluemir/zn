# ADR-0037: visual mode 는 `v`·`V` 둘이고, 고른 범위는 Buffer 가 든다

- 상태: 채택
- 날짜: 2026-08-20

## 맥락

`docs/spec.md` 의 `### visual mode` 는 「**아직 없다**」 한 줄이었다. ADR-0002 는 mode 를 model 로
둔 근거로 「visual mode 는 선택 시작 지점(anchor) 이 필요하다」를 들었고, 정하지 않은 것으로
「visual mode 를 몇 종류(char/line/block) 로 둘지」를 남겼다. ADR-0013·0017·0018 은 각각
「visual mode 에서 고른 범위를 지우는 것/복사하는 것/한 글자로 덮는 것」을 범위 밖으로 미뤘고,
ADR-0012 는 드래그 선택을 「visual mode 를 정할 때 같이 본다」로 남겼다.

즉 이 결정 하나가 다섯 ADR 이 미뤄 둔 자리를 닫는다.

operator 쪽은 이미 다 서 있었다. `motionRange` 가 범위를 나타내고(ADR-0013) `d`·`y`·`c` 가
그것을 받아 지우고 복사하고 바꾼다(ADR-0017, ADR-0033). visual 이 새로 가져오는 것은
**범위를 motion 이 아니라 손이 정한다**는 것뿐이다.

## 결정

**종류는 `v`(글자) 와 `V`(줄) 둘이다.** blockwise(`ctrl+v`) 는 넣지 않았다.

**받는 동작은 `d` `x` `y` `c` 넷과 갈래를 바꾸는 `v` `V`, 나가는 `esc` 다.** 이동 키는 전부
받아서 범위를 늘린다. 숫자 접두와 접두 키(`gg`) 도 그대로 먹는다.

**고른 범위는 `Buffer` 가 든다.** anchor 하나(`selection`) 이고 반대쪽 끝은 커서다.

**범위를 받는 쪽을 motion 에서 떼어냈다.** `deleteByMotion` 이 「span 을 구한다 → 범위에
적용한다」 두 토막이던 것을 `deleteRange`·`yankRange`·`changeRange` 로 갈랐다. visual 은
앞 토막 없이 뒤 토막만 쓴다.

**고른 범위는 커서가 선 글자를 넣는다(inclusive).** `vd` 가 `x` 와 같다.

**색은 256색 고정 배경(238) 에 밝은 글자(231) 다. 검색 강조와 겹치면 검색이 이긴다.**

**mouse 드래그가 charwise visual 을 연다.** 클릭만 하는 것은 지금처럼 커서 이동이다.

**`:` `/` `gt` `gT` `ctrl+w` `ctrl+p` 는 visual 이 받지 않는다.**

## 근거

### 종류를 둘로 줄인 것

**`v` 와 `V` 는 이미 있는 것에 얹히고 `ctrl+v` 는 아니다.** charwise 는
`motionRange{linewise: false}` 이고 linewise 는 `true` 라, 지우기·복사·바꾸기가 한 줄도
바뀌지 않고 그대로 받는다. blockwise 는 `register` 에 갈래를 하나 더 만들고
사각 범위의 지우기·붙여넣기·`I`/`A` 를 새로 짜야 한다. 폭이 다른 글자(한글) 와 tab 이 낀
사각형을 화면 칸 기준으로 잡는 일도 같이 온다.

**쓰는 빈도가 크게 다르다.** 두 종류로 대부분의 흐름이 선다. blockwise 가 필요해지면
그때 `register` 를 손대는 것이 맞고, 지금 미리 갈래를 늘려 두면 쓰지 않는 분기가 남는다.

### 동작을 넷으로 줄인 것

**`d` `y` `c` 는 범위 계산을 이미 공유한다.** 여기에 얹는 것은 「범위를 어디서 얻는가」뿐이다.
`o`(양끝 바꾸기)·visual `p`·visual `r` 은 각각 새 규칙을 하나씩 들여온다. `o` 는 anchor 를
뒤집고, `p` 는 지우기와 붙여넣기를 한 되돌리기 구간으로 묶어야 하고, `r` 은 글자 하나를
기다리는 상태(`normalReplace` 와 같은 자리, ADR-0018) 를 visual 쪽에도 만들어야 한다.
셋 다 visual 이 서 있어야 값을 판단할 수 있는 것이라 미뤘다.

**`x` 를 `d` 와 같게 둔 것은 범위가 이미 정해져 있어서다.** normal 의 `x` 는 `dl` 이라
「한 글자」라는 뜻이 있지만, visual 에서는 고른 것이 전부라 둘이 갈릴 자리가 없다. vim 도 같다.

### 고른 범위를 Buffer 에 둔 것

**이 저장소는 이미 선을 그어 두었다.** `editor` 가 드는 것은 tab 을 넘는 것이다.
`register` 는 「tab 을 넘어 붙는다」이고, 마지막 검색은 「tab 을 옮겨도 `n` 이 같은 것을
찾는다」다(`docs/spec.md`). `Buffer` 가 드는 것은 그 파일에 딸린 것이다. 「파일별 커서 위치와
스크롤은 tab 을 오가도 그대로 남는다」가 그것이다.

고른 범위는 tab 을 넘지 않는다. anchor 는 `lines` 의 index 와 그 줄 안의 byte offset 이라
그 `Buffer` 밖에서는 뜻이 없는 좌표이고, `cursorLine`/`cursorCol` 의 짝이라 `desiredCol` 과
같은 갈래의 값이다.

**mode model(`viewEditorVisual`) 에 두는 길을 버렸다.** ADR-0002 가 그린 그림이고
「mode 를 떠나면 model 과 함께 사라져서 놓는 코드가 없다」는 것이 강했다. 버린 이유는 셋이다.

- **동작이 볼 수 없다.** ADR-0034 가 `run(e *editor)` 하나로 모은 계약을 다시 갈라
  `run(e *editor, sel selection)` 두 번째 interface 를 만들어야 한다. 파서가 돌려주는 한
  목록에 두 갈래가 섞인다. 이동은 `actionMove` 라 `action` 이다.
- **파싱할 때 범위를 계산해 동작에 담는 우회는 틀린다.** 한글은 키 하나가 동작 여럿이 된다
  (ADR-0008). `강` 은 `r` `k` `d` 라서 「위로 → 지우기」가 한 press 에 오는데, 파싱 시점의
  범위는 `k` 가 커서를 옮기기 전 값이다. 범위는 실행 시점에 읽어야 한다.
- **`:'<,'>` 와 `gv` 는 visual 을 떠난 뒤에 마지막 범위를 읽는다.** mode model 에 두면
  그때 다시 어딘가로 옮겨야 한다.

**대가는 놓는 것을 손으로 한다는 것이다.** visual 을 떠나는 문이 `normalMode` 와 `insertMode`
둘뿐이라 그 두 생성자 첫머리가 놓는 자리다. `:` `/` `ctrl+p` 를 받지 않는 것이 「문이 둘뿐」을
지킨다.

### 범위를 받는 쪽을 떼어낸 것

`deleteByMotion` 은 원래 두 토막이었다. 앞은 `m.span(...)` 이고 뒤는 `linewise` 로 갈라
`deleteLines`/`deleteText` 를 부르는 것이다. visual 은 앞이 필요 없고 뒤만 필요하다.

**`motionSelection` 을 만들어 기존 동작에 끼우는 길을 버렸다.** 고른 범위를 그대로 돌려주는
motion type 을 두면 `actionDelete{motion: motionSelection{...}}` 로 아무것도 안 고치고
끝난다. 그러나 `span(buf, count, width)` 가 인자를 하나도 쓰지 않는 거짓말이 되고,
visual 의 동작은 어차피 mode 를 되돌려야 해서 새 type 이 필요하다. 토막을 가르는 쪽이
이미 있던 구조를 드러내기만 한다.

### inclusive

vim 의 visual 이 그렇다. `v` 만 누르고 `d` 를 치면 커서 아래 한 글자가 지워져야 한다.
아무것도 지워지지 않으면 `v` 가 무엇을 골랐는지 화면과 어긋난다.
`e` 가 `span` 에서 `includeCursorCluster` 를 부르는 것과 같은 자리이고(ADR-0013),
grapheme cluster 단위라 한글·이모지도 통째로 든다.

**`v` 가 글자 단위라는 것이 `G`·`gg` 에서 드러난다.** `vGd` 는 마지막 줄의 첫 글자까지지
파일 전체가 아니다. 줄 단위로 지우려면 `VG` 다. vim 과 같다.

### 색과 겹침

반전은 statusBar·tabline 이 이미 쓰고 있어서(ADR-0004) 본문에 쓰면 그 둘과 같은 모양이 된다.
검색 강조가 256색을 고른 것과 같은 자리다(ADR-0010). 글자색까지 고정하는 것도 검색과 같은
이유다. 배경만 정하면 밝은 테마에서 읽히지 않는다.

**겹친 자리는 검색이 이긴다.** 선택 배경이 찾은 자리를 덮으면 `n` 이 데려다 놓은 곳이 어디인지
보이지 않는다. 고른 범위는 커서로 이미 드러나지만 매칭은 색이 유일한 표시다.

`renderRow` 의 walker 는 왼쪽에서 오른쪽으로 한 번만 지나가므로 겹치는 두 목록을 그냥 넘길 수
없다. `rowHighlight.segments` 가 먼저 겹치지 않게 펴서 넘긴다.

**줄 끝을 넘는 선택은 빈 칸 하나를 더 칠한다.** `V` 로 고른 빈 줄은 칠할 글자가 없어서
이 칸이 없으면 골랐다는 것이 화면에 드러나지 않는다. vim 과 같다.

`renderRow` 는 이제 검색만의 것이 아니라서 `search.go` 에서 `render-row.go` 로 옮겼다.
그리는 코드만 든 파일이다(ADR-0036).

### 드래그

**클릭은 커서 이동이고 드래그가 visual 을 연다.** vim 이 그렇다(`mouse=a`). 누른 자리가
anchor 이고 버튼을 누른 채 포인터가 움직이는 순간 들어간다. 뗀 뒤에도 visual 에 머문다.
`MouseReleaseMsg` 는 받지 않는다.

`MouseModeCellMotion` 이라 motion 이벤트는 이미 오고 있었고 지금까지 버렸다(ADR-0012).
좌표 변환도 `positionAt` 이 이미 있다. ADR-0012 가 「나중에 드래그 선택을 넣을 때 그대로
쓴다」고 적어 둔 자리다.

**double/triple-click 은 없다.** bubbletea 의 `Mouse` 에 누른 횟수가 없어서 vim 의
단어·줄 선택을 옮길 수 없다(ADR-0012 가 트리에서 만난 것과 같은 제약이다).

**여는 것은 편집 영역 안의 움직임뿐이고, 일단 열린 뒤에는 밖으로 나가도 따라간다.**
밖에서 시작한 드래그까지 받으면 tabline 을 눌러 tab 을 옮긴 뒤의 움직임이 엉뚱한 범위를 연다.
반대로 열린 뒤에 손을 놓치면 어디까지 골랐는지 알 수 없으므로, 밖으로 나간 좌표는 편집 영역
안으로 당겨서 읽는다. sidebar 쪽으로 끌면 줄 시작이고 statusBar 아래로 끌면 맨 아랫행이다.
포커스는 옮기지 않는다. 끄는 중이라 「다른 영역을 눌렀다」가 아니다.

**위아래로 나가면 한 행씩 굴린다.** motion 이벤트는 포인터가 실제로 움직일 때만 오므로
잡은 채 가만히 있으면 굴러가지 않는다. 타이머를 두면 mode 밖에서 도는 것이 하나 늘고,
「움직이면 굴러간다」로도 화면 끝의 줄에 닿을 수 있어서 두지 않았다.

**visual 에서 클릭하면 visual 이 끝난다.** 누른 자리가 새 시작이다. tab 을 옮기기 전에
놓는다. 옮기고 나면 놓을 `Buffer` 가 바뀌어서 고른 범위가 보이지 않는 tab 에 남는다.
statusBar 만은 눌러도 아무 일이 없다. 다른 mode 와 같다.

### 파서를 나눈 것

`visualState` 는 `normalState` 와 같은 모양이지만 표를 나눠 가진다. `sidebarState` 가 갈린
것과 같은 이유다. `normalStart` 가 `d`·`y`·`c` 를 operator 로 먹는데, visual 에서 `d` 는
다음 키를 기다리지 않고 그 자리에서 끝난다.

**표는 나눠 갖지 않는다.** `motionFor`·`prefixMotion`·`expandHangul`·`keyDigit` 을 그대로
쓰고, 새로 두는 것은 이동이 아닌 키 하나(`visualAction`) 뿐이다. 상태는 셋이다.
operator 가 없어서 `partial` 이 없고 글자 하나를 받는 `normalReplace` 도 없다.

**`V` 는 한글 상태에서 낼 수 없다.** `ㅍ` 의 shift 자리에 다른 글자가 없어서 `G`·`B` 와
같다(ADR-0008). `v` 는 `ㅍ` 으로 낼 수 있다.

### 받지 않는 키

`:` 는 vim 에서 `:'<,'>` 범위 명령이 되는데 범위 문법이 아직 없다. `/` 는 vim 에서 선택을
늘리는 motion 인데 검색은 operator 뒤에도 받지 않는 자리다(ADR-0013). `gt`·`ctrl+w` 는
보고 있는 파일이나 pane 을 바꾸는 것이라 고른 범위가 화면에서 사라진다. `ctrl+p` 도 같다.

짝이 없는 조합이 아무 일도 하지 않는 것과 같은 규칙이라(`dgt`), 잘못 누른 키는 `esc` 없이도
그냥 먹히고 만다. 받는 키를 늘리는 것은 각각 따로 정할 일이다.

## 결과

- `v` `V` 로 골라 `d` `x` `y` `c` 한다. 드래그로도 고른다
- 다섯 ADR 이 미뤄 둔 자리가 닫혔다(ADR-0002, 0012, 0013, 0017, 0018)
- 범위를 받는 함수 셋(`deleteRange`·`yankRange`·`changeRange`) 이 motion 없이 불릴 수 있게 됐다.
  `:1,5d` 같은 범위 명령이 들어올 때 같은 자리를 쓴다
- `renderRow` 가 강조 원천 둘을 받는다. 셋째가 생기면(diff, 진단 marker) 같은 길로 온다
- 공용 `Update` case(크기·클릭·휠) 가 mode 하나만큼 또 늘었다. ADR-0002 가 「늘어나면 공용
  처리로 뺀다」고 해둔 값이라 `docs/tasks.md` 에 적어 둔다

## 뒤에 뒤집은 것

**visual 이 받는 키를 셋 늘렸다**(ADR-0085 를 만들며). 이 ADR 은 「짝이 없는 조합이 아무 일도
하지 않는 것과 같아서 잘못 누른 키는 그냥 먹히고 만다」로 키 면적을 좁게 두었는데, 그 자가
**잘못 누른 키**를 위한 것이지 **일부러 치는 키**를 위한 것은 아니었다.

- **`\c`(leader)**
	- visual 은 leader 자체를 안 받았다. 고른 것을 평문으로 내보내는 문이 필요한데 한 글자
	  키를 가져오면 vim 이 쓸 자리를 닫는다.
	- 여는 값은 상태가 아니라 표 하나였다(`visualPrefixAction`).
	- normal 의 `prefixAction` 을 나눠 쓰지 않은 것은 그 표가 든 것이 `gt`·`\gd` 처럼
	  **visual 이 받지 않기로 한 것이 대부분**이라서다 (ADR-0085)
- **`ctrl+z`**
	- `ctrl+c` 는 받는데 이것만 빠져 있었고 까닭이 적혀 있지 않았다.
	- 둘 다 편집기 밖으로 나가는 손짓이고 고른 것을 건드리지 않는다 (ADR-0023)
- **`ctrl+p`**
	- 팔레트를 **고른 것을 두고** 연다. 상자 뒤로 그대로 칠해져 있고, 무엇을 고르는 순간
	  놓는다(`viewPalette.run`).
	- 놓는 자리가 하나여야 하는 것은 놓지 않았을 때 셋이 어긋나기 때문이다. 커서를 옮기며
	  둘러보는 판에서 강조가 커서를 따라 널뛰고, 특수문자 판은 고른 것이 칠해진 채 커서 뒤에
	  넣으며, 다른 파일을 열면 `normalMode` 가 새 buffer 만 지워서 원래 tab 에 유령 강조가 남는다.
	- **tab 이 바뀌기 전이라 지우는 buffer 가 언제나 옳다**

`:` 는 그대로 안 받는다. 그쪽은 키 면적 문제가 아니라 `'<,'>` 가 서기 전에는 고른 범위를
명령줄에 실을 길이 없어서 걸린 자리다.

## 이 ADR 이 정하지 않는 것

- blockwise visual(`ctrl+v`)
- visual 의 `o`(양끝 바꾸기)·`p`(고른 자리를 register 로 바꾸기)·`r`(한 글자로 덮기)
- `gv`(마지막 선택 되살리기) 와 `:'<,'>`. 지금 `selection` 이 드는 것은 anchor 하나이고
  반대쪽 끝은 커서라, visual 을 나가면서 커서가 움직이면 짝이 사라진다.
  그때는 anchor 가 아니라 확정된 `motionRange` 를 남겨야 한다
- statusBar 에 고른 크기(`3 줄`, `12 글자`) 를 보일지
- insert mode 에서의 드래그. 지금은 받지 않는다
