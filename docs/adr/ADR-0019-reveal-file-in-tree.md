# ADR-0019: 보는 파일이 바뀌면 sidebar 트리가 그 자리를 펼치고 고른다

- 상태: 채택
- 날짜: 2026-08-13

## 맥락

파일을 여는 길은 이제 넷이다 — CLI 인자, sidebar 의 `Enter`, command palette(ADR-0011),
tab 전환(`gt`/`gT`·tabline 클릭). 이 중 트리에서 고른 것만 트리가 알고 있고 나머지는
**트리가 지금 무엇을 보고 있는지 모른다.** `ctrl+w ctrl+w` 로 트리에 가면 커서가 뿌리나
직전에 훑던 엉뚱한 자리에 있다.

불편이 겹치는 자리는 이렇다.

- 팔레트로 `internal/core/editor.go` 를 열고 그 옆 파일을 보려면, 트리에서 `internal` →
  `core` 를 손으로 다시 펼치고 스크롤해서 내려가야 한다. 팔레트가 이름을 알 때는 빠르지만
  "이 파일 근처에 무엇이 있나" 는 트리만 답할 수 있다.
- `zn internal/core/editor.go` 로 시작하면 트리는 뿌리만 펼친 상태다. 편집 중인 파일이
  트리 어디에 있는지가 화면 어디에도 없다.
- tab 을 오가면 statusBar 의 경로만 바뀐다. 트리는 직전 자리에 그대로 남아서, 화면 왼쪽 32 칸이
  지금 보는 파일과 무관한 것을 계속 보여준다.

`docs/tasks.md` 에 "command palette 를 통해서 파일을 열때 sidebar 에서 해당 파일 위치 자동으로
펼치기" 로 잡혀 있던 건이다.

## 결정

**`sidebar.reveal(path)` 를 넣는다.** 뿌리 기준 상대 경로를 앞에서부터 따라가며 지나는
디렉터리를 펼치고, 마지막 항목을 고른 자리(`selected`) 로 삼는다.

**보는 파일이 바뀌는 모든 길이 이것을 부른다.** `editor.openTab`(팔레트와 트리 `Enter` 가
쓴다), `nextTab`/`prevTab`, tabline 클릭, `closeTab`, CLI 시작, `:tree` 로 트리를 다시 열
때다. 이름 없는 buffer(`:tabnew`) 는 경로가 없으므로 아무 일도 하지 않는다.

`closeTab` 이 가리키는 것은 닫은 파일이 아니라 **닫아서 그 자리에 드러난 파일**이다.
`:q` 는 tab 하나만 닫으므로(ADR-0003) 닫은 뒤에도 보는 파일이 하나 있고, 그것이 곧 새로 보는
파일이다.

**고른 자리를 옮기고 화면 안으로 끌어온다.** `scrollTo` 로 최소한만 굴린다. 고른 항목 위에
놓이는 터미널 커서가 곧 포커스 표시이므로(ADR-0005) `ctrl+w ctrl+w` 로 가면 커서가 방금
열린 파일 위에 있다.

**이미 펼쳐진 디렉터리는 다시 읽지 않는다.** 접혀 있는 것만 펼친다.

**sidebar 를 열지는 않는다.** `:tree` 로 닫아둔 상태면 트리 자체가 없으므로 아무 일도 하지
않고, 좁은 화면이라 감춰진 상태면 트리만 펼쳐 둔다.

**찾지 못하면 고른 자리를 건드리지 않는다.** 뿌리 밖의 파일, symlink 디렉터리 안쪽(따라가지
않으므로 펼칠 자식이 없다), 그 사이에 지워진 파일이 그렇다. 그때까지 펼친 것은 되돌리지 않는다.

**시작 시점에는 스크롤하지 않는다.** `Run` 은 첫 `WindowSizeMsg` 를 받기 전이라 화면 크기를
모른다. 고른 자리만 정해두고, 포커스가 트리로 올 때 `sidebarMode` 의 `scrollTo` 가 데려온다.

## 근거

### 왜 펼치기만이 아니라 고른 자리까지 옮기는가

**트리에는 "열린 파일" 표시가 없다.** 색은 파일 종류에 쓰이고(ADR-0005) 반전은 statusBar·tabline
의 것이다. 펼치기만 하면 화면에는 디렉터리가 열린 것만 보이고 그 안 어느 줄이 지금 보는 파일인지는
알 수 없다 — 이름이 같은 파일이 여러 디렉터리에 있으면 더 그렇다.
**고른 자리를 옮기는 것이 지금 있는 표시 수단으로 "여기" 를 말하는 유일한 방법이다.**

트리를 훑던 자리를 잃는다는 대가가 있지만, 트리를 훑는 동안에는 포커스가 트리에 있고
`gt`·`ctrl+p` 는 그 상태에서 파일을 옮기는 키가 아니다. 자리를 잃는 것은 편집 영역에서
tab 을 옮긴 뒤인데, 그때 트리에 남아 있던 자리는 이미 지금 보는 파일과 무관하다.

### 왜 이미 펼친 디렉터리를 다시 읽지 않는가

`expand` 는 자식 노드를 새로 만든다(그것이 새로고침이다 — ADR-0005). 지나는 길의 디렉터리를
전부 다시 읽으면 **그 아래 펼쳐 둔 것이 통째로 접히고**, 고른 자리가 가리키던 노드도 옛 배열의
것이 된다. 파일을 여는 일이 트리를 초기화하는 일이 되어서는 안 된다.
**새로고침은 접었다 펴는 것이지 파일을 여는 것이 아니다.**

곁따라 오는 이득도 있다 — 펼침당 한 번 도는 `os.ReadDir` 과 `git check-ignore` 는 동기
호출이라(`docs/tasks.md`) 파일을 열 때마다 조상 디렉터리를 다시 읽으면 그만큼 멈칫한다.

### 왜 sidebar 를 열지는 않는가

**파일을 여는 것과 화면을 나누는 것은 다른 결정이다.** `:tree` 로 닫아둔 사람은 32 칸을
본문에 쓰기로 한 것이고, 팔레트로 파일을 골랐다고 그 결정이 뒤집히면 본문이 오른쪽으로 밀리고
줄바꿈이 다시 계산된다. 닫아둔 트리는 아예 버리므로(`toggleTree`) 펼쳐 둘 상태도 없다 —
그래서 다시 열 때 그 자리에서 보고 있는 파일을 펼친다.

좁은 화면에서 감춰진 경우는 다르다. 트리는 살아 있으므로 펼쳐만 둔다. 화면이 넓어지면
그 자리가 그대로 보인다.

### 왜 tab 전환에도 붙이는가

트리가 "무엇을 열 수 있나" 만 보여주는 것과 "지금 어디에 있나" 까지 보여주는 것은 다르다.
후자를 고르면 tab 을 옮기는 것도 자리를 옮기는 일이므로 같이 따라와야 한다.
`gt` 로 옮긴 뒤에만 트리가 딴 곳을 보고 있으면 표시를 믿을 수 없게 된다.

## 결과

좋은 점

- 어느 길로 열어도 트리가 그 파일 자리를 가리킨다. `ctrl+w ctrl+w` 다음에 곧바로 이웃 파일을
  본다.
- 팔레트로 이름을 알고 여는 것과 트리로 주변을 훑는 것이 이어진다. 둘을 오갈 때 손으로 다시
  펼치고 내려가는 일이 없다.
- 트리가 "지금 보는 파일" 을 나타내는 표시를 하나 갖게 되었다. 색이나 반전을 새로 쓰지 않았다.

감수하는 것

- **tab 을 옮기면 트리 스크롤 자리를 잃는다.** 트리를 어딘가 굴려둔 채 `gt` 를 누르면 그 자리로
  돌아오지 않는다.
- **파일을 열 때 조상 디렉터리를 펼치는 syscall 이 붙는다.** 접혀 있는 깊은 경로를 열면
  깊이만큼 `os.ReadDir` 과 `git check-ignore` 가 돈다. 큰 디렉터리에서 멈칫하는 것은
  `docs/tasks.md` 의 동기 호출 항목과 같은 자리다.
- **시작 직후에는 스크롤이 최소가 아니다.** 크기를 모른 채 고른 자리만 정하므로, 트리에 처음
  들어갈 때 그 자리가 화면 위나 아래 끝에 붙어 조상 디렉터리가 화면 밖일 수 있다.
- **symlink 디렉터리 안쪽 파일은 트리에서 가리킬 수 없다.** 따라가지 않기로 한 결정(ADR-0005)
  의 연장이다. 그 경우 고른 자리는 그대로 남는다.

## 대안

**펼치기만 하고 고른 자리는 그대로 두기** — 트리를 훑던 자리를 잃지 않는다. 대신 어느 줄이
지금 보는 파일인지 화면에 나타나지 않는다. 표시 수단이 커서뿐이라 반쪽짜리가 된다.

**열린 파일을 색이나 표시로 나타내기** — vscode 처럼 tab 으로 열린 파일 전부를 트리에서
구분해 보여주는 것이다. 커서를 옮기지 않아도 되고 tab 여러 개를 한눈에 볼 수 있다.
색은 이미 파일 종류가 쓰고 있어서(ADR-0005) 팔레트 결정(`docs/tasks.md`) 뒤로 미룬다.
그때 이 결정과 같이 본다.

**파일을 열면 sidebar 도 같이 열기** — 트리를 닫아둔 사람에게도 자리를 보여줄 수 있다.
본문 폭이 파일을 여는 것만으로 바뀌는 것은 값이 너무 크다.

**아무것도 하지 않기** — 지금까지의 동작이다. 팔레트를 쓰는 사람은 이름을 알고 열기 때문에
트리가 필요 없다는 논리인데, 트리를 여는 이유는 이름을 모르는 파일을 찾기 위해서다.
두 길을 섞어 쓰는 것이 실제 쓰는 방식이다.
