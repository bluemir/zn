# ADR-0008: 한글로 온 키를 두벌식 자리의 영문 키로 되돌려 받는다

- 상태: 채택
- 날짜: 2026-08-13

## 맥락

한글로 글을 쓰다가 `esc` 로 normal mode 로 나오면 입력기가 아직 한글이라 명령이 하나도
먹지 않는다. `a` 를 누르면 편집기에는 `ㅁ` 이 오거나, 조합이 끝나지 않아 아무것도 오지 않는다.
한글 문서를 편집할 때마다 겪는 일이라 무시할 수 없다.

고를 수 있는 길이 셋이었다.

1. **앱 안에서 자모를 키로 되돌린다.** 의존성이 없고 터미널·플랫폼을 가리지 않는다.
2. **mode 가 바뀔 때 OS 입력기를 영문으로 돌린다.** 조합 자체가 일어나지 않아 확실하다.
3. **앱 밖에서 해결한다.** macOS 는 Karabiner-Elements, Linux 는 입력기 설정.

2 는 ssh 에서 원리적으로 동작하지 않는다. 입력기는 be 가 도는 원격이 아니라 키를 치는
로컬에 있다. macOS·Linux 별 코드가 갈리는 것에 더해, 이 편집기를 ssh 로 쓰는 순간 효과가 없다.
3 은 가장 확실하지만 편집기가 할 수 있는 일이 없다.

1 의 한계는 **입력기가 자모를 모아서 준다**는 것이다.

- `hk`(왼쪽·위) 를 치면 `ㅗ`+`ㅏ` 가 합쳐져 `ㅘ` 한 글자로 온다. `dj` 는 `어` 다.
- 조합 중인 글자는 커밋될 때까지 터미널이 pty 로 보내지 않는다. 마지막으로 누른 키는
  다음 키를 눌러야 도착한다 — 즉 명령이 한 키씩 밀린다.

## 결정

**1 을 넣는다. 한글로 온 키를 두벌식 자리의 영문 키로 바꿔서 받는다.**

`internal/core/hangul-key.go` 의 `hangulKeys` 가 키 문자열을 받아 영문 키 나열을 준다.
한글이 없으면 `nil` 이고, 부르는 쪽은 원래 키를 그대로 쓴다.

**음절과 겹자모를 자모로 되돌린다.** 조합된 음절은 유니코드 계산으로 초성·중성·종성으로 가르고,
겹모음·겹받침은 그것을 만드는 키 둘로 펼친다. `ㅘ` 는 `h` `k` 이고 `값` 은 `r` `k` `q` `t` 다.
그래서 키 하나가 명령 여럿이 된다.

**적용 범위는 키가 곧 명령인 mode 뿐이다** — normal, sidebar(TREE), 종료 확인창.
insert mode 와 명령줄 mode 는 건드리지 않는다. 거기서는 한글이 글자다.

**풀린 키를 먹이는 도중 mode 가 바뀌면 남은 키는 버린다.** `얌` 은 `d` `i` `a` 인데 `i` 에서
insert mode 로 들어가므로 `a` 는 버려진다. 각 mode 의 `Update` 가 자기 型 으로 형 단정을 해서
같은 型 이 아니면 멈춘다. `cmd` 를 내는 명령(종료, 확인창) 에서도 멈춘다.

## 근거

**두벌식 자리로 매핑하는 것이 근육기억과 맞는다.** 사용자가 누른 것은 물리 키이고 화면에 온 것이
자모일 뿐이다. `ㅁ` 을 `a` 로 되돌리는 것은 누른 키를 그대로 복원하는 것이다.

**겹모음 분해가 실제로 가장 자주 쓰인다.** `h` `j` `k` `l` 이 두벌식에서 모두 모음
(`ㅗ` `ㅓ` `ㅏ` `ㅣ`) 자리라, 이동 키를 이어 누르면 `ㅘ` `ㅚ` 처럼 합쳐지는 조합이 흔하다.
음절 분해가 없으면 가장 많이 쓰는 이동에서 바로 어긋난다.

**남은 키를 버리는 쪽이 안전하다.** vim 처럼 `ia` 를 이어 받으면 잘못 들어온 자모가 파일에
글자로 꽂힌다. 한글 상태로 normal mode 에 온 것 자체가 사고이므로, 사고가 편집을 일으키는 것보다
아무 일도 일어나지 않는 것이 낫다.

**형 단정으로 mode 변경을 알아낸다.** `press` 메서드를 가진 interface 를 만들면 sidebar 에서
normal 로 바뀐 것을 "같은 mode" 로 잘못 보고 남은 키를 새 mode 에 먹인다. `tea.Model` 값 비교는
slice 를 담은 型 이라 panic 이 난다. 그래서 mode 마다 자기 型 으로 단정하는 짧은 loop 를
셋으로 두었다. 같은 모양이 세 번 나오지만 공통 함수로 묶으면 규칙이 표현되지 않는다.

## 결과

- 한글 상태에서도 `hjkl` `w` `b` `gg` `gt` 와 숫자 접두가 동작한다. sidebar 의 `j` `k`,
  확인창의 `y` `n` 도 같다
- **`G` 와 `B` 는 한글 상태에서 낼 수 없다.** `ㅎ` `ㅠ` 는 shift 자리에 다른 글자가 없어서
  `shift+g` 와 `g` 가 같은 글자로 온다. 구분할 방법이 없다. `W` `E` `T` 는 된소리
  (`ㅉ` `ㄸ` `ㅆ`) 가 shift 자리에 있어서 낼 수 있다
- **명령이 한 키씩 밀리는 것은 남는다.** 마지막으로 누른 키는 입력기가 들고 있어서 편집기에
  도착하지 않는다. 이것은 앱이 고칠 수 있는 것이 아니다 — 확실하게 하려면 위의 3 을
  같이 써야 한다(`docs/tasks.md` 에 안내를 남긴다)
- 두벌식만 다룬다. 세벌식은 자리가 달라서 이 표로 되돌릴 수 없다
- `hangulKeys` 는 호환 자모(`ㅁ`, `ㅘ`) 와 조합된 음절(`어`) 만 본다. 조합용 자모
  (U+1100 구간) 로 오는 입력기는 아직 보지 못해서 넣지 않았다

## 대안

**OS 입력기를 mode 에 맞춰 바꾼다** — 조합이 일어나지 않아 밀림도 없고 가장 확실하다.
ssh 에서 동작하지 않고 플랫폼별 코드(cgo 의 Carbon TIS, 또는 `macism` 같은 외부 바이너리) 가
필요하다. 편집기가 OS 전역 상태를 건드리는 것도 이 편집기의 크기에 맞지 않는다.

**Karabiner 등 앱 밖 설정만 안내한다** — 코드가 늘지 않고 ssh·tmux 를 모두 통과한다.
쓰는 사람마다 머신마다 설정해야 해서, 편집기를 받아 바로 쓰는 경우에는 아무것도 해결되지 않는다.
이 결정과 배타적이지 않아서 tasks 에 안내로 남긴다.

**normal mode 명령을 ctrl 조합으로도 받는다** — ctrl 조합은 입력기가 먹지 않아 한글 상태에서도
그대로 온다. 확실하지만 vim 키맵이 아닌 두 번째 키맵을 만드는 일이라 배울 것이 늘고,
`hjkl` 을 쓰던 손과 어긋난다.

**남은 키를 새 mode 로 넘긴다** — vim 에서 `ia` 를 친 것과 같아져 충실하다.
잘못 들어온 입력이 파일을 고치게 된다.

## 이 ADR 이 정하지 않는 것

- 세벌식 지원
- 켜고 끄는 설정. 한글 자모는 normal mode 에서 어차피 아무 명령도 아니라 켜 두어 잃는 것이 없다
- 조합 중인 글자 때문에 명령이 한 키 밀리는 것. 앱 밖의 문제다
- 명령줄 mode(`:`) 에서의 한글. 파일 이름에 한글을 쓸 수 있어야 해서 바꾸지 않는다
