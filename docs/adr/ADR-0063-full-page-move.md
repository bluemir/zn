# ADR-0063 한 화면 이동(`ctrl+f`·`ctrl+b`)

## 맥락

반 화면 이동을 넣고 나서(ADR-0062) 한 화면씩 넘기는 `ctrl+f`·`ctrl+b` 가 남았다. 긴 파일을
훑는 손버릇은 반 화면보다 이쪽이 먼저인 자리도 있다. 읽으며 지나가는 것이 아니라 어디쯤인지
찾아 넘길 때다.

vim 은 이 둘을 반 화면과 **다른 규칙으로** 움직인다. 그래서 정할 것이 둘이다.

1. 한 화면은 정확히 화면 높이인가, 겹치는 행을 남기는가
2. 커서를 어디에 놓는가. vim 은 새 화면의 첫 행(`ctrl+f`)·마지막 행(`ctrl+b`) 에 놓는다

## 결정

### 1. 두 행을 겹친다

화면을 높이-2 만큼 옮긴다. 앞 화면의 마지막 두 행이 다음 화면 맨 위에 다시 선다.
vim 의 `ctrl+f` 와 같고 `less`·`more` 도 같은 손버릇이다.

겹치지 않으면 두 화면 사이가 눈에서 끊긴다. 넘긴 자리의 앞뒤가 한 행도 같이 보이지 않아서,
읽던 문장이 다음 화면 첫 줄에서 어디로 이어지는지 다시 찾아야 한다. 두 행은 그것을 잇는
최소한이다.

반 화면에는 이 겹침을 두지 않는다. 절반씩 가면 앞 화면의 아래쪽 절반이 그대로 위쪽 절반이
되어서 겹침이 이미 화면의 반이다.

높이가 2 이하인 화면에서는 겹칠 자리가 없다. 그때는 한 행이다. 0 으로 두면 키가 안 먹는
것처럼 보인다(`pageRows`).

### 2. 커서는 화면과 같이 간다. vim 을 따르지 않는다

화면이 옮긴 행 수만큼 커서도 옮긴다. 커서가 화면 안 같은 자리에 남는다. 반 화면(ADR-0062) 과
같은 규칙이다.

vim 은 `ctrl+f` 뒤에 커서를 새 화면 첫 행에 놓는다. 화면이 높이-2 만큼 움직이므로 원래 커서는
거의 언제나 새 화면 위로 벗어나고, vim 은 그것을 맨 위로 끌어오는 것이다. 따르지 않는 것은
**같은 손짓의 규칙이 둘로 갈리기 때문이다.** `ctrl+d` 는 커서를 데리고 가는데 `ctrl+f` 는
맨 위로 튕긴다면, 화면 이동 뒤 커서가 어디 있는지를 키마다 따로 기억해야 한다.

가로 칸도 반 화면과 같이 지킨다(`desiredCol`). vim 의 `startofline` 을 따르지 않는 까닭은
ADR-0062 에 적은 그대로다.

### 3. 크기는 값이고 방향은 값이다. 함수는 하나다

ADR-0062 의 `Buffer.moveHalfPage` 를 `Buffer.movePage(direction, span, count, width, height)` 로
넓혔다. `pageSpan`(`pageHalf`·`pageFull`) 이 늘어난 것뿐이고, 몇 행인지는 `pageRows` 한 자리가
안다.

반 화면과 한 화면을 함수 둘로 나누지 않았다. 다른 것은 「몇 행인가」 하나이고 나머지는 전부
같다. 커서를 같이 옮기는 것, 화면 행으로 세는 것, 파일 끝에서 멈추는 자리, 숫자가 되풀이인
것이 모두 같다. 나누면 그 넷이 두 벌이 되어 한쪽만 고치는 자리가 생긴다.

`bool` 이 아니라 이름 있는 값 둘로 받는다(`indentDirection` 과 같은 손이다). `movePage(true,
false, …)` 는 부르는 자리에서 무슨 뜻인지 읽히지 않는다.

## 결과

- normal·visual·트리에서 `ctrl+f`·`ctrl+b` 로 한 화면씩 넘긴다. 두 행이 겹쳐서 넘긴 자리가
  이어져 보인다
- 화면 단위 이동 넷이 커서 규칙 한 벌을 쓴다
	- 반 화면이든 한 화면이든 커서는 화면 안 같은 자리에 남고 가로 칸을 지킨다
- vim 과 갈리는 자리가 하나 늘었다. `ctrl+f` 뒤 커서가 화면 맨 위가 아니다
- 트리에서 숫자를 보는 이동이 여섯에서 여덟이 되었다(ADR-0059 의 표)
- `ADR-0062` 가 적은 `moveHalfPage` 는 지금 `movePage` 다. 그 결정 내용은 그대로다
- tip 한 줄이 늘었다(ADR-0061 의 규칙)
