# ADR-0044: 파일 검사는 작업으로 내리고, stat 을 앞잡이로 둔다

- 상태: 채택
- 날짜: 2026-08-21

## 맥락

ADR-0038 이 「보고 있는 파일이 밖에서 바뀌면 잃을 것이 없을 때 다시 읽는다」를 넣었다. 보는
자리는 포커스 복귀와 5 초 주기 tick 둘이고, 검사는 `Update` 안에서 동기로 돌았다.

git 표시를 라이브러리로 옮기고(ADR-0042) 갱신을 cooldown 으로 바꾸면서(ADR-0043) 「파일 tick 은
이미 cooldown 이니 손댈 것이 없다」고 넘겼다. **주기를 재는 방식만 보면 맞고, 값을 어디서 내는지
보면 틀렸다.** git 갱신은 작업이라 아무리 오래 걸려도 화면이 멈추지 않는데, 파일 검사는 그 값을
이벤트 고리에서 낸다.

`checkOutside` 는 `os.ReadFile` + `sha256.Sum256` 을 파일 전체에 대해 한다. 해시로 판정하는 것은
ADR-0015 가 정한 것이다 — mtime 은 내용이 같아도 바뀌는 일이 흔해서(`git checkout`, 다른 도구의
되쓰기) 그것으로 판정하면 헛경고가 잦다.

`Update(fileTickMsg)` 하나가 붙잡는 시간을 재보면 이렇다.

| 파일 | 그대로일 때 | 밖에서 바뀌었을 때 | (견줌) 키 하나 |
|---|---|---|---|
| 64KB | 68µs | — | 1~3µs |
| 1MB | 0.43ms | 1.6ms | 1µs |
| 10MB | 5.3ms | 12.5ms | 1µs |
| 100MB | 42ms | 122ms | 1µs |

바뀐 것을 만나면 세 배가 되는 것은 파일을 두 번 읽고 해시를 두 번 내기 때문이다 —
`checkOutside` 가 읽고 해시한 뒤 `Reload` 가 다시 읽고 `newBuffer` 가 다시 해시한다.

소스 파일 크기에서는 안 보인다. 큰 로그나 생성물을 열면 5 초마다 걸린다. 키를 잃지는 않는다 —
bubbletea 의 msg 채널이 버퍼 없는 `make(chan Msg)` 라 입력 goroutine 이 막히고, 타이핑한 바이트는
tty 버퍼에 남아 있다가 검사가 끝나면 처리된다. 200MB 파일에서 키를 흩어 넣어도 몰아 넣어도
하나도 빠지지 않았다. **잃지는 않고 늦는다.**

## 결정

**검사를 작업으로 내린다.** 이름은 `파일 검사` 하나다. git 갱신과 같이 job 시스템에 올라가고
(ADR-0025, ADR-0027) `:jobs` 목록과 statusBar 진행 표시에 그대로 나온다 — 예외를 두지 않는다.

**값이 드는 일은 전부 작업 안에서 끝낸다.** 읽기와 해시뿐 아니라 **갈아끼울 새 Buffer 를 만드는
것까지** 거기서 한다. `Update` 에는 아무 I/O 도 남지 않는다.

**`Reload` 에서 「자리 옮겨 담기」를 떼어낸다(`Buffer.adopt`).** 새 Buffer 를 만드는 것은 파일
크기만큼 드는 일이라 백그라운드로 가고, 커서·스크롤을 옮겨 담는 것은 값이 없어서 `Update` 안에
남는다 — 옮겨 담을 「지금 자리」는 그 순간에만 알 수 있는 것이라 미리 할 수도 없다.

**stat 을 앞잡이로 둔다.** buffer 가 마지막으로 맞춰 봤을 때의 크기와 mtime 을 들고 있다가
(`diskSize`·`diskTime`) 다음 검사에서 그 둘이 그대로면 읽지 않는다. 유휴 상태의 값이 파일 크기와
무관해진다.

**앞잡이는 판정이 아니다.** mtime 이 같으면 안 읽고, 다르면 읽어서 해시로 판정한다. ADR-0015 가
기각한 것은 mtime 을 *판정* 으로 쓰는 것이고, 여기서는 「그대로면 안 읽는다」 는 한쪽으로만 쓴다 —
틀리는 방향이 「괜히 한 번 더 읽는다」 라서 판정이 달라지지 않는다.

**기준 해시가 없으면 앞잡이를 쓰지 않는다.** 열 때 파일이 없었으면 견줄 것이 없어서 stat 이 같다는
것이 「내용이 같다」를 뜻하지 않는다.

**결과를 넣을 자리는 경로로 찾는다.** 검사하는 동안 tab 이 닫히거나 바뀔 수 있어서 index 로
기억하지 않는다(`bufferByPath`).

**넣기 전에 기준이 그대로인지 본다.** 검사를 시작할 때의 `diskHash` 와 지금 buffer 의 것이 다르면
그 사이 저장이나 `:e` 가 있었다는 뜻이라 넣지 않고 물러난다. 다음 tick 이 새 기준으로 다시 본다.

**읽을지 말지를 가르는 것은 `dirty` 하나다. mode 는 보지 않는다.** ADR-0038 은 normal·트리에서만
보기로 했는데, 그 조건을 없앤다. 결과가 돌아올 때 어느 mode 인지 알 수 없고(ADR-0002 에서 mode 는
model 타입이다) 알 필요도 없다.

**그래서 `fileTickMsg` 는 모든 mode 에서 똑같이 공용 처리로 간다.** normal·트리가 자기 case 에서
직접 보던 것이 없어진다. 포커스 복귀도 세 자리(normal·트리·insert) 가 모두 작업을 시작하는
한 줄이 된다 — insert 만 `noteOutsideChange`(마커만) 를 쓰던 갈림길도 없어진다.

**cooldown 은 git 과 같은 모양이다(ADR-0043).** tick 을 받는 자리에서 검사를 시작하고, 검사가
끝나는 자리에서 다음 cooldown 을 건다. 예약이 갈라지지 않게 `fileTickScheduled` 가 하나로 묶는다.

## 근거

### 왜 새 Buffer 까지 작업에서 만드는가

**그것이 값의 절반이다.** 100MB 에서 42ms 와 122ms 의 차이가 그것이다. 읽기만 옮기고 만들기를
`Update` 에 두면 바뀐 것을 만날 때마다 80ms 가 남는다.

**만드는 데 필요한 것이 파일 내용뿐이다.** `newBuffer(path, data)` 는 editor 를 보지 않는다.
반대로 커서를 옮겨 담는 일은 「지금 어디를 보고 있는가」가 필요해서 미리 할 수 없다. 이 경계가
그대로 goroutine 과 `apply` 의 경계다.

### 왜 앞잡이를 두는가

**작업으로 내린 뒤에도 값은 그대로 든다.** 화면이 멈추지 않을 뿐, 100MB 파일을 띄워두면 5 초마다
100MB 를 읽고 해시한다. 노트북 배터리로 하루 종일 켜 두면 그것이 값이다.

**git 쪽에 이미 같은 것을 넣었다.** `gitDirty` 가 추적 파일마다 index 의 크기·mtime 을 앞잡이로
보고 그것이 맞으면 내용을 읽지 않는다(ADR-0042). 같은 논리를 같은 방향으로만 쓴다.

**틀리는 방향이 안전하다.** stat 이 다른데 내용이 같으면 → 읽고 해시해서 「그대로」로 끝난다.
stat 이 같은데 내용이 다르면 → 놓친다. 뒤쪽은 mtime 을 일부러 되돌려 놓는 도구가 있어야 생기고,
`git checkout` 도 다른 편집기도 mtime 을 새로 찍는다.

### 왜 mode 를 보지 않는가

**`apply func(*editor)` 가 mode 를 볼 수 없다.** 볼 수 있게 하려면 결과를 mode 마다 받아 갈라야
하고, 그러면 「작업 msg 는 한 자리에 모아 공용 처리로 넘긴다」(ADR-0025) 는 규칙에 예외가 하나
생긴다. 열 곳에 같은 갈림길이 흩어진다.

**조건이 이미 `dirty` 로 충분하다.** ADR-0038 이 insert 를 뺀 것은 「치는 중에 커서 아래 내용이
바뀌면 안 된다」였는데, 치기 시작했으면 `dirty` 라서 그대로 막힌다. 남는 것은 insert 로 들어가
아무것도 치지 않은 5 초 창인데, 그 상태는 normal 과 다를 것이 없다.

**갈림길이 하나 없어진다.** insert 의 포커스 복귀만 `noteOutsideChange` 를 쓰던 것이 없어지고,
`reloadOutsideChange`·`noteOutsideChange` 두 함수가 `applyOutsideResult` 하나가 된다.

### 왜 기준 해시로 낡음을 재는가

**시각이나 세대 번호보다 뜻이 분명하다.** 「검사를 시작할 때 본 것과 지금 buffer 가 보는 것이
같은가」가 그대로 「이 결과가 아직 쓸모 있는가」다. 저장·`:e`·다른 검사의 결과가 모두 `diskHash`
를 바꾸므로 한 가지만 보면 된다.

### 왜 `:jobs` 에 보이는가

**5 초마다 무엇이 도는지는 감출 것이 아니다.** ADR-0030 이 git 갱신에 대해 정한 그대로다.
큰 파일을 열어 두었을 때 무엇이 도는지 볼 자리가 있어야 한다. 요약이 「그대로」·「밖에서 바뀜」
이라 무엇을 알아냈는지도 남는다.

## 결과

좋은 점

- `Update` 가 붙잡히는 시간이 파일 크기와 무관해졌다. tick 을 받는 순간은 0, 결과를 넣는 순간은
  1MB·10MB·100MB 모두 2~6µs 다. 100MB 에서 42ms·122ms 였던 것이 없어졌다.
- 유휴 상태에서는 `Lstat` 하나로 끝난다. 파일을 읽지 않는다.
- 바뀐 파일을 만나도 파일을 한 번만 읽고 해시를 한 번만 낸다. 예전에는 두 번씩이었다.
- `fileTickMsg` 를 다루는 자리가 mode 마다 같아졌다. normal·트리의 특별한 case 가 없어졌다.
- 포커스 복귀 세 자리가 같은 한 줄이 되었다. `noteOutsideChange`·`reloadOutsideChange` 가
  `applyOutsideResult` 하나로 모였다.
- 5 초마다 도는 것이 `:jobs` 에 보인다. git 갱신과 같은 대우다.

감수하는 것

- **insert 로 들어가 아무것도 치지 않은 채 5 초가 지나면 본문이 바뀐다.** ADR-0038 이 mode 로
  막아 두었던 자리다. 커서는 줄과 화면 칸을 이어받지만, 치려던 자리가 아닐 수 있다.
- **mtime 을 되돌려 놓는 도구가 있으면 변경을 놓친다.** 앞잡이가 맞다고 보고 읽지 않는다.
  판정을 mtime 으로 하지는 않지만, 판정에 이르지 못하는 경우를 만든 것은 사실이다.
- **결과가 늦게 도착한다.** 예전에는 tick 을 받은 그 프레임에 갈아끼워졌다. 이제 한 프레임
  뒤다. 사람이 볼 수 있는 차이는 아니지만 시험은 그 길을 지나야 한다(`settle`).
- **낡은 결과를 버리므로 그 회차의 검사가 헛일이 된다.** 검사 중에 저장하면 그렇다.
  다음 tick 이 다시 보므로 최대 5 초 늦는다.
- **`:jobs` 에 주기 작업이 둘이 되었다.** 끝난 목록이 이름당 하나라 길어지지는 않지만,
  statusBar 진행 표시에 둘이 번갈아 뜰 수 있다.
- **예약 상태가 둘이 되었다.** `gitTickScheduled`·`fileTickScheduled` 다. 셋이 되면
  이름→cooldown 표로 옮겨야 한다 — 둘까지는 bool 두 개가 읽기 쉽다.
- **`handleJob` 이 작업 이름을 두 개 본다.** ADR-0043 이 「늘리지 않아야 하는 자리」로 적어둔
  곳이 하나에서 둘이 되었다.

## 대안

**앞잡이만 넣고 동기로 둔다** — 가장 작다. 유휴 상태의 값은 없어지지만, 실제로 바뀐 파일을
만나는 순간은 그대로 `Update` 에서 낸다. 100MB 면 그 한 번이 122ms 다. 큰 파일을 편집기로
따라 보는 흐름(로그·생성물) 이 정확히 그 경우다.

**작업으로만 내리고 앞잡이는 두지 않는다** — 화면은 멈추지 않는다. 유휴 상태에서 5 초마다
파일 전체를 읽는 것이 남는다. 둘은 서로를 대신하지 않는다.

**fsnotify 로 옮긴다** — 주기 검사 자체가 없어지고 바뀐 순간에 알 수 있다. 의존성이 늘고,
플랫폼마다 한계가 다르고(감시 개수 상한, 네트워크 파일 시스템), 놓치는 경우를 대비해 주기 검사를
결국 같이 두게 된다. 지금 구조 위에 얹을 수 있으므로 뒤로 미룬다(`docs/tasks.md`).

**mode 를 결과까지 들고 간다** — ADR-0038 을 그대로 지킨다. 작업 msg 를 mode 마다 갈라 받아야
해서 열 곳에 같은 갈림길이 흩어지고, 공용 처리에 예외가 하나 생긴다.

**해시 대신 mtime 으로 판정한다** — 읽기가 아예 없어진다. ADR-0015 가 기각한 그대로 헛경고가
잦아진다. 앞잡이로만 쓰는 것이 그 둘 사이다.

## 이 ADR 이 정하지 않는 것

- fsnotify. 이 구조 위에 얹는 별개 건이다(`docs/tasks.md`)
- 보고 있지 않은 tab 의 파일도 볼지. 지금은 활성 buffer 하나만 본다(ADR-0038 그대로다)
- 자동으로 다시 읽을 때 undo 이력이 사라지는 것. ADR-0038 이 감수한 그대로다(`docs/tasks.md`)
- cooldown 값. git 과 같은 5 초 상수다
- 예약 상태를 이름→cooldown 표로 모을지. 셋이 되면 그때다
