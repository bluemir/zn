# ADR-0029: tabline 이 꽉 차면 활성 tab 으로 민다

- 상태: 채택
- 날짜: 2026-08-14

## 맥락

tabline 은 열린 tab 을 왼쪽부터 늘어놓고 편집 영역 너비에서 자른다. tab 하나는
`번호 파일이름` 이라 13 칸 안팎이고, sidebar 를 열면 편집 영역이 32 칸 줄어든다.
80 칸 터미널에 트리를 열면 tab 셋이면 넘친다.

넘칠 때 지금까지는 그냥 잘렸다. **활성 tab 이 오른쪽에 있으면 보이지 않는다.** 지금 무엇을
편집하는지가 tabline 의 첫 번째 일인데 그것부터 사라진다. `gt` 로 옮겨 가도 화면이 그대로라
tab 이 바뀐 것조차 tabline 에 나타나지 않는다.

옮기는 길은 `gt`/`gT`(양끝에서 둘러 감) 와 tabline 클릭 둘이고, tab 은 열린 순서대로
늘어서 있으며 순서를 바꾸는 기능은 아직 없다(`docs/tasks.md`).

## 결정

**tabline 이 꽉 차면 활성 tab 이 온전히 보이는 자리까지 가로로 민다.** 이름을 줄이지 않는다.

**민 자리(`tabScroll`) 는 editor 가 들고 있고 최소한만 움직인다.** 활성 tab 이 화면 밖으로
나갈 때만 나간 만큼 밀고, 오른쪽에 자리가 남으면 왼쪽에 가려둔 것을 도로 당긴다.
`Buffer.scrollTo` 와 같은 자리·같은 방식이라, 활성 tab 이나 편집 영역 너비가 바뀌는 곳에서
`scrollTabsTo` 를 부른다.

**가려진 개수는 양끝에 `<n`·`n>` 로 적는다.** 왼쪽으로 몇 개, 오른쪽으로 몇 개인지를
각각 그 방향 끝에 둔다. tab 사이와 같은 구분선으로 가른다.

```
<2│ 3 core.go │ 4 editor.go+ │ 5 mouse.go │1>
```

**반쯤 걸친 tab 은 그리지 않는다.**

**표시보다 tab 이 먼저다.** 좁아서 tab 과 표시를 다 놓을 수 없으면 표시를 뺀다. 표시를 두느라
tab 을 물리는 것은 두 개 이상 그릴 때뿐이고, 마지막 하나는 물리지 않는다.

**양끝 표시를 클릭하면 그 방향으로 한 tab 씩 민다.** 활성 tab 은 바뀌지 않는다.
밀어둔 자리는 `gt`/`gT` 로 tab 을 옮기는 순간 활성 tab 을 따라 다시 맞는다.

**그린 자리는 그리는 자리에서 같이 낸다.** `tabline` 이 줄과 함께 tab 마다의 칸 범위,
양끝 표시의 칸 범위를 담은 `tablineRow` 를 돌려주고 클릭이 그것을 읽는다.

## 근거

### 왜 이름을 줄이지 않고 미는가

**`editor.go` 와 `edit.go` 를 `edi…` 로 줄이면 tab 을 세는 일밖에 못 한다.** 파일 이름은
tabline 이 전하는 정보의 전부다. 줄이는 방식은 몇 칸까지 줄일지, 어느 쪽을 줄일지, 같은
접두사를 어떻게 가를지를 다 정해야 하고 그러고도 애매하다. 미는 방식은 보이는 것은 온전하고
안 보이는 것은 아예 안 보인다 — 화면이 좁을 때 무엇을 잃는지가 분명하다.

vim 도 `tabline` 이 넘치면 잘라내기만 하고 이름을 줄이지 않는다. VS Code·Sublime 의 tab 은
스크롤이다.

### 왜 상태 없이 매번 계산하지 않는가

활성 tab 을 기준으로 좌우를 채우면 필드가 늘지 않는다. 하지만 **같은 tab 을 보고 있어도
직전에 어디를 보고 있었는지와 무관하게 자리가 정해져서** tabline 이 더 자주 흔들린다.
`gT` 로 왼쪽 tab 으로 갈 때마다 창이 통째로 옮겨 다니면 방금 본 이름이 어디로 갔는지
눈으로 쫓아야 한다. 최소 이동은 한 tab 씩만 움직여서 나머지가 제자리에 남는다.

이것은 편집 내용의 스크롤과 같은 문제이고, 그쪽도 `Buffer.topRow` 를 들고 최소로 움직인다.
같은 문제를 같은 방식으로 푸는 것이 읽기 쉽다.

### 왜 오른쪽에 `+n` 하나가 아니라 양쪽인가

`+4` 하나는 **어느 쪽이 가려졌는지를 알려주지 않는다.** 왼쪽으로 밀어둔 것이 있는지가
`gT` 를 누를지 정하는 정보다. 양쪽에 두면 각각 2~3 칸을 먹지만, 가려진 것이 없는 쪽에는
아무것도 그리지 않으므로 넘치지 않을 때는 지금과 한 글자도 다르지 않다.

`<`·`>` 는 ASCII 라 폭이 확실하다. 화살표 글리프(`‹` `›`) 는 ADR-0028 의 ambiguous 폭
문제를 다시 불러온다.

### 왜 반쯤 걸친 tab 을 그리지 않는가

**잘린 이름은 어느 파일인지 알려주지 못하면서 `n>` 의 숫자와도 어긋난다.** 반쪽이 보이는
tab 을 "가려진 것" 에 넣으면 화면에 있는 것을 없다고 세는 것이고, 넣지 않으면 셋 중 둘만
보이는데 `1>` 이라고 적히지 않는다. 그리지 않으면 "보이는 것은 온전하고 나머지는 숫자에
들어 있다" 는 한 문장이 성립한다.

대신 오른쪽에 빈 칸이 남을 수 있다. 다음 tab 하나가 통째로 들어갈 만큼은 아닌 자리다.

### 왜 표시를 클릭하면 스크롤인가

**활성 tab 을 옮기는 것은 이미 `gt` 와 tab 클릭 둘이 한다.** 표시까지 옮기기로 하면
`n>` 이 `gt` 와 같은 뜻이 되어 새로 얻는 것이 없다. 스크롤로 두면 **보고 있는 파일을 놓지
않고** 가려진 쪽에 무엇이 있는지 볼 수 있다 — 편집 중에 다른 파일 이름을 확인하는 일이 그렇다.

대신 밀어둔 자리와 활성 tab 이 어긋난 상태가 생긴다. 그대로 두면 활성 tab 이 보이지 않아
tabline 의 첫 번째 일을 못 하므로, **다음에 tab 을 옮기거나 화면 크기가 바뀌면 다시 맞춘다.**
직접 민 것은 지금 훑어보는 동안만 유지된다.

### 왜 자리표를 렌더가 같이 내는가

이미 그렇게 하고 있던 것을 넓혔다. 배치 계산을 두 벌 두면 `+`(dirty) 하나로 칸이 밀렸을 때
클릭이 옆 tab 으로 간다. 스크롤이 붙으면서 배치가 더 복잡해졌으므로 두 벌을 두는 값이 더
커졌다. `tabAt` 은 이제 `tablineRow` 를 읽는 `clickTabline` 안으로 들어가 사라졌다 —
클릭 한 번에 tab·왼쪽 표시·오른쪽 표시 셋을 가려야 해서 줄 하나를 두 번 배치할 이유가 없다.

## 결과

좋은 점

- tab 이 몇 개든 지금 편집하는 파일이 tabline 에 보인다. sidebar 를 열어도 그렇다.
- 가려진 개수와 방향이 보여서 `gt`/`gT` 를 몇 번 눌러야 하는지 짐작할 수 있다.
- 넘치지 않는 화면은 지금까지와 똑같다. 표시도 스크롤도 나타나지 않는다.

감수하는 것

- **`scrollTabsTo` 를 부르는 자리가 여덟 곳이다.** 활성 tab 이 바뀌는 모든 길과 편집 영역
  너비가 바뀌는 두 곳이다. 하나를 빠뜨리면 활성 tab 이 안 보이는 상태로 남는다.
  `Buffer.scrollTo` 가 이미 같은 모양으로 서른 곳에 흩어져 있다.
- **오른쪽에 빈 칸이 남을 수 있다.** 다음 tab 이 통째로 들어가지 않는 자리다.
- **아주 좁은 tabline(13 칸 아래) 에서는 표시가 빠지고, 더 좁으면 이름이 잘린다.**
  활성 tab 을 아예 안 그리는 것보다 낫다고 봤다.
- **tab 이 열 개를 넘으면 `<10` 처럼 표시가 한 칸 늘어난다.** 그만큼 tab 자리가 준다.

## 대안

**이름 줄이기** — 넘치는 만큼 이름을 잘라 전부 한 줄에 넣는다. 몇 번째 tab 인지는 늘 보이지만
이름을 못 읽는다. 근거에 적었다.

**tabline 을 여러 줄로** — vim 이 `:tabs` 로 하는 것에 가깝다. 편집 영역 높이를 tab 수가
정하게 되어 화면이 위아래로 흔들린다.

**활성 tab 기준으로 매번 계산** — 상태가 없어 간단하다. tabline 이 더 자주 흔들린다.

**`+n` 하나만 오른쪽에** — 자리를 덜 먹는다. 어느 쪽이 가려졌는지 모른다.

**표시 클릭으로 tab 이동** — 다룰 상태가 하나 줄어든다. `gt` 와 같은 뜻이라 새로 얻는 것이 없다.
