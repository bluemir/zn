# ADR-0025 비동기 작업과 진행 표시

## Status

Accepted

## Context

편집기에 비동기 경로가 하나도 없었다. 모든 mode 의 `Update` 는 `nil` 이나 `tea.Quit` 만 돌려주고,
`git ls-files`·`git check-ignore`·`os.ReadDir` 이 전부 `Update` 안에서 동기로 돌았다. 그래서 큰
저장소에서 `ctrl+p` 를 누르면 목록을 다 읽을 때까지 편집기가 통째로 멈췄다.

앞으로 올릴 것들이 전부 같은 모양이다 — 여러 파일 검색, 여러 파일 치환, 대용량 구문 분석.
공통으로 필요한 것은 셋이다.

- 오래 걸리는 일을 화면과 따로 돌리는 길
- 도는 동안 어디까지 왔는지 보여주는 자리
- 결과를 화면 상태로 들여오는 길

이번에는 바탕과 소비자 하나(팔레트 파일 인덱싱)만 만든다. 소비자를 하나 붙여 봐야 바탕이 쓸 만한지
알 수 있고, 결과 모양이 서로 다른 둘째 소비자가 올 때 다시 볼 수 있다.

## Decision

### 진행은 채널로 밀고 `tea.Cmd` 로 받는다

작업은 goroutine 에서 돌면서 조각을 채널로 민다. 채널에서 하나를 받아 msg 로 바꾸는 `tea.Cmd`
(`waitJob`) 를 두고, 받을 때마다 다시 발행해서 고리를 잇는다. 채널이 닫히면 끝났다는 msg 가 된다.

`internal/workers`·`internal/pubsub` 은 쓰지 않는다. 편집기와 무관한 개인 공통 라이브러리이고
저장소 분리 후보다(`docs/tasks.md`). bubbletea 의 msg 흐름 위에 한 겹을 더 얹게 되기도 한다.

`tea.Program.Send` 로 밀지도 않는다. `Run` 이 Program 핸들을 `core` 전체에 흘려야 하고,
테스트에서 Program 없이 작업을 돌릴 수 없다.

### 실행기는 진행률만 안다. 결과는 작업이 넣는다

조각(`jobProgress`) 에는 `done`·`total` 과 함께 `apply func(*editor)` 가 실린다. 결과가 무엇이고
어디에 어떻게 쌓이는지는 작업이 정하고, 실행기는 그것을 부르기만 한다. `handleJob` 에는 작업 종류로
가르는 `switch` 가 없다.

실행기가 결과 모양을 정하면 소비자가 늘 때마다 깨진다. 파일 인덱싱의 결과는 파일 목록이지만 여러 파일
검색의 결과는 파일·줄번호·내용이라 같은 모양이 아니다. 실행기가 소비자를 하나씩 알게 되는 것도
방향이 뒤집힌 것이다.

interface 를 두지 않았다. 지금 필요한 것은 "editor 를 고치는 함수 하나" 뿐이고, type 을 만들면
작업마다 type 하나씩이 따라온다. 필요해지면 그때 함수를 type 으로 올린다.

`apply` 는 goroutine 이 아니라 `Update` 안에서만 불린다. 그래서 editor 를 그냥 고치면 되고
잠금도 복사도 필요 없다.

### 공용 처리 함수를 하나 두고 mode 마다 `case` 로 받는다

`editor.handleJob(msg)` 하나를 두고 각 mode 의 `Update` 에 `case jobProgressMsg, jobDoneMsg:`
한 자리를 둔다. 하는 일은 한 곳에 모이고 mode 쪽에는 "이 msg 를 받는다" 만 남는다.
ADR-0002 가 감수 사항에 "`ctrl+c` 처럼 모든 mode 가 같이 받는 키가 mode 마다 반복된다. 지금은 두
곳이라 그대로 뒀다. 늘어나면 공용 처리로 뺀다" 고 적어둔 자리다. mode 가 일곱이라 여기서 늘어났다.

`Update` 맨 앞에 두지 않는다. 앞에 두면 "내가 처리했는가" 를 알려야 해서 `bool` 을 하나 더 돌려주게
된다. 그 flag 는 mode 를 거치는 msg 흐름에는 없던 것이다.

`default` 에도 두지 않는다. 작업 msg 가 아니면 `nil` 을 주므로 `default` 로도 돌기는 하지만,
그러면 그 mode 가 작업 msg 를 받는다는 것이 코드에 보이지 않는다. `default` 는 "아무 일도 하지
않는다" 는 뜻으로 남긴다. 팔레트는 여기서 목록을 다시 거르는 한 줄을 더하는데, `default` 였다면
마우스가 움직일 때마다(`MouseModeCellMotion`) 수만 개를 다시 걸렀을 것이다.

`WindowSizeMsg` 는 이번에 옮기지 않았다. sidebar 와 팔레트가 크기 변화에 각자 다른 일을 더 한다.

### 확인창은 상태를 고치지 않고 고리만 잇는다 (ADR-0026 이 뒤집음)

`viewConfirmDiscard` 는 `editor` 를 embed 하지 않고 부모 model 과 closure 만 든다. 진행을 반영할
곳이 없지만, 그렇다고 msg 를 흘려보내면 다음 조각을 받을 `Cmd` 를 아무도 발행하지 않아 작업이 영영
멈춘다(goroutine 은 보내다 막힌 채 남는다). 그래서 `waitJob` 만 다시 발행한다.

### 값으로 복사되는 editor 를 그대로 둔다 (ADR-0026 이 뒤집음)

mode model 이 `editor` 를 값으로 embed 하므로(ADR-0002) 확인창을 거쳐 되돌아간 복사본은 그 사이의
진행을 모른다. 이것을 포인터로 바꾸지 않고 두 가지로 메운다.

- **msg 가 채널을 들고 다닌다.** 다음 조각을 받을 곳을 목록에서 찾지 않으므로 목록이 어긋나도
  고리가 끊기지 않는다. 확인창처럼 editor 가 아예 없는 화면도 고리를 이어줄 수 있다.
- **조각은 누적분 전체를 갈아끼운다.** delta 를 append 하면 놓친 조각이 영영 빈다.
  통째로 갈아끼우면 다음 조각 하나로 맞는다. 목록에 없는 작업이 오면 다시 끼워 넣는다.

작업이 다 모아서 정렬해 둔 배열은 그 뒤로 고치지 않으므로, 조각이 그 앞부분(`all[:n]`) 을 그대로
가리켜도 된다. 누적분 전체를 보내지만 복사는 없다.

**나중에**: ADR-0026 이 `editor` 를 포인터로 바꿔서 이 절의 전제가 사라졌다. 두 성질은 안전을 위해
필요하지 않게 되었지만, 목록을 뒤지지 않아도 되고 다시 부어도 같은 결과가 되어 그대로 남겼다.
확인창도 이제 `*editor` 를 들고 다른 mode 와 같은 `case` 로 진행을 받는다.

### 같은 이름은 하나만 돈다

작업의 이름이 곧 신원이다. 같은 이름이 이미 돌고 있으면 새로 시작하지 않고 그것에 붙는다.
결과를 이름으로 가르는 곳이 없으므로 `jobKind` 같은 type 을 만들지 않고 `string` 을 쓴다.

작업은 여럿이 같이 돌 수 있다. statusBar 에는 맨 앞, 곧 가장 먼저 시작한 것 하나와 나머지 개수
(`(+N)`) 를 찍는다. 끝날 때까지 가리키는 것이 바뀌지 않아야 눈이 따라갈 수 있다.

취소는 넣지 않았다. 편집기를 끝낼 때 보내다 막힌 goroutine 은 프로세스가 끝나면서 사라진다.

### 진행은 statusBar 위 줄, git 왼쪽에 그린다

늘 보이는 줄이라 놓치지 않는다. 아래 줄은 명령 결과와 showcmd 가 쓰는 자리다.

칸이 모자라면 진행 표시부터 줄인다. 막대를 떼어 `이름 42%` 로 만들고, 그래도 모자라면 진행 표시를
통째로 뺀다. git 은 늘 같은 자리에 있어야 눈이 찾는다. 붙일 칸이 아예 없으면 mode 와 파일 경로가
먼저다 — `withGit` 이 이미 따르던 시상이다.

전체를 모르는 동안에는 막대를 그리지 않고 지금까지 한 개수를 찍는다(`파일 인덱싱 12,431`).
반쯤 찬 막대가 거짓말이 되기 때문이다.

### 막대는 점자로 그린다. 칸당 여섯 단계다

바닥선(dot 7·8) 을 늘 켜 두고 남은 여섯 점을 아래에서 위로, 왼쪽 열 다음 오른쪽 열로 채운다.

`⣀`(28C0) `⣄`(28C4) `⣆`(28C6) `⣇`(28C7) `⣧`(28E7) `⣷`(28F7) `⣿`(28FF)

점이 하나씩만 늘어 단조 증가이고, 빈 칸이 바닥선으로 남아 막대의 끝이 보인다. 열 칸이면 예순 단계라
파일 십만 개를 훑어도 눈에 보이게 움직인다.

점자(U+2800–U+28FF) 는 East Asian Width 가 **Neutral** 이다. 블록 문자(`█` U+2588) 와 박스 그리기
문자는 Ambiguous 라 터미널이 두 칸으로 잡으면 statusBar 가 넘쳐 화면이 통째로 밀린다.
ADR-0020 이 공백 마커로 Ambiguous 인 `·` 대신 `⋅` 를 고른 것과 같은 기준이다.

색은 쓰지 않는다. 팔레트를 아직 정하지 않았고(ADR-0004) 모양만으로 이미 갈린다.

### 팔레트 인덱싱은 `ctrl+p` 를 누를 때 시작한다

여는 순간 시작하고 목록은 차는 대로 붓는다. 캐시하지 않는 것은 그대로다(ADR-0011) — 다 읽을 때까지
기다리지 않을 뿐이다. 이미 돌고 있으면 그것에 붙으므로 닫았다 다시 열어도 두 번 훑지 않는다.

앞서 모아둔 목록이 있으면 그것을 보면서 시작한다. 빈 목록에서 시작하면 열 때마다 화면이 한 번
번쩍인다. 새 조각이 오면 통째로 갈리고, 목록을 읽은 뒤 지워진 파일은 열 때 `os.Stat` 이 막는다.

훑는 동안에는 목록을 보내지 않고 개수만 알린다. 어디까지 왔는지 모르는 채로 조금씩 보여주면 나중에
정렬하면서 순서가 뒤집힌다. 다 모아 정렬한 뒤 1024 개씩 조각을 낸다.

인덱싱이 목록을 부을 때마다 팔레트는 다시 거르되 고른 자리는 그대로 둔다(`refilter`). 매번 맨 위로
튀면 목록을 훑을 수 없다.

## Consequences

좋은 점

- 십오만 개짜리 디렉터리에서도 `ctrl+p` 가 즉시 뜨고, 도는 동안 치고 편집할 수 있다.
- 다음 소비자는 goroutine 하나와 `apply` 하나만 쓰면 된다. 실행기도 statusBar 도 건드리지 않는다.
- 진행 표시가 mode 와 무관하다. 어느 mode 로 옮겨가도 이어진다.

감수하는 것

- **작업이 결과를 어디에 넣는지 한눈에 보이지 않는다.** `handleJob` 을 읽어도 알 수 없고 각 작업의
  `apply` 를 따라가야 한다. 실행기가 소비자를 알게 되는 것과 맞바꾼 값이다.
- **취소가 없다.** 큰 디렉터리에서 팔레트를 닫아도 인덱싱은 끝까지 돈다.
- **점자 글리프가 없는 터미널 글꼴에서는 두부로 보인다.** 폭은 Neutral 이라 화면이 밀리지는 않는다.
- **`editor` 의 값 복사가 다시 걸린다.** 이번에는 위 두 가지로 메웠다. 소비자가 늘면 매번 같은
  것을 지켜야 하는 것이 걸려서, 곧바로 ADR-0026 에서 `*editor` 로 바꿨다.

## Alternatives

**결과를 실행기가 들고 종류로 가르기** — `jobProgress` 에 `items []string` 을 두고 `handleJob` 이
작업 이름으로 갈라 제자리에 넣는 방식. 결과가 어디로 가는지 한 곳에서 읽히지만, 실행기가 결과 모양을
정하게 되어 여러 파일 검색이 붙는 순간 깨진다.

**`jobResult` interface** — 작업마다 `apply(*editor)` 를 구현한 type 을 두는 방식. 하는 일이 함수와
같은데 작업마다 type 이 하나씩 는다. interface 는 반드시 필요하기 전에는 도입하지 않는다.

**편집기를 열 때 미리 인덱싱** — `ctrl+p` 가 이미 다 된 목록을 바로 보여준다. 대신 목록이 오래되는
문제가 생겨 새로고침 시점을 정해야 하고, 팔레트를 쓰지 않는 실행에서도 매번 상자를 훑게 된다.

**막대를 ASCII 로 그리기(`[####----]`)** — 폭도 글꼴도 걱정이 없다. 점자가 폭이 확실하다는 것을
확인해서 고르지 않았다.
