# ADR-0031: 바깥 변경은 창이 돌아올 때 보고 statusBar 의 `[!]` 로 들고 있는다

- 상태: 채택
- 날짜: 2026-08-14

## 맥락

보고 있는 파일이 밖에서 바뀌었는지는 두 자리에서만 봤다 — 저장하기 직전(ADR-0015) 과 `ctrl+z`
로 셸에서 올라올 때(ADR-0023) 다. 그래서 다른 창에서 고쳐놓고 편집기로 돌아와 한참 더 치다가,
`:w` 를 하고 나서야 "파일이 밖에서 바뀌었습니다. 덮어쓰려면 `:w!` 입니다" 로 막힌다. 그 시점에는
이미 두 벌의 편집이 갈라져 있고, 합칠 길은 없다.

`docs/tasks.md` 에 "밖에서 바뀐 것을 알리는 자리를 더 넓힐지 정한다" 가 열려 있었고, 남은 자리로
터미널 포커스 복귀(`tea.FocusMsg`, vim 의 진짜 `checktime`), 트리에 포커스가 있는 경우, 여러 tab 을
한 번에 보는 것을 적어두었다. 뒤의 둘에는 "알림을 여러 줄로 띄울 자리가 먼저 필요하다" 고 달려
있었다.

바로 앞에서 git 표시를 5 초마다 다시 읽기로 했으므로(ADR-0030), 같은 방식을 여기에도 쓸지가
자연스러운 물음이 된다. 두 가지가 다르다.

**검사 비용이 다르다.** `checkOutside` 는 `os.Stat` 이 아니라 파일 전체를 읽어 sha256 을 낸다.
mtime 은 내용이 같아도 바뀌는 일이 흔해 헛경고가 잦다는 이유로 ADR-0015 가 고른 방식이다.

**알릴 자리가 다르다.** git 표시는 statusBar 위 줄의 고정된 한 칸이라 언제 갱신되어도 조용하다.
바깥 변경은 `editor.message` 로 아래 줄에 뜨는 **지나가는 알림** 이고 다음 키에 사라진다. 주기적
으로 띄우면 타이핑 중에 떴다가 못 보고 지나가거나, 명령 결과를 계속 덮어쓴다.

**흐름이 다르다.** git 은 편집기를 보고 있는 채로도 옆 터미널에서 바뀐다 — 그래서 주기가 필요했다.
반면 파일 내용이 바뀌었다는 것은 사람이 다른 창을 만졌다는 뜻이라, 거의 언제나 포커스가 나갔다
돌아온다.

## 결정

**터미널 포커스가 돌아올 때 검사한다.** `view.ReportFocus` 를 켜서 `tea.FocusMsg` 를 받는다.
주기적으로는 보지 않는다.

**normal·insert·트리에서 받는다.** 오래 머무는 mode 이자 알림을 그릴 줄을 가진 mode 다.
명령줄·검색·팔레트·작업 목록·확인창은 지나가는 화면이라 받지 않는다.

**셸에서 올라올 때(`tea.ResumeMsg`) 와 같은 자리로 묶는다.** 둘 다 "바깥을 만지고 왔다" 는 뜻이다.

**결과는 buffer 에 남기고 statusBar 에 `[!]` 로 찍는다.** 파일 경로 뒤, `[+]` 옆이다.
`[+]` 가 내 손의 미저장 변경이고 `[!]` 는 남의 변경이라, 둘이 같이 붙으면 양쪽에 잃을 것이
있다는 뜻이다.

**알림은 깨끗했던 것이 달라지는 순간에만 한 번이다.** 이미 `[!]` 가 붙어 있는데 또 바뀌면
조용하다. 되돌아가 다시 같아지면 마커가 사라지고, 그것도 알리지 않는다.

**마커는 보고 있는 buffer 하나에만 붙는다.** tabline 에는 넣지 않는다.

**저장·다시 읽기가 마커를 지운다.** `:w!` 로 덮어쓰거나 `:e` 로 가져오면 어긋난 것이 없어진다.

## 근거

### 왜 주기가 아니라 포커스인가

**바깥에서 파일을 고치는 흐름에는 포커스 이동이 딸려 온다.** 다른 편집기, 다른 터미널, IDE —
전부 창을 옮겨야 한다. 그 순간을 짚으면 유휴 상태에서 아무것도 하지 않고도 같은 것을 잡는다.

**사람이 화면으로 눈을 막 돌린 순간이라 알림이 읽힌다.** 주기 검사는 타이핑 한가운데에 뜬다.
지나가는 알림과 궁합이 맞지 않는다.

**파일 전체를 읽어 해시를 내는 비용이다.** 5 초마다 큰 파일을 읽는 것은 `git status` 세 개와
성격이 다르지 않다. 포커스 복귀는 사람이 창을 옮길 때뿐이다.

**터미널이 포커스를 보고하지 않으면 지금까지와 같다.** msg 가 오지 않을 뿐이고 저장할 때의
검사(ADR-0015) 가 그대로 마지막 그물이다. 못 쓰게 되는 것이 없다.

### 왜 마커인가

**알림만으로는 놓치면 다시 볼 길이 없다.** 다음 키에 사라지므로, 돌아오자마자 타이핑을 이어가면
알림을 지나친다. 그 뒤로는 저장할 때까지 아무 표시가 없다 — 지금과 똑같아진다.

**마커는 mode 와 무관하다.** statusBar 위 줄은 명령줄이 아니라 늘 같은 것을 그리는 자리다.
ADR-0023 이 트리에서 파일 검사를 뺀 이유가 "알림을 놓을 자리" 였는데, 그 자리가 이제 생겼다.

**상태와 알림은 다른 것이다.** 알림은 발견을 알리고, 마커는 지금 상태를 들고 있다. 둘을 하나로
합치면 "계속 뜨는 알림" 이거나 "놓치면 끝인 상태" 중 하나가 된다.

### 왜 한 번만 알리는가

**밖에서 계속 바뀌는 파일이 있다.** 로그, 생성물, 남이 작업 중인 파일이다. 창을 오갈 때마다
알리면 아래 줄이 그 알림에 덮여서 명령 결과를 볼 수 없다.

**두 번째 알림에는 새 정보가 없다.** 이미 `[!]` 가 붙어 있고 할 일(`:e` 로 가져오거나 `:w!` 로
덮어쓰기) 도 같다.

**되돌아간 것은 알리지 않는다.** 볼 것이 없어졌다는 알림은 읽는 사람이 할 일이 없다. 마커가
조용히 사라지는 것으로 충분하다.

### 왜 tabline 에는 넣지 않는가

**검사하는 것은 보고 있는 buffer 하나뿐이다.** 활성 tab 에만 마커가 붙으면, 나머지 tab 에 마커가
없는 것이 "저 파일들은 깨끗하다" 로 읽힌다. 사실은 본 적이 없는 것이다. statusBar 는 원래
보고 있는 파일 하나를 말하는 자리라 아는 만큼만 말하게 된다.

**여러 tab 을 한 번에 검사하는 것은 별개 건이다.** tab 열 개면 열 파일을 읽어야 하고, 무엇이
바뀌었는지 알리려면 줄 하나로는 모자란다 — `docs/tasks.md` 가 적어둔 그대로다.

### 왜 normal·insert·트리인가

**오래 머무는 mode 다.** 창을 옮겼다 돌아오는 순간에 사람이 있는 자리는 거의 이 셋이다.

**알림을 그릴 줄을 가지고 있다.** 셋 다 `messageOr` 로 아래 줄을 그린다. 명령줄과 검색은 그 줄을
자기 입력에 쓴다.

**빠뜨린 mode 에서 놓쳐도 다음 복귀에 잡힌다.** 팔레트를 띄운 채 창을 옮겼다 돌아오면 이번에는
못 보지만, 팔레트를 닫고 다시 창을 오가면 잡힌다. 저장할 때의 검사도 그대로다.

### 판정을 그대로 쓴다

`checkOutside` 와 `outsideChange` 는 ADR-0015 가 만들어 둔 것이고 판정 기준(내용 해시) 도
그대로다. 새로 정한 것은 **언제 부르고 결과를 어디에 두느냐** 뿐이다. 문구를 부르는 쪽이 만드는
나눔도 그대로여서, 저장이 막힌 자리는 `:w!` 를, 발견한 자리는 `:e` 를 알린다.

## 결과

좋은 점

- 다른 창에서 고치고 돌아오면 그 자리에서 안다. 남의 변경 위에 한참 더 치다가 저장할 때에야
  막히는 일이 준다.
- 마커가 남아서 알림을 놓쳐도 상태를 볼 수 있다. mode 와도 무관하다.
- 트리에 포커스가 있어도 본다. ADR-0023 이 미뤄둔 자리가 메워졌다.
- 유휴 상태에서는 아무것도 하지 않는다. 창을 옮길 때만 파일 하나를 읽는다.

감수하는 것

- **포커스를 보고하지 않는 터미널에서는 아무 일도 없다.** 지금까지와 같을 뿐이지만, 터미널에
  따라 동작이 갈리는 기능이 하나 생겼다.
- **창을 오갈 때마다 파일 하나를 통째로 읽는다.** 큰 파일을 띄워두고 창을 자주 오가면 그만큼
  읽는다. 주기 검사보다는 훨씬 적다.
- **보고 있지 않은 tab 은 여전히 모른다.** 마커가 없는 tab 이 깨끗하다는 뜻은 아니다.
- **명령줄·검색·팔레트에서 창이 돌아오면 이번 복귀는 놓친다.** 다음 복귀나 저장 때 잡힌다.
- **`[+]` 와 `[!]` 가 둘 다 붙으면 statusBar 위 줄이 그만큼 더 찬다.** 경로가 긴 파일에서는
  오른쪽 git 표시가 먼저 밀려난다(ADR-0009 의 규칙 그대로다).

## 대안

**5 초 tick 에 얹기(ADR-0030 과 같은 고리)** — 포커스를 안 주는 터미널에서도 따라오고, 밖에서
저절로 바뀌는 파일도 잡는다. 대신 유휴 상태에서도 파일을 계속 읽고, 알림을 마커로 바꾸지 않으면
쓸 수 없다. 포커스 쪽이 같은 것을 훨씬 싸게 잡으므로 먼저 넣고, 부족하면 그때 얹는다.

**mtime 만 보기** — 읽지 않아도 되어서 주기 검사가 싸진다. 내용이 같아도 mtime 이 바뀌는 일이
흔해 헛경고가 잦다는 이유로 ADR-0015 가 이미 물린 기준이다. "mtime 이 그대로면 건너뛴다" 는
앞잡이로 쓰는 길은 남아 있지만, 지금은 포커스 복귀 때만 부르므로 값이 없다.

**발견하면 바로 다시 읽기(vim 의 `autoread`)** — 손이 덜 간다. 저장하지 않은 변경이 있으면 그것을
버리게 되고, 없더라도 커서와 화면이 갑자기 움직인다. 가져오는 것은 `:e` 라는 ADR-0016 의 나눔을
깨뜨린다.

**확인창을 띄우기** — 놓칠 수가 없다. 창을 옮겨 돌아올 때마다 키를 하나 요구하게 되고, 로그처럼
계속 바뀌는 파일에서는 편집기를 쓸 수 없다.

**tabline 에도 마커 넣기** — 어느 tab 이 바뀌었는지 한눈에 보인다. 검사하지 않은 tab 이 깨끗해
보이는 거짓 표시가 따라온다. 모든 tab 을 검사하기로 정하면 그때 같이 본다.

## 이 ADR 이 정하지 않는 것

- 여러 tab 을 한 번에 검사하는 것과 그 알림·표시 자리
- 주기 검사를 얹을지. 포커스만으로 부족한 경우가 실제로 나오면 그때 정한다
- 발견한 뒤 자동으로 가져오는 길(`autoread`). 지금은 `:e` 뿐이다
- 밖에서 바뀐 내용과 손에 든 것의 차이를 보여주는 것(diff)
- 디렉터리 감시(inotify·FSEvents). 파일 하나를 읽는 것보다 나은지는 따로 볼 문제다
