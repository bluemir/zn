# ADR-0006: normal mode 의 키 입력을 상태 기계로 받고, 이동 키에 숫자 접두를 붙인다

- 상태: 채택
- 날짜: 2026-08-12

## 맥락

`hjkl` 이동은 `docs/tasks.md` 에서 "vim 키맵 정의를 기다린다" 로 열려 있었고
`docs/spec.md` 도 "vim 키맵(`hjkl` 등) 은 아직 없다" 로 남아 있었다. 화살표로만 커서를
옮길 수 있어서 vim 을 쓰던 손이 그대로 오지 못했다.

키를 넣기 전에 정해야 할 것이 네 가지였다.

1. **`10j` 같은 숫자 접두(count).** 이동 키를 넣는 이유의 절반이 이것이다.
   `viewEditorNormal` 에는 접두 키 하나를 담는 `pending string` 필드만 있었다. 숫자를 받으려면
   필드가 하나 더 늘고, `Update` 의 `switch` 앞에 조건이 하나 더 붙는다.
2. **`j`/`k` 의 단위.** 이 편집기는 가로 스크롤 대신 줄바꿈으로 긴 줄을 보여주고(ADR-0001),
   `↑`/`↓` 는 화면 행 단위로 움직인다. vim 의 `j` 는 논리 줄이고 화면 행은 `gj` 다.
3. **`0`.** vim 에서 `0` 은 줄 시작으로 가는 키라 count 의 첫 자리가 될 수 없다.
4. **치는 동안의 표시.** ADR-0003 이 "`g` 를 누른 동안 화면에 아무 표시가 없다" 를 감수하는 것으로
   남겨 뒀다. 숫자까지 받기 시작하면 안 보이는 상태가 더 늘어난다.

## 결정

**normal mode 의 키 입력을 상태 기계로 받는다.** `internal/core/normal-key-parser.go` 의
`normalState` 가 키를 하나씩 먹고 다음 상태를 준다. 명령이 완성되면 `normalKey{name, count}` 를
주고, 아직이면 빈 이름을 준다. `command-parser.go` 의 `tokenizerState` 와 같은 모양이다.

상태는 셋이다 — `normalStart`(처음), `normalCount`(숫자를 모으는 중),
`normalPending`(`g`·`ctrl+w` 뒤). 접두 키가 붙은 명령은 `g t` 처럼 공백으로 이어 붙인 이름
하나가 되고, `viewEditorNormal.run` 이 그것을 평평한 `switch` 로 받는다.

**count 는 이동 키에만 붙는다.** `h` `j` `k` `l` `w` `W` `e` `E` `b` `B` `$` `G` 와 접두 키
`g`(`42gg` 를 위해 숫자를 들고 넘어간다) 다. 다른 키는 모으던 숫자를 버리고 한 번만 동작한다.
`$` 와 `gg`/`G` 는 숫자의 뜻이 되풀이가 아니다 — 각각 줄 수와 줄 번호다. vim 과 같다.

**단어 경계는 글자 부류가 바뀌는 자리다.** 부류는 넷이다 — 공백 / 단어 글자(영문·숫자·`_`) /
한글·한자·가나 / 그 밖의 문장부호. `w` `b` `e` 는 이 부류로 끊고, `W` `B` `E` 는 공백으로만 끊는다.
`camelCase` 와 `snake_case` 안에서는 멈추지 않는다.

**`j`/`k` 는 논리 줄 단위, `↑`/`↓` 는 화면 행 단위다.** 둘 다 남긴다.

**`0` 은 vim 과 같다.** count 를 모으는 중이면 자릿수이고, 아니면 아직 아무 기능이 없는 키다.

**치고 있는 키를 statusBar 아래 줄 오른쪽 끝에 보여준다.** vim 의 `showcmd` 다. 숫자와 접두 키
둘 다이고, sidebar 의 `ctrl+w` 도 같이 보여준다.

## 근거

### 상태 기계

**기다리는 상태가 계속 늘어난다.** 지금은 접두 키와 숫자 둘이지만, 앞으로 들어올
operator-pending(`d` `c` `y`), 인자를 한 글자 더 받는 키(`f` `t`), register(`"a`) 가 전부
"다음 키를 기다리는 상태" 다. 필드로 두면 필드가 하나씩 늘고 `Update` 앞의 if 도 같이 늘어난다.
상태로 두면 type 이 하나 늘고 나머지는 그대로다. ADR-0003 이 "operator 가 들어와서 '무엇을
기다리는가' 가 진짜 상태가 되면 그때 다시 본다" 로 미뤄 둔 자리가 여기다.

**조합이 곱해지지 않는다.** 필드 방식이면 "숫자를 모으는 중에 `g` 를 받으면" 같은 조합을
`Update` 안에서 손으로 풀어야 한다. 상태 기계에서는 `normalCount` 가 모르는 키를
`normalStart` 에 넘기는 한 줄로 끝난다.

**`showcmd` 가 상태에서 그냥 나온다.** 화면에 무엇을 보여줄지는 "지금 무엇을 기다리는가" 와
같은 말이다. 상태가 그 답을 이미 들고 있어서 `showcmd()` 하나면 된다.

**저장소에 이미 있는 idiom 이다.** `tokenize` 가 글자를 먹어 토큰을 뱉는 것과 모양이 같다.
`docs/tasks.md` 의 "command parser — state pattern 을 기반으로 만든다" 와 같은 결정이다.

### 단어 경계

**한글을 단어 글자와 다른 부류로 본다.** vim 이 하는 동작이다. 한글 문서에 영문 낱말이 섞이는
것이 흔한데(`한글abc`), 둘을 같은 부류로 보면 `w` 가 그 덩어리를 통째로 건너뛴다. 영문 낱말만
고쳐 쓰려면 경계에서 멈춰야 한다. 부류 판정은 Go 의 `unicode.Han`/`Hangul`/`Hiragana`/`Katakana`
script 를 그대로 쓴다 — 범위를 직접 적으면 틀리고, 나중에 늘어나는 것도 따라가지 못한다.

**`camelCase`·`snake_case` 안에서는 멈추지 않는다.** README 의 "vim 의 개선 판" 에 걸리는 자리라
subword 이동을 고려했지만, `w` 자체를 바꾸면 vim 근육기억과 밀린다. 지금 단계는 이동 키를
vim 과 맞추는 것이고, subword 는 별도 키로 나중에 볼 여지를 남겼다(`docs/tasks.md`).

**부류가 바뀌면 끊는다는 규칙 하나로 `W`/`B`/`E` 까지 덮는다.** 큰 단어는 "공백이 아닌 것을
전부 한 부류로 본다" 로 끝나서, 이동 코드는 하나이고 부류 판정만 갈린다.

### count 는 이동 키에만

**지금 뜻이 분명한 것이 이동뿐이다.** vim 에서 `3i` 는 친 것을 세 번 되풀이해 넣는 것이고
`3u` 는 세 번 되돌리는 것인데, 되풀이 기록(`.` 이 쓰는 것) 이 아직 없다. 뜻이 정해지지 않은
키에 숫자를 붙이면 눌러 보고 아무 일도 안 나는 것보다 나쁘다 — 무언가 일어날 것처럼 보인다.

**넓히는 것은 나중에 한 줄이다.** 상태 기계에서 count 를 받는 키 목록에 이름을 더하면 된다.
`docs/tasks.md` 에 열어 뒀다.

### `j`/`k` 는 논리 줄

**vim 그대로다.** ADR-0003 에서 `gt`/`gT` 를 고른 것과 같은 이유 — 개선할 것이 있어서가 아니라
손가락이 이미 알고 있어서다. `10j` 가 열 줄이 아니라 열 화면 행이면 `10j` 를 치는 이유가 없다.
줄 번호를 보고 세는 동작이기 때문이다.

**화면 행 이동도 남긴다.** 긴 줄을 줄바꿈으로 보여주는 이상 화면에 보이는 대로 한 행씩 내려가는
동작이 필요하다. vim 은 그것을 `gj`/`gk` 에 두었는데, 여기서는 이미 `↑`/`↓` 가 그것이다.
키가 갈라져 있으니 단위도 갈라 두는 편이 설명이 짧다.

### `0`

**자리를 비워두는 것이 싸다.** `0`(줄 시작) 은 곧 넣을 키다. 지금 `0` 을 count 첫 자리로 쓰게
해두면 나중에 그 동작을 도로 빼야 한다. 반대로 지금 비워두면 `run` 에 case 하나를 더하는 것으로
끝난다. `10j` 는 어느 쪽이든 동작하므로 잃는 것이 없다.

### showcmd

**안 보이는 상태가 늘었다.** 접두 키 하나일 때는 감수할 만했지만(ADR-0003), 숫자는 여러 키를
누르는 동안 계속 기다린다. 편집기가 키를 먹었는지 무시했는지 화면으로 알 수 없으면 다시
누르게 되고, 그러면 `33j` 가 된다.

**자리는 이미 비어 있다.** statusBar 아래 줄은 커서 위치(`1:1  (5 줄)`) 만 쓰고 오른쪽이
비어 있다. vim 도 같은 자리다. 칸이 모자라면 붙이지 않는다 — 커서 위치가 밀려나는 것이 더 나쁘다.

## 결과

좋은 점

- `10j`, `20k`, `5l` 이 동작한다. `hjkl` 이 화살표와 같은 자리에 붙었다.
- `Update` 가 짧아졌다. "어떤 키 나열이 명령인가" 는 상태 기계가, "그 명령이 무엇을 하는가" 는
  `run` 의 평평한 `switch` 가 맡는다. `runPending` 이 없어졌다.
- 상태 기계만 model 없이 테스트할 수 있다. 키 나열 규칙은 화면과 무관하다.
- `g` 와 `ctrl+w` 를 누른 동안 화면에 표시가 생겼다. ADR-0003 이 감수하기로 한 것을 갚았다.

감수하는 것

- **키 처리가 두 곳으로 나뉜다.** ADR-0002 의 "mode 별 키 처리는 한 파일에" 와 어긋나 보이지만,
  나뉜 것은 문법과 의미이지 mode 가 아니다. normal mode 의 의미는 여전히
  `view-editor-normal.go` 한 곳에 있다.
- **키 넷을 넣는 데 필요한 코드보다 많다.** 필드 두 개면 될 것을 type 셋으로 했다.
  위의 "기다리는 상태가 계속 늘어난다" 를 믿고 미리 낸 값이고, 틀리면 되돌리기 어렵지 않다.
- **wrap 된 줄에서 `j`/`k` 의 유지 칸이 vim 과 다르다.** `desiredCol` 이 화면 행 안에서 센 칸이라
  (`buffer.go`), wrap 된 줄의 둘째 행 이후에서 `j` 를 누르면 vim 이 가는 칸과 다르다.
  wrap 되지 않은 줄에서는 같다. `docs/tasks.md` 에 남겼다.
- **`↑`/`↓` 와 `j`/`k` 가 다르게 움직인다.** 한 키를 다른 키로 설명할 수 없어서
  `docs/spec.md` 의 키 표에 둘을 따로 적어야 한다.

## 대안

**필드 두 개(`pending string`, `count int`)** — 지금 넣는 키에는 이것이 가장 짧다.
`Update` 앞에 조건이 둘 붙고 끝난다. 다음에 들어올 것이 operator-pending 이라 그때 다시
갈아엎게 되는데, 그 시점에는 잡아둘 테스트가 지금보다 많아서 더 비싸다.

**mode 처럼 별개 model 로 두기(ADR-0002 방식)** — `viewEditorCount` 같은 type 을 만들어
model 을 갈아끼운다. 전환 함수와 `WindowSizeMsg` 껍데기, `View` 가 type 마다 따라붙는다.
mode 는 화면과 커서 모양이 달라지지만 count 를 모으는 중에는 화면이 그대로라 그 값을 낼 이유가 없다.

**`j`/`k` 를 화면 행 단위로(`↑`/`↓` 와 같게)** — 코드가 가장 적다. `moveDown` 이 이미 count 를
받으므로 case 만 늘리면 끝이었다. `10j` 의 뜻이 줄 번호와 어긋나는 것이 이유가 되지 못한다.

**`hjkl` 만 넣고 count 는 나중에** — 이동 키를 넣는 이유의 절반이 count 라 나눌 이유가 없다.
접두 상태를 다시 손대야 해서 두 번 일하는 쪽이기도 하다.

**`run` 의 switch 도 표(map)나 command type 으로** — 이름별로 `normalCommand{count, run}` 표를
두거나 동작마다 type 을 하나씩 만들면, 키맵이 코드 흐름이 아니라 데이터가 된다. 상태 기계와
idiom 도 맞는다. 두 가지가 걸려서 두지 않았다. 하나는 20 개 중 5 개(`ctrl+c` `:` `i` `a`
`ctrl+w w`) 가 다른 model 을 돌려주는 mode 전환이라, type 을 하나로 두면 나머지 15 개가 전부
`return m, nil` 껍데기를 갖는다는 것이다. 다른 하나는 이 선택이 `docs/tasks.md` 의
"`config 는 compile 됨` 의 실제 형태를 정한다 — 키맵을 Go 코드 어디에 어떤 타입으로 쓸지가
곧 코드 구조다" 와 같은 결정이라는 것이다. 이동 키를 넣는 김에 곁다리로 정할 것이 아니라
그 ADR 에서 한 번에 정한다. 그때까지는 평평한 `switch` 가 곧 키맵 표를 겸한다 — 어느 키가
무엇을 하는지 한 화면에서 읽힌다. 읽어서 알기 어려워지면 그때 다시 본다.

## 이 ADR 이 정하지 않는 것

- "vim 대비 무엇을 개선하는가"(`docs/tasks.md` 의 첫 항목). 이번 결정은 그중 이동 키에 대한 답일 뿐이다
- subword 이동을 별도 키로 둘지. `w` 는 vim 과 같게 두기로만 했다
- `ge`(앞 단어의 끝), `{count}gt`(숫자로 tab 고르기), `f`/`t`(줄 안에서 글자 찾기)
- `{`/`}`/`(`/`)` 같은 문단·문장 이동. 문단과 문장의 경계를 먼저 정해야 한다
- operator-pending(`d` `c` `y`) 의 상태 이름과 `3d2w` 처럼 count 가 둘 붙는 문법
- count 를 이동 키 밖으로 넓힐지. 되풀이 기록(`.`) 을 정할 때 같이 본다
- `desiredCol` 을 줄 기준으로 둘지 화면 행 기준으로 둘지
