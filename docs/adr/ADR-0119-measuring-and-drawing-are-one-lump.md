# ADR-0119: 재는 일과 그리는 일은 한 덩어리다. `internal/lines` 를 물린다

## 맥락

ADR-0117 이 cluster.go 와 word.go 를 `internal/lines` 로 냈다. 근거는 「buffer 쪽과 그리는 쪽이 나눠 쓰는 아래층이고, 받은 줄과 tab 폭만으로 답하는 순수 계산이라 어느 한쪽에 넣으면 틀린다」였다.

**그 뒤 사흘 동안 그 경계가 세 번 샜다.**

| 언제 | 무엇이 샜나 |
|---|---|
| ADR-0117 §5 | `screenRow`·`rowBefore` 가 그 안에 있었다. 화면을 채우는 일이라 core 로 돌려보냈다 |
| ADR-0117 §5 | `WordKind` flag 가 `ClassAt` 에 있었다. 키의 개념이라 core 로 돌려보냈다 |
| ADR-0118 §6 | `WidthOf`·`WidthOfStyled`·`EscapeSizeAt` 이 그 안에 있었다. 전제를 다는 것이라 core 로 냈다 |

세 번 다 「이건 그쪽 말이 아니다」로 밀어냈다. 그런데 밀어낼수록 남은 것이 순수해지기는커녕 **그리는 일을 더 짊어졌다.** `ADR-0118` 에서 `ScreenText` 를 넣은 것이 정점이다. 좌표를 옮기는 패키지가 화면에 그릴 문자열을 짓는다.

그러고도 어긋남이 남았다. tab 이 마커로 찍히는 줄에서는 core 가 여전히 손수 폈고(ADR-0118 §6), 그것을 고쳐도 **`^[` 는 글자를 lines 가 정하고 색은 core 가 입히는** 모양이 남았다. 한 글자를 두 겹이 나눠 짓는다.

## 1. 경계가 아니라 전제가 틀렸다

「좌표 변환」과 「화면에 그리기」를 가를 수 있다고 보았다. **가를 수 없다.**

```go
func glyphAt(line []byte, offset, col, tab int) (size, width int) {
	if line[offset] == '\t' {
		return 1, tab - col%tab      // tab 을 몇 칸으로 펼 것인가
	}
	if controlText(line[offset]) != "" {
		return 1, 2                  // 제어문자를 몇 칸으로 보일 것인가
	}
	...
}
```

**이 함수는 이미 「이 편집기가 화면에 그리는 방식」이다.** tab 을 4 칸으로 펴는 것도, 제어문자를 `^[` 두 칸으로 보이는 것도 이 편집기가 정한 것이지 유니코드가 정한 것이 아니다. vim 은 `list` 를 끄면 다르게 그리고, tab 을 8 칸으로 보는 편집기도 있다.

그리고 그 위에 선 `screenColAt`·`offsetAtScreenCol`·`wrapOffsets` 는 전부 그 결정을 물려받는다. **재는 함수가 그리는 규칙을 알고 있다.** 그러니 「재는 것만 아래층으로」가 성립하지 않는다.

거꾸로 보면 이렇다. `widthOf` 는 이미 지어진 글을 받아 정직하게 칸만 센다. 그것이 오히려 순수한 쪽인데, ADR-0118 이 그것을 core 로 **밀어냈다.** 남은 쪽이 더 그리는 일에 붙어 있는데 그쪽을 아래층이라고 부르고 있었다.

## 2. 셌던 숫자도 근거가 아니었다

ADR-0117 §4 는 「cluster.go 를 buffer 쪽이 60, 그 밖이 89 회 쓴다. 양쪽이 나눠 쓰니 아래로 내리는 것만 맞다」로 냈다.

**그 89 회의 대부분이 `WidthOf`(74 회) 였다.** 그리고 그것은 ADR-0118 에서 core 로 갔다. 남은 것을 다시 세면 buffer\* 70, 그 밖 29 다. 「양쪽이 나눠 쓴다」가 성립하지 않는다.

숫자가 근거였는데 그 숫자를 만든 함수가 다른 겹의 것이었다. **무엇을 세는지가 틀리면 얼마나 정확히 세도 소용이 없다** (ADR-0117 의 되짚음이 같은 말을 하고 있었는데 이번에도 걸렸다).

## 3. 그래서 물린다

`internal/lines` 를 없애고 내용을 core 로 되돌렸다.

| 지금 | 파일 |
|---|---|
| `glyphAt`·`glyphSize`·`screenColAt`·`offsetAtScreenCol`·`prevGlyphStart`·`wrapOffsets`·`rowIndexAt`·`rowRange`·`controlText`·`screenText` | cluster.go |
| `charClass`·`glyphClass`·`class*` | glyph-class.go |

패키지 접두가 없어졌으므로 이름에 `screen`·`glyph` 를 되살렸다. `ColAt` 은 core 에서 `screenColAt` 이라야 무엇을 재는지 말한다.

**이번 대화로 고친 것은 전부 살아 있다.** 제어문자를 보이게 그리는 것(ADR-0118), `widthOf` 와 `widthOfStyled` 를 합친 것, `ClassAt` 의 flag 를 걷어낸 것, `screenRow` 를 제자리로 옮긴 것이 그렇다. **패키지만 물렸다.**

## 4. 파일 경계는 남는다

패키지가 아니어도 갈래는 그대로다. 오히려 파일로 두니 어긋남이 없어졌다.

| 파일 | 무엇을 받나 | `\x1b` 를 |
|---|---|---|
| cluster.go | **파일에서 온 줄.** 화면에 그리면 몇 칸인지 답하고, 그릴 글자로 바꾼다 | 내용. `^[` 두 칸 |
| width.go | **이미 지어진 화면 글.** 몇 칸인지 답한다 | 색. 0 칸 |
| render-row.go | 조각으로 갈라 색을 입힌다 | |

「변환 전이냐 후냐」가 cluster.go 와 width.go 를 가르고, 「글자를 정하는가 색을 입히는가」가 cluster.go 와 render-row.go 를 가른다. **패키지 벽이 없어도 이 갈림은 읽힌다.** 벽이 있을 때 오히려 「그쪽 말이 아니다」를 세 번 밀어내야 했다.

## 되짚은 것

**패키지를 가르는 근거로 「누가 쓰는가」를 셌다.** ADR-0117 이 「나가는 의존이 0 인 잎부터 본다」로 닫았고 cluster.go 가 그 잣대에 맞았다.

그 잣대가 놓친 것이 **「이것이 무엇을 아는가」** 였다. 나가는 의존이 0 인 것은 「아무것도 안 물어본다」는 뜻이지 「아무 결정도 안 들었다」는 뜻이 아니다. `glyphAt` 은 아무에게도 안 묻지만 tab 폭과 제어문자 폭이라는 **편집기의 결정 둘을 몸에 지니고** 있었다.

그리고 그것을 알아챌 기회가 세 번 있었다. `screenRow` 를 밀어낼 때, flag 를 밀어낼 때, `WidthOf` 를 밀어낼 때. **매번 「그건 예외다」로 처리했다.** 예외가 셋이면 규칙이 틀린 것인데 그때마다 규칙을 지키는 쪽으로 고쳤다.

다음에 패키지를 가를지 물을 때는 의존 방향을 세기 전에 **「이 덩어리가 무엇을 결정하고 있나」**를 먼저 적는다. 그 결정이 위 겹의 것이면 아무리 잎이어도 잎이 아니다.
