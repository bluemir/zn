# ADR-0077 여러 파일 검색은 작업으로 돌리고, 결과는 줄 내용을 든 전체 화면 목록이다

- 상태: 채택
- 날짜: 2026-08-25

## 맥락

`docs/tasks.md` 가 오래 열어 두고 결정할 것을 적어 두었다.

> 여러 파일에 걸친 검색.
> - 결과를 담을 화면을 새로 정해야 한다. `GOTO`(`viewLocations`) 는 하단 drawer 로 내려갔고
>   최대 열여섯 줄이라, 수백 개가 올 수 있는 검색 결과와는 갈린다. 붙일 것은 줄 내용 칸과,
>   목록을 띄운 뒤에도 검색을 이어 가는 길이다
> - 검색어를 입력할 modal

만들 조각은 거의 다 있었다. 파일 열거는 팔레트가 쓰는 `indexFiles` 가 git 을 통해 `.gitignore`
까지 받아 오고(ADR-0042), 패턴 문법은 `/` 의 `parseSearchPattern` 이 이미 정해 두었고,
작업 틀은 `startJob(name, args, ...)` 이다 — **`args` 를 `[]string` 으로 둔 근거가 바로
「여러 파일 검색의 패턴+범위」였다**(ADR-0075).

## 1. 결과는 화면을 통째로 쓰는 목록이다

하단 drawer 를 쓰지 않았다. 두 가지 때문이다.

- 오는 것이 수백 곳인데 판은 최대 열여섯 줄이다. 상한을 올리면 ADR-0069 가 그 상한을 둔
  근거(「판이 화면을 다 먹으면 쓰는 까닭 자체가 사라진다」) 를 뒤집게 된다
- **줄 내용 칸을 넣을 폭이 필요하다**(§2)

화면 문법은 `:jobs`·`MESSAGES` 와 같다 — 맨 위가 반전 제목 띠, 키 안내가 statusBar 바로 위 줄,
statusBar 는 트리가 없는 것으로 치고 그린다(ADR-0027, ADR-0053).

## 2. 목록에 줄 내용을 넣는다. 그래서 둘러보기 판이 아니다

`GOTO` 는 `j`/`k` 가 커서를 실제로 옮겨 보여주는 둘러보기 판인데(ADR-0073), **그렇게 만든
까닭이 「목록에 `경로:줄` 뿐이라 그 줄이 무엇인지 보려면 어차피 가 봐야 했다」였다.**

줄 내용이 목록에 있으면 그 까닭이 사라진다. 게다가 수백 곳을 `j` 로 훑는 동안 파일을 계속
여는 것은 값이 없다. 그래서 `j`/`k` 는 목록만 움직이고 `enter` 가 판을 닫으며 뛴다.

**매칭이 칸 밖으로 밀리면 앞쪽을 접어 끌어온다**(`grepWindow`). 줄 앞부터 그린 뒤 오른쪽을
자르면 찾은 글자가 화면에 아예 안 나오는 줄이 생긴다 — 실제로 `newBuffer` 를 찾았을 때
ADR 문서의 긴 줄들이 그랬다. 그러면 줄 내용을 넣은 까닭이 도로 사라진다. 앞 문맥 여덟 칸은
남긴다 — 매칭이 칸 맨 앞에 붙으면 그것이 무엇의 일부인지 안 보인다.

경로는 **왼쪽부터** 접고 내용은 오른쪽부터 접는다. 경로에서 값을 지닌 것은 뒤쪽(파일 이름)
이고 내용에서는 앞쪽이다(ADR-0069).

## 3. 「검색을 이어 가는 길」은 다시 훑는 것이 아니라 거르는 것이다

`/` 로 목록을 좁힌다. **이미 담은 적중을 거를 뿐 저장소를 다시 훑지 않는다** — 글자마다
곧바로 좁아진다. 거르는 자는 `경로 + 줄 내용` 에 그 글자가 들었는지이고 대소문자를 보지 않는다.
정규식이 아닌 것은, 정규식으로 찾은 결과를 다시 정규식으로 좁힐 일이 드물어서다.

`filtering`(치는 중) 과 `filter`(거른 글자) 를 갈라 든다. `/` 만 누른 상태와 아무것도 안 한
상태에서 아래 줄이 달라야 하고, `j` 가 목록을 옮길지 글자로 먹힐지도 그것으로 갈린다.

## 4. 패턴은 `:grep` 이 통째로 받는다 — 토크나이저가 이름을 알게 되었다

**`\` 가 이 결정을 강제했다.** `tokenEscaped` 는 `\` 뒤 글자를 뜻 없이 그대로 받으므로
`\d` 가 `d` 가 된다. 뜯은 인자를 다시 공백으로 이어 붙이면 `\d+` 가 `d+` 로 **조용히 다른
정규식이 된다.**

그래서 `:grep` 뒤는 `!` 처럼 `tokenRest` 가 통째로 준다. ADR-0045 는 「뜻이 갈리는 것은
자리뿐」으로 두었는데 — `!` 는 줄 맨 앞이라는 자리로 알 수 있다 — 정규식은 그렇지 않다.
`:e pat` 의 pat 은 파일 이름이라 뜯어야 하고 `:grep pat` 의 pat 은 통째여야 한다.
**자리가 같고 이름만 다르다.**

첫 토큰을 모으는 상태(`tokenName`) 를 새로 두고, 그 이름이 통째로 받는 것이면 `tokenRest` 로
넘긴다. 아는 이름이 하나뿐이라 표를 두지 않았다 — 둘째가 오면 그때 표로 모은다.

**뒤가 공백뿐이면 인자가 아니다.** `:grep ` 도 `:grep   ` 도 `:grep` 과 같다. 공백 둘을
인자로 세면 「패턴을 댔다」가 되어 물어보는 길로 못 가고, 온 저장소가 걸린다 — 오타일
가능성이 훨씬 크다. 공백을 정말 찾아야 하면 `\s` 나 `[ ]` 로 쓴다. 이름 자리의 `!` 가 빈
경우를 `commandName` 에서 이미 가르던 것을 공백까지로 넓힌 것이다.

## 5. 부르는 길은 셋이고 모두 한 자리로 모인다

- `:grep <패턴>` — 곧바로 시작한다
- `:grep` — 아래 줄에서 패턴을 받는다(`viewGrepInput`). `:rename` 과 같은 손이다(ADR-0067)
- 팔레트의 「프로젝트 검색」 — 같은 입력창을 연다

입력창은 `/` 검색창과 같은 틀이다 — 아래 줄에 앞머리와 친 글자, 커서는 그 끝. 패턴을 치는
자리가 화면에서 같은 곳이어야 손이 헷갈리지 않는다.

**미리보기가 없다.** `/` 는 치는 동안 첫 매칭으로 화면이 따라가는데(incsearch) 여기서 그러면
글자마다 저장소를 훑는 일이 된다. Enter 로 한 번만 시작한다.

**지난 패턴을 채워 주지 않는다.** 대개 다른 것을 찾으려고 여는 자리라 채워 두면 늘 먼저
지우게 된다 — 이름 바꾸기가 지금 이름을 채워 주는 것과 갈리는 자리다(ADR-0067).

## 6. 고치던 buffer 는 디스크가 아니라 buffer 의 글을 훑는다

사람이 화면에서 보고 있는 글을 찾아야 방금 친 이름이 바로 걸리고 지운 이름이 결과에 안 나온다.

작업은 goroutine 에서 돌고 buffer 는 `Update` 가 건드리므로 **시작하는 자리에서 복사해 실어
보낸다**(`dirtyOverlay`). 작업이 buffer 를 들여다보면 편집과 겹친다(ADR-0001). 결과는
「시작한 순간의 글」이다.

**`buf.path` 는 상대일 수도 절대일 수도 있다.** CLI 인자·트리·팔레트가 저마다 주는 대로
담긴다. 훑는 목록의 자는 뿌리 기준 상대 경로라 `filepath.Abs` 를 지나 맞춰야 한다 —
맞추지 않으면 `Rel` 이 실패해서 overlay 가 **조용히 비고** 고치던 글이 검색에서 빠진다.
실제로 처음 구현이 그랬고, 실제로 띄워 보고서야 드러났다.

## 7. 상한을 두는 첫 목록이다

알림 목록과 끝난 작업 목록은 상한이 없다 — 담기는 것이 코드에 있는 종류만큼만이라 늘 자라지
않는다(ADR-0030). 검색은 다르다. **사람이 친 패턴에 달렸고 `.` 하나면 저장소의 모든 줄이
온다.** 그래서 적중 5,000 에서 그만두고 **닿았다는 것을 제목줄에 적는다**(`5,000+`).
조용히 자르면 「이게 전부」로 읽힌다.

같이 두는 상한 셋이 더 있다. 파일 8MB, 한 줄 1MB, 그리고 이진 파일은 아예 건너뛴다 —
앞부분 8,000 byte 에 NUL 이 있으면 이진으로 본다(git 과 같은 판정이고 확장자로 가르지 않는다).
줄마다 첫 매칭만 담는다 — 같은 글이 목록에 두 줄 서면 훑는 데 방해가 되고, 뛴 뒤 `n` 이
나머지를 짚는다.

## 8. 뛰면 마지막 검색으로 굳힌다

`enter` 로 간 자리에서 `n`·`N` 이 그 패턴을 이어 짚는다. 뛰어간 자리에서 같은 패턴을 다시
칠 이유가 없다 — `*` 가 커서 단어를 마지막 검색으로 두는 것과 같다.

뛰기 전 자리는 jumplist 에 남아서 `ctrl+o` 로 돌아온다. 둘러보기 판이 아니라 커서가 그대로
있으므로 `recordJump`(지금 자리) 를 쓴다 — 판을 열기 전 자리를 따로 적어 둘 필요가 없다
(ADR-0070, ADR-0073).

## 결과

- `grep.go`(작업)·`view-grep.go`(결과 목록)·`view-grep-input.go`(패턴 입력) 셋이 늘었다
- `:jobs` 에서 검색은 이름 줄 `프로젝트 검색 (1)` 아래에 패턴이 자식 줄로 접힌다.
  ADR-0075 가 내다본 첫 쓰임이고 새로 정할 것이 없었다
- 결과는 `editor.grep` 에 산다. 팔레트의 `files` 와 같은 자리다 — 작업이 화면보다 오래 살고
  조각이 도착하는 곳이 `Update` 라 mode 와 무관하다
- **늦은 조각은 새 결과를 덮지 않는다.** 이름이 같아도 인자가 다르면 다른 작업이라(ADR-0075)
  두 검색이 겹칠 수 있어서, `apply` 가 지금 패턴과 다르면 넣지 않는다
- 여러 파일 replace 는 그대로 열려 있다. 되돌리기가 buffer 안의 일이라 디스크에 쓴 것을
  못 돌리는 문제(ADR-0067 의 이름 바꾸기와 같은 자리) 를 먼저 정해야 한다
