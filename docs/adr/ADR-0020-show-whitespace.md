# ADR-0020: 공백을 화면에 드러낸다 — tab 폭 4 칸과 들여쓰기·줄끝 마커

- 상태: 채택
- 날짜: 2026-08-13

## 맥락

화면에서 tab 과 space 는 **똑같은 빈 칸**이다. 편집기가 tab 을 tab stop 까지 공백으로
펼쳐 그리기 때문에(`docs/done.md` 의 "tab 이 화면에서 사라지는 것을 고친다") 그려진 결과만
보면 둘을 구분할 방법이 없다.

이것이 실제로 문제가 되는 자리는 이렇다.

- **들여쓰기가 tab 과 space 로 섞인 파일.** Go 소스는 tab 이지만 붙여넣은 조각이나 다른
  편집기가 건드린 줄은 space 인 경우가 있다. 화면에서는 같은 자리에 있는 것처럼 보이는데
  `^` 나 `dw` 가 다르게 움직이고, `gofmt` 가 줄을 통째로 바꿔놓는다.
- **줄 끝 공백.** 보이지 않으므로 지울 생각을 못 한다. 「줄 끝 공백 지우기」 명령이 있어도
  어느 줄이 걸리는지 알 수 없어서 쓰기 전에는 무엇이 바뀔지 모른다.
- **공백뿐인 줄.** 빈 줄과 구분되지 않는다.

여기에 tab 폭 자체도 다시 볼 자리였다. 처음에는 vim 의 `tabstop` 기본값이자 터미널 기본
tab stop 인 8 칸으로 정했다(`docs/done.md`). 그런데 8 칸은 세 단계만 들어가도 24 칸을 먹는다.
편집 영역은 왼쪽에 줄번호 7 칸을 떼고 sidebar 를 열면 32 칸을 더 뗀 뒤에 남는 자리다.
80 칸 터미널에서 sidebar 를 열면 본문이 41 칸인데, 그 중 24 칸이 들여쓰기가 된다.

`docs/tasks.md` 에 "tabsize 는 4칸 으로 표시 한다" 와 "tab 문자와 space 를 구분해서 보여주기"
로 각각 잡혀 있던 건이다. 둘 다 "공백을 화면에서 어떻게 다룰 것인가" 라 같이 정한다.

## 결정

**tab 폭을 4 칸으로 한다.** `tabWidth` 상수 하나이고, 이것을 쓰는 곳은 `clusterAt` 뿐이라
커서 이동·줄바꿈·마우스 클릭·검색 강조가 모두 따라온다. 파일에 들어가는 문자는 그대로 `\t` 다 —
저장 형식은 건드리지 않는다.

**tab 은 `»`(U+00BB), space 는 `⋅`(U+22C5 DOT OPERATOR) 로 찍는다.** 본문보다 흐린
색(256색 240) 이다. sidebar·상대 줄번호·검색 강조와 같이 256색 고정값을 쓴다(ADR-0005, ADR-0007).
둘 다 East Asian Width 가 **Neutral** 이라 터미널 설정과 무관하게 한 칸이다.
(2026-08-13 수정. 처음에는 space 마커가 `·`(U+00B7) 였는데 그것은 Ambiguous 다 —
아래 "마커 글자의 폭" 참고.)

**찍는 자리는 줄 앞 들여쓰기와 줄 끝 공백뿐이다.** 줄 가운데 space 와 tab 은 마커 없이
빈 칸으로 둔다. 공백뿐인 줄은 줄 전체가 들여쓰기이므로 전부 찍힌다.

**tab 마커는 tab 이 시작하는 한 칸뿐이고 남는 칸은 빈 칸이다.** 줄 앞 tab 하나는 `»` 와
빈 칸 3 개다.

**항상 켜져 있다.** 끄는 명령을 두지 않는다.

**화면 행을 조각(`screenPart`) 으로 나눠 조각마다 style 을 한 번씩 입힌다.** 마커 조각과
본문 조각이 갈리고, 검색 강조는 조각들 위에 base style 로 얹힌다. 마커 조각은
`강조style.Foreground(회색)` 처럼 합친 하나의 style 로 그린다.

## 근거

### 왜 8 칸이 아니라 4 칸인가

**8 칸은 남는 본문 폭에 비해 너무 크다.** 터미널 기본 tab stop 이 8 인 것은 화면 전체를
쓰는 `cat` 의 사정이고, 편집기는 줄번호와 sidebar 를 떼고 남은 자리에 본문을 그린다.
깊게 들여쓴 Go 코드가 화면 밖으로 밀리거나 wrap 되면 들여쓰기 자체가 읽기를 방해한다.

vim 기본값을 따르는 이점은 있었지만, 실제 Go 프로젝트에서 `tabstop=4` 를 쓰는 쪽이
훨씬 흔하다. 파일 내용이 바뀌지 않으므로 이 선택은 언제든 되돌릴 수 있다 — 상수 하나다.

### 왜 줄 가운데 공백은 찍지 않는가

**모든 space 를 찍으면 산문과 주석이 점으로 뒤덮인다.** 이 편집기의 주석과 문서는 한국어
문장이라 단어 사이 공백이 많다. `이·편집기는·이렇게·보인다` 는 읽을 수 없다.

반면 들여쓰기와 줄 끝은 **공백 자체가 정보**인 자리다. 들여쓰기는 tab 인지 space 인지가
중요하고, 줄 끝 공백은 존재 자체가 알아야 할 사실이다. 그 사이 — 줄 가운데 — 는 공백이
그냥 단어 구분이라 찍을 이유가 없다.

줄 가운데 tab 은 애매하다. struct tag 정렬이나 TSV 는 tab 인지 space 인지가 중요하다.
지금은 "space 와 같은 범위" 로 맞춰 두고 `docs/tasks.md` 에 다시 볼 항목으로 남긴다.
범위를 둘로 가르면 규칙이 "들여쓰기·줄끝의 공백, 그리고 어디든 tab" 이 되어 설명이 길어진다.

### 왜 tab 의 남는 칸을 점으로 채우지 않는가

`»···` 처럼 채우면 tab 4 칸과 space 4 칸이 **화면에서 거의 같아 보인다.** 앞 글자 하나만
다른 두 줄을 비교하게 되는데, 그것이 바로 이 기능이 없애려던 문제다.
`»` 뒤를 비우면 tab 은 "표시 하나 + 빈 칸", space 는 "점 여러 개" 라 덩어리 모양부터 다르다.

vim 의 `listchars=tab:»-` 처럼 채움 문자를 따로 두는 길도 있지만, 글자가 셋으로 늘고
줄마다 `»---` 가 반복되면 그것대로 시끄럽다.

### 마커 글자의 폭 (2026-08-13)

처음에 `»` 와 `·` 를 둘 다 Ambiguous 로 적어뒀는데 재보니 아니었다. `golang.org/x/text/width`
로 확인한 값이다.

```
»  U+00BB  Neutral               ← 기욤은 유럽 조판용이라 Ambiguous 범위에서 빠져 있다
·  U+00B7  EastAsianAmbiguous    ← 이것만 문제였다
⋅  U+22C5  Neutral               ← 모양은 거의 같고 폭이 확실하다
```

**Ambiguous 만 갈아치운다.** 터미널의 "ambiguous 를 두 칸으로" 설정(iTerm2 의 옵션, CJK
로케일에서 종종 켠다) 은 Ambiguous 에만 걸린다. Neutral 은 그 설정과 무관하게 한 칸이라
`»` 는 그대로 두면 된다. 편집기 계산은 `charm.land/x/ansi` 가 하고 그쪽은 Ambiguous 를
한 칸으로 보므로, 터미널이 두 칸으로 잡는 순간 둘이 어긋나 들여쓰기가 밀린다.

**space 마커는 `⋅`(U+22C5 DOT OPERATOR) 로 바꾼다.** `·` 과 화면에서 거의 구분되지 않아
보이는 것이 달라지지 않는다. ASCII `.` 이 폭으로는 가장 확실하지만(Narrow) 밑줄에 붙어
마침표로 읽히고, 들여쓰기가 `....` 이면 코드처럼 보인다. Neutral 로도 터미널 설정 문제는
사라지고, 남는 것은 폰트 폴백이 글리프만 넓게 그리는 경우인데 그때도 칸 전진은 1 이라
글리프가 잘릴 뿐 아래가 밀리지 않는다.

**박스 그리기 문자는 이 결정에서 건드리지 않는다.** `│ ─ ┌ ┐ ├ ┤ └ ┘`(U+2500 블록) 이
전부 Ambiguous 인데 대체할 Neutral 글자가 없다 — sidebar 구분선과 팔레트 테두리 이야기라
이 ADR 의 범위 밖이고, `docs/tasks.md` 에 따로 남겼다. 마커보다 위험은 크다(구분선이 두 칸이
되면 모든 행에서 편집 영역이 한 칸 밀린다). 트리의 `▸`/`▾`(U+25B8, U+25BE) 는 Neutral 이다.

### 왜 끄는 방법을 두지 않는가

**켜고 끄는 것은 상태이고, 상태는 어디에 사는지를 정해야 한다.** editor 에 두면 tab 마다
다를지, 세션 전체일지, 다음에 켤 때 기억할지가 따라 붙는다. `config 는 compile 됨` 의 형태가
아직 정해지지 않았고(`docs/tasks.md`) 그 결정 전에 런타임 상태를 늘리고 싶지 않다.

범위를 들여쓰기·줄끝으로 좁힌 덕에 **끄고 싶어질 이유가 줄었다.** 모든 space 를 찍었다면
토글이 사실상 필수였을 것이다. 필요해지면 그때 `docs/tasks.md` 의 항목으로 넣는다.

### 왜 행을 조각으로 나누는가

마커에 색을 입히려면 행 안에 색이 들어간다. 그런데 검색 강조도 행의 일부에 색을 입히므로
**두 색이 겹친다.** 강조 구간 안의 문자열에 마커 색을 미리 넣어두고 바깥에서 강조 style 로
감싸면 이렇게 나간다.

```
ESC[fg16;bg220m  ab  ESC[fg244m ·· ESC[m  cd  ESC[m
                                    ↑ 마커 색을 끝내는 리셋이 강조까지 함께 끈다
```

`cd` 가 노란 배경을 잃는다. lipgloss 가 색을 끝낼 때 "이 속성만 원래대로" 가 아니라
상황에 따라 전체 리셋(`ESC[m`) 을 쓰기 때문이고, 어느 쪽을 쓸지는 우리가 정할 수 없다.

**겹쳐 씌우는 대신 나눠 그리면 리셋이 조각 경계에서만 일어난다.** `expandRow` 가
`[]screenPart` 를 돌려주고 `renderParts` 가 조각마다 style 을 한 번씩만 입힌다.
검색 강조와 마커가 만나는 조각은 두 style 을 합쳐서 한 번에 그린다.

이 구조는 앞으로 색이 하나 더 늘어도(문법 강조, 현재 줄 강조) 같은 방식으로 얹힌다.
행을 문자열 하나로 보는 대신 조각 목록으로 보는 것이 색이 여럿인 렌더의 자연스러운 모양이다.

## 결과

좋은 점

- 들여쓰기가 tab 인지 space 인지 눈으로 바로 갈린다. 섞인 줄이 화면에서 드러난다.
- 줄 끝 공백과 공백뿐인 줄이 보인다. 「줄 끝 공백 지우기」 를 쓰기 전에 무엇이 바뀔지 안다.
- 깊게 들여쓴 코드가 화면에 더 들어온다. sidebar 를 연 80 칸 터미널에서 세 단계 들여쓰기가
  24 칸이 아니라 12 칸이다.
- 행 렌더가 조각 목록이 되어 색을 하나 더 얹을 자리가 생겼다.

감수하는 것

- **줄 가운데 tab 은 여전히 space 와 구분되지 않는다.** struct tag 정렬과 TSV 가 그렇다.
  `docs/tasks.md` 에 다시 볼 항목으로 남겼다.
- **끌 수 없다.** 마커가 거슬리는 상황(화면을 그대로 복사해 붙이려는 경우 등) 에 방법이 없다.
  화면 글자를 그대로 얻는 길은 「화면을 cat 형태로 보여주기」(`docs/tasks.md`) 쪽 문제다.
  > ADR-0085 가 그쪽을 답했다. `\c`·`:cat` 이 내는 것은 화면이 아니라 파일의 byte 라
  > 마커도 색도 없다. 마커 자체를 끄는 설정은 여전히 없고, 그것은 설정 파일 쪽 물음이다.
- **마커가 ASCII 가 아니다.** `»` `⋅` 둘 다 Neutral 이라 터미널의 ambiguous 설정에는 안 걸리지만,
  폰트에 글리프가 없으면 두부(`□`) 로 나온다. ASCII 로 내려가면 그것도 없어진다.
- **행마다 조각을 만드는 비용이 붙는다.** 보이는 행 수만큼이라 실제로는 수십 개다.
- **tab 폭 8 을 전제한 것을 전부 고쳐야 했다.** 테스트와 `run-zn` skill 의 smoke 검사가
  그랬다. 앞으로도 폭을 바꾸면 같은 자리가 걸린다.

## 대안

**모든 space 를 찍기** — tasks.md 문구 그대로다. 공백이 빠짐없이 드러나지만 한국어 주석과
문서가 점으로 뒤덮여 읽을 수 없다. 이 저장소의 주석 밀도에서는 못 쓴다.

**줄 끝 공백만 찍기** — 가장 조용하다. 하지만 들여쓰기가 tab 과 space 로 섞인 것을 잡지
못하는데, 그것이 애초에 이 기능을 넣는 첫 번째 이유였다.

**tab 만 찍고 space 는 두기** — tab 이 보이면 나머지 빈 칸은 space 라고 추론할 수 있다.
추론이 필요하다는 것이 문제다. 줄 끝 공백은 여전히 보이지 않는다.

**tab 폭을 그대로 8 로 두기** — vim 기본값과 터미널 tab stop 을 따르는 이점이 있다.
편집 영역이 줄번호와 sidebar 를 뗀 나머지라는 사정이 그 이점보다 크다.

**마커에 색을 넣지 않기** — 조각 나누기가 필요 없어진다. 대신 마커가 본문과 같은 색이라
`·` 이 문장 부호처럼 읽히고, 코드를 훑을 때 눈에 계속 걸린다. 흐린 색이 있어야 "배경 정보"
로 물러난다.
