# ADR-0048: 한 단계는 `.editorconfig` → 파일에서 재기 → 언어 관례 순으로 정한다

- 상태: 채택
- 날짜: 2026-08-22

## 맥락

autoindent(ADR-0047) 는 「한 단계 더 들어간다」까지만 답한다. 그 한 단계에 무엇을 붙일지는 따로 정해야 한다. tab 하나일 수도 space 두 칸일 수도 넷일 수도 있고, **파일마다 다르다.** 이 저장소는 tab 이지만 남의 js 를 열면 space 두 칸이다. 틀리면 그 파일의 들여쓰기가 섞인다.

zn 은 설정 파일을 두지 않는다. README 의 DONOT 이 「config 는 code 내에 하드코딩 한다」라고 못 박아 두었다. 그러면 답은 파일에서 되짚는 것뿐인데, 되짚을 것이 없는 파일이 있다. 새로 만드는 파일과 아직 한 줄도 들여쓰지 않은 파일이다.

`.editorconfig` 가 그 물음에 이미 있는 답이다. `docs/tasks.md` 에 「`editorconfig` 존중」이 backlog 로 올라 있었다. 이 저장소에도 하나 있고 `indent_style = tab` 이라고 적혀 있다.

## 결정

**세 근거를 순서대로 본다.**

1. `.editorconfig` 의 `indent_style` · `indent_size` · `tab_width`
2. 파일이 이미 쓰고 있는 것을 잰다. 앞의 들여쓴 줄 500 개까지다
3. 그 언어의 관례를 따른다. golang·makefile 은 tab, python 은 space 넷, 나머지는 space 둘이다

**읽는 키는 셋뿐이다.** `end_of_line` `trim_trailing_whitespace` `charset` 은 읽지 않는다.

**파서는 `github.com/editorconfig/editorconfig-core-go/v2` 를 쓴다.** 직접 쓰지 않는다.

**정하는 곳은 `internal/core` 다.** 파일 하나에 딸린 것이라 `Buffer` 가 들고, 게을러서 처음 쓸 때 정한 뒤 경로가 달라지면 다시 정한다. `syntaxCache.path` 와 같은 방식이다.

**makefile 은 이 순서 밖이다.** GNU make 가 조리법 줄을 tab 으로만 알아보므로 `.editorconfig` 가 space 라고 적어 두었어도 따를 수 없다. 규칙이 단계가 아니라 tab 을 그대로 내보내서 (ADR-0047 의 `prefix`) 이 셈을 아예 거치지 않는다.

## 근거

**`.editorconfig` 는 zn 의 설정이 아니라 그 파일의 성질이다.** 「config 는 compile 됨」이 막으려는 것은 **편집기의 동작**이 사람마다 갈리는 것이다. 키맵, 색, 켜고 끄는 기능이다. 여기서 읽는 것은 그것이 아니라 「이 파일은 tab 으로 쓰였다」는 사실이고, 그것은 줄끝 형식 (`lineEnding`) 이나 파일 이름으로 고르는 언어와 같은 갈래다. 둘 다 이미 파일에서 읽어 그대로 따르고 있다. 분기가 늘지도 않는다. 값이 하나 달라질 뿐 코드의 길은 하나다.

**적힌 것이 잰 것보다 앞선다.** 재는 것은 이미 쓰인 것에서 되짚는 짐작이고, `.editorconfig` 는 그 저장소가 쓰기로 한 것을 사람이 적어 둔 것이다. 짐작이 맞는 경우가 대부분이지만 둘이 갈리는 곳은 정확히 「파일이 아직 그 규칙을 따르지 않는 곳」이라 적힌 쪽이 맞다.

**재는 것은 절대값이 아니라 이웃한 두 줄의 차이를 본다.** 들여쓰기의 칸 수를 그대로 세면 깊이 들어간 줄이 답을 흐린다. space 네 칸 파일에서 세 단계 들어간 줄은 12 다. 걸음을 세면 그 파일이 한 번에 얼마씩 들어가는지가 바로 나온다.

**라이브러리를 쓴 값을 쟀다.** 손으로 쓰면 INI 읽기와 상위 디렉터리 훑기와 `root = true` 와 glob(`*` `**` `?` `{a,b}` `[abc]` `{n..m}`) 이 200 줄쯤 된다. 이 저장소의 `.editorconfig` 만 해도 `*.{js,jsx,html,json}` 을 쓴다. 붙는 값은 go.mod 에 세 줄 (`editorconfig-core-go/v2`, `gopkg.in/ini.v1`, `golang.org/x/mod`) 이고 바이너리는 22.7MB → 23.1MB 다(+345KB, 1.6%. autoindent 코드 전체를 포함한 값이다). go-git 을 고른 것과 같은 판단이다(ADR-0042). 남이 이미 맞춰 둔 명세를 다시 맞추는 일에 비용을 쓰지 않는다.

**오류를 삼키는 것은 다음 근거가 있기 때문이다.** 파일을 못 읽거나 문법이 깨졌으면 재는 쪽으로 내려간다. 편집을 시작하는 순간에 설정 파일 이야기를 꺼낼 일이 아니다.

## 결과

- 남의 저장소를 열어도 그 저장소의 들여쓰기로 쓰게 된다
- 설정 파일을 하나 읽게 되었다. **읽는 키를 셋으로 묶은 것이 이 결정의 울타리다.** 나머지 키는 그 키가 건드리는 기능을 고칠 때 따로 연다
- `.editorconfig` 가 정하는 값이 새 줄의 들여쓰기 하나가 아니게 되었다. `tab` `shift+tab` `backspace` `>` `<` `=` 가 전부 여기서 나온 한 단계를 쓴다. **읽는 키는 셋 그대로인데 그것이 닿는 키는 여섯으로 늘었다**(ADR-0047 의 이후)
- 첫 Enter 에서 파일 시스템을 만진다. 상위 디렉터리를 훑어 올라가는 것이라 작지만 0 은 아니다. 한 번 정하면 담아 두므로 그 뒤로는 없다
- `.editorconfig` 가 있는 저장소에서 시험을 돌리면 그것이 답을 바꾼다. `internal/core/indent_test.go` 는 `root = true` 를 붙인 임시 디렉터리를 쓴다

## 대안

**파서를 손으로 쓴다.** 새 의존성이 없고 「의존성 없이 언어마다 lexer 를 직접 쓴다」와 결이 같다. 뺀 이유는 lexer 와 성질이 다르기 때문이다. lexer 는 우리가 무엇을 강조할지 우리가 정하지만, `.editorconfig` 는 남이 정한 명세이고 부분만 맞추면 조용히 틀린 답을 준다. `{n..m}` 을 안 만든다는 판단은 우리 것이지만, 그 판단이 틀렸을 때 사용자에게 보이는 것은 「zn 이 내 설정을 무시한다」다.

**`.editorconfig` 를 읽지 않고 재기만 한다.** 설정 파일을 읽지 않는다는 선이 깔끔하게 남는다. 뺀 이유는 잴 것이 없는 파일이 정확히 새 파일이고, 새 파일이야말로 규칙을 알아야 하는 것이기 때문이다.

**화면의 tab 폭(`tabWidth = 4`) 도 `tab_width` 를 따른다.** 지금 그것은 상수이고 그리기·커서 계산·줄바꿈·공백 마커가 전부 거기 매달려 있다(ADR-0020). buffer 마다 다른 값으로 바꾸는 것은 그 ADR 을 다시 여는 별개의 건이라 이번에는 넣지 않았다.

## 이 ADR 이 정하지 않는 것

- **`.editorconfig` 의 나머지 키.** `trim_trailing_whitespace` 와 `insert_final_newline` 은 저장할 때의 동작인데, 지금 zn 은 줄끝 공백을 손으로 부르는 팔레트 명령으로만 지우고 마지막 줄바꿈은 열 때 본 대로 되돌린다. 그 셋을 바꾸면 「열었을 때 모습을 지킨다」는 지금 규칙이 뒤집히므로 같이 정해야 한다
- **`tab` 키가 무엇을 넣을지.** 정해졌다. 여기서 읽은 한 단계를 넣는다(ADR-0047 의 이후). `indent_style = space` 인 저장소에서는 `tab` 을 쳐도 space 가 들어간다
- **화면의 tab 폭**(ADR-0020)
