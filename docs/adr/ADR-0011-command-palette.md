# ADR-0011: 팔레트는 화면 위에 겹쳐 그리고, `>` 명령은 `:` 와 별개의 표로 둔다

- 상태: 채택
- 날짜: 2026-08-13

## 맥락

`README.md` 가 "fzf, command palette" 를 대표 기능으로 걸어두었고 `docs/spec.md` 의
`## Command Palette` 는 `TBD` 로 비어 있었다. 파일을 여는 길이 CLI 인자와 sidebar 트리의
`Enter` 둘뿐이라, 이름을 아는 파일을 바로 여는 방법이 없었다(`:e <파일>` 도 아직 없다).

만들 것은 VSCode 의 command palette 다 — `ctrl+p` 로 열고 기본은 파일 fuzzy 찾기,
`>` 를 치면 명령 목록으로 넘어간다. 여기서 정할 것이 여섯이다.

1. **화면을 어떻게 나눌 것인가.** 지금까지 화면은 tabline·편집 영역·sidebar·statusBar 로
   **잘라서** 썼다. 떠 있는 박스는 처음으로 화면을 **겹친다**
2. **파일 목록을 어디서 얻는가.** 그리고 언제 읽는가 — 저장소에는 비동기 전례가 없다
3. **무엇을 매칭이라 부를 것인가.** 부분문자열인가 fzf 식 부분수열인가
4. **`>` 목록이 `:` 명령 표와 같은 것인가**
5. **`ctrl+p` 를 어느 mode 에서 받고, 팔레트 안에서는 무엇을 하는가**
6. **팔레트가 끝나면 어디로 돌아가는가**

## 결정

**1. 박스는 `lipgloss.NewCompositor` 로 편집 화면 위에 얹는다.** `render` 가 만든 화면 문자열이
바닥 layer 이고 박스가 그 위 layer 다. 합성은 **팔레트가 열렸을 때만** 태운다.

**2. 자리는 화면 위쪽 가운데다.** 편집 영역 가운데가 아니다. tabline(맨 윗줄) 은 덮지 않고
statusBar 앞에서 멈춘다. 너비는 최대 64 칸, 목록은 최대 10 행이다.

**3. 못 그릴 화면에서는 열지 않는다.** 24 칸을 못 채우거나 목록이 한 행도 안 나오면 열지 않고
알린다. 열린 뒤에 좁아지면 normal 로 나온다.

**4. 파일 목록은 저장소 안이면 `git ls-files --cached --others --exclude-standard` 하나로,
밖이면 직접 훑고 `.git` 만 건너뛴다.** 열 때 동기로 읽고 **캐시하지 않는다.**

**5. 매칭은 fzf 식 부분수열 + 점수다.** 맞은 글자에 색을 입힌다(256색 214). 대소문자는
smartcase 다. 점수는 fzf 의 값을 따르되 **파일 이름의 시작(마지막 `/` 뒤)에 큰 값을 준다.**

**6. `>` 목록은 `:` 명령과 별개의 표(`paletteCommands`)다.** 이름은 한국어로 설명적이고,
영문 설명(`hint`) 과 짝이 되는 `:` 명령(`alias`) 이 행 오른쪽에 흐리게 붙으면서 함께 매칭된다.

**7. `ctrl+p` 는 normal 과 sidebar 에서 받는다. 팔레트 안에서는 아무 일도 하지 않는다.**
이동은 `↑` `↓` 뿐이다.

**8. 팔레트는 어디서 열렸는지 기억하지 않는다.** 끝나면 언제나 편집 영역(normal) 으로 나온다.

## 근거

### 겹쳐 그리기

**셀 버퍼가 이 문제의 정답이다.** 행 문자열을 손으로 잘라 끼우려면 네 가지를 매번 맞춰야 한다 —
경계에 걸친 두 칸 글자로 잃은 칸 메우기, 왼쪽 조각의 색이 박스로 새지 않게 막기, 오른쪽
조각에서는 반대로 색을 되살리기, sidebar 가 닫혔을 때의 빈 채움 행 늘리기. 넷 다 off-by-one 이
나는 자리이고, 하나만 틀려도 화면 절반이 밀린다. `Layer.Draw` 는 그리기 전에 자기 영역을 지워서
불투명 박스가 공짜이고, 폭 계산이 틀려도 줄바꿈 없이 잘리기만 한다.

**대신 화면 문자열이 다시 만들어진다.** 셀 버퍼를 지나면 줄 끝의 스타일 없는 빈 칸이 잘리고
색 escape 가 재조립된다(속성 순서까지 달라진다). 그래서 **팔레트에서만** 합성을 태운다.
normal·insert·search 의 화면은 한 글자도 달라지지 않고, 기존 테스트도 한 줄 안 바뀌었다.
sidebar 가 닫혀 있으면 예전과 똑같이 그린다는 ADR-0005 의 태도와 같다.

**직접 재본 것**(임시 probe 로 확인하고 지웠다): z 순서는 `.Z()` 를 명시하면 정확하고,
statusBar 의 반전이 화면 오른쪽 끝까지 남고, 200×60 화면 한 번 합성이 674µs 다. 키 입력마다
태워도 되는 값이다. **박스가 화면 밖으로 한 칸이라도 나가면 캔버스가 그만큼 커진다** —
행이 길어지거나 늘어나서 화면이 밀린다. 그래서 좌표를 반드시 화면 안으로 가둔다.

### 화면 가운데

**편집 영역 가운데로 하면 sidebar 를 여닫을 때 박스가 옮겨 다닌다.** 팔레트는 편집 중인
파일에 딸린 것이 아니라 편집기 전체의 것이다. statusBar 가 sidebar 아래를 지나 화면을
가로지르는 것과 같은 이유다(ADR-0005).

**tabline 은 덮지 않는다.** 어느 tab 을 보고 있었는지가 팔레트를 여는 동안에도 남아야, 고른
파일이 새 tab 으로 열렸는지 원래 tab 으로 옮겨갔는지가 눈에 들어온다.

**64 칸에서 끊는다.** 넓은 터미널에서 박스가 화면만큼 넓어지면 경로가 아니라 여백을 보게 된다.

### 좁은 화면

`sidebarVisible()` 이 세운 규칙을 그대로 복제한다 — **폭과 관련된 모든 코드가 "실제로 그릴 수
있는가" 하나만 본다.** 다만 sidebar 와 달리 팔레트는 **mode** 라서 "안 보이는데 켜져 있는"
상태가 있을 수 없다. 보이지 않는 mode 에 갇히면 키를 쳐도 아무 일이 안 나고 나가는 방법도 알 수
없다. 그래서 열 때는 거절하고, 열린 뒤에 좁아지면 나간다.

### 파일 목록

**gitignore 규칙을 직접 구현하지 않는다.** sidebar 의 흐린 표시에서 이미 내린 결론이다
(ADR-0005) — 중첩 `.gitignore`, `!` 부정, `**` 의 의미 차이까지 다시 만들 이유가 없다.
`git ls-files` 는 그 답을 **프로세스 하나로** 준다. `--others` 가 있어서 아직 `git add` 하지
않은 파일도 나온다 — 방금 만든 파일이 목록에 없으면 팔레트를 믿을 수 없다.

**저장소 밖에서도 열려야 한다.** 그래서 `filepath.WalkDir` 갈래를 같이 둔다. 이때는 gitignore 를
모르므로 `.git` 만 건너뛴다 — 틀린 목록이 아니라 걸러지지 않은 목록이다.

**캐시하지 않는다.** 편집기를 띄워둔 채로 바깥에서 파일을 만드는 일이 잦고, 캐시를 두면
새로고침 키가 따라온다(ADR-0009 의 git 표시가 이미 그 빚을 지고 있다). 이 저장소는 118 개라
읽는 것이 눈에 띄지 않고, 수만 개짜리 저장소에서 실제로 거슬리면 그때 인덱싱을 정한다.

**동기로 읽는다.** `internal/core` 에는 비동기가 하나도 없다 — nil 이 아닌 `tea.Cmd` 는
`tea.Quit` 뿐이고 custom `tea.Msg` 도 goroutine 도 없다. 팔레트 하나 때문에 그 구조를 들이면
"결과가 도착했는데 mode 가 바뀐" 경우를 mode 마다 다뤄야 한다. `git status`(ADR-0009) 와
`git check-ignore`(ADR-0005) 가 이미 동기인 것과 같은 태도로 둔다.

**목록은 이름순으로 정렬한다.** git 은 추적 중인 것과 아닌 것을 따로 모아서 주기 때문에, 그대로
쓰면 아무것도 치지 않았을 때 보이는 첫 화면의 차례가 설명되지 않는다.

### 부분수열 매칭

**경로를 건너뛰며 치는 것이 fzf 를 쓰는 이유 그 자체다.** `icedit` 으로
`internal/core/edit.go` 를 여는 것이 부분문자열로는 안 된다.

**파일 이름 시작 보너스가 fzf 에서 벗어나는 유일한 지점이고, 이 기능의 질을 정하는 지점이다.**
`edit` 을 쳤을 때 `internal/core/edit.go` 가 `internal/core/view-editor-command.go` 를 이겨야
한다. 이 보너스가 없으면 경로가 깊은 저장소에서 목록이 쓸모없어진다. **`/` 뒤를 전부 그렇게
치면 안 된다** — 그러면 `core` 에 대해 `internal/core.go` 와 `internal/core/buffer.go` 가
같은 점수를 받아서, 정작 가리려던 것을 못 가린다.

**길이는 점수에 넣지 않는다.** 넣으면 위의 보너스 서열이 길이에 눌린다. 짧은 것을 위로 올리는
것은 정렬의 동점 처리가 맡는다. **동점 처리의 마지막 항은 원래 자리 순이어야 한다** —
`slices.SortFunc` 는 안정 정렬이 아니라서, 없으면 키를 칠 때마다 같은 점수끼리 자리를 바꾼다.

**smartcase 는 검색(`/`) 과 다르다.** 검색은 `/i` flag 로 명시하게 했는데(ADR-0010) 팔레트는
자동이다. 갈린 이유는 지속 시간이다 — 검색어는 `n` 으로 한참 뒤까지 살아남으니 규칙이 화면에
글자로 남아야 하고, 팔레트 입력은 고르는 순간 사라진다. 매번 flag 를 치게 하는 것이 더 나쁘다.

**완전한 DP(fzf 의 V2) 를 쓰지 않는다.** 앞에서 훑고 뒤에서 조이는 V1 로 충분하다. 파일 경로는
짧아서 결과가 거의 같은데 코드는 몇 배가 된다.

### `>` 표를 나눈 것

**두 표는 서로 다른 것을 최적화한다.** `:` 는 vim 의 ex command 라 **치는 것**이고 짧은 것이
미덕이다(`:w`, `:q`). 팔레트 목록은 **읽는 것**이라 이름이 문장에 가까워야 하고, 영문 설명이
곁들여져야 이름을 몰라도 찾을 수 있다. 한 표에 두 요구를 담으면 둘 다 어정쩡해진다.

**`:` 표를 재사용할 수 없기도 하다.** 그쪽은 파싱된 `command{name, force, args}` 위의
평평한 switch 이고 각 case 가 오류 문구에 친 글자를 쓴다. 그것을 표로 펴는 것은
`docs/tasks.md` 의 「`config 는 compile 됨` 의 실제 형태를 정한다」가 명시적으로 미뤄둔
작업이다. 지금은 작고 목적이 분명한 표를 따로 두고, 합칠지는 그 결정에서 본다.

**「줄 끝 공백 지우기」에 짝이 되는 `:trim` 을 만들지 않았다.** 이유가 생기기 전까지 한 기능에
진입점 하나다. 반대로 `:tree` 는 이미 있으니 `alias` 로 적어서 팔레트에서도 그 이름으로 찾힌다.

### 팔레트 안의 `ctrl+p`

**VSCode 와 fzf 가 정반대다.** VSCode 는 여는 키를 연타해 아래로 내려가고, fzf·readline·vim 은
`ctrl+p` 가 previous(위) 다. 이 편집기는 vim 결이라 아래로 내려가게 하면 `ctrl+n`/`ctrl+p` 의
관습과 어긋나고, 위로 올라가게 하면 방금 누른 키가 반대로 도는 것처럼 느껴진다.

**그래서 아무 일도 하지 않게 뒀다.** 두 관습 중 하나를 잘못 고르면 매번 손이 어긋나지만,
아무 일도 안 하는 키는 한 번 눌러보고 화살표로 손이 간다. `ctrl+n`/`ctrl+j` 를 이동 키로 줄지는
쓰면서 정한다(`docs/tasks.md`).

### 돌아갈 곳

**어디서 열렸는지 기억하지 않는다.** sidebar 에서 열어도 끝나면 편집 영역으로 나온다.
기억하려면 `parent` 를 model 이 들고 다녀야 하는데, ADR-0005 가 "sidebar 는 `:` 를 받지 않는다"
에서 이미 거절한 비용이다. 그리고 팔레트로 하는 일(파일 열기, 명령 실행) 은 대부분 편집 영역을
보게 되는 일이라, 돌아가는 곳이 하나인 편이 오히려 예측하기 쉽다. 트리로 돌아가려면
`ctrl+w ctrl+w` 한 번이다.

## 결과

좋은 점

- 이름을 아는 파일을 두세 글자로 연다. 트리를 펼쳐 내려가지 않아도 된다
- `.gitignore` 가 공짜로 적용된다. `node_modules` 나 `build/` 가 목록을 채우지 않는다
- `>` 로 기능을 이름으로 찾는다. 키를 외우지 않아도 되고, 영문으로도 찾힌다
- 겹쳐 그리는 방법이 생겼다. 나중에 자동완성 목록이나 진단 표시가 같은 길을 쓴다
- 매칭기가 순수 함수라 테스트가 촘촘하다. 순위가 이상하면 점수 상수 한 곳만 본다

감수하는 것

- **열 때마다 `git ls-files` 를 동기로 부른다.** 수만 개짜리 저장소에서는 여는 순간 멈칫한다.
  `git check-ignore`(ADR-0005), `git status`(ADR-0009) 와 같은 종류의 빚이다
- **키를 칠 때마다 전체 목록을 훑고 정렬한다.** 5 만 개 × 40 byte 면 수 ms 지만 공짜는 아니다
- **화면 문자열이 팔레트에서만 다른 경로로 만들어진다.** 두 경로가 생겼고, 셀 버퍼 쪽은
  줄 끝 빈 칸을 잘라내서 눈에는 같아도 문자열은 다르다
- **색 고정값이 둘 늘었다**(214 강조, 244 설명). 팔레트를 정하는 일의 빚이 또 커졌다
- **매칭이 파일 이름만 보지 않고 경로 전체를 본다.** 디렉터리 이름이 우연히 맞아 끼어드는 후보가
  생긴다. 파일 이름 시작 보너스가 그것을 눌러주지만 완전히 없애지는 않는다
- **`ctrl+p` 가 팔레트 안에서 죽어 있다.** 두 관습 사이에서 고르지 않은 대가다

## 대안

**아래에서 자라나는 fzf 식 화면** — 지금 구조(행을 위에서 아래로 쌓기) 에 그대로 얹혀서 겹침
합성이 아예 필요 없다. 편집 화면 아래쪽을 먹어서 "떠 있는 것" 으로 읽히지 않고, VSCode 를
닮게 해달라는 요구와 멀어진다.

**행마다 `ansi.Truncate`/`TruncateLeft` 로 잘라 끼우기** — 의존성이 늘지 않고 화면 문자열이
지금 경로 그대로다. 위에 적은 네 가지 off-by-one 을 전부 손으로 맞춰야 한다. 합성이 안 되면
이쪽으로 돌아온다.

**`git ls-files` 없이 walk 하며 `git check-ignore` 로 묻기** — 저장소 안팎에서 같은 코드가 돈다.
디렉터리마다 프로세스가 뜨고(이 저장소만 30 개) 큰 저장소에서는 초 단위가 된다.

**목록을 editor 에 캐시하고 새로고침 키를 두기** — 두 번째부터 즉각적이다. 낡은 목록과
새로고침 키가 따라오고, ADR-0009 가 이미 같은 빚을 지고 있어서 두 번째 "왜 안 보이지" 가 된다.

**비동기로 읽고 차오르게 하기** — 큰 저장소에서도 안 멈춘다. 저장소의 첫 비동기 코드가 되고,
결과가 도착했을 때 mode 가 바뀌어 있는 경우를 다뤄야 한다. 그 자체로 별개의 결정이다.

**부분문자열 매칭** — 규칙이 하나고 예측이 쉽다. 경로를 건너뛰며 치는 fzf 의 장점이 통째로
없어진다.

**`:` 표와 하나로 합치기** — 명령이 한 곳에 모인다. 짧은 이름과 읽히는 이름 중 하나를 포기해야
하고, `:` 표를 자료구조로 펴는 것은 이미 다른 결정에 딸려 있다.

## 이 ADR 이 정하지 않는 것

- `!` 로 shell 명령을 돌리는 것. `README.md` 와 `docs/tasks.md` 에 남아 있다
- 열린 tab 목록·심볼(`@`)·줄번호(`:`) 같은 다른 접두. `>` 하나만 정했다
- 팔레트 이력(최근에 연 파일을 위로). 검색 이력(ADR-0010) 과 같이 본다
- 큰 저장소의 인덱싱과 비동기. 실제로 거슬릴 때 다시 본다
- `ctrl+n`/`ctrl+j` 를 이동 키로 줄지
- 강조와 설명의 색 고정값. 팔레트를 정할 때 다른 색과 같이 본다
