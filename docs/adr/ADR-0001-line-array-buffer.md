# ADR-0001: 편집 buffer 를 줄 배열로, undo 를 줄 범위 snapshot 으로 둔다

- 상태: 채택
- 날짜: 2026-08-11

## 맥락

editor 를 구현하려면 파일 내용을 메모리에 어떤 자료구조로 들고 있을지 먼저 정해야 한다.
단순한 `[]byte` 하나로 들면 파일 중간에 한 글자를 넣을 때마다 뒤쪽 전체를 밀어야 하므로
별도의 구조가 필요하다.

이 결정은 undo 와 분리해서 정할 수 없다. 구조를 persistent(불변) 하게 만들면 undo 가
"예전 root 를 다시 가리키기" 로 끝나지만, 그렇지 않으면 변경 이력을 직접 기록해야 한다.
그래서 두 가지를 한 번에 정한다.

이 프로젝트의 조건은 다음과 같다.

- 철저히 개인용이다. minify 된 거대 파일처럼 극단적인 입력을 열 일이 없다.
- 내건 기능이 대부분 줄 단위다. 상대/절대 줄번호 동시 표시, 화면에 보이는 범위만 렌더,
  vim 의 `dd`/`yy` 같은 줄 단위 연산.
- 실제 난관은 buffer 구조가 아니라 한글 폭 계산과 grapheme cluster 처리다. 여기에 힘을 써야 한다.

## 결정

**저장 형태**

- 파일 전체를 **backing buffer 하나**(`[]byte`) 로 읽는다. 이 buffer 는 로드 이후 **읽기 전용** 이다.
- 각 줄은 그 buffer 를 가리키는 **subslice** 로 둔다(`[][]byte`). 줄 내용을 복사하지 않는다.
- rune / grapheme / 폭 계산은 **화면에 그릴 때 보이는 줄에만** 한다. 미리 `[]rune` 으로 펼쳐두지 않는다.

**편집**

- 줄을 고칠 때 backing buffer 에 쓰지 않는다. **그 줄만 새 `[]byte` 로 만들어 갈아끼운다.**
  나머지 줄은 계속 backing buffer 를 가리킨다.
- 같은 배열에 제자리 삽입하는 최적화는 **하지 않는다.** 아래 undo 와 상충한다.

**undo**

- 어떤 줄을 **처음 건드리기 직전에**, 그 줄 범위의 slice 들을 undo 기록에 넣는다.
  갈아끼우기 방식이라 옛 slice 가 그대로 살아있으므로 **내용 복사가 일어나지 않는다.**
- **타이핑 연속 구간을 하나의 undo 항목으로 합친다.** `Esc` 와 insert mode 에서의 커서 이동이
  구간을 끊는다. vim 이 실제로 하는 방식이다(화살표로 움직이면 undo 구간이 끊긴다).
  중간 버전들은 참조가 끊겨 GC 가 회수한다.
- 되돌리기 단위는 "lines 의 [at, at+count) 를 옛 줄들로 바꾼다" 하나로 표현한다.
  줄 수가 바뀌는 편집(Enter, 줄 합치기) 도 같은 모양으로 담긴다.
- **redo 는 선형 스택**이다. undo 할 때 지금 내용으로 역방향 항목을 만들어 쌓고,
  새 편집이 생기면 비운다. 같은 자료구조를 양방향으로 쓴다.
- undo 기록은 처음부터 같이 만든다. 나중에 얹는 기능으로 미루지 않는다.

## 근거

**줄 단위 접근이 공짜다.** gap buffer 나 rope 에서 "n 번째 줄이 어디부터인지" 를 알려면
줄 시작 위치 index 를 따로 유지해야 한다. 줄 배열은 그게 필요 없다. 이 editor 가 하는 일의
대부분이 줄 단위라 이 이점이 계속 돌아온다.

**로드 비용은 자르는 데 있지 않고 rune 변환에 있다.** 95MB / 125 만 줄로 측정한 결과다
(macOS, page cache 상태).

| 단계 | 시간 | 추가 heap |
| --- | --- | --- |
| 파일 읽기 | 19.5 ms | 95 MB |
| 개행 스캔 | 4.6 ms | — |
| `[][]byte` subslice 로 자르기 | 13.6 ms | 29 MB |
| (안 함) 줄마다 `[]rune` 변환 | 152.5 ms | 410 MB |

subslice 는 내용을 복사하지 않으므로 늘어난 29MB 는 전부 slice header(125 만 x 24 byte) 다.
결과적으로 95MB 파일 로드가 **33ms, 메모리 124MB** 다. `[]rune` 으로 펼치면 여기에 152ms 와
410MB 가 더 붙는데, 폭 계산 때문에 "rune index = 화면 칸" 이 어차피 성립하지 않아 얻는 것도 없다.

**이 스캔은 어떤 구조를 골라도 못 피한다.** piece table 도 "N 번째 줄" 을 그리려면 줄 시작 index 가
필요하고 그것이 같은 개행 스캔이다. 자료구조를 바꿔서 줄일 수 있는 비용이 아니라,
rune 변환과 줄별 복사를 안 하면 되는 비용이다.

**편집 비용은 줄 하나로 국한된다.** backing buffer 를 안 건드리므로 한 글자 삽입에 밀리는 범위가
파일 전체가 아니라 그 줄뿐이다. 줄 전체를 새로 만드는 가장 순진한 방식으로 측정했다.

| 줄 길이 | 한 글자 삽입 |
| --- | --- |
| 80 B (보통 소스코드) | 15 ns |
| 1 KB | 89 ns |
| 100 KB (minify 된 js) | 4.8 us |
| 1 MB (극단적) | 49 us |

사람 타이핑 간격이 100ms 단위임을 생각하면 어느 쪽도 문제가 되지 않는다.
제자리 삽입으로 최적화하면 5~10 배 빨라지지만 절대값이 이미 무의미한 영역이라 하지 않는다.
게다가 제자리 삽입은 옛 내용을 덮어쓰므로 undo 를 위해 그때 복사가 필요해져서,
갈아끼우기 방식이 undo 와 궁합이 더 좋다.

**vim 도 본질은 줄 단위다.** vim 은 줄들을 4KB 블록에 담고 그 블록들을 B-tree 로 묶어
swap 파일로 paging 한다(`memline.c`). 하지만 그 복잡도는 메모리보다 큰 파일을 열어야 했던
1991 년 제약과 crash 복구에서 온 것이다. 개인용 editor 에서 그 제약은 없다.
블록 paging 을 걷어내면 남는 것이 줄 배열이다.

vim 이 편집 중인 줄을 따로 들고 있다가 줄을 벗어날 때 반영하는 것(`ml_flush_line`) 도
블록에 다시 써넣는 비용(블록 분할, 트리 재균형, swap 쓰기) 때문이다.
우리는 갈아끼울 대상이 slice header 하나뿐이라 미룰 이유가 없다.

**undo 는 vim 방식이 30 년 검증된 가장 단순한 답이다.** 줄 범위 snapshot 만으로도
vim 7.0 의 undo tree 까지 도달했다. persistent 자료구조 없이 undo tree 가 가능하다는 증거다.

## 결과

좋은 점

- 줄 번호로 바로 접근한다. 화면 렌더가 `lines[top:top+height]` 로 끝난다.
- 자료구조 자체에 시간을 거의 쓰지 않고 시작할 수 있다.
- undo 기록이 사람이 읽을 수 있는 형태라 디버깅이 쉽다.
- undo snapshot 이 참조만 저장하므로 기록 자체에는 복사 비용이 없다.

감수하는 것

- **긴 줄에서 undo 가 메모리를 먹는다.** 편집 속도는 위 측정대로 문제가 없다. 문제는 undo 다.
  1MB 짜리 한 줄을 편집하면 그 줄의 옛 버전 1MB 가 undo 항목에 붙들려 남는다.
  타이핑 연속 구간을 한 항목으로 합치는 것이 이 완화책이고, 그래도 항목 수만큼은 쌓인다.
  개인용이라는 전제에서 받아들인다. 전제가 깨지면 그때 이 ADR 을 다시 연다.
- **줄 삽입/삭제가 뒤쪽 slice 이동을 유발한다.** 줄 수에 비례하지만 slice header 이동이라 비용은 작다.
- **backing buffer 가 통째로 살아있는다.** 한 줄이라도 그것을 가리키고 있으면 GC 가 회수하지 못한다.
  어차피 대부분의 줄이 가리키고 있으므로 실질적인 손해는 아니다.
- **메모리보다 큰 파일은 열 수 없다.** 파일 전체를 메모리에 올린다.
- **crash 복구가 없다.** vim 의 `.swp` 는 paging 구조의 부산물이었는데 그 구조를 안 쓰기 때문이다.
  필요하면 주기적 저장처럼 훨씬 단순한 방법으로 따로 얻는다.

## 대안

**Gap buffer** — 커서 위치에 빈 틈을 두고 그 자리에서 삽입/삭제한다. 삽입/삭제가 O(1) 이고
구현도 단순하지만, 줄 번호로 접근하려면 별도 index 가 필요하고 커서를 멀리 옮길 때마다
gap 을 옮기는 비용이 든다. Emacs 가 쓴다. 줄 단위 접근 이점이 없어 기각한다.

**Rope** — 문자열 조각을 균형 이진 트리로 들고 있는다. 삽입/삭제가 위치와 무관하게 O(log n) 이고,
persistent 로 만들면 undo 가 사실상 공짜다. 하지만 구현 복잡도가 가장 높고, 줄 단위 접근에는
여전히 별도 메타데이터가 필요하다. 그 복잡도로 얻는 이점이 개인용 editor 에서는 크지 않다.
Helix 가 쓴다.

**Piece table** — 원본 파일(읽기 전용) 과 추가분(append-only) 두 buffer 를 두고 조각 목록만 조작한다.
파일 로드가 사실상 공짜고 undo 도 자연스럽다. 다만 조각이 늘어날수록 위치 계산이 느려지고
줄 단위 접근에 index 가 필요하다. VS Code 가 쓴다.
"원본은 읽기 전용, 변경분만 따로" 라는 발상 자체는 이 결정이 그대로 가져왔다.

**vim 의 memline (블록 B-tree + swap paging)** — 위 "근거" 참고. 메모리보다 큰 파일과 crash 복구를
얻지만, 그 요구가 없어 복잡도만 남는다.

## 이 ADR 이 정하지 않는 것

- 한글 폭 계산과 grapheme cluster 처리 방식
- 줄바꿈(LF/CRLF) 과 tab 폭 처리
- 파일 저장 방식과 미저장 상태 관리
- undo tree(분기 undo) 도입 여부. 이 결정은 도입을 막지 않는다.
