# ADR-0083 대소문자는 `~` 와 visual 의 `u`·`U` 로 준다

- 상태: 채택
- 날짜: 2026-08-26
- 관련: ADR-0018(`r` 이 글자 하나를 기다리는 것), ADR-0037(visual), ADR-0013(operator 와 motion)

## 맥락

`docs/tasks.md` 에 「대소문자 전환 키 추가」가 한 줄로만 있었다. **무엇을 넣을지가 적혀 있지 않았다.** vim 이 이 일에 준 키가 셋 갈래라서 그 줄만으로는 정해지지 않는다 (`/usr/share/vim/vim91/doc/change.txt`, vim 9.1 로 읽었다).

갈래 | 키 | 하는 일 ---|---|--- 글자 하나 | `~` | 커서 글자를 뒤집고 오른쪽으로. `3~` 는 세 글자 operator | `g~{이동}` `gu{이동}` `gU{이동}` | 범위를 뒤집기·소문자·대문자. `g~~`·`guu`·`gUU` 는 그 줄 visual | `~` `u` `U` | 고른 자리를 뒤집기·소문자·대문자

셋을 다 넣는 것과 골라 넣는 것의 값이 갈린다. **앞의 둘은 표에 줄을 더하는 일이고 operator 갈래만 파서 구조를 건드린다.**

## 1. `~` 와 visual 의 `~`·`u`·`U` 를 넣는다

`~` 는 `standaloneAction` 표의 한 줄이고 visual 셋은 `visualAction` 표의 세 줄이다. 알맹이는 `buffer-case.go` 하나에 모였다. `changeCaseChars`(글자 몇 개) 와 `changeCaseRange`(고른 범위) 둘이고, 어느 쪽으로 맞출지는 `caseKind` 가 든다.

**`r` 과 같은 갈래다.** 지우고 넣는 것이 아니라 그 자리 글자를 갈아끼운다(buffer-replace.go). 줄 수도 글자 수도 바뀌지 않아서 `growEdit` 이 없고, 되돌리기 구간은 언제나 제 것이다. 앞의 타이핑에 섞이면 `u` 한 번에 남의 편집까지 딸려온다.

**넣을 글자가 사람이 아니라 있던 글자에서 나온다.** 그래서 `r` 과 갈리는 곳이 하나 생긴다.

- `3rx` 는 줄에 세 글자가 없으면 **아무것도 바꾸지 않는다**. 「세 글자를 `x` 로」가 친 것의 뜻이라 두 글자만 바꿔 주면 부탁과 다른 일이 된다(ADR-0018)
- `3~` 는 없으면 **있는 만큼 바꾼다**. 「보이는 것을 뒤집어라」라 줄 끝에서 멈춰도 친 것과 어긋나지 않는다. vim 도 그렇다(9.1 에서 `99~` 를 쳐서 쟀다)

그래서 `clusterEnd`(모자라면 false) 옆에 `clusterEndClamped`(모자라면 줄 끝) 가 섰다. 어느 쪽인지는 부르는 키가 정한다.

**나중에 그 둘째를 물렸다.** §6 을 보라.

**커서는 바뀐 것이 없어도 옮긴다.** `~` 는 훑어 가는 키라 한글·문장부호 위에서도 오른쪽으로 간다. 파일은 그대로 두고 커서만 가는 것이고 vim 과 같다. 반대로 **파일을 건드리는 것은 정말 바뀐 때뿐이다.** 같은 글자를 그냥 갈아끼우면 고친 표시가 서고 redo 가 날아간다 (`replaceIndented` 와 같은 건이다).

**대소문자가 없는 글자는 가려내지 않는다.** `unicode.ToUpper` 가 한글·한자·문장부호에는 같은 값을 돌려주므로 표를 따로 둘 것이 없다. 글자로 읽히지 않는 byte 는 건드리지 않고 옮긴다. 편집기가 여는 파일이 언제나 올바른 UTF-8 은 아니고, 깨진 자리를 바꾸는 것은 이 키가 부탁받은 일이 아니다.

## 2. operator 갈래(`g~`·`gu`·`gU`) 는 넣지 않는다

**두 키짜리 operator 를 여는 길이 파서에 없다.** 지금 `partial.op` 이 드는 것은 한 글자 (`d` `y` `c` `>` `<` `=`) 고, 그것을 여는 곳은 `normalStart`·`normalCount` 두 곳이다. 접두 키 뒤(`normalPending`) 는 motion 이나 홀로 서는 동작만 낼 수 있고 **operator 를 열지 못한다.** `g` 를 먹은 상태에서 `u` 가 오면 그 자리에서 끝나게 되어 있다.

넣으려면 셋이 같이 움직인다.

1. `normalPending` 이 `startOperator` 를 부를 수 있어야 한다
2. `partial.op` 이 `"gu"` 같은 두 글자를 들어야 하고, 그것을 읽는 `operate`·`motionFor` (`c` 만 보는 곳이 있다)·`showcmd` 가 같이 넓어진다
3. **「같은 것을 두 번 치면 줄 단위」가 접두 키 쪽으로 옮겨간다.** 지금 그 규칙은 `s.building.op == key` 라는 한 글자 견줌으로 두 상태에 박혀 있는데, `guu` 는 `gu` 뒤의 `u` 한 글자이고 `gugu` 는 접두 키가 다시 오는 것이라 견줄 것이 둘이 된다

**값이 그만큼 되지 않는다.** operator 갈래가 주는 것은 「범위를 이동 키로 대는 것」인데, 그 일은 visual 로 이미 할 수 있다. `vjU` 와 `gUj` 는 같은 곳을 대문자로 만든다. vim 이 둘 다 두는 것은 vim 을 쓰는 사람이 operator 를 먼저 배우기 때문이고, 이 편집기는 visual 을 먼저 갖췄다(ADR-0037).

미룬 것이지 안 하기로 한 것이 아니다. 넣을 날에는 위 셋이 그대로 일거리이고, 그때 `g?` (rot13) 처럼 같은 곳에 설 것들이 같이 온다. `docs/tasks.md` 에 남겼다.

## 3. 대문자·소문자로 **맞추는** 것은 visual 에만 있다

`~` 만 두면 뒤집기밖에 없다. **여러 글자를 한 방향으로 맞추는 일**, 곧 `foo_bar` 를 `FOO_BAR` 로 만드는 것이 빠지는데, 그것이 대소문자 키를 찾는 까닭의 절반이다.

vim 은 그 일을 `gU`·`gu` 로만 주고 normal 에 한 글자짜리 대문자 키를 두지 않았다. 우리도 새 키를 만들지 않고 **visual 로 보낸다.** `v` 로 범위를 눈으로 고르고 `U` 를 친다. 없던 키를 지어내지 않는 쪽이고, `~` 가 뒤집기 하나만 뜻하는 것도 그대로 남는다.

`U` 는 한글 입력 상태에서 낼 수 없다. `ㅕ` 의 shift 자리에 다른 글자가 없어 `V` `G` `B` 와 같은 건이다(ADR-0008). `u` 와 `~` 는 낼 수 있다. 그대로 두는 근거는 §5 다.

## 4. 커서는 visual 의 다른 동작과 같은 자리로 간다

고른 범위의 시작이다. `moveToRangeStart` 를 그대로 쓴다(buffer-yank.go).

**vim 과 한 군데 갈린다.** vim 은 줄 단위로 고른 뒤 `U` 를 치면 커서를 그 줄의 **0 칸**에 놓는데, 여기서는 고르기 시작한 칸을 지킨다. 이것은 이번에 정한 것이 아니라 `Vjy` 가 이미 그렇게 하고 있어서다(vim 은 `y` 도 0 칸이다). **한 편집기 안에서 visual 동작들끼리 같은 것**이 vim 과 같은 것보다 앞선다.

## 5. 한글 상태에서 낼 수 없는 키는 그대로 둔다

`U` 가 넷째다. `G` `B` `V` 에 이어진다. 넷 다 같은 까닭이고(shift 자리에 다른 글자가 없어 `shift+x` 와 `x` 가 같은 글자로 온다) 앱 안에서 가를 방법이 없다(ADR-0008).

**넷을 위한 우회로를 만들지 않는다.** `\U` 같은 leader 조합을 붙이거나, 한글 상태를 따로 기억해 두었다가 shift 를 헤아리는 길이 있는데 둘 다 두지 않는다.

**한글로 온 키를 되돌려 받는 것은 최소한의 방어책이자 편의이지 주요 역할이 아니다.** 한글 상태로 normal mode 에 와 있는 것 자체가 사고이고(ADR-0008 의 「남은 키를 버리는 쪽이 안전하다」가 이미 그 자리에 서 있다), 이 편집기가 그 상태에서 **모든 키를 다 낼 수 있게** 만드는 것은 부탁받은 일이 아니다. 우회로를 넷에 붙이면 「한글 상태에서만 있는 키」라는 갈래가 새로 서고, 그다음부터 키를 더할 때마다 그 갈래를 같이 채워야 한다. 얻는 것보다 짐이 크다.

확실하게 하려는 사람에게는 이미 길이 있다. 입력기를 mode 에 맞춰 바꾸는 것이고, ADR-0008 이 그것을 앱 밖의 일로 남겨 두었다.

## 6. `~` 의 범위는 motion 이 낸다. 창의 문은 하나다

§1 이 알맹이를 둘로 두었다 — `changeCaseChars`(글자 몇 개) 와 `changeCaseRange`(고른 범위). 나중에 보니 **그 둘의 편집 부분이 글자 하나 다르지 않았다.** 한 줄짜리 글자 단위 범위로 `changeCaseRange` 를 부르면 `changeCaseChars` 와 같은 일을 한다. 겹친 것이 여덟 줄이었다.

다른 것은 커서 셋뿐이었고, 그것은 §4 가 적어 둔 대로 **키마다 다른 규칙**이다.

그리고 `~` 가 잡는 범위를 다시 보니 **이미 있는 것이었다.**

```
clusterEndClamped(line, col, n)  col 에서 글자 n 개 뒤. 줄에 없으면 줄 끝
MoveRight(n)                     줄 끝에 닿으면 남은 횟수를 버리고 멈춘다
```

`motionRight.span(buf, count)` 이 내는 범위가 `3~` 가 잡는 것과 같다. `3l` 이 가는 자리이자 `d3l` 이 지우는 자리다.

**그래서 `~` 도 그것을 쓴다.** 창에는 `ChangeCaseRange` 하나만 남고, 「어느 범위인가」는 `actionChangeCase` 가 정한다. `changeCaseChars` 와 `clusterEndClamped` 가 없어졌다.

§1 의 「없으면 있는 만큼 바꾼다」는 그대로다. 근거가 `clusterEndClamped` 에서 `MoveRight` 의 클램프로 옮겨갔을 뿐이고, 둘이 같은 규칙이라 동작이 안 바뀐다.

### 이 손이 잠자던 버그를 하나 잡았다

커서를 옮기는 방법이 `Cursor.Col += len(changed)` 에서 `MoveRight(count)` 로 바뀌었다. 둘 다 「바꾼 줄 위에서 count 글자 오른쪽」이라 같은 자리를 내는데, **빈 줄에서 갈렸다.**

옛것은 `UpdateDesiredCol` 을 늘 불러서 빈 줄에서 친 `~` 가 기억한 칸을 0 으로 지웠다. `MoveRight` 는 갈 곳이 없으면 그대로 돌아온다.

vim 9.1 로 쟀다.

```
lll     1:4:cw4
lllj    2:1:cw4     빈 줄. 기억한 칸은 4
lllj~   2:1:cw4     ~ 가 아무것도 안 한다. 기억한 칸도 그대로다
lll~    1:5:cw5     글자 위에서는 오른쪽으로 가고 기억한 칸도 따라간다
```

vim 쪽이 새 동작과 같다. `TestTildeOnEmptyLineKeepsDesiredCol` 이 못 박는다.

### byte 길이가 달라지는 것은 여전히 조심할 자리다

`applyCase` 는 rune 을 1:1 로 옮기지만 byte 수는 달라진다 — `ı`(2) 가 `I`(1) 이 되고 `İ`(2) 가 `i`(1) 이 된다. 그래서 **바꾸기 전 범위의 끝으로 커서를 잡으면 안 된다.** `MoveRight` 가 바꾼 뒤의 줄을 훑으므로 이 자리는 저절로 맞다.

## 고르지 않은 것

- **operator 갈래를 지금 넣기.** §2 다
- **`~` 를 operator 로 만들기(`tildeop`).** vim 이 설정으로 주는 것인데 설정 파일이 아직 없다(ADR-0061). 있어도 「같은 키가 상황에 따라 다른 것을 기다린다」는 파서에 두고 싶지 않은 갈래다
- **`g?`(rot13).** 대소문자와 같은 모양(글자를 그 자리에서 갈아끼운다) 이지만 부탁받은 일이 아니다. operator 갈래를 열 때 같이 본다
- **visual 에 `~` 를 빼고 `u`·`U` 만 두기.** 셋이 `caseKind` 값 하나만 다른 같은 동작이라 빼서 아끼는 것이 없다
- **한글 상태에서 `U` 를 낼 다른 길.** §5 다
- **터키어 `i`.** `unicode.ToUpper('i')` 는 `I` 다. 터키어 locale 은 `İ` 를 원하는데, 편집기가 locale 을 보는 곳이 아직 없고 소스 코드를 고치는 사람에게는 `I` 가 맞다
