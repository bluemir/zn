# ADR-0012: mouse 는 좌표를 영역으로 바꿔서 mode 마다 다르게 먹는다

- 상태: 채택
- 날짜: 2026-08-13

## 맥락

`docs/tasks.md` 에 "file tree 를 mouse 로도 펼치기 접기 열기 가능하도록" 과 "커서 위치를
이동 할수 있도록" 이 열려 있었고 `README.md` 에도 "mouse 지원" 이 목표로 적혀 있었다.

상태가 어중간했다. `editor.render` 가 이미 `view.MouseMode = tea.MouseModeCellMotion` 을 켜고
있었다 — 즉 터미널은 mouse 를 앱에 넘기는 중이고, 그 대가로 **터미널 자체의 드래그 복사가
이미 막혀 있었다**. 그런데 어느 mode 의 `Update` 도 mouse 메시지를 받지 않아서
(전부 `default: return m, nil` 로 버렸다) 눌러도 아무 일이 없었다. 비용만 치르고 있었다.

정할 것이 다섯 가지였다.

1. 좌표를 뜻으로 바꾸는 일을 어디에 둘 것인가. mode 가 型 교체라(ADR-0002) 공용화가 어렵다
2. 화면 좌표에서 buffer 위치로 가는 역변환. 지금은 정방향(`cursorScreenPos`) 만 있다
3. 클릭 하나에 어디까지 반응할 것인가. mode 마다 다르게 할 것인가
4. 휠이 무엇을 움직이는가 — 화면인가 커서인가, 포커스 쪽인가 포인터 쪽인가
5. tabline 의 칸에서 tab 번호를 어떻게 얻는가. 그 배치는 지금 closure 안에만 있다

## 결정

**좌표 → 영역 판별(`editor.regionAt`) 과 영역별 동작은 `editor`·`Buffer`·`sidebar` 에 두고,
dispatch 는 mode 마다 `Update` 에 반복해 쓴다.** ADR-0002 가 예고한 "공용 메시지의 case 반복" 을
`WindowSizeMsg` 에 이어 두 번째로 받아들인다. 영역은 `regionNone`·`regionSidebar`·
`regionTabline`·`regionText` 네 가지의 내부 enum 이다.

**`Buffer.positionAt(x, y, width, height)` 로 역변환한다.** `visibleRows` 로 화면 행을 찾고
그 행을 잘라 `offsetAtScreenCol` 에 넘긴다. 줄번호 칸(x 가 음수) 은 줄 시작이고,
마지막 줄 아래 빈 자리는 없는 자리다.

**누를 때(`MouseClickMsg`) 반응하고 왼쪽 버튼만 본다.** `MouseReleaseMsg` 와
`MouseMotionMsg` 는 버린다.

**클릭 한 번이 고르기와 열기를 겸한다.** 트리에서 디렉터리는 펼치거나 접고 파일은 tab 으로 연다.

**다른 영역을 클릭하면 포커스도 그리로 간다.** 단 **편집 영역을 클릭할 때 insert mode 는
유지한다** — 커서만 옮기고, 화살표 이동과 같이 `endEdit()` 으로 undo 구간을 끊는다.

**명령줄·검색 mode 는 휠만 받고 클릭은 무시한다.** 종료 확인창은 둘 다 받지 않는다.
**팔레트(ADR-0011) 는 휠이 목록을 오르내리고**, 여기서만 포인터 위치를 보지 않는다.

**휠은 화면만 굴리고, 커서는 화면을 벗어날 때만 밀려난 쪽 끝 행으로 데려온다.**
노치당 3 행(`wheelRows`) 이다. **작용 대상은 포커스가 아니라 포인터가 얹힌 영역이다.**

**`tabline` 이 그리면서 각 tab 의 칸 범위를 같이 돌려준다.** `tabAt(x)` 가 그것으로 답한다.

`:mouse` 로 여닫는 것과 드래그는 넣지 않는다.

## 근거

### 판별은 공용, dispatch 는 mode 별

**mouse 는 키와 반대다.** 키는 "무엇을 눌렀는가" 가 이름으로 오고 그 뜻이 mode 마다 갈린다.
mouse 는 뜻은 대체로 같은데(눌린 것을 고른다) **무엇을 눌렀는지가 좌표로만 온다**. 그래서
좌표를 영역으로 바꾸는 단계가 mode 앞에 공용으로 있어야 하고, 그 뒤가 mode 별로 갈린다.
키의 상태 기계(ADR-0006) 가 놓인 자리와 같은 층이다.

**dispatch 까지 공용화할 수는 없다.** 포커스 이동이 곧 `tea.Model` 型 교체라(ADR-0002)
"어느 화면으로 돌아갈지" 를 `editor` 메서드가 대신 정할 수 없다. 편집 영역 클릭 하나가
normal 에서는 `viewEditorNormal`, insert 에서는 `viewEditorInsert`, sidebar 에서는
`viewEditorNormal` 로 끝난다. 이것을 한 함수에 넣으면 "지금 어느 mode 냐" 를 되묻는 flag 나
enum 이 필요해지는데, 그것이 정확히 ADR-0002 가 없애기로 한 것이다.

**대신 짧은 `click` 메서드 셋을 `internal/core/mouse.go` 한 파일에 모았다.** 동작이 갈리는
자리가 한눈에 보이고, 갈리지 않는 부분(`clickText`, `clickSidebar`, `clickTabline`, `wheel`) 은
`editor` 에 한 벌만 있다.

**수치를 새로 두지 않았다.** `regionAt` 은 `render` 가 쓰는 `sidebarVisible()`·`sidebarLeft()`·
`textHeight()` 를 그대로 쓴다. 그리는 쪽과 판별하는 쪽이 어긋나면 한 칸 옆을 누른 것이 되는데,
그 어긋남은 화면에 드러나지 않아서 찾기 어렵다. 특히 `sidebar.open` 이 아니라
`sidebarVisible()` 을 봐야 한다 — ADR-0005 가 "폭과 관련된 모든 곳" 에 요구한 것이다.

### 좌표 변환

**행을 잘라서 넘겨야 한다.** tab 이 다음 tab stop 까지 벌어지는 기준이 논리 줄이 아니라
**화면 행의 시작** 이다(`wrapOffsets`). 줄을 통째로 `offsetAtScreenCol` 에 넘기면 tab 으로
들여쓴 Go 소스에서 wrap 된 둘째 행 이후가 엉뚱한 byte 로 간다. 실제로 이 프로젝트 소스가
전부 tab 들여쓰기라 첫 시험에서 바로 드러날 자리였다.

**줄번호 칸은 줄 시작으로 본다.** x 가 음수로 들어오므로 `max(0, x)` 한 번으로 끝난다.
"그 행을 골랐다" 로 읽는 것이 자연스럽고, 무시하면 번호 위에서 눌렀을 때 아무 일도 없어서
고장으로 보인다.

**마지막 줄 아래는 무시한다.** vim 도 그렇다. 아무것도 없는 곳을 눌렀는데 커서가 움직이면
"누른 자리로 간다" 는 약속이 깨진다. `visibleRows` 가 화면 높이보다 짧게 주는 것을
그대로 이용하므로 따로 세지 않아도 된다.

**두 칸짜리 글자와 grapheme cluster 는 손댈 것이 없다.** `offsetAtScreenCol` 이 이미 글자
시작으로 맞춰준다(ADR-0001 이 rune 이 아니라 cluster 단위로 정해둔 덕이다).

### 누를 때, 왼쪽 버튼만

**뗄 때를 기다릴 이유가 드래그뿐이다.** 드래그를 넣지 않았으므로 누른 자리가 곧 고른 자리다.
누를 때 반응하는 것이 손에 붙는다.

**double-click 은 알 수 없다.** bubbletea v2.0.7 의 `Mouse` 에 누른 횟수가 없어서 직접 시간을
재야 한다. 그러면 `Update` 안에서 시계를 봐야 하고, 그것은 ADR-0009 가 "렌더 안에서 프로세스를
띄우지 않는다" 로 그은 선과 같은 결의 문제다. **그래서 클릭 한 번이 고르기와 열기를 겸한다** —
트리에서는 이것이 오히려 `enter` 한 번과 같아서 자연스럽다.

**가운데·오른쪽 버튼에 붙일 동작이 아직 없다.** 삼켜두면 나중에 붙일 때 이미 뭔가 하는 것처럼
보였던 이력이 걸림돌이 된다. 지금은 지나가게 둔다.

### insert mode 를 유지하는 것

**눌러서 자리를 잡고 이어 치는 것이 mouse 를 쓰는 이유다.** 클릭이 insert 를 끊으면 매번
`i` 를 다시 눌러야 하고, 그러면 mouse 로 얻은 것이 없다. GUI 편집기와 같고 vim 의 `mouse=a`
와도 같다.

**대신 undo 구간은 끊는다.** 화살표 이동이 이미 `endEdit()` 을 부르고 있고(vim 과 같다),
클릭도 커서 이동이다. 끊지 않으면 여기 치고 저기 치고 한 것이 `u` 한 번에 통째로 사라진다.

### 명령줄·검색 중에는 휠만

**치던 명령이 클릭 한 번에 조용히 사라지면 안 된다.** `:` 나 `/` 를 치는 중이라는 것은 화면
아래 줄에만 드러나므로, 클릭으로 mode 가 바뀌면 무엇을 잃었는지도 보이지 않는다.
esc 와 같이 처리하고 클릭을 수행하는 쪽은 GUI 답지만, 잘못 눌렀을 때 잃는 것이 더 크다.

**화면을 둘러보는 것은 막을 이유가 없다.** 명령을 치다가 위쪽을 확인하는 일은 흔하다.
다만 `/` 검색은 다음 글자를 치면 incsearch 의 `preview()` 가 첫 매칭으로 화면을 다시
잡아당기므로 굴려둔 것이 그때 사라진다 — 알려진 한계로 남긴다.

**종료 확인창은 `editor` 를 embed 하지 않아 좌표 계산에 쓸 geometry 가 없다.** 선택지 둘짜리
창이라 키로 충분하다. 대신 그 `View` 가 `MouseMode` 를 부모에서 복사하도록 고쳤다 —
안 하면 확인창이 뜰 때마다 터미널에 mouse 를 끄고 켜는 escape 가 오간다. `AltScreen` 을
복사하는 것과 같은 이유다.

**팔레트만 휠의 규칙에서 벗어난다.** 팔레트는 편집 화면 위에 박스를 합성해서 얹으므로
(ADR-0011) 아래 내용을 굴려도 박스에 가려 볼 수 없다. 그래서 "포인터가 얹힌 영역" 을 따르는
것이 오히려 무의미하고, 목록을 오르내리는 것이 유일하게 쓸모 있는 동작이다.
이것은 좌표를 전혀 보지 않으므로 박스의 geometry 를 `regionAt` 에 넣지 않아도 된다 —
팔레트 클릭을 넣으려면 그때 다섯 번째 영역이 필요해진다.

### 휠

**화면만 굴리는 것이 휠에 대한 기대다.** 커서까지 따라오면 "보려고 굴렸는데 자리가 바뀌었다"
가 된다. vim 기본값과 같다. `scrollTo` 가 "커서를 따라 화면을 옮긴다" 였으니 `scrollBy` 는
그 반대 방향이고, 커서가 화면 밖으로 밀려날 때만 데려온다.

**데려오는 방향을 뒤집기 쉽다.** 아래로 굴리면 화면이 커서를 지나쳐 내려가므로 커서는 화면
**위** 로 벗어난다 — 맨 윗줄로 데려와야 한다. 처음 구현에서 이것을 반대로 써서 아래로 굴렸을
때 커서가 맨 아랫줄로 갔고, 테스트가 잡았다.

**포인터 쪽이 굴러가야 한다.** 편집 영역을 보면서 트리만 훑어보는 것이 흔한 동작이고, 그때
포커스를 옮기고 싶지는 않다. 터미널 앱과 편집기의 보편적 관습이다.
**hover 를 따로 추적하지 않는다** — 휠 이벤트 자체가 그 순간의 좌표를 실어 오므로
`MouseModeAllMotion` 으로 올릴 필요가 없다. 올리면 포인터를 움직이는 동안 이벤트가 쏟아진다.

**노치당 3 행.** 1 행은 너무 느려서 휠을 계속 굴려야 하고, 화면 절반(vim 의 `scroll` 기본값)은
어지럽다. 그 값은 `ctrl+d` 용이다.

**sidebar 의 휠은 `top` 만 옮기고 `selected` 는 두지 않는다.** `scrollTo` 를 부르면 고른 항목을
화면에 넣으려고 `top` 을 되돌려서 굴린 것이 그대로 없어진다. 고른 항목이 화면 밖으로 나가면
`selectedRow` 가 false 를 주고 `viewSidebar.View` 가 이미 커서를 지운다 — ADR-0005 의
"커서가 곧 포커스 표시" 가 잠시 안 보이지만 다음 `j`/`k` 가 데려온다.

**좌우 휠은 쓰지 않는다.** 가로 스크롤이 없다(ADR-0001).

### tabline 의 칸 범위

**배치 계산을 두 벌 두면 반드시 어긋난다.** tab 이름 옆의 `+`(dirty) 하나로 칸이 밀리는데,
클릭 쪽이 그것을 빠뜨리면 눌렀을 때 옆 tab 으로 간다. 그리는 쪽은 이미 `put` 안에서 `col` 을
옮기고 있으므로, 그 값을 그대로 내주는 것이 가장 싸고 어긋날 수 없다.

**호출자가 하나뿐이라 부담이 없다.** `screenRows` 만 문자열을 쓰고 클릭 경로만 범위를 쓴다.

## 결과

좋은 점

- 이미 켜 두고 있던 mouse reporting 이 마침내 값을 한다. 드래그 복사를 잃은 대가를 받는다.
- 트리 조작이 눈에 보이는 대로 된다. `ctrl+w ctrl+w` → `j` 여러 번 → `enter` 가 클릭 한 번이다.
- 긴 파일에서 화면을 굴리는 것이 `ctrl+e`/`ctrl+y` 를 외우지 않고 된다.
- 좌표 변환이 `cursorScreenPos` 의 짝으로 생겼다. 나중에 드래그 선택을 넣을 때 그대로 쓴다.
- `tabline` 이 자기 배치를 내주게 되어, tab 을 가로로 밀어 보이게 하는 일(`docs/tasks.md`) 도
  같은 자리에서 하게 된다.

감수하는 것

- **터미널 자체의 드래그 복사가 계속 막혀 있다.** 이 결정이 새로 만든 문제는 아니지만
  해결하지도 않았다. 대부분의 터미널에서 `shift`+드래그로 우회되고, 제대로는 "키 하나로
  cat 형태 표시"(`docs/tasks.md`) 를 만들 때 같이 본다.
- **`Update` 에 case 두 개가 mode 마다 반복된다.** ADR-0002 가 예고한 값이지만 이제 mode 당
  세 종류(크기·클릭·휠) 다. 한 번 더 늘면 공용 처리로 빼는 것을 다시 봐야 한다.
- **double-click 이 없어서 트리의 "고르기" 와 "열기" 를 나눌 수 없다.** 파일을 눌러보기만
  하려 해도 tab 이 열린다.
- **드래그가 없어서 선택도, sidebar 너비 조절도 mouse 로 못 한다.** motion 이벤트는 이미
  오고 있으므로 버리고 있는 셈이다.
- **큰 디렉터리를 클릭으로 펼치면 키로 펼칠 때와 똑같이 멈칫한다.** `os.ReadDir` 과
  `git check-ignore` 가 동기라(ADR-0005) 클릭이 그 경로를 새로 만들지는 않지만 더 쉽게 밟게 한다.

## 대안

**`tea.View.OnMouse` 훅에 맡기기** — bubbletea 가 `View` 에 mouse 훅을 준다. 그리는 쪽에서
좌표를 바로 해석할 수 있어 매력적이다. 그런데 훅은 `View` 에 달려 있어서 `tea.Model` 型 교체를
표현할 수 없다 — 포커스 이동이 곧 型 교체인 이 설계(ADR-0002) 와 맞지 않는다. 결국 훅에서
받아 `Update` 로 다시 보내는 우회가 필요해진다.

**컴포넌트 트리에 hit-test 를 맡기기** — 영역마다 bounds 를 들고 있는 컴포넌트를 두고 좌표로
찾아 내려보내는 방식이다. mouse 를 다루는 GUI 의 정석이고 mode 별 반복도 사라진다.
그런데 `core` 는 자기 화면을 직접 그리고(ADR-0005) `internal/tui/components` 에는 bounds
개념이 아예 없다. mouse 하나 때문에 화면 구조를 통째로 뒤집는 것은 순서가 거꾸로다.
영역이 넷뿐이라 지금은 `regionAt` 하나로 충분하다.

**`:mouse` 로 여닫기** — vim 이 그렇게 한다. 드래그 복사가 필요할 때 끌 수 있다. 그런데 지금
켜져 있던 것을 끄고 켤 수 있게 만드는 것은 별개 기능이고, 진짜 해결책은 화면을 cat 형태로
보여주는 것이라 그쪽과 같이 정하는 편이 낫다. 상태 하나를 미리 늘리지 않는다.

**휠에 커서를 따라 움직이기** — 굴린 뒤 바로 칠 수 있다. 보려고 굴린 경우에 자리를 잃는다.
`ctrl+e`/`ctrl+y` 가 아니라 `j`/`k` 를 여러 번 누른 것과 같아져서 휠이라는 물건에 대한
기대와 다르다.

**클릭에서도 `MouseMode` 를 낮추기** — 드래그를 안 쓰니 motion 을 아예 안 받으면 좋겠지만
bubbletea 의 `MouseMode` 는 `None`·`CellMotion`·`AllMotion` 셋뿐이고 `CellMotion` 이
click·release·wheel 을 받는 최소값이다. motion 은 버튼을 누른 동안만 오므로 가만히 두면
이벤트가 쏟아지지 않는다. 지금 값이 이미 최소다.

## 이 ADR 이 정하지 않는 것

- 드래그로 범위를 고르는 것. visual mode 를 정할 때 같이 본다
- mouse 로 sidebar 너비를 바꾸는 것
- double-click 과 가운데·오른쪽 버튼
- `:mouse` 로 여닫는 것. 화면을 cat 형태로 보여주는 기능과 같이 본다
- 팔레트 목록을 클릭해서 고르는 것. 박스의 자리를 `regionAt` 이 알아야 한다
- statusBar 를 눌러서 무엇을 하는 것(mode 표시를 눌러 바꾸기 같은 것)
- `Mod`(shift/alt/ctrl) 조합에 다른 뜻을 붙이는 것
- 잘려서 안 보이는 tab 을 어떻게 보이게 할지. `tabline` 이 칸 범위를 내주게 된 것이 그 일의
  발판이지만 결정은 별개다
