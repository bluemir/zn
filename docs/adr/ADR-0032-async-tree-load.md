# ADR-0032: 디렉터리 읽기를 백그라운드 작업으로 끝까지 내린다

- 상태: 채택
- 날짜: 2026-08-14

## 맥락

트리를 펼치는 곳(`treeNode.expand`) 이 `os.ReadDir` 과 `git check-ignore` 를 `Update` 안에서 차례로 동기 호출했다. `docs/tasks.md` 에 두 줄로 열려 있던 건이다.

- 아주 큰 디렉터리를 펼치면 한 키가 멈춘다. `os.ReadDir` 이 전부 읽고 `Update` 안에서 동기로 돈다.
- `git check-ignore` 도 같은 이유로 동기 호출이다. 느린 저장소에서 펼치는 순간 멈칫한다.

재보니 `git check-ignore` 는 경로 100 개에 20ms, 20,000 개에 70ms 다. 고정비인 프로세스 띄우기가 대부분이라 작은 디렉터리를 펼칠 때도 매번 20ms 를 문다. `os.ReadDir` 은 항목 수에 비례해서, 십만 개짜리 디렉터리에서는 읽기와 정렬만 수십 ms 다.

비동기 바탕은 이미 있다. 작업 실행기(ADR-0025) 와 작업 관리자(ADR-0027) 다. 팔레트 파일 인덱싱과 git 갱신(ADR-0030) 이 그 위에 올라가 있고, 이것이 셋째 소비자다.

`docs/tasks.md` 에는 "`File.ReadDir(n)` 으로 끊고 `… N개 더` 행을 두는 것을 본다" 도 적혀 있었다. 행이 십만 개면 `sidebar.rows()` 가 그릴 때마다 십만 행 slice 를 새로 만들고 `Update` 한 번이 그것을 여러 번 부르므로(`selectedNode`·`scrollTo`·`cells`) 그쪽이 병목이 될 것으로 보았다. 그래서 처음에는 앞 1000 개만 항목으로 만들었는데, 값을 재보니 근거가 틀렸다.

| 자식 수 | 키 한 번(scrollTo + View) | 그중 `rows()` 한 번 |
|---|---|---|
| 1,000 | 0.26ms | 0.01ms |
| 10,000 | 0.52ms | 0.11ms |
| 50,000 | 1.20ms | 0.46ms |
| 200,000 | 4.50ms | 2.11ms |

십만 개를 다 들고 있어도 키 한 번이 1ms 대다. 사람이 느끼는 수준이 아니고, 파일을 감춰서 살 만한 것도 아니다.

## 결정

### 1. 디렉터리 읽기는 작업이다

펼치기(`editor.expandNode`) 가 `startJob` 으로 읽기 작업을 시작하고 Cmd 를 돌려준다. 펼침 표시(`▾`) 는 기다리지 않고 지금 서고, 자식 자리에는 `… 읽는 중` 한 행이 선다. 결과가 도착하면 조각의 `apply` 가 자식을 채운다. `git check-ignore` 도 같은 작업 안에서 돈다. 펼치는 길에 동기 호출을 하나도 남기지 않는다.

조각은 하나뿐이다. 이름순 앞부분을 고르려면 어차피 다 읽어야 해서 나눠 보낼 것이 없다.

`apply` 는 노드 포인터가 아니라 **경로로 자리를 다시 찾는다**(`sidebar.nodeAt`). 결과가 도착할 때 그 포인터는 이미 어느 화면에도 없을 수 있다. 접혔거나 `:tree` 로 트리를 새로 열었을 때다. 찾지 못하거나 이미 접혀 있으면 결과를 버린다.

작업 이름은 뿌리 기준 상대 경로가 들어간 `디렉터리 읽기 internal/core` 다. 이름이 곧 신원이라 (ADR-0027) 경로가 들어가야 디렉터리마다 따로 돌고, 접을 때 그것만 `cancelJob` 으로 끊는다.

### 2. 표시 상한을 두지 않는다. 끝까지 읽어 다 보여준다

항목 수에 상한이 없다. 십만 개짜리 디렉터리도 끝까지 읽어 전부 항목으로 만든다. 위의 값이 근거다. 감출 이유가 없고, 감추면 트리에서 그 파일로 갈 길이 아예 없어진다.

`… 읽는 중` 안내 행은 `children` 에 넣지 않고 `rows()` 가 그릴 때마다 만든다(`placeholder`). `children` 은 실제 항목만 들어야 `child(name)` 조회와 reveal 이 안내 행을 파일로 착각하지 않는다. 이 행은 gitignore 된 항목과 같은 흐린 색이고, 골라서 `Enter` 를 눌러도 아무 일도 하지 않으며 "보고 있는 파일" 표시도 받지 않는다.

### 3. reveal 은 한 층씩 내려가고 도중에 멈춰 기다린다

보는 파일이 바뀌면 트리가 그 자리를 펼치고 고른다(ADR-0019). 그 걸음이 이제 한 번에 끝나지 않는다. `sidebar.pendingReveal` 에 갈 자리를 들고, `continueReveal` 이 갈 수 있는 만큼 걸어간 뒤 아직 읽지 않은 디렉터리를 만나면 그것을 읽는 작업을 시작하고 물러난다. 자식이 도착하면 그 자리부터 다시 걷는다. 자리를 잡거나 항목을 찾지 못하면 `pendingReveal` 을 비운다.

이어서 미는 곳은 `handleJob` 하나다. `apply` 는 `func(*editor)` 라 Cmd 를 낼 수 없어서, 조각을 처리한 뒤 `tea.Batch(waitJob(...), e.continueReveal())` 로 돌려준다. 기다리는 것이 없으면 `continueReveal` 이 곧바로 nil 이라 다른 작업의 조각에는 얹히지 않는다.

사용자가 직접 접으면 그 안으로 향하던 reveal 은 그만둔다. 남겨 두면 다음 조각이 도착할 때 방금 접은 것이 도로 펼쳐진다.

### 4. reveal 을 부르는 함수들이 Cmd 를 돌려준다

`revealInSidebar`·`nextTab`·`prevTab`·`openTab`·`replaceTab`·`toggleTree`·`clickTabline` 이 `tea.Cmd` 를 돌려주고 부르는 mode 가 그것을 `tea.Batch` 로 내보낸다. 트리의 첫 읽기는 `core.Run` 이 아니라 normal mode 의 `Init` 이 `startTree` 로 낸다. `Run` 은 Program 이 뜨기 전이라 Cmd 를 낼 곳이 없다. git 첫 갱신과 같다(ADR-0030).

## 근거

### 왜 상한을 두지 않는가

재보고 정했다(위 표). 상한이 주는 것은 "그릴 행이 적어진다" 하나뿐인데 그것이 키 한 번에 1ms 대라 사람에게 닿지 않는다. 대가는 반대쪽이 크다. 트리는 파일을 찾는 곳이고, 감춘 파일은 트리에서 갈 길이 아예 없다. 특히 감추는 기준이 이름순 앞부분이면 **디렉터리**도 감춰져서, 그 안의 파일을 열었을 때 트리가 따라가지 못한다.

### 왜 `File.ReadDir(n)` 으로 끊지 않는가

`docs/tasks.md` 에는 `File.ReadDir(n)` 으로 앞 n 개만 읽는 것을 적어두었다. 그것은 정렬을 포기하는 것이다. `os.ReadDir` 만 이름순으로 주고 `File.ReadDir(n)` 은 디렉터리 순서 그대로다. 읽는 일 자체가 이제 화면 밖에서 도니 끊어 읽을 이유가 없다.

### 왜 조각을 나눠 보내지 않는가

이름순으로 놓으려면 다 읽고 정렬해야 해서 첫 조각을 일찍 보낼 수 없다. 다 읽은 뒤에 항목을 만들어 넘기는 것은 slice 하나를 건네는 일이라 나눠도 빨라지지 않는다. 그래서 조각은 하나이고 `done/total` 은 `1/1` 이다. 진행 표시가 아니라 `… 읽는 중` 이 그 자리를 대신한다. 팔레트 파일 인덱싱은 조각을 나누는데(ADR-0011) 그쪽은 결과가 목록이라 앞부분만으로도 쓸 수 있어서 다르다.

### 왜 경로별 작업 이름인가

이름 하나(`디렉터리 읽기`) 로 두면 같은 이름은 한 번에 하나만 돈다는 규칙에 걸려서, 읽는 중에 다른 디렉터리를 펼치면 그쪽이 `… 읽는 중` 에서 영영 멈춘다. reveal 은 한 걸음에 여러 층을 펼치기도 한다. 취소도 이름으로 하므로(`cancelJob`) 한 이름이면 접을 때 남의 읽기까지 끊는다.

### 왜 `handleJob` 이 reveal 을 이어 미는가

`apply` 가 Cmd 를 낼 수 없다는 것이 실행기의 성질이다(ADR-0025). 그것을 고쳐 `apply` 가 Cmd 를 돌려주게 하면 작업마다 그 서명을 지고 가야 하는데, 그것이 필요한 소비자는 지금 트리 하나다. `handleJob` 에 붙은 것은 작업 종류로 가르는 `switch` 가 아니라 "미진한 일을 이어 간다" 한 줄이라 ADR-0025 의 "실행기는 작업 종류를 모른다" 는 그대로다.

5 초마다 도는 git tick 도 같은 곳을 지나므로, 어딘가에서 Cmd 를 흘려도 트리는 늦어도 5 초 안에 따라온다. 안전망이지 설계는 아니다. Cmd 는 부르는 쪽이 끝까지 들고 나가야 한다.

## 결과

- 아주 큰 디렉터리에서 펼치기와 시작하기가 키를 멈추지 않는다. 항목 5 만 개짜리 디렉터리에서 띄워 보면 편집기가 곧바로 뜨고, 다 읽은 뒤 5 만 행이 그대로 트리에 있으며 `:jobs` 에 `디렉터리 읽기 big  끝남  50,001 개` 가 남는다.
- `:jobs` 의 끝난 목록에 펼친 디렉터리마다 한 줄이 생긴다. ADR-0030 이 "이름은 코드에 있는 종류만큼만 있으니 개수 상한을 두지 않는다" 고 한 가정이 여기서 흔들린다. 사용자가 펼친 만큼만 늘고 주기 작업처럼 스스로 쌓이지는 않으므로 이번에는 그대로 둔다.
- 이름이 길어서 `:jobs` 의 이름 칸(16) 을 넘고 그만큼 상태·시간 칸이 밀린다.
- 항목이 아주 많은 디렉터리를 펼쳐 두면 `rows()` 가 키마다 그만큼의 slice 를 새로 만든다. 20 만 개에서 키 한 번이 4.5ms 이고 백만 개면 20ms 대로 올라간다. 그때의 답은 파일을 감추는 것이 아니라 `rows()` 를 캐시하는 것이다. 지금은 필요하지 않다.
- 트리를 보는 시험이 작업을 돌려야 한다. `openSidebarSync`·`toggleSync`(작업이 부르는 것과 같은 함수를 그 자리에서 부른다) 와 `settle`·`sendSync`(Cmd 가 낸 msg 를 더 나올 것이 없을 때까지 다시 먹인다) 를 두었다.
- `readDir` 이 남은 개수를 같이 돌려주고 `markIgnored` 가 ctx 를 받는다. 취소하면 git 프로세스도 죽는다(ADR-0027).

## 대안

- **표시 상한 1000 개 + `… N개 더` 행.** 처음 구현한 것이고 되돌렸다. 값을 재보니 상한이 사는 것이 사람에게 닿지 않고, 대신 이름순 뒤쪽의 파일과 디렉터리가 트리에서 사라진다.
- **비동기 없이 상한만.** 가장 적게 고치지만 이름을 다 읽어 정렬하는 일과 git 호출이 `Update` 안에 남는다. 느린 저장소에서 멈칫하는 것은 그대로다.
- **reveal 만 동기로 남긴다.** `revealInSidebar` 를 부르는 곳이 여덟이라 Cmd 를 잇는 손이 가장 적게 든다. 그러나 팔레트로 큰 디렉터리 안의 파일을 열면 그 순간 다시 멈춘다. 동기 호출을 하나도 남기지 않기로 했다.
- **작업 관리자를 거치지 않는 가벼운 msg 경로.** `:jobs` 는 깨끗하게 남지만 진행·취소·실패 알림을 이 경로에만 다시 만들게 된다. 소비자 하나를 위해 둘째 실행기를 두는 셈이다.

## 이 ADR 이 정하지 않는 것

- `rows()` 캐시. 항목이 백만 개일 때 필요해질 수 있다. 어디서 무효화할지(펼치기·접기· 작업 결과) 가 같이 정해져야 한다.
- 파일 시스템 watcher. 접었다 펴는 것이 여전히 새로고침이다(ADR-0005).
- `:jobs` 이름 칸 폭. 긴 이름이 상태 칸을 밀어내는 것은 목록 쪽 표시 문제다.
