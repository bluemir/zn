# ADR-0136: 터미널에게 우리가 클러스터로 센다고 알린다 (mode 2027)

## 맥락

터미널은 글자를 셀 격자에 놓으므로 「이 글자가 몇 칸인가」를 정해야 한다. 방식이 둘이다.

**코드포인트 단위(전통 방식, wcwidth)**: 코드포인트마다 폭을 매겨 더한다. 유니코드에는 여러 코드포인트가 모여 한 글자를 이루는 것이 많아서 이 방식은 그런 글자를 여러 칸으로 센다.

```
U+1F468 U+200D U+1F4BB    눈에는 사람 한 명, 코드포인트는 셋
U+261D U+FE0F             글자 하나 + 「이모지로 그려라」 표시
U+0939 U+093F             데바나가리 자음 + 모음 기호
```

**grapheme cluster 단위**: UAX #29 가 정의한 「사람이 한 글자로 보는 단위」로 묶어 그 덩어리에 폭을 매긴다.

**zn 은 이미 뒤쪽으로 센다.** `x/ansi` 의 `GraphemeWidth` 를 쓰고, lipgloss 와 ultraviolet 도 같은 자를 쓴다. 그런데 **터미널에는 그 사실을 알리지 않았다.** 그래서 터미널만 코드포인트 단위로 세고 있었다.

터미널에 글자를 찍고 커서 열을 물어(DSR 6) 잰 값이다.

| 잰 것 | zn | Ghostty 1.3.1 | Ghostty + 2027 | tmux 3.6a |
|---|---|---|---|---|
| `U+1F468 U+200D U+1F469 U+200D U+1F467` | 2 | **6** | 2 | 2 |

우리는 두 칸을 예약하는데 Ghostty 는 여섯 칸으로 그린다. 넘친 네 칸이 뒤 글자를 덮는다. 큐레이션 표에 그런 글자가 여섯 개 있다(`개발자`·`여성 개발자`·`요리사`·`학생`·`선생님`·`의료인`).

`mode 2027` 은 「클러스터 단위로 세라」고 켜는 DEC private mode 다. 스위치인 이유는 기존 프로그램 대부분이 wcwidth 를 가정하고 있어서다 — 터미널이 임의로 바꾸면 그것들이 깨진다. 그래서 프로그램이 「나는 클러스터 단위로 세는 프로그램이다」라고 선언하는 opt-in 이다.

## 결정

**시작할 때 `\x1b[?2027h` 를 보낸다.** `startInitialJobs` 가 내는 Cmd 하나가 된다.

```go
func enableGraphemeClustering() tea.Cmd {
	return tea.Raw(ansi.EnableGraphemeClustering)
}
```

**근거는 「이미 하고 있는 것을 알린다」다.** 새 규칙을 세우는 것이 아니다. 우리 폭 계산과 lipgloss 와 ultraviolet 이 벌써 클러스터 단위이고, 터미널만 그것을 모른 채 다르게 세고 있었다. 알리지 않는 쪽이 오히려 장부를 둘로 두는 것이다.

### 자리는 `startInitialJobs` 다

`bubbletea` 는 `Init` 을 첫 model 에게만 부르고, 그 첫 model 이 normal 일 수도 빈 화면일 수도 있다. 두 `Init` 이 이미 `startInitialJobs` 하나를 부르고 있어서(ADR-0064) 거기 한 줄이 늘면 두 길이 같이 덮인다.

**`internal/terminal` 에 두지 않는다.** 그 패키지는 `tea.NewProgram` 보다 **먼저** 부르는 것들이다(ADR-0028) — stdin 을 raw 로 바꾸고 터미널의 답을 직접 읽는 자리다. 이것은 답을 읽지 않고, 대체 화면에 들어간 뒤에 유효해야 한다. `tea.Raw` 로 보내면 `bubbletea` 가 화면을 잡은 뒤에 쓴다. 나가는 바이트를 받아 확인했고 정확히 한 번 나간다.

### 지원 여부를 묻지 않는다

`DECRQM`(`\x1b[?2027$p`) 으로 물어볼 수 있고 `bubbletea` 에 `ModeReportMsg` 도 있다. 묻지 않는다.

**받지 않는 터미널은 이 escape 를 무시한다.** 물어서 갈라도 할 일이 같다 — 받으면 켜고, 안 받으면 켤 수 없다. 묻는 답을 기다리는 자리만 하나 늘고, 그 답이 오기 전에 그린 첫 화면은 어느 쪽 눈금인지 알 수 없게 된다.

받는 터미널: Ghostty(재서 확인), Contour(이 모드를 제안한 곳), foot, Windows Terminal. WezTerm·Kitty·Warp 는 요청이 올라와 있다. **tmux 3.6a 는 받지 않는다**(재서 확인).

### 끄는 자리를 두지 않는다

프로그램이 끝나면 `bubbletea` 가 대체 화면을 나가면서 터미널 상태를 되돌린다. `RUNEWIDTH_EASTASIAN`(ADR-0072) 과 달리 이것은 프로세스 밖에 남지 않는다 — 그쪽은 env 를 얹어 자기를 다시 실행하는 것이라 되돌릴 것이 없었고, 이쪽은 터미널에 켜는 것이라 화면을 나가면 함께 내려간다.

### 폭을 정하는 축이 둘이라는 것

**ADR-0072 와 다른 축이다.** 헷갈리기 쉬운 자리라 적어 둔다.

- **축 1 — 어느 표를 쓰는가**: `①` 같은 East Asian Width `Ambiguous` 글자를 한 칸으로 볼지 두 칸으로 볼지. ADR-0072 가 프로세스를 다시 시작해 `RUNEWIDTH_EASTASIAN` 을 켜는 것으로 맞춘 축이다
- **축 2 — 무엇을 한 글자로 묶는가**: 코드포인트인가 클러스터인가. 이 ADR 의 축이다

두 축이 독립이라 하나를 맞춰도 다른 하나가 남는다.

## 감수하는 것

**tmux 를 통하면 이득이 없다.** tmux 가 이 모드를 받지 않아서 그 안에서는 tmux 의 폭 계산이 적용된다. 다만 **tmux 는 이미 우리와 같은 답을 낸다**(ZWJ 를 두 칸으로 센다). 그래서 tmux 안에서는 원래 맞고 있었고, 이 변경의 이득은 터미널을 직접 쓸 때만이다.

**켜도 모든 어긋남이 사라지지 않는다.** spacing mark(`ि` U+093F) 는 2027 을 켜도 Ghostty 가 두 칸으로 센다. 클러스터로 묶는 것과 **그 클러스터의 폭을 몇으로 볼지**는 별개 판단이고, Ghostty 는 묶으면서도 spacing mark 의 폭을 따로 센다. 그 갈래는 목록에서 뺐다(docs/issues/0005).

**렌더러가 여러 rune 글자가 든 행의 마지막 칸을 빠뜨리는 것도 그대로다.** 폭과 무관한 별개 문제다(docs/issues/0005).

## 결과

- 터미널을 직접 쓸 때 ZWJ 로 이은 이모지가 우리가 세는 칸 수대로 그려진다. 큐레이션 표의 여섯 개와 본문에 넣은 것 전부다
- 우리 폭 계산과 터미널의 폭 계산이 같은 규칙을 쓴다. 장부가 하나가 됐다
- 받지 않는 터미널에서는 아무 일도 일어나지 않는다. 지금과 같다
- 시험은 `TestEnableGraphemeClusteringSendsMode2027` 이다
