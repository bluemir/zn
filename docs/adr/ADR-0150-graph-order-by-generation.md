# ADR-0150 커밋 기록은 자식이 모두 나간 커밋만 내보내고, 그것을 세대 번호로 가른다

- 상태: 채택
- 날짜: 2026-10-02
- 관련: ADR-0115(커밋 기록 화면, 조금씩 읽기), ADR-0141(git 의 그래프 알고리즘, 이 결정이 §3 의 전제를 되집는다), ADR-0042(go-git)

## 맥락

「다른 저장소에서 이미 merge 한 branch 가 zn 에서는 merge 안 된 것처럼 보인다. `git graph` 에서는 제대로 나온다」에서 시작했다.

재현하니 merge 와 그 둘째 부모가 커밋한 때가 초까지 같았다. 차례가 커밋한 때로만 정해지고 같으면 해시 순이라서, 해시가 작은 부모가 merge 위로 올라갔다. 그 부모는 branch ref 덕분에 처음부터 씨앗으로 큐에 있었다. 부모가 먼저 나가 버리니 merge 가 그 갈래를 받지 못하고 새 열을 열었다.

**같은 초만의 문제가 아니었다.** 시계가 틀려서 자식이 부모보다 이르게 커밋된 자리가 있으면 똑같이 깨진다. 공개 저장소에서 세어 보니 이런 자리가 흔했다. 아래는 「큐에 든 자식이 다 나갔는가」만 보고 내보냈을 때 부모가 자식보다 먼저 나간 횟수다.

| 저장소 | 커밋 | 부모가 먼저 나간 횟수 | 처음 난 행 |
|---|---:|---:|---:|
| zn·logbook·redzone-sector-0 | 191~426 | 0 | |
| prometheus | 21,130 | 0 | |
| grafana | 94,791 | 9 | 21,434 |
| kubernetes | 162,302 | 390 | 5,797 |
| linux | 1,484,278 | 327 | 4,343 |

ADR-0141 §3 은 「커밋한 때 내림차순은 git 의 `--date-order` 와 같다」고 적었다. **그 말은 시계가 맞을 때만 참이다.** git 의 `--date-order` 도 자식이 모두 나간 커밋만 내보내고, 커밋한 때는 그것들 사이의 차례일 뿐이다. 그러려면 자식 수를 세야 하고, git 은 commit-graph 파일이 없으면 범위 전체를 먼저 읽는다(`sort_in_topological_order`). ADR-0141 이 그 비용을 피하려고 고른 차례가 실은 다른 차례였다.

## 1. 자식이 모두 나간 커밋만 내보낸다

커밋마다 아직 나가지 않은 자식 수(`indegree`) 를 센다. 0 이 된 커밋만 차례(`queue`) 에 서고, 차례 안에서는 지금처럼 커밋한 때 내림차순이다.

**시계를 믿지 않는다.** 부모는 늘 자식 아래다. git 이 보장하는 것이 이것이고 우리 그림이 git 과 같아야 하는 까닭도 이것이다(ADR-0141 §2).

## 2. 어디까지 세는가는 세대 번호가 정한다

자식 수를 세려면 그 자식을 다 찾아야 한다. 기록 전체를 읽지 않고 그것을 아는 값이 세대 번호다. 뿌리가 1 이고 커밋마다 부모 중 가장 큰 값에 1 을 더한다. **자식은 늘 부모보다 크다.**

그래서 커밋 C 의 자식을 다 찾으려면 세대가 C 보다 큰 커밋까지만 내려가면 된다(`exploreTo`). 차례보다 앞서 내려가는 앞머리(`explore`) 를 세대 내림차순으로 두고, 커밋을 내보내기 전에 그 부모의 세대까지 내려간다. git 이 commit-graph 로 `--topo-order` 를 게으르게 내는 방법과 같다.

## 3. 세대 번호는 commit-graph 에서 읽고, 없으면 직접 센다

`.git/objects/info/commit-graph`(또는 `commit-graphs/` 의 chain) 에 세대 번호가 적혀 있다. go-git 이 이것을 읽어 준다(`plumbing/format/commitgraph/v2`).

- **파일에 있으면** 그대로 쓴다. 부모 목록도 거기서 읽어서 커밋 객체를 풀지 않는다
- **파일에 없으면** 부모의 세대를 먼저 세고 1 을 더한다
	- 파일을 쓴 뒤에 생긴 커밋이 그렇다. redzone-sector-0 은 426 개 중 32 개가 빠져 있었다
	- 옛 git 이 쓴 파일은 모든 커밋에 0 을 적었다. 0 은 모른다는 뜻으로 읽는다
- **파일이 아예 없으면** 첫 씨앗을 셀 때 기록 전체를 읽는다. 그 값이 남아서 그다음은 바로 나온다

파일은 `git gc` 가 쓴다. 갓 받은 clone 과 gc 가 돌지 않은 작은 저장소에는 없다. 재 본 저장소에서는 zn·logbook·llama.cpp·n3r/web-ui 와 갓 받은 clone 넷에 없었다.

**파일이 없어도 차례는 같다. 첫 화면이 늦을 뿐이다.** 정확함을 파일에 걸지 않는다.

## 4. 씨앗은 넣을 때가 아니라 꺼낼 때 가른다

ref 가 가리키는 커밋도 다른 ref 의 조상일 수 있다. 이번 버그의 `core-thread` 가 그랬다. git 은 시작할 때 가장 낮은 씨앗의 세대까지 내려가 세고 나서 씨앗을 가른다.

**그러면 오래된 tag 하나가 그 깊이를 기록 끝으로 끌어내린다.** 그대로 옮겼더니 commit-graph 가 있어도 linux 에서 148 만 개를 다 읽었다(12 초).

그래서 씨앗은 일단 차례에 넣고, 꺼낼 때 제 세대까지 내려가 아직 안 나간 자식이 있는지 본다. 있으면 차례에서 빼고, 마지막 자식이 나갈 때 다시 들어온다. 이렇게 바꾸니 linux 첫 1,000 개가 커밋 2 만여 개만 읽고 1.4 초에 나왔다.

## 5. 같은 시각은 git 처럼 먼저 들어온 것이 앞이다

예전에는 해시 순이었다. 어느 쪽이든 부모는 자식 아래라 그림은 맞지만, 같은 초에 커밋이 몰린 자리에서 git 과 차례가 달랐다. grafana 와 kubernetes 를 끝까지 견주어 처음 갈린 자리가 둘 다 이것이었다. 같은 초에 merge 를 여럿 받는 저장소(kubernetes 의 봇 merge) 에서는 드문 일이 아니다.

git 의 차례 큐(`prio_queue`) 는 커밋한 때가 같으면 넣은 순번(`ctr`) 으로 가른다. 먼저 넣은 것이 먼저 나온다. 그래서 순번만이 아니라 **들어오는 순간**도 git 과 같아야 한다. git 2.52 의 `revision.c`·`commit.c` 를 읽고 맞췄다.

- **씨앗은 ref 의 전체 이름순이다.** `--all` 은 `refs/` 아래를 이름순으로 넣고(`refs/heads/` → `refs/remotes/` → `refs/tags/`) 그다음 HEAD 를 넣는다. 같은 커밋이면 앞의 자리다. 날짜로 다시 줄 세우지만 안정 정렬이라 같은 초에서는 이 차례가 남는다
	- `origin/HEAD` 같은 상징 참조도 제 이름 자리에 든다. 이름표는 달지 않는다
	- 이름표의 차례(`--decorate`, HEAD → branch → tag → remote) 와 다르다
- **다른 씨앗의 조상인 씨앗은 마지막 자식이 나가는 순간 든다.** 우리는 씨앗을 처음에 다 넣어 두고 꺼낼 때 가르므로(§4), 그 순간에 빼서 뒤에 다시 꽂는다
- **부모는 마지막 자식이 나가는 순간, 그 커밋의 부모 차례대로 든다**

commit-graph 가 있을 때 git 이 타는 길(`init_topo_walk`) 과 없을 때의 길(`sort_in_topological_order`) 이 이 점에서 같은 차례를 낸다. 우리 쪽도 파일 유무와 상관없이 같다.

## 결과

첫 1,000 개가 나오기까지다. 이 Mac 에서 캐시가 데워진 상태로 쟀다.

| 저장소 | 커밋 | 바꾸기 전 | commit-graph 있음 | commit-graph 없음 |
|---|---:|---:|---:|---:|
| zn·logbook·redzone-sector-0 | 191~426 | 20~35ms | 38ms (redzone-sector-0) | 26ms (zn·logbook) |
| prometheus | 21,130 | 0.22s | 0.36s | 1.5s |
| grafana | 94,791 | 0.40s | 0.67s | 6.5s |
| kubernetes | 162,302 | 0.45s | 0.96s | 9.9s |
| linux | 1,484,278 | 0.42s | 1.4s | 83s |

비교 기준으로 git 이 `log --graph --all` 의 첫 줄을 내는 시간은 kubernetes 가 0.13s(commit-graph 없으면 0.75s), linux 가 2.7s(없으면 6.3s) 다.

- 네 공개 저장소를 끝까지 훑어 부모가 자식보다 먼저 나온 자리가 0 이다. kubernetes 는 commit-graph 없이도 확인했다
- 커밋 차례가 `git log --all --date-order` 와 끝까지 같다. prometheus·grafana·kubernetes·linux·llama.cpp·n3r/web-ui·zn·redzone-sector-0 이다. kubernetes 는 commit-graph 없이도 견줬다
- 같은 초에 만든 저장소로 차례를 git 과 견주는 시험을 두었다. 해시 순으로 되돌리면 실패한다
- 시계가 어긋난 저장소, commit-graph 가 있는 저장소, 낡은 저장소를 시험으로 git 과 견준다(`git-graph_test.go`)
- **commit-graph 가 없는 큰 저장소는 첫 화면이 몇 초에서 1 분 넘게 걸린다.** 그동안 `커밋 읽기` 작업이 돌 뿐 화면에 진척이 없다
- 기록 전체를 셀 때 커밋마다 세대와 부모를 들고 있는다. linux 에서 230MB 남짓이다

## 대안

- **커밋한 때로만 줄 세우기(그대로 두기)**
	- 여는 비용이 가장 적다
	- 이번 버그가 그대로 남는다
- **큐에 든 자식만 세기**
	- 비용이 없고 이번 버그(같은 초 + ref 씨앗) 는 막는다
	- 아직 찾지 못한 자식은 세지 못한다. 위 표의 위반이 이 방식으로 센 것이다
- **큐에 든 자식만 세다가 위반을 만나면 처음부터 다시 훑기**
	- 위반은 그 간선을 지날 때 정확히 드러난다
	- kubernetes 에서 390 번을 다시 읽는다
- **여는 순간 기록 전체를 읽어 자식 수를 세기**
	- 단순하고 정확하다
	- commit-graph 가 있어도 늘 기록 전체를 읽는다. 위 표의 「없음」 열이 모든 저장소에 든다
- **씨앗을 git 처럼 시작할 때 가르기**
	- git 과 똑같다
	- 오래된 tag 하나로 기록 끝까지 내려간다(§4)

## 이 ADR 이 정하지 않는 것

- **commit-graph 가 없을 때 진척을 보여주는 것.** 지금은 다 셀 때까지 빈 화면이다
- **`--all` 이 담는 ref 의 범위.** git 은 `refs/` 아래를 모두 담는다(`refs/stash`·`refs/notes/*`·`refs/pull/*` 따위). 다른 worktree 의 HEAD 도 담는다. 우리는 branch·tag·remote 와 HEAD 만이다
- **prometheus 에서 그림이 git 과 다른 것.** 커밋 차례는 같은데 81 번째 행부터 다르다. git 은 열을 `* / / /` 로 당기고 우리는 `* | | |` 로 둔다. 차례가 아니라 그리는 쪽(`git-graph-draw.go`) 의 일이다
- **`--topo-order`.** 이제 자식 수를 세므로 길은 열렸다. 차례를 바꿀지는 따로 정한다
