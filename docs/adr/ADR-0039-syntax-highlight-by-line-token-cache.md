# ADR-0039: 문법 강조는 줄 단위 토큰 캐시로 그리고, 색은 core 가 정한다

- 상태: 채택
- 날짜: 2026-08-20

## 맥락

본문에 색을 입히는 것이 둘뿐이었다 — 검색 매칭(ADR-0010) 과 visual 선택(ADR-0037). Go 소스를
열어도 keyword·문자열·주석이 본문과 같은 색이라, 편집기로 코드를 읽는 일이 `cat` 과 다르지 않았다.

`docs/tasks.md` 는 이것을 두 자리에 적어 두었다. 하나는 「언어 지원」 아래 golang·markdown 의
`syntax highlight` 이고, 다른 하나는 인터페이스 결정이다 — 「syntax highlight 는 어느 지점이
어떤 색이어야하는가만 buffer 에 알려주고, 어떻게 그 색이 산출되었는지는 editor 나 buffer 가
모르게 한다」.

정할 것이 넷 있었다. 무엇으로 훑는가, 그 결과를 어디에 담는가, 색을 누가 정하는가, 그리고
이미 있는 두 층과 어떻게 겹치는가.

## 결정

### 엔진은 직접 쓴다

언어별 lexer 를 손으로 쓴다. Go 는 표준 라이브러리 `go/scanner` 를 감싼다.

**chroma 를 쓰지 않는다.** 재보고 갈렸다.

| `internal/core/buffer.go` 896 줄 한 번 토큰화 | |
|---|---|
| chroma | 12.3 ms |
| `go/scanner` | 0.23 ms |

54 배다. 그런데 속도보다 결정적인 것은 **chroma 위에 캐시를 지을 수 없다**는 점이었다.
`chroma.LexerState` 는 exported 이고 `Stack []string` 도 exported 인데, `Tokenise` 가 그것을
돌려주지 않는다(`return state.Iterator`). 우리가 직접 `LexerState` 를 만들면 unexported
`options` 가 error 경로(`l.State != l.options.State`) 에서 nil 역참조로 죽는다. 즉 아래에서
고르는 「줄 단위 + 나가는 문맥」 구조를 chroma 로는 표현할 방법이 없다. 캐시가 반드시 필요한
속도인데 캐시를 못 짓는다.

바이너리도 15.2 MB 에서 21 MB 로 늘었다. `lexers` 패키지가 `//go:embed embedded` 로 언어
279 개를 통째로 넣기 때문이고, Go 와 markdown 은 하필 XML 이 아니라 Go 코드로 짜여 있어서
필요한 것만 골라 담을 수도 없다.

**tree-sitter 도 쓰지 않는다.** 캐시 구조는 가장 좋다 — 비용이 파일 크기가 아니라 편집 크기에
비례한다. 대신 CGO 가 붙는다. README 가 「plugin 도 설정 파일도 없어서 그 밖의 런타임 의존성이
없다. 결과물은 binary 하나다」 라고 적어 둔 자리와 부딪힌다.

### `internal/syntax` 는 색을 모른다

새 패키지가 「몇 번째 byte 가 어떤 갈래인가」까지만 말한다. 갈래→style 표는 `core` 에 있다
(`internal/core/style.go` 의 `styleSyntax`). tasks.md 가 정해 둔 경계가 이것이다.

계약은 넷이다.

```go
type Kind int
type Token struct { Start, End int; Kind Kind }
type State interface { Lex(line []byte) ([]Token, State) }
func Detect(path string) State   // nil 이면 강조하지 않는다
```

### 갈래는 열어 두고, 색표가 접는다

`Kind` 는 닫힌 집합이 아니다. 필요하면 늘린다.

늘리는 값이 싼 이유는 표가 갈래를 **색이 아니라 style 로** 옮기기 때문이다. 새 갈래가 기존
색을 그대로 쓰거나 굵기·기울임만 얹을 수 있어서, 갈래 하나가 팔레트에 색 하나를 요구하지
않는다. 지금 갈래는 열이고 색은 여덟이다 — 제목과 emphasis 가 keyword 색을 나눠 쓴다.

**이름은 그것이 무엇인지로 짓는다.** 어떤 색이어야 하는지로 짓지 않는다. 그래서 markdown
제목은 `KindKeyword` 가 아니라 `KindHeading` 이다. 언어 이름도 붙이지 않는다
(`KindMarkdownHeading` 아님) — 같은 개념이 언어 수만큼 갈라지면 색표가 어차피 그것을 다시
합치고, 갈라 둔 보람이 거기서 사라진다.

**갈래를 열어 두었다고 다 칠하지는 않는다.** markdown 의 목록 표시(`- ` `* ` `1. `) 는
일부러 뺐다 — 이 저장소의 markdown 은 거의 전부 목록이라 표시마다 색이 붙으면 글이 점으로
뒤덮인다. 갈래를 늘리는 값이 싼 것과 「늘려야 하는가」는 다른 물음이다.

### 굵기·기울임은 색 없이 쓰지 않는다

`KindHeading` 은 굵기 + keyword 색이고 `KindEmphasis` 는 기울임 + 같은 색이다.

굵기를 흉내만 내고 밝은 색으로 바꾸는 터미널이 있고, 기울임을 아예 안 그리는 터미널도 있다.
속성 하나에 뜻을 걸면 그런 곳에서 표시가 사라진다. ADR-0022 가 트리에서 굵기에 밑줄을 갈아타지
않고 *더한* 것과 같은 판단이다. 밑줄은 쓰지 않는다 — 같은 ADR 이 적어 둔 대로 lipgloss 가
글자마다 style 을 내서 본문에서는 escape 가 너무 길어진다.

굵기의 뜻이 트리와 본문에서 갈린다. 트리에서는 「지금 보고 있는 파일」(ADR-0022) 이고 본문에서는
제목이다. 둘은 칸이 갈려 있어서 한 화면에 같이 있어도 섞이지 않는다.

### 파서는 state pattern 이고, 나가는 문맥이 곧 캐시 키다

`State` 는 줄을 먹고 다음 문맥을 돌려준다. `command-parser.go` 의 `tokenizerState` 와 같은
모양인데 먹는 단위가 글자가 아니라 줄이다.

**구현은 반드시 `==` 로 견줄 수 있는 값이어야 한다.** `core` 가 나온 문맥을 캐시에 든 것과
견주어 다시 훑기를 멈춘다.

**`Language` enum 을 두지 않는다.** 시작 State 가 곧 언어다. 대가가 하나 있고 **이것은
정리하면 안 된다** — Go 와 js 가 `blockComment{}` 하나를 같이 쓰면 나가는 문맥이 다음 줄이
어느 언어인지 말하지 못한다. `goBlockComment`·`jsBlockComment`·`cssComment` 는 몸이 거의 같아도
따로 둔다.

### 캐시는 `Buffer` 가 들고, 무효화 자리는 한 곳이다

줄마다 토큰과 나가는 문맥을 담는다. `Buffer` 의 **값 필드**라, `newBuffer` 로 새로 열 때와
`Reload` 가 buffer 를 통째로 갈아끼울 때(`*buf = next`) 저절로 비워진다.

무효화는 `replaceLines`(`edit.go`) 에 한 줄이다. 그것이 `buf.lines` 를 갈아끼우는 유일한
함수이고, 제자리 수정은 undo 를 깨서(ADR-0001) 앞으로 편집 경로가 늘어도 그곳을 지나지 않을
수 없다. 편집·지우기·바꾸기·붙여넣기·줄끝공백·되돌리기까지 열넷이 이미 그 길이다.

**세는 값이 셋이다.** 셋 다 다른 사실이라 묶을 수 없다.

- `valid` — 지금 담아둔 토큰이 맞는 줄 수. 그리는 쪽이 이것만 믿는다
- `filled` — 한 번이라도 훑어서 `after` 가 뜻을 가지는 줄 수(최고 수위)
- `changedEnd` — 내용이 달라진 마지막 줄 다음

`valid` 와 `changedEnd` 를 묶으면 처음 훑을 때 파일 전체가 「달라진 것」이 되어 그 뒤 어떤
편집도 수렴을 볼 수 없다. 그리고 `changedEnd` 하나로는 부족하다 — `c` 는 지우기와 넣기가
각각 `replaceLines` 를 불러서 한 키가 떨어진 두 자리를 고친다.

`filled` 를 따로 두는 이유는 **색이 사라지기 때문**이다. 편집은 `valid` 를 고친 줄까지
끌어내리는데, 수렴했을 때 `valid` 를 「수렴한 자리 바로 뒤」까지만 올리면 화면에 보이는 그
아래 줄들이 아직 안 훑은 것으로 취급되어 색 없이 그려진다. 한 프레임에 한 줄씩만 되살아나서
눈에 띈다. 수렴하면 `valid` 를 `filled` 만큼 되돌려 놓는다 — 파일 끝까지가 아니다. 훑지 않은
줄을 맞다고 하면 같은 증상이 그 아래에서 난다.

**줄 수가 그대로인 편집은 캐시 slice 를 새로 만들지 않는다.** 타이핑 한 번이 거의 다 이
길이다. 갈아끼운 줄의 `after` 도 지우지 않는다 — 그 값이 「이 줄이 전에는 이렇게 끝났다」라서
수렴을 견주는 데 쓰인다. 지우면 고친 줄에서 멈출 수 없다.

### 훑는 자리는 그리는 길 하나다

`editorView` 가 화면 맨 아래 줄까지 채운다. receiver 가 `*editor` 로 바뀐다.

`Update` 마다 챙기는 길을 고르지 않았다. 화면이 움직이는 자리가 normal·insert·visual·sidebar·
palette·incsearch·휠로 일곱 곳이라, 빠뜨린 mode 에서 고리가 끊긴다 — ADR-0038 의 `fileTickMsg`
가 이미 그 대가를 보여줬다. 백그라운드 작업(ADR-0025, ADR-0027) 도 고르지 않았다. `Buffer` 를
쓰는 goroutine 이 늘 뿐이고 `apply` 는 어차피 `Update` 에서 돈다.

### 층 순서는 검색 > 선택 > 문법이고, 문법은 글자색만이다

`rowHighlight.segments` 가 위 층 사이의 빈 자리를 문법 색으로 메워 행을 빈틈 없이 덮는다.
지금 두 층을 펴던 함수는 `topSegments` 로 내려갔다.

문법은 배경을 정하지 않는다. 검색과 선택이 배경을 쓰고 있어서 겹치면 위 층의 경계가 보이지
않는다. 고른 자리가 문법 색을 잃는 것은 vim 도 같다.

## 근거

**측정이 갈랐다.** chroma 를 고르면 캐시가 필요한데 API 가 캐시를 막고, 직접 쓰면 캐시가
없어도 될 만큼 빠르다. 어느 쪽도 취향이 아니다.

**갈래와 색을 떼어 두면 언어를 더하는 값이 줄어든다.** 언어 하나가 늘 때 손대는 것은 파일
하나와 `languageRules` 한 줄이다. 색표도 그리는 코드도 그대로다.

**행을 조각으로 나눠 조각마다 style 을 한 번씩만 입히는 구조가 이미 있었다.** ADR-0020 이
공백 마커를 넣을 때 「앞으로 색이 하나 더 늘어도(문법 강조) 같은 방식으로 얹힌다」고 적어
두었다. 그 예고대로 얹혔다.

**무효화를 빠뜨릴 자리가 구조적으로 없다.** undo 가 이미 요구하는 규칙(제자리 수정 금지) 이
캐시가 요구하는 규칙과 같아서, 새로 지킬 것이 늘지 않았다.

## 결과

`internal/syntax` 가 새로 생겼다. 언어 여덟(go, markdown, html, js, css, python, makefile,
dockerfile) 이고 파일 하나가 언어 하나다. `internal/core` 쪽은 `syntax.go`(캐시) 와
`style.go`(색) 가 늘고, `render-row.go`·`editor.go`·`edit.go`·`buffer.go` 가 조금씩 바뀌었다.

**`style.go` 로 색을 모았다.** 새 갈래별 색과 함께, `search.go`·`selection.go`·`sidebar.go`·
`layout.go`·`render-row.go`·`view-palette.go`·`editor.go` 에 흩어져 있던 상수 열넷을 옮겼다.
이름은 그대로다. tasks.md 의 「색상 상수를 파일 하나로 모으기」가 여기서 닫힌다.

**본문에 256색 고정값이 들어왔다.** ADR-0004 가 「팔레트를 정하지 않는다」고 미뤄 둔 뒤
sidebar(ADR-0005)·줄번호(ADR-0007)·검색(ADR-0010)·공백(ADR-0020) 이 차례로 벗어났고, 이번이
마지막으로 남았던 본문이다. 밝은 테마와 어두운 테마 양쪽에서 읽히도록 밝기를 가운데로 모았지만
테마별 최적은 아니다. tasks.md 의 「팔레트를 정한다」는 이 ADR 이 닫지 않는다.

이후: **양쪽을 노린 것이 한쪽에서도 안 되는 값이 되었다.** 어두운 배경에서 본문 색 전부가
3.4~4.7:1 한 띠에 뭉쳐 계층이 사라졌고, 하필 가장 어두운 둘이 keyword 와 문자열이라 Go 의
`import` 문이 통째로 묻혔다. ADR-0041 이 어두운 배경 하나에 맞춰 다시 잡는다.

**「본문에 색이 없다」가 더 이상 성질이 아니다.** ADR-0007 과 `view-editor_test.go` 의 주석이
그것을 성질로 적어 두었어서 「강조하지 않는 확장자는 본문에 색이 없다」로 고쳤다. 시험 helper
`newTestEditor` 는 `test.txt` 를 그대로 쓴다 — 강조하지 않는 확장자라 글자를 그대로 견주는
단정이 전부 살아 있다. 경로를 받는 `newTestEditorFile` 을 형제로 두었다.

**`View` 가 상태를 고친다.** 지금 `View` 를 부르는 것은 bubbletea 하나이고 단일 goroutine 이라
문제가 없다. 다른 goroutine 에서 한 프레임을 그리는 길이 생기면 캐시 쓰기가 경쟁이 된다.

**갈래를 열어 둔 것이 곧 값을 냈다.** markdown 링크에 색을 주는 요청이 들어왔을 때 손댄 것이
`Kind` 에 `KindLink` 한 줄, 색표에 한 줄, markdown lexer 에서 갈래 이름 두 곳뿐이었다. 그리는
코드도 캐시도 다른 언어도 바뀌지 않았다. 색을 여덟에서 아홉으로 늘린 것은 이때가 처음이다 —
링크는 기존 색을 나눠 쓸 자리가 없었다(문자열 색으로 두면 문서에서 링크와 인용된 글자가 같아
보이는 것이 애초에 고치려던 것이다).

색표에 넣기를 잊으면 조용히 색이 없어지는 위험은 `TestEveryKindHasStyle` 이 실제로 잡는다.
색표에서 한 줄을 빼고 돌려 「갈래 11 에 색이 없습니다」로 떨어지는 것을 확인했다.

재본 비용은 이렇다(M4, 한 줄에 예약어·문자열·숫자·한글 주석이 든 Go 소스).

| | 10,000 줄 | 100,000 줄 |
|---|---|---|
| 타이핑 한 번의 lexing | 1.0 us | 1.0 us |
| 그때 `replaceLines` 가 쓰는 시간 | 55 us | 336 us |

lexing 은 파일 크기와 무관하다. 남은 비례 비용은 `replaceLines` 가 `buf.lines` 를 새 slice 로
담는 것인데 undo 가 요구하는 규칙이라(ADR-0001) 문법 강조가 들여온 값이 아니다. 차가운 캐시에서
`G` 로 뛰는 한 프레임만 파일 전체를 훑는다(1 만 줄에 12 ms).

감수하는 것

- **줄 수를 그대로 두고 한 줄의 내용만 `replaceLines` 없이 바꾸는 경로**는 길이 검사가 못
  본다. 그 경로는 undo 를 깨므로 이미 금지돼 있고 지금 없다.
- **차가운 캐시에서 `G` 로 뛰면** 파일 전체를 한 번 훑는다. 300 KB 에 수 ms 다. 거슬리면
  `lexSyntaxTo` 안쪽만 고치면 되고 부르는 자리는 그대로다.
- **언어마다 하지 않은 것이 있다.** js 의 정규식 리터럴, python 의 f-string 보간, markdown 의
  setext 제목, css 의 nesting 등이다. 반쯤 만들지 않고 tasks.md 에 남겼다.
- **Go 의 type 자리는 gofmt 에 기댄다.** 「식별자 둘이 공백만 두고 붙으면 뒤쪽이 type」이 기본
  규칙이고 이것은 Go 문법이 보장한다 — 표현식 사이에는 연산자나 구두점이 반드시 낀다. 다만
  포인터(`*Buffer`) 와 곱셈(`a * b`) 은 그 규칙으로 갈리지 않아서 **`*` 가 이름에 붙어 있는지**로
  가른다. gofmt 가 그렇게 쓰기 때문이고, gofmt 를 거치지 않은 소스에서는 곱셈이 type 으로 보인다.

## 대안

**한 언어당 갈래를 따로 두기**(`KindMarkdownHeading`, `KindHtmlTag` …) — 언어가 자기 어휘를
그대로 쓴다. 고르지 않은 이유는 색표가 어차피 여러 갈래를 같은 style 로 보내서, 갈라 둔 보람이
색에서 사라지기 때문이다. 개념 이름 하나로 두고 색표가 접는 쪽을 골랐다.

**갈래를 여덟으로 못 박기** — 결정할 것이 가장 적다. 고르지 않은 이유는 markdown 의 emphasis 가
그 여덟에 정직하게 들어갈 자리가 없어서다. 열어 두는 값이 「색표에 넣기를 잊으면 조용히 색이
없어진다」 하나뿐이고 그것은 시험으로 막힌다(`TestEveryKindHasStyle`).

**화면에 보이는 줄만 매 프레임 다시 훑기** — 캐시가 없어 가장 단순하다. 여러 줄에 걸친 주석·
문자열을 틀리게 그린다. 화면 위로 몇십 줄만 되돌아보는 보정도 재봤는데, 그보다 긴 코드펜스나
블록 주석 안에서 색이 어긋난다. vim 이 `:syntax sync minlines` 로 주는 knob 이 이것이고, vim
에서도 그것은 snapshot 캐시의 *보정*이지 본체가 아니다.

**파일 전체를 매 키마다 파싱** — 캐시도 무효화도 없다. `go/scanner` 라면 896 줄에 0.23 ms 라
실은 견딜 만하지만, markdown 처럼 훑는 값이 더 비싼 언어와 만 줄짜리 파일에서 무너진다.

**`revision` 카운터로 무효화** — 한 줄이면 된다. 키마다 파일 전체를 버려서 줄별 캐시의 뜻이
없어진다.

## 이 ADR 이 정하지 않는 것

- **코드펜스와 `<script>`·`<style>` 안을 그 언어로 훑는 것.** 이 저장소의 fenced block 30 개
  중 언어 이름이 붙은 것이 8 개, 그중 lexer 가 있는 것이 6 개다. 여섯을 위해 상태 공간을 언어
  수만큼 곱하지 않았다. 안쪽을 **색 없이** 두었으므로(문자열 색이 아니라) 나중에 위임이 들어와도
  되돌릴 것이 없다.

  이후: **셈이 틀렸다.** 상태 공간은 언어 수만큼 곱해지지 않는다 — 늘어난 것은 이미 있는 상태
  둘에 붙는 interface 칸 하나이고, 닫는 줄이 그 사슬을 통째로 버린다. ADR-0040 이 이 결정을
  뒤집는다. 다만 「안쪽을 색 없이 두었으므로 되돌릴 것이 없다」는 예측은 맞았다 — 위임을 넣으면서
  지운 코드가 없었다.
- **팔레트 전체와 테마별 색.** ADR-0004 에서 이어지는 결정이다.
- **`treeRow.style()` 과 `styleSyntax` 가 확장자 표를 둘로 든 것.** 트리는 묶음이 더 굵고
  일부러 다르다(`.html`·`.css`·`.js` 가 한 색, `.txt` 도 색이 있다). 합치면 lexer 를 더할 때마다
  트리 색이 조용히 바뀐다.
- **파일 내용으로 언어를 알아보는 것**(shebang). 지금은 이름만 본다.
- **강조를 켜고 끄는 것.** ADR-0020 이 공백 마커에서 두지 않기로 한 것과 같은 이유다.
