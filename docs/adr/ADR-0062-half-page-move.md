# ADR-0062 반 화면 이동(`ctrl+d`·`ctrl+u`)

## 맥락

먼 곳으로 가는 길이 `20j` 와 `42G` 뿐이었다. 둘 다 「몇 번째」를 알아야 하는 이동이라, 화면을 한 장씩 넘기며 훑는 손버릇은 휠밖에 없었다. 그런데 휠은 커서를 데려가지 않으므로 훑다가 편집하려면 커서를 다시 찾아 데려와야 한다.

vim 의 `ctrl+d`·`ctrl+u`(반 화면) 를 넣는다. 편집 영역(normal·visual) 과 트리 둘 다다. 사이를 오가는 손이 한 키를 두 벌로 기억하지 않아야 한다.

정해야 하는 것들:

1. motion 인가 홀로 서는 동작인가. 반 화면은 화면 높이가 있어야 정해진다
2. 화면만 굴리는가 커서까지 데려가는가. 휠이 이미 앞쪽이다
3. 반 화면을 무엇으로 세는가. 논리 줄인가 화면 행인가
4. 숫자 접두를 어떻게 받는가
5. 파일 끝에서 어디까지 굴리는가
6. 이동 뒤 커서의 가로 칸

## 결정

### 1. motion 이 아니라 홀로 서는 동작이다

`motion` 은 buffer 와 폭만 받는다(`move(buf, count, width)`, motion.go). 화면 높이는 그 계약에 없고, 넣으면 스물 몇 개 motion 이 전부 쓰지 않는 인자를 하나 더 받는다. 그래서 `actionHalfPage` 는 `standaloneAction` 쪽에 둔다. 동작은 `editor` 를 받으므로(ADR-0026) 거기서 `textHeight()` 를 본다.

**그래서 operator 뒤에는 올 수 없다.** `d ctrl+d` 는 아무것도 지우지 않는다. vim 도 반 화면을 operator-pending 의 motion 으로 받지 않으므로 손버릇이 갈리지 않는다.

visual 에서는 `visualAction` 이 같은 동작을 준다. 고른 범위는 anchor 와 커서로 정해지므로 (selection.go) 커서를 옮기는 것만으로 범위가 자란다. 이동 키가 그렇게 동작하는 것과 같다.

### 2. 화면과 커서를 같은 행 수로 옮긴다

`scrollBy`(휠) 는 화면만 굴리고 커서는 밀려날 때만 끝 행으로 데려온다(ADR-0012). 반 화면은 그 반대쪽이 필요하다. 화면이 반쪽 내려가고 커서가 화면 안 같은 자리에 남아야 훑는 손이 「지금 보는 곳」을 잃지 않는다.

새 메서드(`Buffer.moveHalfPage`) 를 두고 `scrollBy` 에 갈림길을 만들지 않았다. 커서를 데려갈지 말지가 flag 가 되면 그 함수 안에 두 동작이 겹쳐 산다.

**`scrollToCursor` 를 부르지 않는다.** 그것은 커서를 좇아 top 을 **최소한으로** 당기는 것이라, 반 화면 굴린 뒤에 부르면 그 반쪽이 한 행으로 줄어든다. 대신 `moveHalfPage` 안에서 `scrollTo` 를 한 번 부른다. 커서와 화면을 같이 옮겼으니 할 일이 없고, 머리줄(ADR-0049) 이 커서를 덮은 자리만 맞춘다.

### 3. 세는 것은 화면 행이다

반 화면은 눈에 보이는 절반이다. wrap 된 긴 줄이 화면을 다 차지하면 그 줄 안에서 움직이는 것이 맞다. `↓` 와 같은 단위이고 `j` 와는 갈린다(ADR-0006).

옮기는 것은 `advanceRows`·`retreatRows` 로 한다. 한 행씩 되풀이하는 `moveDown`·`moveUp` 은 파일 끝에 닿아도 남은 횟수를 다 돌아서, 숫자 곱 반 화면인 여기서는 그 횟수가 크게 자란다.

### 4. 숫자는 되풀이다

`3ctrl+d` 는 반 화면 세 번이다. 트리의 `20j` 와 같은 「숫자는 되풀이」 규칙이라 새로 기억할 것이 없다.

vim 은 `10ctrl+d` 의 숫자를 `scroll` 에 **기억해** 다음 `ctrl+d` 까지 바꾼다. 따르지 않는다. 설정 파일도 `:set` 도 없는 지금(docs/tasks.md) 그 기억은 아무 데도 보이지 않는 상태 하나가 느는 것이고, 손이 한 번 친 숫자를 화면 어디에서도 확인할 수 없다.

### 5. 파일 끝에서는 마지막 줄이 화면 맨 아래에 오는 데까지다

거기서 화면이 멈추고 커서만 마지막 줄로 간다. vim 의 `ctrl+d` 와 같다.

그 뒤로도 굴릴 수 있게 하면(vim 의 `ctrl+e` 가 그렇다) 눌러도 새로 보이는 것 없이 빈 행만 는다. 이동 키가 「눌렀는데 아무것도 안 보인다」로 끝나는 경우를 만들지 않는다. 휠은 이 한계를 두지 않는다. 마지막 줄을 위로 올려 보는 것은 눈으로 훑는 일이라 그쪽 손에 맡긴다.

### 6. 가로 칸은 지킨다

`placeCursorInRow` 로 놓아 `desiredCol` 을 살린다. `j`·`k`·휠이 이미 그렇다.

vim 은 `startofline` 이 기본으로 켜져 있어 반 화면 이동 뒤 커서가 줄의 첫 비공백으로 간다 (neovim 은 기본이 꺼져 있다). 따르지 않는 것은 이 편집기에 그 설정이 없기 때문이다. 끌 수 없는 채로 두면 「이동하면 칸은 살아남는다」는 규칙에 예외가 하나 생긴다.

### 7. 트리도 같은 규칙이다

`sidebar.moveHalfPage` 가 고른 항목과 `top` 을 같은 수만큼 옮긴다. 트리는 줄을 접지 않으므로 한 항목이 한 행이고, 화면 행과 항목 번호가 같은 수다. 파서는 손대지 않았다. `ctrl+d` 는 접두 키가 아닌 키 하나라 이미 이름 그대로 올라오고 숫자도 실려 온다(ADR-0059).

## 결과

- 편집 영역과 트리에서 `ctrl+d`·`ctrl+u` 로 반 화면씩 훑는다. 커서가 따라오므로 멈춘 자리에서 바로 편집한다
- 화면 높이를 보는 동작이 처음 생겼다. motion 은 여전히 높이를 모르고, 높이가 필요한 것은 `action` 쪽에 둔다는 것이 이것으로 정해졌다
- 트리에서 숫자를 보는 이동이 넷에서 여섯이 되었다(ADR-0059 의 표)
- `visualAction` 이 count 를 받는다. visual 에서 숫자를 보는 동작이 처음이라 그 인자가 없었다
- tip 한 줄이 늘었다(ADR-0061 의 규칙)
- `H`·`M`·`L`(화면 위·가운데·아래) 과 `zz`·`zt`·`zb` 는 아직 없다. 그 둘은 화면 안 자리를 가리키는 것이라 이 결정과 다른 물음이다(docs/tasks.md)
