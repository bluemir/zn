# ADR-0045: `:!` 는 터미널을 셸에 넘기고, Enter 로 돌아온다

- 상태: 채택
- 날짜: 2026-08-21

## 맥락

셸 명령 하나를 돌릴 길이 `ctrl+z` 뿐이었다. `go test` 를 돌려보려면 프로세스째 내려가서
셸에서 치고 `fg` 로 올라온다. ADR-0023 이 그 길을 만들면서 마지막 줄에 이렇게 적어 두었다 —
*"`:!<shell command>` 로 셸 명령 하나만 돌리는 것. 셸로 내려가는 것과 목적이 겹치지만 별개다"*.
ADR-0011 도 팔레트의 `!` 접두를 정하지 않은 것으로 남겼고, `README.md` 의 roadmap 과
`docs/tasks.md` 의 세 항목이 같은 자리를 가리키고 있었다.

정할 것이 넷이다.

1. **명령을 어떻게 돌리고 출력을 어디에 보이는가.** 이 편집기에는 출력을 담을 자리가 없다 —
   알림은 statusBar 아래 한 줄이고, 여러 줄을 보여주는 화면은 `:jobs` 목록 하나다
2. **파싱.** 명령줄은 `이름[!] [인자 ...]` 이고 인자를 따옴표·`\` 로 뜯는다. 셸에 넘길 줄은
   **뜯으면 안 된다** — 따옴표를 읽는 것은 셸이다
3. **팔레트에서 들어가는 길**
4. **어느 셸로 돌리는가**

## 결정

### 터미널을 셸에 넘긴다. vim 의 `:!` 와 같다

`tea.Exec` 로 대체 화면을 나가고, 명령이 터미널에 직접 쓴다. 편집기는 그동안 멈춰 있다.
`git commit`·`less`·`htop` 처럼 화면과 stdin 을 쓰는 명령도 그대로 돈다 — 물려주는 것이
파이프가 아니라 터미널 그 자체이기 때문이다.

**출력을 저장하지 않는다.** 화면에 흐르고 지나간다. 그래서 새 mode 도, 출력을 담을 자료구조도,
스크롤도 없다. 이 결정으로 늘어나는 상태가 하나도 없다.

### 끝나면 Enter 를 기다린다

명령이 끝난 자리에서 `계속하려면 Enter 를 누르세요` 를 찍고 한 줄을 읽는다. 여기서 멈추지
않으면 **돌아가는 순간 대체 화면이 출력을 덮는다** — bubbletea 가 터미널을 돌려줄 때 alt screen
을 나갔다가 복귀하며 다시 들어가기 때문에, 그 사이에 사람이 읽을 틈이 없으면 출력이 있었다는
것조차 모른다. vim 의 「Press ENTER or type command to continue」가 있는 이유가 이것이다.

그래서 `tea.ExecProcess`(exec.Cmd 를 그대로 넘기는 것) 를 쓰지 않고 `tea.ExecCommand` 를 직접
구현한다(`shellRun`). 멈춰 서는 자리를 만들 수 있는 곳이 `Run` 안뿐이다.

**출력이 없어도 묻는다.** 규칙이 하나여야 한다. 묻지 않으려면 출력이 있었는지를 세어야 하고,
그러면 출력을 가로채는 겹이 하나 생긴다 — 지금 그것을 넣지 않는 것이 이 결정의 핵심이다.

**무엇이 돌았는지 먼저 찍는다.** `:!<친 것>` 을 한 줄 내고 시작한다. 셸 화면에는 이전에 돌린
것들이 그대로 남아 있어서, 출력만 있으면 어느 명령의 것인지 갈리지 않는다.

### 파싱은 상태 기계 둘이다

**맨 앞의 `!` 는 위치가 곧 뜻이다.** `:!ls -la` 의 `!` 는 "뒤를 통째로 셸에" 이고,
`:w !foo` 의 `!` 는 파일 이름의 첫 글자다. 그 갈림을 아는 자리는 **첫 상태를 고르는 자리**라서,
글자 단위 기계의 시작 상태를 `tokenPlain` 에서 `tokenHead` 로 바꾼다. `tokenHead` 가 `!` 를
보면 `!` 를 토큰 하나로 끊고 `tokenRest` 로 넘어가, 나머지를 **한 토큰**으로 통째로 준다.
공백도 따옴표도 `\` 도 전부 글자다.

`tokenRest` 는 끝날 수 없는 자리가 없다. 그래서 `:!echo "닫히지 않은` 이 오류가 아니다 —
따옴표를 읽는 것은 셸이고, 셸이 자기 문법으로 알린다.

**토큰에서 command 를 만드는 단계에도 상태 기계를 넣는다.** `docs/tasks.md` 는 이 단계를
*"지금은 '첫 토큰이 이름, 나머지가 인자' 로 끝나서 필요하지 않다. 범위 문법(`:1,5d`) 을 넣을 때
다시 본다"* 며 미뤄 두었는데, `:!` 가 그 필요를 지금 만든다 — **첫 토큰이 `!` 인지에 따라 다음
토큰의 뜻이 갈린다**(이름 뒤의 인자냐, 뜯지 않은 셸 줄이냐). 평평한 함수에 두면 토큰이 다 나온
뒤에 `tokens[0]` 을 다시 들여다보는 자리가 되고, 그것이 ADR-0034 가 지운 「파싱이 세 겹」이다.

상태는 셋이다. `commandName`(첫 토큰을 기다린다. 이름과 force 를 가르는 것도 여기다) →
`commandShell`(`:!` 뒤를 기다린다) → `commandArgs`(나머지를 인자로 모은다). 범위 문법은
`commandName` **앞에** 상태가 하나 붙는 자리가 된다.

`end` 는 오류를 내지 않는다. 세 상태 모두 끝날 수 있는 자리이고, 끝나면 안 되는 것(닫히지 않은
따옴표) 은 글자 단위 쪽이 이미 막았다.

**`command` 에 필드는 늘지 않는다.** 셸 줄은 `args[0]` 이다. `tokenRest` 가 한 토큰으로 주므로
「첫 토큰이 이름, 나머지가 인자」가 그대로 맞는다.

### 팔레트는 `!` 접두다

`>` 가 명령 목록인 것과 같은 결이다. 별도 키도 상태도 아니고, 맨 앞 글자를 지우면 파일 찾기로
저절로 돌아온다. 갈래를 `paletteKind`(`File`·`Command`·`Shell`) 로 세워서, `>` 하나만 보던
2 갈래 함수가 3 갈래가 되는 것을 type 이 받게 했다.

**셸 갈래에는 고를 목록이 없다.** 후보가 비어 있어서 거르는 코드는 이 갈래를 몰라도 되고,
목록 자리에는 안내 한 줄이 들어간다(`! 뒤에 셸 명령을 칩니다` / `Enter 로 셸에서 실행합니다`).
statusBar 아래 줄의 `걸린 수/전체 수` 는 비운다 — `0/0` 은 아무것도 못 찾은 것처럼 보인다.

**`>` 목록에 「셸 명령 실행」항목을 넣지 않았다.** 한 기능에 진입점 하나라는 ADR-0011 의 태도이고,
`!` 가 이미 그 진입점이다.

### `$SHELL -c` 로 돌린다. 없으면 `sh -c`

vim 의 `shell` 옵션 기본값과 같다. 사용자가 쓰는 셸에 넘겨야 그 셸의 문법으로 친 것이 돈다.

### `ctrl+c` 는 명령에 가고 편집기는 살아남는다

`:!` 가 도는 동안 터미널은 cooked mode 라 `ctrl+c` 가 **진짜 SIGINT** 가 된다. 그런데
`cmd/main.go` 가 `signal.NotifyContext` 로 SIGINT 를 root ctx 에 이어 두고 있어서, 도는 명령을
끊는 손짓 한 번에 편집기가 통째로 끝났다 — tab 구성과 undo 이력이 같이 사라진다. `ctrl+z` 가
그것을 지키려고 만들어진 것인데(ADR-0023) `:!` 가 그 자리에 구멍을 낸다.

**그래서 SIGINT 를 root ctx 에서 뺀다.** 편집기가 도는 동안 터미널은 raw mode 라 `ctrl+c` 는
신호가 아니라 글자로 오고, 종료 확인창은 그 **키**가 띄운다. 신호로 오는 SIGINT 는 bubbletea 가
이미 처리한다(`InterruptMsg` → 종료) 그리고 `Exec` 가 도는 동안에는 스스로 무시한다.
`NotifyContext` 에는 SIGTERM 만 남는다.

**끊긴 것은 실패로 알리지 않는다.** 신호로 끝난 프로세스는 종료 코드가 없어서 -1 이고, 그때는
아래 줄에 아무 말도 남기지 않는다. 그만하라고 한 사람이 결과를 이미 안다 — `:jobs` 의 취소가
조용한 것과 같은 규칙이다(ADR-0027).

### 돌아와서 보는 것

**실패만 알린다.** 종료 코드가 0 이 아니면 `셸 명령이 실패했습니다: exit status 1` 을 아래 줄에
남긴다. 출력에 이유가 섞여 있어도 종료 코드는 눈에 안 띈다. 성공은 조용하다 — 방금 화면에서 보고
Enter 로 넘어온 것이라 다시 말할 것이 없다.

**보고 있는 파일을 다시 검사한다.** 셸에 다녀오는 이유의 대부분이 파일을 바꾸는 일이다.
`ctrl+z` 복귀·터미널 포커스 복귀와 같은 자리이고(ADR-0023, ADR-0031) 잃을 것이 없으면 그대로
가져온다(ADR-0038). git 은 여기서 읽지 않는다 — 주기 갱신이 따라온다(ADR-0030).

돌아갈 곳은 언제나 normal 이다. 팔레트에서 시작해도 그렇다 — 팔레트가 어디서 열렸는지 기억하지
않는 것과 같은 태도다(ADR-0011).

## 근거

### 왜 작업(job) 으로 돌리지 않는가

이 저장소에는 비동기 바탕이 이미 있다(ADR-0025, ADR-0027). `:!` 를 작업으로 돌리면 편집기가
멈추지 않고 `:jobs` 에서 `x` 로 취소된다. 그런데 값이 셋 붙는다.

**출력을 담을 자리를 새로 만들어야 한다.** `:jobs` 는 상태만 보여주고, 산출물로 들어가는 길이
없다는 것은 ADR-0027 이 감수 사항으로 적어둔 그대로다. 스크롤되는 텍스트 화면은 하단 pane 결정
(register 보기·quickfix 와 같은 자리) 에 걸린 큰 결정이다.

**대화형 명령이 통째로 빠진다.** stdin 이 없으면 `git commit` 은 편집기를 못 띄우고 `less` 는
막힌다. 셸에 내려가서 하는 일의 절반이 그런 것들이다.

**출력을 우리가 해석하게 된다.** 색 escape 가 든 출력을 우리 화면에 그리려면 폭을 재고 잘라야
한다. 터미널에 그대로 흘리면 그 일이 아예 없다.

### 왜 statusBar 한 줄로만 알리지 않는가

가장 작다. 그런데 `:!ls` 가 쓸모없어진다 — 셸 명령을 돌리는 이유의 대부분이 출력을 보는 것이다.
그러면 남는 것은 "돌렸고 성공했다" 뿐이고, 그것만 원한다면 `ctrl+z` 로 내려가는 것이 낫다.

### 왜 `!` 를 tokenizer 의 상태로 두는가

`parseCommand` 앞에서 `strings.CutPrefix(input, "!")` 로 잘라내는 길이 세 줄로 끝난다. 그런데
그러면 tokenize 를 지나지 않는 입력이 하나 생긴다 — 파싱의 입구가 둘이 되고, 나중에 범위 문법
(`:1,5d`) 이 앞자리에 붙을 때 "그건 `!` 갈래에도 되나" 를 매번 물어야 한다.
위치에 따라 뜻이 갈리는 글자를 다루는 것은 상태 기계가 하는 일 그 자체이고, 그 자리가 이미 있다.

### 왜 `args[0]` 이고 `shell` 필드가 아닌가

셸 줄을 담는 필드를 따로 두면 `command` 에 "이름이 `!` 일 때만 차는 자리" 가 생긴다.
`tokenRest` 가 뒤를 한 토큰으로 주는 덕에 그럴 필요가 없다 — 「첫 토큰이 이름, 나머지가 인자」가
그대로 맞고, 인자가 하나라는 것이 `:!` 의 성질이 된다. 대신 `args` 의 뜻이 자리마다 갈리는
것은 주석으로 적었다.

### 왜 이것이 `internal/core` 의 첫 `os/exec` 인가

ADR-0042 가 git 을 프로세스에서 라이브러리로 옮겼다. 그 결정의 근거는 "우리가 아는 일을 프로세스로
띄우지 말자" 였다 — index 를 읽는 것은 우리가 할 수 있는 일이었다. 여기는 반대다. 사용자가 시킨
남의 프로세스이고, 대신할 수 있는 것이 아무것도 없다. 두 결정은 어긋나지 않는다.

## 결과

좋은 점

- 셸 명령 하나를 편집기 안에서 돌린다. tab 구성·트리·undo 이력을 잃지 않는다
- 대화형 명령이 그대로 돈다. `git commit`·`less`·대화형 rebase 까지 터미널을 그대로 쓴다
- 늘어난 상태가 없다. 새 mode 도, 출력 저장소도, 스크롤도 없다
- 셸에 넘길 글자를 우리가 뜯지 않는다. 따옴표·파이프·리다이렉트·glob 이 전부 셸 문법 그대로다
- 파싱이 상태 기계 둘로 모였다. 범위 문법이 붙을 자리가 코드에 생겼다
- `:!` 로 파일을 고치면 돌아오는 자리에서 그것을 안다. 자동 다시 읽기(ADR-0038) 가 이어진다
- `ctrl+c` 로 도는 명령만 끊긴다. 편집기를 죽이던 구멍이 같이 막혔다

감수하는 것

- **출력이 남지 않는다.** Enter 를 누르면 사라진다. 다시 보려면 다시 돌린다
- **출력이 없는 명령도 Enter 를 묻는다.** `:!git add .` 이 한 번 더 손이 간다
- **도는 동안 편집기가 멈춘다.** 오래 걸리는 것은 `ctrl+z` 로 내려가서 도는 편이 낫다
- **`:jobs` 에 남지 않는다.** 취소도 목록도 `:jobs` 가 아니라 터미널의 `ctrl+c` 다
- **`!` 로 시작하는 파일은 팔레트에서 못 찾는다.** `>` 가 이미 지고 있는 것과 같은 빚이다
- **SIGINT 로 편집기를 끝낼 수 없게 되었다.** raw mode 에서는 원래 신호로 오지 않았고 다른
  창에서 보내는 경우만 갈린다. `kill`(SIGTERM) 은 그대로 듣는다
- **`internal/core` 에 `os/exec` 가 들어왔다.** 프로세스를 띄우는 자리가 다시 생겼다

## 대안

**작업으로 비동기 실행 + 출력 화면** — 편집기가 멈추지 않고 `:jobs` 에서 취소된다. 출력을 담을
화면이 새로 필요하고 대화형 명령이 빠진다. 출력을 편집기로 가져오는 것(`docs/tasks.md`) 을
정할 때 이쪽을 다시 본다.

**비동기 + statusBar 한 줄** — 가장 작다. 출력을 보려고 치는 명령이 쓸모없어진다.

**출력이 없으면 Enter 를 묻지 않기** — 손이 덜 간다. 출력을 세려면 가로채는 겹이 하나 생기고,
규칙이 "때에 따라 다르다" 가 된다.

**buffer 로 출력을 열기(`:r !cmd` 결)** — 결과를 편집하고 저장할 수 있다. 셸 명령을 돌리는 것과
결과를 들여오는 것은 별개 결정이라 `docs/tasks.md` 에 남긴다.

**`sh -c` 고정** — 어디서든 같은 문법이다. 사용자의 zsh 문법(`**/`, `=(...)`) 이 안 먹는다.

**셸 없이 토큰을 그대로 exec** — 프로세스가 하나뿐이고 인용 문제가 없다. 파이프·리다이렉트·glob·
환경변수 전개가 전부 안 되어서 `:!` 로 하려는 일의 절반이 막힌다.

**`!` 를 `parseCommand` 에서 문자열로 잘라내기** — 세 줄로 끝난다. 파싱의 입구가 둘이 된다.

**팔레트 `>` 목록에 항목 하나** — 팔레트 구조를 안 건드린다. 고른 뒤 `:!` 가 채워진 명령줄로
넘기게 되어, 한 기능에 진입점이 셋(`:!`·`>`·명령줄) 이 된다.

## 이 ADR 이 정하지 않는 것

- `:!cat %` 의 `%` 를 보고 있는 파일 경로로 바꾸는 것
- 셸 명령의 출력을 buffer 로 가져오는 것(`:r !cmd`) 과 buffer 를 명령에 넘기는 것(`:%!sort`)
- `:!!`(마지막 셸 명령 되풀이). 지금은 `!` 를 셸에 넘긴다
- 셸 명령을 `:jobs` 에서 보고 취소하는 것. 비동기 실행을 정할 때 같이 본다
- 출력이 없고 성공했으면 Enter 를 묻지 않을지
