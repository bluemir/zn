# ADR-0030: git 표시는 5 초마다 백그라운드 작업으로 다시 읽는다

- 상태: 채택 (주기를 재는 방식은 ADR-0043 이 cooldown 으로 바꿨고, 읽는 방법은 ADR-0042 가 바꿨다)
- 날짜: 2026-08-14

## 맥락

ADR-0009 는 git 표시를 **편집기를 열 때·파일을 열 때·저장할 때만** 읽기로 하고 주기적 갱신을
명시적으로 기각했다. "편집만 하고 있어도 계속 프로세스가 뜬다" 는 것이 그 이유였고, 대가로
"편집기를 띄워둔 채 다른 터미널에서 `commit`·`checkout` 을 하면 다음에 파일을 열거나 저장할
때까지 낡은 값이 보인다" 를 적어 두었다. ADR-0023 이 `ctrl+z` 로 내려갔다 올라오는 길을 메웠지만
편집기를 띄워둔 채 옆 터미널에서 일하는 경우는 그대로 남아, `docs/tasks.md` 에 열린 채였다.

그 사이 두 가지가 바뀌었다.

**비동기 작업 바탕이 생겼다(ADR-0025, ADR-0027).** ADR-0009 이 재던 저울에서 git 호출은
`Update` 안에서 도는 동기 호출이었다. 주기를 붙이면 몇 초마다 편집기가 멈칫한다는 뜻이었다.
지금은 goroutine 에서 돌리고 결과만 msg 로 받을 수 있고, 작업마다 ctx 가 있어 편집기를 끝내면
프로세스까지 정리된다.

**낡은 값이 실제로 거슬렸다.** branch 는 몇 시간에 한 번 바뀐다고 적었지만, 옆 터미널에서
`checkout` 하고 편집기로 눈을 돌리는 흐름에서는 표시가 틀린 채로 한참 남는다. 틀린 표시는
표시가 없는 것보다 나쁘다. 다른 branch 인 줄 모르고 고치지 않게 하려고 넣은 표시다.

## 결정

**5 초마다 다시 읽는다.** 저장소가 아니어도 돈다.

**읽기는 job 시스템에 올린다(ADR-0025, ADR-0027).** 이름은 `git 상태` 하나다. 같은 이름은 한 번에
하나만 돌므로 앞 갱신이 안 끝났으면 그 tick 은 새로 시작하지 않고 지나간다. 다른 작업과 똑같이
`:jobs` 목록에 보이고 statusBar 진행 표시에도 그대로 찍힌다. 예외를 두지 않는다.

**tick 을 잇는 자리는 `handleJob` 한 곳이다.** mode 마다 두는 `case jobProgressMsg, jobDoneMsg,
gitTickMsg:` 가 여기로 넘긴다. 첫 고리는 `viewEditorNormal.Init` 이 건다.

**이벤트 시점 갱신은 저장 직후와 파일을 열 때만 남긴다.** `:w`·`:wq`·`:x`·`:w <파일>` 과
`:tabnew <파일>`·`:e <파일>`·트리 Enter·팔레트다. `:e` 로 같은 파일을 다시 읽을 때와 셸에서
올라올 때 읽던 것은 지운다. `gt`·`gT` 로 tab 을 오가는 것에는 붙이지 않는다. ADR-0009 가 정한
그대로다.

**갱신을 발행하는 것은 `openTab`·`replaceTab` 이 아니라 그것을 부르는 mode 쪽이다.** 여는 함수는
지금까지처럼 `error` 만 돌려주고, 호출자가 `tea.Batch(cmd, e.startGitRefresh())` 로 같이 낸다.

**첫 읽기도 비동기다.** 편집기가 뜨는 길에는 git 이 없다. 첫 화면의 statusBar 오른쪽은 잠깐 비어
있다가 채워진다.

**끝난 작업 목록은 이름당 마지막 결과 하나다.** 개수 상한(ADR-0027 의 스무 개)은 없앤다.

## 근거

### 왜 주기가 5 초인가

**옆 터미널에서 `checkout` 하고 편집기로 눈을 돌리는 사이보다 짧다.** 그보다 길면 눈이 먼저
닿아서, 낡은 값을 한 번은 읽게 된다.

**유휴 상태에서 뜨는 프로세스가 분당 서른여섯 개다.** ADR-0009 이 걱정한 것은 이 부담 자체가
아니라 그것이 **키 입력 경로에 붙는 것** 이었다. 작업으로 내리면 그 경로에는 아무것도 없다.
남는 것은 유휴 상태의 CPU 인데, `git status` 세 번은 편집기가 화면을 다시 그리는 것과 같은 자릿수다.

### 왜 늘 도는가

**저장소 밖에서도 `git init` 을 하고 돌아올 수 있다.** "저장소가 아니면 tick 을 안 건다" 로 하면
그 뒤로 영영 안 뜬다. 저장소 밖에서 `git rev-parse` 는 바로 실패해서 값이 가장 싸다. 아낄 것을
아끼려다 못 따라오는 경우를 만드는 셈이다.

**유휴일 때만 도는 것도 보지 않았다.** 마지막 키 시각이라는 상태가 늘고, 계속 편집하는 동안에는
갱신이 아예 멈춘다. 정작 오래 켜 두는 경우가 그 경우다.

### 왜 job 시스템인가

**ctx 와 중복 방지가 이미 있다.** 작업마다 ctx 가 갈라져 나와서 편집기를 끝내면 도는 `git status`
프로세스까지 끊긴다(ADR-0027). 같은 이름은 하나만 도는 규칙이 그대로 "느린 저장소에서 갱신이
겹쳐 쌓이지 않는다" 가 된다. 따로 만들면 이 둘을 다시 구현한다.

**보이는 것이 정직하다.** 큰 저장소에서 5 초마다 `git status` 가 돈다는 사실은 감출 것이 아니라
`:jobs` 에서 보이는 편이 낫다. 느리다고 느낄 때 어디를 볼지가 정해진다.

**statusBar 진행 표시에 예외를 두지 않는다.** `renderJobText` 는 가장 먼저 시작한 작업을 찍으므로,
파일 인덱싱이 도는 중에 낀 git 갱신은 `(+1)` 로만 세어지고 표시를 가로채지 않는다. 혼자 돌 때만
잠깐 `git 상태` 가 뜬다. 느린 저장소에서는 그것이 오히려 지금 무엇을 기다리는지 알려준다.
예외를 만들면 "job 인데 진행 표시에는 안 나오는 것" 이라는 규칙이 하나 는다.

### 왜 tick 을 잇는 자리가 한 곳인가

**두 곳에서 예약하면 고리가 갈라진다.** tick 을 받은 mode 마다 새로 걸면 mode 를 옮길 때마다
주기가 반으로, 다시 반으로 줄어든다. 반대로 한 mode 라도 흘려보내면 아무도 예약하지 않아 갱신이
조용히 멈춘다. 작업 msg 를 mode 마다 한 자리에 모아 공용 처리로 넘기는 방식이 이미 있어서
(ADR-0025) 거기에 붙였다. `case` 목록에 `gitTickMsg` 가 같이 적혀 있어 그 mode 가 무엇을 받는지도
그대로 보인다.

**`Init` 은 프로그램이 시작할 때 한 번만 불린다.** mode 는 model 을 갈아끼워 나타내지만(ADR-0002)
`Init` 은 처음 model 에게만 간다. 고리를 거는 자리로 이보다 확실한 곳이 없다.

### 왜 저장 직후와 파일 열기는 남기는가

**저장은 dirty 를 바꾸는 유일한 편집기 안의 동작이다.** 내가 방금 한 일의 결과가 5 초 뒤에
나타나면 편집기가 굼떠 보인다.

**파일을 여는 것은 바깥에서 무언가 하고 돌아온 직후일 때가 많다.** ADR-0009 이 이 시점을 고른
이유가 그대로 살아 있다. 값이 바뀌는 자리는 아니지만, 편집기를 계속 띄워두고 쓰는 흐름에서
사람이 화면을 새로 보는 자리다. 거기서 낡은 branch 를 한 번 읽고 지나가는 것이 5 초의 대가다.

**셸 복귀와 `:e` 다시 읽기는 뺐다.** 두 자리 모두 "무언가 있었을 **만한** 자리" 를 짚은 것이고,
그 역할은 주기 갱신이 통째로 대신한다. 특히 셸에서 올라오는 길은 내려가 있는 동안에도 tick 이
돌아서, 올라온 시점에는 이미 맞아 있는 경우가 많다.

### 왜 여는 함수가 아니라 부르는 쪽인가

**`openTab` 이 Cmd 를 돌려주게 해도 호출자 코드가 줄지 않는다.** 어느 쪽이든 호출자는
`tea.Batch` 를 써야 한다. 다른 점은 그 자리에 `refresh` 라는 변수가 하나 더 있느냐뿐이고,
그 대신 `(tea.Cmd, error)` 라는 반환값 둘과 "이걸 내보내라" 는 숙제가 시그니처에 붙는다.

**언제 다시 읽을지는 정책이다.** 이 ADR 이 목록으로 들고 있는 것이 그것이고, 그 목록은 mode 쪽에
있어야 읽힌다. `openTab` 은 "파일을 tab 으로 연다" 하나만 한다. `editor` 가 `tea.Cmd` 를 돌려주는
것 자체는 `startJob` 이 이미 하지만, 그쪽은 작업을 시작하는 함수라 Cmd 가 곧 그 함수의 결과다.

**대신 여는 길이 늘면 갱신을 기억해야 한다.** 네 곳에 같은 한 줄이 있다. 빠뜨려도 오류가 나지
않고 그 길로 연 파일에서만 표시가 최대 5 초 낡을 뿐이라 눈에 띄지 않는다. `git_test.go` 가
네 길을 하나씩 지킨다.

**이미 열어둔 tab 으로 옮겨가는 경우에도 읽는다.** 호출자는 여는 함수가 새로 열었는지 옮겨갔는지
모른다. 그래도 되는 것은 그 길이 사람이 "이 파일 열어" 라고 한 네 자리뿐이라서다. `gt`·`gT` 로
tab 을 오가는 것은 여기를 지나지 않으므로, ADR-0009 가 막고 싶었던 "tab 전환마다 git" 은 그대로
막혀 있다.

### 왜 첫 읽기도 비동기인가

**큰 저장소에서 편집기가 뜨는 것이 `git status` 를 기다린다.** 시작하는 길은 사람이 가장 예민하게
느끼는 자리다. 잠깐 빈 자리는 곧 채워지지만 늦게 뜨는 것은 매번 겪는다.

**`readGitStatus` 를 부르는 곳이 하나로 남는다.** 갱신 작업뿐이다. "화면 그릴 때 부르면 안 된다" 를
주석으로 지키던 것이 구조로 지켜진다.

### 왜 끝난 목록이 이름당 하나인가

**주기적으로 도는 작업이 생겼기 때문이다.** 끝난 순서대로 스무 개를 쌓으면 백 초 만에 목록 전체가
`git 상태` 로 찬다. 그 목록은 "조용히 실패한 것을 나중에 찾는 자리" 인데(ADR-0027) 그 쓸모가 없어진다.

**종류마다 마지막 결과가 알고 싶은 것이다.** 같은 작업의 옛 결과는 볼 일이 없다. 파일 인덱싱을
다섯 번 했으면 마지막 것이 지금 팔레트가 들고 있는 목록이고, git 갱신은 마지막 것이 지금 표시다.

**상한이 필요 없어진다.** 이름은 코드에 있는 종류만큼만 있어서 목록이 저절로 짧다.

## 결과

좋은 점

- 옆 터미널에서 `commit`·`checkout` 을 해도 5 초 안에 표시가 따라온다. ADR-0009 이 감수한 대가가 없어졌다.
- 키 입력 경로에도, 편집기가 뜨는 길에도, 저장하고 파일을 여는 길에도 동기 git 호출이 없다.
  `:w` 마다 프로세스 세 개가 붙던 것(`docs/tasks.md`)도 같이 없어졌다.
- `readGitStatus` 를 부르는 곳이 갱신 작업 하나다.
- `openTab`·`replaceTab` 은 시그니처가 그대로다. 언제 읽을지는 mode 쪽 한 줄로 보인다.
- 끝난 작업 목록이 종류별 마지막 결과가 되어 짧고 읽을 만해졌다.

감수하는 것

- **유휴 상태에서도 5 초마다 프로세스 세 개가 뜬다.** 노트북 배터리로 편집기를 하루 종일 띄워두면
  이것이 값이다. ADR-0009 이 내지 않기로 한 값을 이제 내기로 한 것이다.
  > ADR-0042 가 프로세스를 없앴다. 남은 값은 in-process 훑기다.
- **큰 저장소에서는 갱신이 계속 도는 것처럼 보인다.** `git status` 가 5 초를 넘으면 다음 tick 이
  겹쳐도 새로 시작하지 않으므로 사실상 쉼 없이 도는 상태가 된다. statusBar 에 `git 상태` 가
  거의 늘 떠 있게 되고, 그때는 그것이 정확한 표시다.
  > ADR-0043 이 이 항목을 없앴다. 5 초를 재는 출발선이 「지난 tick」에서 「지난 갱신이 끝난
  > 시각」으로 옮겨가서, 갱신이 얼마나 걸리든 쉬는 시간이 5 초 들어간다.
- **첫 화면의 statusBar 오른쪽이 잠깐 비어 있다.** 곧 채워지지만 처음 한 프레임은 표시가 없다.
- **셸에서 올라오는 길과 `:e` 다시 읽기는 최대 5 초 늦다.** 그 두 자리에서 값을 바로 확인하는
  흐름이라면 전보다 늦게 맞는다.
- **파일 여는 길 네 곳에 같은 한 줄이 흩어져 있다.** 여는 길을 새로 만들면서 빠뜨리면 오류 없이
  그 길만 낡은 표시를 낸다. test 가 네 길을 지키지만, 기억해야 하는 규칙인 것은 사실이다.
- **이미 열어둔 tab 으로 옮겨가기만 할 때도 한 번 읽는다.** 호출자는 새로 열었는지 옮겨갔는지
  모른다. 사람이 파일을 고른 자리뿐이라 값은 작다.
- **끝난 작업의 이력이 남지 않는다.** 같은 이름이 실패했다가 다음에 성공하면 실패한 사실이 사라진다.
  실패를 그 자리에서 statusBar 아래 줄로 알리는 것은 그대로다(ADR-0027).

## 대안

- **갱신 키를 둔다**
	- ADR-0009 이 "새로고침 키가 필요해지면 그때 넣는다" 고 적어둔 길이다. 값이 가장 싸다.
	- 표시를 믿을 수 있으려면 사람이 눌러야 한다는 뜻이다. 눌러야 맞는 표시는 눌러야 한다는 것을
	  아는 사람에게만 맞는다.
- **job 이 아니라 그냥 goroutine 과 msg 로 한다**
	- `:jobs` 목록과 진행 표시가 조용해진다.
	- ctx 취소와 중복 방지를 다시 구현하게 되고, 5 초마다 도는 것이 코드에만 있고 화면에는
	  없는 상태가 된다.
- **끝나지 않는 작업 하나가 안에서 5 초마다 도는 고리를 돈다**
	- tick msg 도, mode 마다 두는 자리도 필요 없다.
	- 그 작업이 편집기 수명 내내 `jobs[0]` 에 앉아서 statusBar 진행 표시를 영구히 차지하고
	  `:jobs` 에 늘 「도는 중」으로 남는다. 표시 규칙 전체를 이것 하나 때문에 비틀게 된다.
- **유휴일 때만 돈다**
	- 타이핑 중에는 멈춰서 부담이 준다.
	- 마지막 키 시각이라는 상태가 늘고, 오래 켜 두고 계속 편집하는 경우, 곧 정작 갱신이
	  필요한 경우에 갱신이 멈춘다.
- **갱신이 끝난 뒤부터 주기를 잰다**
	- 갱신 시간을 셈에 넣는다.
	- 그때는 예약이 갈라지지 않게 막을 자리가 하나 필요하다.

	> ADR-0043 이 이 대안을 골랐다.
- **주기를 설정으로 뺀다**
	- 저장소 크기마다 맞는 값이 다르다.
	- 설정 파일이 아직 없고, 이 값 하나를 위해 만들 것은 아니다. 필요해지면 그때 다른 설정과
	  같이 본다.

- 설정 파일과 주기 조절. 지금은 상수 하나다
- 큰 저장소에서 `git status --porcelain` 대신 더 싼 것을 쓸지. 기준이 갈리면 표시와 `git status` 가
  달라진다는 ADR-0009 의 이유가 그대로 남아 있다
- sidebar 의 `git check-ignore` 동기 호출(`docs/tasks.md`). 같은 바탕 위에 올릴 것이지만 별개 건이다
- ahead/behind, stash 개수 같은 추가 표시. ADR-0009 이 미뤄둔 그대로다
- `:jobs` 에서 주기 작업을 취소하면 어떻게 되는지. 지금은 그 회차만 끊기고 다음 tick 에 다시 시작한다
