# ADR-0005: sidebar 는 struct 로 두고 포커스만 mode 로 나타낸다. 색은 256 색 고정값을 쓴다

- 상태: 채택
- 날짜: 2026-08-12

## 맥락

`README.md` 가 "integration 잘 된 file tree" 를 대표 기능으로 걸어두었고 `docs/spec.md` 의
UI 구성에도 좌측 sidebar 가 있었다. `docs/tasks.md` 는 "너비와 토글 여부를 정한다" 로 미뤄두고 있었다.

sidebar 는 이 편집기에서 처음으로 화면을 **가로로** 자른다. 지금까지 화면은 tabline(1줄) +
편집 영역 + statusBar(2줄) 로 세로로만 잘려 있었고, 편집 영역은 언제나 화면 왼쪽 끝에서
시작했다. 그래서 정할 것이 트리 자체보다 두 가지 더 있었다 — **위젯을 무엇으로 만들 것인가**,
그리고 **포커스를 어떻게 나타낼 것인가**.

여기에 더해 파일 종류별 글자색과 gitignore 된 파일 흐리게 표시가 요구사항으로 들어왔다.
ADR-0004 가 "팔레트를 정하지 않는다" 로 난 결정이라 그것을 뒤집어야 했다.

## 결정

**1. sidebar 는 평범한 struct 다. `tea.Model` 로 만들지 않는다.**
데이터(펼친 상태, 고른 항목, 스크롤)와 렌더를 `sidebar` struct 가 갖고, `editor` 가 값으로 들고 있다.

**2. 포커스가 트리에 있는 상태만 mode 로 둔다.** `viewSidebar` 가 그 mode 다(ADR-0002).

**3. 포커스 표시는 터미널 커서 자체다.** 고른 항목 위에 커서를 놓고, 반전을 따로 칠하지 않는다.

**4. 파일 종류별 글자색은 256 색 고정값이다.** ADR-0004 의 "팔레트를 정하지 않는다" 를
sidebar 에 한해 뒤집는다.

**5. gitignore 판정은 git 에게 묻는다.** 디렉터리를 펼칠 때 `git check-ignore -z --stdin` 를
한 번 부른다.

수치와 키: 너비 24 칸(고정), 편집 영역이 20 칸 아래로 떨어지면 자동 숨김, `:tree` 로 여닫고
`Ctrl+W Ctrl+W`(또는 `Ctrl+W w`)로 포커스를 오간다.

## 근거

### sidebar 를 `tea.Model` 로 만들지 않은 이유

bubbletea 답게 만들면 `sidebar` 가 `Init`/`Update`/`View` 를 갖고 부모가 메시지를 넘겨주는
중첩 model 이 된다. 그러면 키가 어디서 처리되는지가 한 겹 숨고, 돌려받은 `tea.Model` 을
다시 `sidebar` 로 型 단언해야 한다.

ADR-0002 가 型 교체를 고른 것은 **mode** 에 대해서였고, 그 근거는 "bubbletea 가 이미
`tea.Model` 을 갈아끼우고 있으니 그 결을 따른다" 였다. pane 은 그렇게 끌어당기는 것이 없다.
`internal/tui/components` 가 그 방식이지만 `core` 는 지금 그것을 쓰지 않고 자기 화면을 직접 그린다.

평범한 struct 에 평범한 method(`cells`, `rows`, `scrollTo`)면 충분하다.

### 포커스를 mode 로 둔 이유

트리에 포커스가 있으면 키 해석이 통째로 다르다 — 위아래가 커서 이동이 아니라 트리 이동이고,
`Enter` 는 줄 나누기가 아니라 파일 열기다. `editor` 에 `focus bool` 을 두고 mode 마다 분기하면
ADR-0002 가 없앤 "잘못된 상태" 가 돌아온다.

`viewSidebar` 는 필드가 `pending` 하나뿐인 거의 빈 型 이다. 그래도 값을 한다 — **키 표를 소유한다.**

### 포커스 표시를 커서로 한 이유

처음에는 고른 항목을 반전으로 칠하려 했다. 그런데 이 저장소에서 **반전은 이미 "커서" 를 뜻한다**
(ADR-0004: statusBar, tabline). 반전된 줄과 진짜 터미널 커서가 동시에 보이면 어느 쪽이 커서인지
알 수 없다.

커서를 고른 항목 위에 놓으면 그 자체가 포커스 표시가 된다. 포커스가 편집 영역에 있으면 커서도
거기 있으니 트리 선택은 안 보인다 — vim 에서 창을 옮기는 것과 정확히 같은 모양이다.
덤으로 `render` 에 "포커스가 어디인가" 를 넘기는 인자가 필요 없어졌다.

### sidebar 본문을 칠하지 않은 이유

24 칸을 통째로 반전하면 tabline(반전) + statusBar(반전) + 24 칸 세로 띠가 되어 화면 대부분이
뒤집힌다. "vim" 이 아니라 "UI 안에 편집기 창이 들어 있는" 모양이 된다. NERDTree 도 그렇게 하지 않는다.
구분선 `│` 이 경계를 맡는다.

### 256 색 고정값 — ADR-0004 를 뒤집는 부분

ADR-0004 는 "터미널과 싸우지 않는다" 를 이유로 반전만 쓰고 색값을 하나도 정하지 않았다.
그 결정을 sidebar 에 한해 뒤집는다. 파일 종류를 구분하려면 색이 여러 개 필요하고,
반전은 한 가지뿐이라 종류를 나눌 수가 없다.

```
디렉터리          117 + bold
.go                81
.md .txt          150
.html .css .js    179
그 외             기본색 (아무것도 안 입힘)
gitignore 된 것   244  ← 종류별 색을 덮어쓴다
```

"그 외" 에 색을 주지 않는 것이 중요하다. 대부분의 파일이 터미널 기본 글자색으로 남아서
색이 붙은 것만 눈에 띈다. 색을 다 칠하면 아무것도 강조되지 않는다.

### gitignore 를 git 에게 물은 이유

gitignore 문법은 생각보다 크다 — 중첩 `.gitignore`, `!` 부정(뒤에 오는 것이 이김),
맨 뒤 `/` 는 디렉터리만, `**` 와 중간 `/` 의 의미 차이, `.git/info/exclude`, 전역 설정.
직접 구현하면 sidebar 본체만한 작업이 되고, 미묘하게 틀리면 "흐린데 사실 추적됨" 이 나와서
없느니만 못하다.

`git check-ignore` 는 정의상 정답이다. 렌더가 아니라 **디렉터리를 펼칠 때 한 번** 부르므로
비용이 갇힌다. git 이 없거나 저장소 밖이면 아무것도 흐리게 하지 않는다 — 흐린 것이 없을 뿐 틀리지 않는다.

### 너비를 고정한 이유

비율로 하면 터미널 크기를 바꿀 때마다 트리 폭이 달라지고, **편집 영역의 줄바꿈 위치가 같이 흔들린다.**
고정 24 칸이면 리사이즈해도 트리가 제자리다.

### `open` 과 `visible` 을 가른 이유

24 칸 sidebar 를 20 칸 터미널에 그리면 편집 영역 너비가 음수가 된다. `wrapOffsets` 이 줄을 아예
접지 않게 되고 빈 칸 채우기가 panic 한다. 그래서 `sidebar.open`(사용자 의도)과
`sidebarVisible()`(실제로 그리는지)이 다른 것이고, **폭과 관련된 모든 코드가 후자만 봐야 한다.**
한 군데라도 어긋나면 화면 절반만 밀린 상태가 된다.

## 결과

좋은 점

- 트리 상태가 `sidebar` 하나에 모여서 `editor` 가 위젯 내부를 모른다.
- 포커스가 型 이라 "sidebar 에 포커스가 있는데 편집 키가 도는" 상태가 만들어지지 않는다.
- 커서 하나가 포커스 표시를 겸해서 새로 배울 시각 언어가 없다.
- `root` 가 필드라 테스트가 `t.TempDir()` 를 넣는다. `os.Getwd()` 나 `fs.FS` interface 가 필요 없었다.
- sidebar 가 닫혀 있으면 예전과 한 글자도 다르지 않게 그린다. 기존 테스트가 한 줄도 안 바뀌었다.

감수하는 것

- **밝은 테마 터미널에서 회색(244)이 거의 안 보일 수 있다.** 고정값의 대가이고,
  ADR-0004 가 피하려던 바로 그것이다. 팔레트를 제대로 정할 때 다시 본다.
- **포커스가 편집 영역에 있으면 트리에서 무엇을 골라뒀는지 보이지 않는다.** vim 과 같지만,
  돌아가기 전까지는 알 수 없다.
- **`git check-ignore` 가 외부 프로세스다.** 느린 저장소에서는 디렉터리를 펼치는 순간 멈칫한다.
  `Update` 안에서 동기로 돌기 때문이다.
- **디렉터리를 펼칠 때 `os.ReadDir` 이 전부 읽는다.** 항목이 수만 개인 디렉터리에서는 한 키가 멈춘다.
- **`viewSidebar` 가 거의 빈 型 이다.** 型 하나가 늘고 `WindowSizeMsg` 껍데기도 같이 는다
  (ADR-0002 가 이미 감수한 비용이다).
- **sidebar 는 `:` 를 받지 않는다.** 받으면 명령이 끝난 뒤 어디로 돌아갈지를 `viewEditorCommand`
  가 들고 다녀야 한다. 한 키 편하자고 치를 비용이 아니다.

## 대안

**bubbles 의 `filepicker`** — 의존성 추가 없이 쓸 수 있다(`charm.land/bubbles/v2` 가 이미 직접
의존성이다). 하지만 한 디렉터리씩 드릴다운하는 방식이라 정한 펼침형 트리와 다르고, `tea.Model`
이라 위에서 말한 중첩 model 문제를 그대로 가져온다.

**`datastruct.Tree` 재사용** — 이름은 맞지만 pubsub 라우팅용 concurrent trie 다. 자식 순서도
순회도 없어서 화면에 그릴 수가 없다.

**`editor` 에 `focus` 필드** — 型 을 안 늘려도 된다. 대신 mode 마다 "포커스가 어디냐" 분기가
생기고, mode 를 옮기는 모든 자리에서 focus 를 맞춰줘야 한다. 빠뜨리기 쉽다.

**`.gitignore` 직접 파싱** — 외부 프로세스가 없어진다. 위에 적은 문법 크기가 이유로 충분하다.

**드릴다운 트리(한 디렉터리씩)** — 펼침 상태를 들고 있지 않아도 되어 구현이 짧다.
대신 전체 구조가 한눈에 안 들어온다.

## 이 ADR 이 정하지 않는 것

- 전체 팔레트. 여기서 정한 것은 sidebar 의 파일 종류 색뿐이다. mode 별 색은 여전히 없다
- 트리에서 파일을 만들거나 지우거나 이름을 바꾸는 것
- sidebar 너비를 사용자가 바꾸는 방법
- 파일 변경 감지(watcher). 지금은 접었다 펴는 것이 새로고침이다
