# ADR-0072: 잰 ambiguous 폭에 맞춰 눈금을 켜고 프로세스를 다시 시작한다

- 상태: 채택
- 날짜: 2026-08-25

## 맥락

ADR-0028 에서 터미널이 Ambiguous 글자를 몇 칸으로 그리는지 재기 시작했다. 그때 물러선 것은
테두리·구분선뿐이고 **파일 내용의 폭 계산(`clusterAt`) 은 건드리지 않았다.** 그 결정의 끝에
「미루는 값이 크지 않다. 재는 값은 이미 손에 있다」고 적었는데, 실제로 넓히려고 보니 값을
쥐고 있는 것과 그 값을 쓰는 것은 거리가 멀었다.

### 지금 눈금이 둘이다

| 자리 | Ambiguous 를 몇 칸으로 세나 |
|---|---|
| `clusterAt` → `screenWidthOf` → 커서·검색 강조·줄바꿈·정렬 | 늘 **1** |
| 특수문자 격자의 `symbolWidth` | 잰 값 (재지 못했으면 2) |

두 칸으로 그리는 터미널에서 격자만 맞고 나머지가 전부 어긋난다. `docs/spec.md` 처럼 `─` 가
든 파일을 열면 그 줄부터 커서가 글자 수만큼 왼쪽에 선다.

### 우리 산수만 고쳐서는 안 되는 이유

`clusterAt` 이 `displaywidth.Options{EastAsianWidth: true}` 를 타게 만드는 것은 쉽다. 그런데
화면을 실제로 만드는 것은 우리가 아니라 ultraviolet 이다. 그쪽이 셀 폭을 재는 자리를 읽어 보면
전부 `x/ansi` 다(`buffer.go:617`, `styled.go:73`, `terminal_renderer.go:225`).

`─ab` 를 폭 10 짜리 창에 그린다고 하자. 터미널은 `─` 를 두 칸으로 그린다.

```
물리 화면          칸 1  2  3  4        ultraviolet 의 셀 버퍼   칸 1  2  3
                     ──────  a  b                                  ─  a  b
```

- `b` 를 고치려고 셀 버퍼의 3 번 칸으로 `CUP` 을 쏘면 물리 화면에서는 `a` 자리다
- 10 칸을 채웠다고 믿고 글자를 열 개 내보내면 화면에서는 11 칸이 되어 넘친다

우리 계산만 2 칸으로 바꾸면 **우리 산수와 ultraviolet 이 어긋나서** 어긋나는 자리가 옮겨갈
뿐이다. 눈금은 셋이 다 같아야 한다.

### 눈금 손잡이는 하나뿐이다

`x/ansi` 는 그 값을 unexported 패키지 변수로 들고 `init()` 에서 한 번 세운다.

```go
// x/ansi@v0.11.8 method.go
var dwOptions = &displaywidth.Options{EastAsianWidth: false}

func init() {
	if ea, err := strconv.ParseBool(os.Getenv("RUNEWIDTH_EASTASIAN")); err == nil && ea {
		wcOptions.EastAsianWidth = true
		dwOptions.EastAsianWidth = true
	}
}
```

이름과 달리 `1` 은 칸 수가 아니라 참이다. 켜면 Ambiguous 가 **2 칸**이 된다.

다른 길을 하나씩 확인했다.

| 길 | 되나 |
|---|---|
| `RUNEWIDTH_EASTASIAN` 을 세운 채로 프로세스를 시작 | **된다** |
| `main()` 에서 `os.Setenv` | **안 된다.** `init()` 이 이미 지났다(재봤다) |
| `tea.NewProgram` 옵션으로 넘기기 | **안 된다.** 공개 옵션 열두 개에 폭에 손대는 것이 없다 |
| `ultraviolet.WidthMethod` 구현을 넣기 | **안 된다.** 인터페이스(`uv.go:36`) 로 열려 있지만 bubbletea 의 renderer 는 `setWidthMethod(ansi.Method)` 인데 소문자에 enum 이라 밖에서 못 부른다 |
| bubbletea 를 걷어내고 ultraviolet 직접 | 편집기를 다시 짜는 값 |

`ansi.WcWidth`/`ansi.GraphemeWidth` 는 다른 축이다. 코드포인트로 볼지 grapheme cluster 로
볼지이지, Ambiguous 를 몇 칸으로 칠지가 아니다. 둘 다 같은 전역을 본다.

## 결정

**시작할 때 재서 두 칸이면, `RUNEWIDTH_EASTASIAN=1` 을 세우고 자기 자신을 다시 실행한다.**
`syscall.Exec` 이라 같은 pid 에서 실행 이미지만 갈린다. 열린 fd 도 인자도 그대로다.

새 프로세스는 `x/ansi` 의 `init()` 이 East Asian 눈금을 켠 채로 시작하므로, 그때부터
`clusterAt`·lipgloss·ultraviolet 이 전부 터미널과 같은 폭을 센다. **바꾸는 것은 터미널이
아니라 우리 쪽 장부다.** 터미널의 답은 이미 정해져 있고, 우리가 그 답에 맞춰 선다.

**환경에 그 변수가 이미 있으면 아무것도 하지 않는다.** 값이 무엇이든 그렇다. 사용자가 정한
것이 먼저이고, 우리가 세운 뒤에는 같은 문이 무한 재실행을 막는다.

**재는 값이 2 일 때만 한다.** 1 이면 지금 눈금이 이미 맞고, 재지 못했으면(0) 아무것도 모른다.

**재실행에 실패하면 그냥 이어서 뜬다.** Windows(`syscall.Exec` 이 `EWINDOWS` 를 준다) 와
실행 파일을 못 찾는 경우다. 오늘 동작 그대로다.

**재실행 뒤에는 다시 잰다.** 잰 값을 물려주는 통로를 따로 두지 않는다.

**`symbolWidth` 특례를 지운다.** 격자도 `screenWidthOf` 를 쓴다. 눈금을 하나로 모으는 것이
이 ADR 이라 특례를 남길 자리가 없다.

**`editor.ambiguousWidth` 필드를 지운다.** 잰 값은 `core.Run` 의 지역 변수로 남아 박스 문자를
고르는 데만 쓰인다. 그리는 자리는 아무도 그 값을 되묻지 않는다. 이미 눈금에 녹아 있다.

**박스 문자는 이번에 안 건드린다.** 두 칸 터미널에서는 여전히 ASCII 로 내린다(ADR-0028).
눈금이 맞았으니 유니코드 박스도 이제 안 깨지지만, 그건 이 변경의 목적이 아니라 결과다.
`docs/tasks.md` 로 넘긴다.

## 근거

### 왜 재실행이라는 기괴한 수단을 쓰나

**아는 시점이 읽는 시점보다 늦어서다.** 터미널의 답은 DSR 왕복으로 실행 중에만 알 수 있는데,
그 답을 읽는 자리는 `main()` 보다 먼저 지나가는 `init()` 이다. 이 간극을 메우는 길은 「알아낸
답을 갖고 처음부터 다시 시작」뿐이다.

재실행은 사용자가 `RUNEWIDTH_EASTASIAN=1 zn` 으로 실행하는 것을 우리가 대신하는 것이다.
`.zshrc` 에 넣어 둔 사람에게는 아예 일어나지 않는다.

### 왜 안내만 하고 말지 않나

「이 터미널에서는 env 를 세워 실행하세요」는 **틀린 화면을 본 사람에게 주는 숙제**다. 우리는
이미 답을 알고 있고, 그 답을 쓰는 데 필요한 것이 프로세스 재시작 한 번뿐이다. 재는 것을
자동으로 하기로 한 ADR-0028 과 같은 태도다.

### 왜 재지 못했을 때(0) 는 켜지 않나

**대부분의 터미널이 한 칸으로 그린다.** 모르는 채로 2 칸을 켜면 다수의 화면이 깨진다.
「재지 못하면 넓게」는 격자 한 칸 안에서만 성립하던 규칙이다. 그 안에서는 좁게 잡으면 행이
넘치고 넓게 잡으면 칸이 벌어질 뿐이라 손해가 비대칭이었지만, 화면 전체에서는 양쪽 다 어긋난다.
그래서 이 규칙은 `symbolWidth` 와 함께 사라진다.

### 왜 잰 값을 새 프로세스에 물려주지 않나

통로를 두면 규약이 하나 는다(`ZN_AMBIGUOUS_WIDTH` 같은 것). 아끼는 것은 시작할 때
100ms 한 번이고, 그 값을 안 믿게 되는 자리(다른 터미널로 옮겨 붙은 세션) 를 생각하면
**다시 재는 쪽이 늘 맞다.**

### 왜 env 가 있으면 값까지 보지 않나

`RUNEWIDTH_EASTASIAN=0` 을 일부러 세운 사람은 「내 터미널이 2 칸이어도 1 칸으로 쳐라」라고
말한 것이다. 우리가 재서 뒤집을 일이 아니다. 그리고 「있으면 손대지 않는다」는 규칙 하나가
사용자 존중과 무한 재실행 방지를 같이 해낸다.

### 왜 `os/exec` 로 자식을 띄우지 않나

자식을 띄우면 부모가 살아서 신호·터미널 상태·종료 코드를 중계해야 한다. TUI 에서 그 중계는
그 자체로 버그 자리다. `syscall.Exec` 은 pid 를 유지한 채 이미지만 갈아서 중계할 것이 없다.

### 왜 `os.Args[0]` 이 아니라 `os.Executable()` 인가

`os.Args[0]` 은 `PATH` 로 실행하면 `zn` 처럼 이름만 온다. 다시 실행할 때 그 이름을 그대로
쓰면 `PATH` 를 다시 뒤져야 하고, 그 사이 `PATH` 가 다른 zn 을 가리키면 다른 물건이 뜬다.

## 결과

좋은 점

- 두 칸으로 그리는 터미널에서 커서·검색 강조·줄바꿈·정렬이 파일 내용에서도 맞는다
- 눈금이 하나다. `symbolWidth` 특례와 `editor.ambiguousWidth` 필드가 사라져서, 폭을 되묻는
  자리가 편집기 안에 없다
- 한 칸으로 그리는 터미널은 아무것도 달라지지 않는다. 재실행도 안 일어난다

나쁜 점

- **프로세스가 두 번 뜬다.** 시작이 100ms 남짓 늦고, 로그에 시작이 두 번 남는다
- `ps` 로 보면 env 가 우리가 세운 값으로 보인다. 사용자가 세우지 않은 변수다
- 시험이 이 길을 통째로 지나가지 못한다. 갈림(`needsRestart`) 은 시험이 보지만 `syscall.Exec`
  뒤는 못 본다. tty 가 필요한 자리라 `internal/terminal` 의 다른 것들과 같은 처지다
- 재지 못한 터미널의 특수문자 격자가 이제 1 칸으로 센다. ADR-0056 §6 이 넓게 잡던 자리다

따라오는 것

- 두 칸 터미널에서 유니코드 박스를 되살릴 수 있게 됐다(ADR-0028 의 전제가 사라졌다).
  `docs/tasks.md` 에 남겼다
- bubbletea 가 `WidthMethod` 인터페이스를 밖으로 열어 주면 재실행이 필요 없어진다.
  `docs/issues/` 에 남긴다

## 관련

- ADR-0028: 재는 방법과 박스 문자 물러서기. 이 ADR 이 그 미룬 자리를 잇는다
- ADR-0056 §6: 특수문자 격자가 잰 값을 쓰던 자리. 이 ADR 이 걷어낸다
- `docs/knowledges/grapheme-cluster-and-width.md`: 층 넷과 눈금 이야기
