# ADR-0092 gopls 는 디스크를 스스로 보지 않는다. HEAD 가 움직이면 달라진 Go 파일을 알린다

- 상태: 채택
- 날짜: 2026-08-28
- 관련: ADR-0051(gopls 로 정의 찾기), ADR-0068(사용처로 가기), ADR-0042(git 을 라이브러리로), ADR-0030(백그라운드 작업), ADR-0044(파일 검사를 작업으로), ADR-0038(밖에서 바뀐 파일)

## 맥락

「분명 함수를 쓰는 곳이 있는데 `\gr` 이 없다고 나온 적이 있다」는 보고에서 시작했다. `docs/tasks.md` 에는 「저장할떄 gopls 에 재 인덱싱 하면 어떨까?」로 적혀 있었다.

**저장과 재인덱싱의 문제가 아니었다.** 재서 찾은 것은 이것이다.

### 0. 잰 값

임시 모듈을 만들어 zn 과 똑같은 악수로 gopls v0.23.0 을 띄우고 물었다.

| 잰 것 | 값 |
| --- | --- |
| `a.go` 에 `func Foo()` 를 두고 사용처를 묻기 | 0 개(맞다. 쓰는 곳이 없다) |
| 밖에서 `b.go` 를 만들어 `Foo()` 를 쓰게 하고 다시 묻기 | **0 개.** 2 초 뒤도, 5 초 뒤도 0 개 |
| 그 파일을 `didOpen` 으로 알린 뒤 | 1 개 |
| 알리는 대신 `workspace/didChangeWatchedFiles` 한 통을 보낸 뒤 | **500ms 뒤 1 개** |
| 그 파일을 지우고 같은 알림(type 3) 을 보낸 뒤 | 0 개 |

**gopls 는 스스로 디스크를 감시하지 않는다.** 클라이언트가 보내는 그 알림에 기댄다. zn 은 한 번도 보내지 않았으므로, zn 이 열지 않은 파일이 밖에서 바뀌면 gopls 는 처음 읽은 사본을 끝까지 든다.

### 기각한 가설들

전부 재서 기각했다. 적어 두는 것은 같은 증상을 다시 팔 때 여기서부터 시작하지 않기 위해서다.

| 가설 | 잰 값 |
| --- | --- |
| 인덱싱이 끝나기 전에 물어서 빈 답이 온다 | **아니다.** `didOpen` 직후에 물어도 gopls 가 1.6 초 막고 34 개를 다 준다 |
| 편집 중이라 문법이 깨져서 못 찾는다 | **아니다.** 그 파일도, 같은 패키지의 남의 파일도 깨뜨려도 개수가 그대로다 |
| 커서가 이름이 아닌 자리에 있다 | **아니다.** `no identifier found` **오류**로 온다. 「찾지 못했습니다」가 되지 않는다 |
| 패키지를 넘는 사용처를 못 본다 | **아니다.** 18 개 그대로 |
| 하위 디렉터리에서 띄워 뿌리가 좁아진다 | **아니다.** gopls 가 `go.mod` 를 찾아 올라간다 |
| gopls 가 죽었다 | **증상이 다르다.** 죽으면 요청이 오류다(§5) |

### 갈래가 둘이고 약이 다르다

| | 열지 **않은** 파일 | 열어 둔 tab 의 파일 |
| --- | --- | --- |
| gopls 가 든 것 | 처음 읽은 디스크 사본 | zn 이 보낸 overlay |
| `didChangeWatchedFiles` | **듣는다** | **안 듣는다.** overlay 가 이긴다(재서 확인) |
| 필요한 것 | 바뀐 파일 **목록** | zn 이 그 buffer 를 **다시 읽는 것** |

## 1. 능력을 알리지 않고 알림만 보낸다

규격은 `workspace.didChangeWatchedFiles` 능력을 알리고 `client/registerCapability` 로 서버가 감시 규칙을 등록하게 되어 있다.

**채우지 않는다.** 재보니 gopls 는 알리지 않아도 이 알림을 받는다(§0).

ADR-0051 이 능력을 비워 둔 까닭이 「알리면 서버가 그만큼 우리에게 되묻기 시작한다」였다. 등록을 받으려면 그 되묻기에 답하는 자리를 만들어야 하고, 답하지 않으면 서버가 그 자리에서 기다린다. **알림 하나로 되는 일에 그 문을 열 이유가 없다.** 진단을 받을 때와 같은 판단이다(ADR-0086 §2).

## 2. HEAD 가 움직인 것만 잡는다

밖에서 파일이 바뀌는 길은 둘이다.

1. **git 이 움직인 것.** `git checkout`·`pull`·`rebase`
2. **다른 도구가 고친 것.** 다른 창의 편집기, 다른 터미널의 zn, AI 가 코드를 고친 것

**이 ADR 은 1 만 답한다.** HEAD 가 옮겨간 것을 알아채고, 두 commit 사이에 달라진 Go 파일을 git 에게 물어 알린다.

까닭은 값이다. git 은 **목록을 이미 안다** — tree 둘을 견주면 나온다. 2 를 잡으려면 훑거나 감시해야 하는데 둘 다 값이 다르다(§4).

**HEAD 를 자르지 않은 해시로 든다.** 짧은 해시는 저장소 크기에 따라 길이가 달라져서(ADR-0042 의 `gitShortHashLen`) 견주는 자로 쓸 수 없다.

**처음 읽을 때는 알리지 않는다.** 견줄 앞이 없고, 서버는 그때 막 떠서 디스크를 지금 모습으로 이미 읽었다.

**HEAD 가 안 움직이는 git 동작은 못 잡는다.** `git stash`·`git restore <파일>`·`git reset --mixed` 다. 잡으려면 결국 §4 의 훑기가 필요해서 여기서 긋는다.

## 3. Go 파일만 보낸다

브랜치를 옮기면 수백 개가 달라질 수 있다. 그 전부를 보내면 서버가 읽을 이유 없는 파일을 읽는다.

**열어 둔 파일은 걸러내지 않는다.** overlay 가 디스크를 이기므로 그 파일에 대한 알림은 서버가 알아서 무시한다. 거르려면 「무엇이 열려 있나」를 tree 를 견주는 자리까지 들고 와야 해서 값이 더 크다.

**이름이 바뀐 것은 지운 것과 만든 것 둘로 보낸다.** go-git 의 tree 차이가 rename 을 따로 세지 않는데, gopls 에게는 그 둘이 곧 답이라 맞춰 줄 것이 없다.

## 4. 다른 도구가 고친 것은 이번에 안 잡는다

값을 재서 갈랐다.

| 길 | git | 다른 도구 | 값 |
| --- | --- | --- | --- |
| 저장·열기·닫기에 알림 붙이기 | ✗ | ✗ | **0.** zn 이 손댄 파일은 overlay 이고, 닫으면 gopls 가 스스로 디스크를 다시 읽는다(재서 확인) |
| **HEAD 가 움직이면 알리기(이 ADR)** | ○ | ✗ | 작다. 목록은 git 이 준다 |
| 주기로 모듈 전체를 훑어 mtime 을 견주기 | ○ | ○ | 크다. dirty 판정 walk 은 첫 차이에서 곧바로 나오게 짜여 있어서(git-dirty.go) 공짜로 얹히지 않는다. 전부 훑으면 monorepo 120ms 를 tick 마다 낸다 |
| fsnotify | ○ | ○ | 크다. 의존성과 플랫폼별 한계 |

첫 줄이 값 0 인 것이 이 표에서 가장 값진 측정이다. **직관과 다르다** — 「저장할 때 알리면 되겠지」가 답이 아니다.

## 5. 죽은 gopls 는 세 번까지 되살린다

찾다가 나온 다른 버그다.

자리를 비우는 문이 나가는 길(`shutdownGopls`) 하나뿐이었고 `startGopls` 는 `e.gopls != nil` 이면 곧바로 돌아간다. 그래서 **서버가 한 번 죽으면 그 세션 내내** `\gd`·`\gr`·이름 바꾸기·자동완성이 「연결이 닫혔다」였다.

`Client.Closed()` 를 열고 `goplsClient()` 가 죽은 자리를 비운다.

**되살리는 자리는 `syncGopls` 다.** tick 마다 지나므로 사람이 무엇을 묻기 전에 돌아온다. 되살아난 서버는 `finishGopls` 가 열려 있는 Go 파일들을 다시 알려 주므로 overlay 도 같이 돌아온다.

**죽은 것과 뜬 적 없는 것을 가른다.** 자리를 비우기 **전에** 한 번 재 두는 것이 그 일이다 — 비운 뒤에는 둘이 같은 모습이 된다. 「부르는 자리가 둘뿐이고 둘 다 서버가 떠 있어야 닿는다」는 논증으로도 되는데, 그 논증은 나중에 부르는 자리가 하나 늘면 조용히 깨진다. **Go 파일을 열지도 않은 세션에서 서버가 뜨는 것**이 그때 나오는 답이라, 논증에 기대지 않고 한 줄로 가른다(그 자리를 지키는 시험이 이미 있었다 — `TestSyncGoplsWithoutServer`).

**세 번까지다.** 뜨자마자 죽는 서버를 끝없이 되살리면 tick 마다 프로세스가 하나씩 뜬다. 셋으로 둔 것은 그 수가 **「어쩌다 한 번 죽은 것」과 「뜨자마자 죽는 것」을 가르기** 때문이다 — 앞쪽은 한 번이면 돌아오고, 뒤쪽은 세 번이면 되살려서 나아지는 종류가 아님이 드러난다. 넘으면 `goplsFailed` 를 세우고, 그러면 `startGopls` 가 그 자리를 보고 물러나므로 고리가 끊긴다. 설치가 끝나면 그 자리가 다시 풀린다(`installGopls`).

**셈과 판단을 `recordGoplsDeath` 로 갈라 두었다.** 「죽었나」는 `Closed()` 한 줄이고 그것은 lsp 가 시험한다. 「몇 번까지 되살리고 무엇을 알리나」는 판단이고 그것은 core 가 시험한다.

## 결과

- `git checkout` 뒤에 `\gr` 이 그 브랜치의 사용처를 찾는다
- gopls 가 죽으면 다음 tick 이 새 서버를 띄우고, 열려 있던 Go 파일을 다시 알린다. 세 번까지다
- 새로 오는 것은 `lsp.FilesChanged`·`lsp.Closed` 둘과 `gopls-watch.go` 하나다. 악수는 그대로 비어 있다

감수하는 것

- **다른 도구가 고친 파일은 아직 모른다.** AI 나 다른 창의 편집기다(§4)
- **열어 둔 tab 의 파일이 밖에서 바뀌면 낡은 overlay 가 이긴다.** zn 은 활성 buffer 하나만 밖의 변경을 보고(ADR-0044), `syncGopls` 가 tick 마다 그 낡은 것을 덮어씌운다. 알리지 않는 것보다 나쁜 자리다
- **HEAD 가 안 움직이는 git 동작을 못 잡는다.** `stash`·`restore`(§2)
- **능력을 알리지 않은 채 알림을 보낸다.** 규격이 정한 순서가 아니다. gopls 가 이 문을 닫으면 그때 능력을 알리는 길로 옮긴다
- **브랜치를 크게 옮기면 알림 한 통이 커진다.** Go 파일만 골라도 큰 저장소에서 수백 개다. 그때 서버가 읽는 값을 우리가 정하지 못한다
- **되살릴 때마다 진단을 기다리는 goroutine 하나가 남는다.** 죽은 client 의 종을 기다리고 있고 그 종은 다시 울리지 않는다. 되살리기가 세 번까지라 최대 셋이고, 걷으려면 죽을 때 그 채널을 닫는 배선이 conn 과 진단 저장소 사이에 하나 생긴다

## 대안

- **저장할 때 재인덱싱을 부탁하기(처음 적어 둔 것)**
	- 손이 닿는 자리가 분명하다.
	- **값이 0 이다.** zn 이 저장한 파일은 이미 overlay 이고, 닫으면 gopls 가 스스로 디스크를 다시 읽는다(재서 확인, §4).
	- 그리고 「재인덱싱」에 해당하는 요청이 규격에 없다. 있는 것은 파일이 바뀌었다는 알림이다.

- **주기로 모듈 전체를 훑어 mtime 을 견주기**
	- git 도 다른 도구도 다 잡는다.
	- dirty 판정 walk 에 얹으려 했는데 그 walk 은 첫 차이에서 곧바로 나온다. 전부 훑게 만들면 성질이 바뀌고 tick 마다 120ms 다(§4).

- **fsnotify**
	- 바뀐 순간에 안다. VS Code 가 가는 길이고 별도 설치가 필요 없다(§6).
	- 의존성이 붙고 플랫폼별 한계(감시 개수 상한, 네트워크 파일 시스템) 가 온다.
	- **이 ADR 을 쓰는 동안 milestone 으로 올렸다.** §6 의 측정이 「제대로 하는 곳은 감시기를 에디터가 들고 있다」를 보여 주었고, 이것 없이는 다른 도구가 고친 파일을 끝까지 못 잡는다.

- **능력을 알리고 registerCapability 에 답하기**
	- 규격이 정한 순서다.
	- 서버가 우리에게 되묻는 문을 연다. ADR-0051 이 닫아 둔 자리이고, 알림 하나로 되는 일에 그 값을 낼 이유가 없다(§1).

- **죽은 서버를 자리만 비우고 다시 띄우지 않기**
	- 되살리는 고리가 아예 생기지 않는다. 다음에 묻는 사람이 띄운다.
	- 사람이 그 사이에 `\gd` 를 치면 1.6 초를 다시 기다린다. tick 이 미리 띄워 두면 그 기다림이 사라진다 — 파일을 열 때 미리 띄우는 것과 같은 까닭이다(startGoplsForOpenFile).

## 6. 남들은 어떻게 하는가

재서 적는다.

**VS Code.** 설치된 `golang.go` 0.56.0 의 `dist/goMain.js` 를 직접 읽었다. `didChangeWatchedFiles.dynamicRegistration = true` 와 `relativePatternSupport = true` 를 알리고, `vscode.workspace.createFileSystemWatcher(globPattern)` 으로 OS 수준 감시를 붙인다. **즉 §4 표의 마지막 줄(fsnotify) 을 규격대로 가는 길이다.** 능력을 알리고 서버의 등록 요청에 답한다.

**vim.** vim 9.1 에 `-u NONE` 으로 물어보니 `autoread` 기본값이 `0`(꺼짐) 이다. 그리고 vim 9 에는 LSP 클라이언트가 없어서 이 물음 자체가 플러그인의 몫이다.

**vim + coc.nvim.** `~/.vim/plugged/coc.nvim/build/index.js` 를 읽었다. 능력 선언은 VS Code 와 똑같다 — `didChangeWatchedFiles.dynamicRegistration = true` 와 `relativePatternSupport = true` 다. 그런데 감시를 **watchman**(외부 프로그램) 에 맡기고, coc 의 문서(`doc/coc.txt:156`) 가 이렇게 적어 두었다.

> The watchman command is detected from your `$PATH`, **the feature will silently fail when watchman can't work.**

**이 기계에 watchman 이 없다.** 그래서 지금 이 손이 쓰는 vim + coc 는 능력을 알리고 서버가 감시 규칙을 등록해 놓고도 **아무 통도 받지 못한다.** zn 과 같은 구멍이고, 문서에 적힌 대로 조용하다.

셋을 나란히 놓으면 이렇게 된다.

| | 능력 선언 | 감시 | 별도 설치 없이 되는가 |
| --- | --- | --- | --- |
| VS Code(`golang.go` 0.56.0) | 한다 | `createFileSystemWatcher`(에디터 내장) | **된다** |
| vim + coc.nvim | 한다 | watchman(외부 프로그램) | **안 된다.** 조용히 실패 |
| zn(이 ADR) | 안 한다 | HEAD 가 움직일 때 git 목록 | git 동작만 된다 |
| plain vim | LSP 없음 | `autoread` 기본값 0(재서 확인) | 해당 없음 |

**VS Code 가 이기는 자리는 「능력을 알렸다」가 아니라 감시기를 에디터가 들고 있다는 점이다.** zn 은 Go 프로그램이라 `fsnotify` 를 안에 들고 갈 수 있어서 그 자리에 설 수 있다. coc 처럼 외부 프로그램에 맡기면 안 깔린 손에서 조용히 실패한다. 이 측정이 fsnotify 를 backlog 에서 milestone 으로 올린 근거다.

**Neovim 은 확인하지 못했다.** 깔려 있지 않아서 재지 못했고, 기억으로 적지 않는다.

## 이 ADR 이 정하지 않는 것

- **다른 도구가 고친 파일을 어떻게 알아채는가.** 훑기와 fsnotify 중 무엇으로 갈지 (§4)
- **보고 있지 않은 tab 의 파일을 다시 읽는 것.** 낡은 overlay 를 걷는 일이고 `docs/tasks.md` 에 열려 있다 (ADR-0044)
- **`go.mod`·`go.sum`·`go.work` 를 같이 알릴지.** 지금은 `.go` 만 본다 (§3)
- **되살릴 때 남는 진단 대기 goroutine 을 걷을지.** 셋까지라 두었다 (§5)
