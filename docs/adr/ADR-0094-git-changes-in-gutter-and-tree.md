# ADR-0094 git 변경은 HEAD 기준이다. 줄은 마커 칸에, 파일은 트리 오른쪽 끝에 그린다

- 상태: 채택
- 날짜: 2026-08-28
- 관련: ADR-0009(statusBar 의 git 표시), ADR-0042(go-git 으로 옮김), ADR-0043(갱신 cooldown), ADR-0051(gopls 와 맞추는 250ms), ADR-0086(진단 마커 칸), ADR-0005(sidebar), ADR-0007(줄번호 칸), ADR-0044(파일 검사를 작업으로)

## 맥락

statusBar 오른쪽에 `master(a1b2c3d*)` 가 있다(ADR-0009). `*` 하나가 「commit 하지 않은 것이 있다」를 말하는데, **무엇이** 바뀌었는지는 말하지 않는다. 편집기 안에서 그것을 보려면 밖에서 `git status` 를 치거나 `:!git diff` 를 돌려야 했다.

자리는 이미 예약되어 있었다. ADR-0086 이 진단 마커를 놓으며 「git 변경 표시도 나중에 이 칸에 들어온다. 두 마커가 한 칸에서 만날 때 무엇이 이기는지는 그때 정한다」 고 적어 두었고, ADR-0009 도 편집 영역 안의 변경 표시를 미뤄 두었다.

읽는 길도 이미 있었다. `readGitStatus` 가 5 초 cooldown 으로 백그라운드에서 돌고(ADR-0043), `gitDirty` 가 index·HEAD·작업 트리 셋을 이미 견준다. 지금은 그 셋을 **참/거짓 하나로 접어서** 버리고 있었다.

없는 것은 둘이었다. 줄 단위 diff 를 낸 적이 없고, 파일별 상태를 들고 있는 자리가 없었다.

정할 것은 여섯이다. 무엇을 기준으로 재는가, 판정을 몇 벌 두는가, 진단과 칸을 어떻게 나누는가, 무엇을 재서 그리는가, 언제 다시 내는가, 트리에 어떻게 그리는가.

## 0. 먼저 쟀다

줄 diff 값을 재고 시작했다. `sergi/go-diff` 는 go-git 을 따라 이미 들어와 있다.

| 잰 것 | 값 |
| --- | --- |
| 500 줄, 한 군데 고침 | 91µs |
| 5,000 줄, 한 군데 고침 | 1.2ms |
| 50,000 줄, 한 군데 고침 | 7.7ms |
| 앞뒤 공통 줄을 떼고 나서, 5,000 줄 한 군데 | 4µs |
| 앞뒤 공통 줄을 떼고 나서, 50,000 줄 한 군데 | 5µs |
| 5,000 줄, 흩어진 쉰 군데 | 2.6ms |
| 50,000 줄, 흩어진 쉰 군데 | 10.2ms |
| 파일이 통째로 다름(50,000 줄) | 110ms(상한에 걸림) |

**앞뒤 공통 줄을 떼는 것이 값을 정한다.** 떼고 나면 고친 크기에 비례하고, 떼지 않으면 파일 크기에 비례한다. 한 군데 고친 5 만 줄 파일에서 7.7ms 와 5µs 의 차이다.

**값이 터지는 자리는 하나다.** 파일이 통째로 달라진 때인데 `git checkout` 직후나 포매터가 전부를 고친 뒤가 그렇다. 상한(100ms) 에 걸리면 go-diff 는 거친 답을 주고 멈춘다 — 마커가 조금 굵어질 뿐 틀리지 않는다.

## 1. 기준은 index 가 아니라 HEAD 다

vim-gitgutter 도 VS Code 도 **index** 와 견준다. `git add` 한 조각은 마커가 사라진다. 우리는 **HEAD** 와 견준다.

- 사람이 묻는 것이 「마지막 commit 이후 무엇을 바꿨나」다. stage 는 그 답의 일부이지 답의 반대편이 아니다.
- 조각별로 stage 하는 손(`git add -p`) 을 쓰지 않으면 `git add` 뒤에 표시가 사라지는 것이 「왜 사라졌지」가 된다. 그 손을 쓸 때만 index 기준이 이득이다.
- statusBar 의 `*` 가 이미 HEAD 기준이다(ADR-0009). 한 화면에서 둘이 다른 것을 세면 안 된다.

**잃는 것은 「무엇을 stage 했는지」를 화면에서 볼 수 없다는 것이다.** 그것은 `:!git status` 가 답한다.

## 2. 판정은 한 벌이다

`gitDirty` 가 하던 일을 **파일별 표**(`gitChanges`) 로 넓히고, `*` 는 그 표가 비었는지로 답한다.

두 벌로 두면 `*` 와 트리 마커가 서로 다른 순간의 사실을 말하는 날이 온다. 같은 저장소를 두 번 훑는 값도 그대로 든다.

**대가는 조기 종료를 잃는 것이다.** 예전에는 다른 것을 하나 찾으면 그 자리에서 훑기를 끊었다. 이제 트리가 파일마다 물으므로 끊을 자리가 없다. 다만 깨끗한 저장소를 확인하는 일은 예전에도 전부를 보는 일이었고(ADR-0009 가 「그것이 이 판정의 바닥값이다」 라고 적어 둔 그것이다), 이 훑기는 5 초 cooldown 의 백그라운드 작업 안에 있다(ADR-0043).

**표에 디렉터리도 담는다.** 파일마다 그 위 디렉터리에 표시를 올려 둔다. 그리는 자리에서 「내 아래에 뭔가 있나」를 물으면 행마다 표를 훑어야 하고, 그 값이 트리 높이에 비례해 든다.

**키는 절대 경로다.** 트리의 항목이 절대 경로를 들고 있어서 그리는 자리가 표를 그대로 물을 수 있다. index 의 경로는 뿌리 기준 슬래시 표기라 표를 만들 때 한 번 맞춘다 — 그리는 자리마다 맞추면 그 셈이 여러 군데로 흩어진다.

### go-git 의 `index.Merged` 에 물렸다

이 표를 만들자마자 **안 고친 파일까지 전부 `M`** 이 되었다. 까닭은 우리 코드가 아니었다. go-git 의 `index.Merged` 는 1 인데 디코더는 파일에 적힌 값(충돌이 없으면 0) 을 그대로 넣는다. 그대로 견주면 모든 항목이 충돌로 읽힌다(`docs/issues/0002`).

**이 자리는 예전에도 틀려 있었다.** `gitStagedChanged` 가 같은 견줌을 하고 있었는데, 답이 참/거짓 하나였고 index 의 TREE 캐시가 성하면 그 앞에서 끝나서 드러나지 않았다. 캐시가 깨진 저장소에서만 이 길로 왔고 그때는 대개 실제로도 dirty 였다. 「하나라도 있나」가 「어느 것인가」가 되면서 곧바로 보였다.

## 3. 칸을 하나 더 둔다. 진단과 겹치지 않는다

ADR-0086 이 미뤄 둔 「두 마커가 한 칸에서 만나면」의 답이다. **만나지 않게 한다.** 마커 칸이 두 칸이 되었다.

- 오류가 있는 줄은 **대개 방금 고친 줄**이다. 한 칸을 나눠 쓰면 정작 보고 싶은 순간에 git 표시가 가려지고, 오류를 고쳐야 그제야 드러난다.
- 두 표시의 성격이 다르다. 진단은 있다가 없어지는 것이고 git 표시는 commit 할 때까지 그 줄에 남는다. 하나가 다른 하나를 밀어낼 관계가 아니다.

**진단이 왼쪽 끝, git 이 번호 옆이다.** 본문에 가까운 쪽을 오래 서 있는 것에 준다.

**대가는 본문이 한 칸 더 좁아지는 것이다.** 폭 34 인 화면에서 줄이 26 칸이 아니라 25 칸에서 접힌다. 아무것도 없어도 늘 잡는 것은 진단 칸과 같은 까닭이다(ADR-0086 §3) — 있을 때만 잡으면 첫 표시가 뜨는 순간 본문 전체가 밀린다.

## 4. 재는 것은 buffer 다. 디스크가 아니다

저장하지 않은 편집도 마커에 든다. 치는 대로 마커가 붙는다.

디스크 기준이 훨씬 싸다(파일 해시가 이미 있다). 그런데 그러면 **새 줄을 쳐도 저장 전까지 아무 표시가 없다.** 「지금 뭘 고쳤나」를 보려고 있는 표시가 저장할 때까지 침묵하면 그 자리에 있을 이유가 절반 없어진다.

**추적하지 않는 새 파일에는 마커가 없다.** 견줄 원본이 없다. 모든 줄에 `+` 를 세우는 길도 있지만, 그것은 파일이 새것이라는 말을 줄 수만큼 되풀이하는 것이다 — 그 사실은 트리의 `?` 가 한 번 말한다.

**지운 줄은 앞 줄에 표시한다.** 없어진 줄에는 그릴 칸이 없다. 파일 맨 앞이 지워졌으면 갈 곳이 없어서 첫 줄에 선다. 한 줄에 둘이 겹치면 **그 줄 자신에 대한 사실**(넣음·고침) 이 이긴다 — 지움 표시는 옆줄에 얹히는 것이라 그 줄의 사실을 밀어내서는 안 된다.

**글자는 `+`·`~`·`_` 다.** 셋 다 ASCII 라 East Asian Width 를 볼 것도 없다(ADR-0020). 색은 ANSI 의 밝은 쪽(10·12·9) 이다 — 이 칸이 진단 칸(ANSI 1) 과 절대 줄번호(ANSI 3) 사이에 끼어 있어서, 어두운 쪽을 쓰면 옆 칸과 한 덩이로 보인다(ADR-0086 §4 가 경고를 3 이 아니라 11 로 둔 것과 같은 자리다).

## 5. 다시 내는 때가 둘이다

**타이핑이 멎으면**(250ms) 보고 있는 파일의 마커를 다시 낸다. **git 갱신 작업이 돌면**(5 초 cooldown) 열려 있는 파일 전부를 다시 낸다.

앞의 것이 내가 고친 것을 따라오고, 뒤의 것이 밖에서 일어난 일(`commit`·`checkout`) 을 따라온다. `:w` 는 git 갱신을 한 번 더 내므로 저장 직후는 그 자리에서 맞는다.

**예약 상태를 늘리지 않았다.** 250ms 뒤에 하는 일이 하나 더 생겼는데, tick 을 하나 더 두면 같은 250ms 를 재는 타이머가 둘이 된다. `lspTick` 을 `editTick` 으로 넓혀서 「타이핑이 멎었다」가 뜻이 되게 했다 — 이름이 lsp 였던 것은 그때 매달린 일이 하나뿐이어서다(ADR-0043 이 예약을 하나로 묶어 둔 것과 같은 자리다).

**HEAD 원본은 갱신 작업이 읽어 온다.** blob 을 푸는 것은 I/O 라 그리는 goroutine 이 할 일이 아니다. buffer 마다 「그 원본을 어느 HEAD 에서 읽었나」를 들고 있어서, HEAD 가 그대로면 다시 읽지 않는다 — 5 초마다 도는 자리에서 매번 풀면 그 값이 그대로 든다.

**diff 자체는 Update 안에서 한다.** 값이 밀리초 단위라(§0) Cmd 로 내보내고 낡은 답을 가려내는 값이 더 크다. 자동완성이 seq 를 들어야 했던 것과 다른 자리다(ADR-0066).

## 6. 트리는 오른쪽 끝 한 칸이다

`M`(HEAD 와 다름) 과 `?`(git 이 모르는 새 파일) 다. `git status --short` 의 글자를 그대로 쓴다.

**이름 앞이 아니라 오른쪽 끝이다.** 앞에 두면 깊이마다 이름이 한 칸씩 밀려 트리 모양이 흐트러진다. 오른쪽에 세우면 마커끼리 한 줄로 서서 세로로 훑을 수 있다.

**색은 줄 마커와 같다.** 왼쪽 칸의 `~` 와 트리의 `M` 이 같은 사실을 가리킨다는 것이 색으로 이어진다.

**갈래를 둘로 나눈다.** 「HEAD 와 다름」 하나로 묶는 길도 있지만, commit 을 빠뜨리는 사고는 대개 `git add` 를 안 한 새 파일에서 난다. 그 둘은 눈으로 갈려 있어야 한다.

**디렉터리에도 선다.** 접혀 있어도 「이 안에 뭔가 있다」가 보여야 한다. 섞여 있으면 변경이 이긴다 — commit 할 것이 있다는 쪽이 더 급한 소식이다. 뿌리에는 서지 않는다. 뿌리 행은 늘 서 있게 되어 아무것도 가리키지 않는다.

**이름 칸이 한 칸 줄었다**(30 → 29). sidebar 폭 32 는 그대로다.

## 결과

- 고친 줄이 `~`, 넣은 줄이 `+`, 지운 자리가 `_` 로 줄번호 왼쪽에 선다. 저장하지 않은 편집도 든다
- 트리에서 어느 파일이 바뀌었는지(`M`) 와 어느 것이 아직 git 밖인지(`?`) 가 보인다. 접힌 디렉터리도 안에 있는 것을 알린다
- statusBar 의 `*` 와 트리 마커와 줄 마커가 **같은 훑기 한 번**에서 나온다
- 본문이 한 칸 더 좁아졌다. 마커 칸이 둘이다
- 250ms tick 의 이름이 `editTick` 이 되었다. 매달린 일이 둘이다
- `docs/issues/0002` 가 생겼다. go-git 의 stage 상수에 물린 자리다

**대가**

- **타이핑 직후 250ms 는 마커가 낡아 있다.** 진단이 250ms 어긋나는 것과 같은 자리다(ADR-0086 §6)
- **밖에서 commit 하면 5 초까지 늦는다.** cooldown 그대로다(ADR-0043)
- **추적하지 않는 새 파일에는 줄 마커가 없다**(§4)
- **`git add` 해도 마커가 남는다.** stage 한 것을 화면에서 가릴 수 없다(§1)
- **깨끗한 저장소에서도 늘 전부 훑는다.** 조기 종료를 잃었다(§2)
- **파일이 통째로 달라지면 diff 가 100ms 까지 든다.** 상한에 걸리면 마커가 거칠어진다(§0)
- **submodule 안은 보지 않는다.** ADR-0042 그대로다

## 대안

- **index 와 견주기(vim-gitgutter·VS Code 와 같게)**
	- 조각별로 stage 하는 손과 맞고, 남들과 같은 뜻이라 설명이 필요 없다.
	- `git add` 한 순간 표시가 사라지는 것이 그 손을 안 쓰는 사람에게는 사고로 보인다(§1).
	- statusBar 의 `*` 와 기준이 갈린다.
- **한 칸을 진단과 나눠 쓰기**
	- 본문 폭을 지킨다.
	- 오류가 있는 줄이 곧 방금 고친 줄이라, 가장 보고 싶은 순간에 가려진다(§3).
- **디스크 파일과 견주기**
	- 싸다. 파일 해시를 이미 들고 있고 갱신 자리도 이미 있다.
	- 새 줄을 쳐도 저장 전까지 아무 표시가 없다(§4).
- **그릴 때마다 diff 내기(캐시 없이)**
	- 마커가 늘 정확하고 tick 이 필요 없다.
	- 흩어져 고친 5,000 줄 파일에서 키마다 2.6ms 이고, 통째로 다른 파일에서는 100ms 다(§0).
- **줄 diff 를 백그라운드 작업으로 돌리기**
	- 아무리 커도 화면이 멈추지 않는다.
	- 값이 밀리초라 낡은 답을 가려내는 장치가 그 값보다 크다. `:jobs` 목록이 250ms 마다 한 줄씩 늘어나는 것도 같이 온다(§5).
- **추적하지 않는 파일의 모든 줄에 `+` 그리기**
	- 「이 파일은 전부 새것」이 한눈에 보인다.
	- 같은 말을 줄 수만큼 되풀이한다. 트리의 `?` 가 이미 한 번 말한다(§4).
- **git 은 배경색, 진단은 글자색으로 갈라 그리기**
	- 두 칸이 눈에 다르게 잡혀서 마커 영역이 덜 뚱뚱해 보인다. 색 막대라 세로로 훑기도 좋다.
	- **지운 줄 표시가 거짓말이 된다.** `_` 는 그 줄이 아니라 **그 줄 다음에 없어진 것**을 말하는데(§4), 배경은 칠한 그 줄 자신을 가리키는 손이다. 칸을 칠하면 「이 줄이 지워졌다」로 읽힌다.
	- 진단만 배경으로 돌리는 길도 오류·경고의 차이가 색 하나로 줄어서 뜻이 덜 전해진다. 글자(`✖`·`⚠`) 가 갈래를 말하던 것을 잃는다(ADR-0086 §4).
	- 배경은 이 편집기에서 「지금 고른 것·찾은 것」 하나를 가리켜 왔다(검색 매칭·visual 선택). 뜻을 하나 더 얹지 않는다.
	- **마커 칸 둘이 뚱뚱해 보이는 것은 받아들인다.** 본문 한 칸과 바꾼 것이고(§3), 그것을 되돌리는 값이 위 셋이다.
- **하단 drawer 로 변경 파일 목록 열기(`:changes`)**
	- 골라서 뛸 수 있다. ADR-0069 의 판을 그대로 쓴다.
	- 불러야 보인다. 트리는 이미 늘 떠 있고 파일이 놓인 자리도 함께 보여준다.
	- 트리 마커를 놓고 나서 「목록도 필요한가」를 보고 정한다.

## 이 ADR 이 정하지 않는 것

- **바뀐 자리로 뛰는 키**(vim 의 `]c`·`[c`). 마커가 먼저 서고 나서 볼 일이다
- **그 줄의 원래 내용을 보는 것**(gitgutter 의 hunk preview). 원본을 이미 들고 있어서 낼 수는 있는데, 어디에 어떻게 띄울지가 새 결정이다
- **되돌리기**(hunk 단위 `git checkout`). 편집기가 저장소를 고치는 첫 자리가 된다
- **`:changes` 목록**. 위 대안에 적어 두었다
- **tabline 의 마커.** ADR-0086 이 진단에 대해 열어 둔 것과 같은 자리다
- **stage 한 것과 안 한 것을 갈라 보이기.** §1 에서 HEAD 하나로 정했다
- **submodule 안의 변경.** ADR-0042 그대로다
- **끄는 설정.** 설정 파일이 아직 없다(ADR-0061, ADR-0065, ADR-0066 과 같은 건이다)
