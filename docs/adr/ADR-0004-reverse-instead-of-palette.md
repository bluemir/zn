# ADR-0004: statusBar 와 tabline 은 색을 정하지 않고 반전만 쓴다

- 상태: 채택
- 날짜: 2026-08-12

## 맥락

statusBar 와 tabline 이 색·배경 없이 그려져서 파일 내용과 구분되지 않았다. Go 소스를 열면
`NORMAL  buffer.go` 가 코드 한 줄처럼 보인다. tabline 을 넣으면서 그런 줄이 하나 더 늘었고,
색이 없어서 활성 tab 을 대괄호(`[1 buffer.go]`) 로 표시하고 있었다.

`docs/tasks.md` 에 "statusBar 를 편집 내용과 눈으로 구분되게 한다 … 색 결정이 없어서 미뤘다" 로
열려 있던 항목이다. 미룬 이유가 색을 고르는 일 자체였다. 팔레트를 정하면
"`config 는 compile 됨` 의 실제 형태를 정한다" 는 아직 열려 있는 결정을 앞당겨 당기게 된다.

## 결정

`lipgloss.NewStyle().Reverse(true)` 로 **터미널의 전경·배경을 뒤집기만 한다.** 색값은 하나도
정하지 않는다.

- statusBar 는 **위 줄만** 반전이다. 아래 줄은 배경을 그대로 둔다.
- tabline 은 **보고 있는 tab 만** 편집 내용과 같은 색이고 나머지는 반전이다.
  색이 활성 표시를 대신하므로 대괄호는 뗐다.
- 두 줄 모두 줄 끝의 남은 칸까지 채워서 줄 전체가 한 덩어리로 보이게 한다.

## 근거

**팔레트를 정하지 않아도 된다.** 미뤄 둔 이유가 그것이었다. 반전은 고를 색이 없다.
`config 는 compile 됨` 의 형태를 정하는 결정을 당겨쓰지 않고 눈에 보이는 문제만 먼저 없앤다.

**어느 터미널 테마에서도 맞는다.** 명시적인 색은 사용자의 배경색과 어긋날 수 있다. 어두운 테마에
맞춘 회색 배경은 밝은 테마에서 뜬금없어 보인다. 반전은 그 터미널이 쓰는 두 색을 뒤집는 것이라
밝은 테마든 어두운 테마든 항상 대비가 생긴다. 개인용이라 환경이 하나일 것 같지만,
같은 편집기를 다른 기계·다른 터미널에서 열면 바로 드러난다.

**vim 의 기본값이 정확히 이것이다.** `StatusLine` 은 `term=reverse cterm=reverse` 이고
`TabLine`/`TabLineSel` 도 같은 방식으로 활성 tab 만 반전을 뺀다. 이 저장소가 vim 을 기준으로
삼고 있으니(ADR-0003) 기본값도 따른다.

**활성 tab 이 아래 내용과 이어져 보인다.** tab 이라는 비유 자체가 그것이다. 대괄호는 "어느 것이
활성인가" 만 알려주지만, 색은 "이 tab 의 내용이 아래에 있다" 를 보여준다. 그래서 대괄호를 뗐다.
같은 것을 두 가지로 표시할 이유가 없다.

**아래 줄을 칠하지 않은 이유.** 그 줄은 커서 위치가 뜨다가 `:` 를 치면 명령줄로 바뀌는 자리다.
vim 도 statusline 은 칠하고 맨 아래 명령줄은 배경 그대로 둔다. 칠하면 `:wq` 를 칠 때 배경이 뜨고
명령 결과와 오류 메시지도 반전된 바탕 위에 얹힌다. 읽기만 나빠진다.

## 결과

좋은 점

- 편집 내용과 UI 가 눈으로 갈라진다. 열려 있던 task 가 닫힌다.
- 색을 하나도 정하지 않았다. 나중에 팔레트를 정하면 `reverse` 변수 한 곳만 바꾸면 된다.
- tabline 에서 대괄호가 빠져서 tab 하나가 두 칸 짧아졌다. 좁은 화면에서 하나라도 더 들어간다.

감수하는 것

- **mode 를 색으로 구분할 수 없다.** 반전은 한 가지뿐이라 NORMAL 과 INSERT 의 바탕이 같다.
  mode 는 statusBar 의 글자와 커서 모양(블록/막대) 으로만 드러난다. lightline 처럼 mode 별로
  색을 쓰려면 팔레트를 정해야 하고, 그것이 이 ADR 이 피한 것이다.
- **`ESC[7m` 을 제대로 다루지 못하는 터미널에서는 아무 구분이 없다.** 옛 터미널 이야기이고
  대신 글자가 깨지지는 않는다.
- **테스트가 escape 를 걸러야 한다.** 화면 문자열을 비교하는 검사는 `ansi.Strip` 을 거친다.
  대신 "어디에 색이 갔는가" 를 직접 보는 검사(`splitByReverse`) 가 생겨서 활성 tab 표시가
  실제로 옮겨 다니는지를 확인할 수 있게 됐다.
- **줄 끝까지 칠하느라 폭 계산이 렌더에 들어왔다.** tabline 은 조각마다 색이 달라서
  자르는 것을 색 입히기 전에 해야 한다. escape 가 섞이면 폭을 셀 수 없기 때문이다.

## 대안

- **명시적인 배경색·글자색**
	- 원하는 모양을 정확히 만들 수 있다.
	- 색을 정해야 하고, 밝은 테마 터미널에서 어떻게 보일지도 같이 정해야 한다.
	- `lipgloss` 의 adaptive 색을 쓰면 테마 문제는 줄지만 이번에는 색을 두 벌 정해야 한다.
	  얻는 것에 비해 정할 것이 많다.
- **mode 별로 다른 색**
	- NORMAL/INSERT/COMMAND 를 색으로 구분한다(lightline·airline 방식). mode 를 한눈에 알 수 있다.
	- 색을 셋 이상 정해야 하고, mode 는 이미 커서 모양과 statusBar 글자로 드러나 있다.
	- 팔레트를 정한 뒤에 다시 볼 수 있다.
- **굵게(bold) 나 밑줄**
	- 색을 안 정해도 된다는 점은 같다.
	- 줄 전체를 덮지 못해서 "이 줄은 UI 다" 가 아니라 "이 글자가 강조됐다" 로 읽힌다.
	  편집 내용과 갈라놓는 데는 약하다.

## 이 ADR 이 정하지 않는 것

- 팔레트. 언젠가 색을 정하면 그때 이 결정을 다시 본다
- 편집 내용의 색(syntax highlight). 언어별 지원과 같이 본다
- 종료 확인창의 색. 그 화면은 아직 터미널 너비도 모른다
