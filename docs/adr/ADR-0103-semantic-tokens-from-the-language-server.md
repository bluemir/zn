# ADR-0103 문법 갈래를 언어 서버에게 묻고 lexer 가 받친다

- 상태: 채택
- 날짜: 2026-08-29
- 관련: ADR-0039(문법 강조 뼈대), ADR-0040(안쪽 언어), ADR-0041(색표), ADR-0051(gopls 를 띄우고 맞춘다), ADR-0086(진단), ADR-0092(죽은 서버 되살리기)

## 맥락

`docs/tasks.md` 의 문법 강조 후속에 이 항목이 있었다.

> Go 의 generic 인자(`List[T]`) 와 함수 type 필드(`handler func()`) 도 type 자리로 본다

`internal/syntax/go.go` 는 표준 라이브러리 `go/scanner` 로 토큰을 나눈다. 나누는 일은 Go 가 해 주지만 **`go/scanner` 가 답하는 것은 어휘까지다.** `Foo` 가 `token.IDENT` 라는 것은 알려주고, 그것이 type 인지 변수인지 함수인지는 알려주지 않는다. 그 자리를 `goTypePosition` 이 생김새로 메우고 있었다. 「식별자 둘이 공백만 두고 붙으면 뒤쪽이 type 이다」가 그 규칙이고, `*` 가 이름에 붙었는지로 포인터와 곱셈을 가르는 것도 같은 손이다.

생김새로는 갈리지 않는 자리가 남는다. 재 보니 이랬다.

| 줄 | 색이 빠진 이름 | 까닭 |
|---|---|---|
| `var x List[T]` | `T` | `arr[i]` 의 index 와 생김새가 같다 |
| `func Map[T any, R any](...)` | `T`, `R` | 위와 같다 |
| `handler func(ev int) Result` | `Result` | `)` 뒤의 결과 type 을 보지 않는다 |
| `func f() (int, error)` | (이름 있는 type 이면) | 위와 같다 |

규칙을 더 적어서 메울 수 있다. 대괄호를 여는 이름이 type 자리인지 보고, `)` 뒤를 결과 type 으로 보면 위 넷이 잡힌다. 그러나 그 길은 끝이 없다. `func(Foo, Bar)` 의 이름 없는 인자와 `func(a, b Foo)` 의 인자 이름은 괄호 안을 통째로 봐야 갈리고, 가려도 어림이다.

**우리는 이미 답을 아는 프로그램을 옆에 띄워 두고 있다.** gopls 가 그 파일을 type 검사까지 마친 채로 도는데(ADR-0051), 색만 어림으로 칠하고 있었다.

## 1. 갈래는 서버가 정하고 lexer 가 받친다

`textDocument/semanticTokens/range` 로 묻는다. 서버가 말한 줄은 서버가 정하고, 서버가 없거나 아직 말하지 않은 줄은 lexer 의 답이 그대로 남는다.

lexer 를 걷어내지 않는 까닭이 셋이다.

- 아홉 언어 중 서버가 붙은 것은 Go 하나다.
- 서버가 뜨는 데 1 초 남짓 걸리고(잰 값), 깔려 있지 않을 수도 있고, 죽기도 한다(ADR-0092).
- 들여쓰기와 감싸는 머리줄이 같은 토큰을 본다(ADR-0047). 그것들은 답을 기다릴 수 없다.

`go/parser` 나 `go/types` 를 직접 부르는 길도 있는데 가지 않았다. `go/parser` 는 파일 하나가 온전해야 AST 를 주고 편집 중 소스는 문법이 깨져 있다. `go/types` 는 패키지 전체와 import 해석이 필요하다. 그 둘을 편집기 안에서 돌리는 것이 곧 gopls 를 다시 만드는 일이고, gopls 는 이미 떠 있다.

## 2. 능력이 아니라 설정 하나로 켠다

ADR-0051 이 `capabilities` 를 일부러 비워 두었다. 능력을 알리면 서버가 우리에게 되묻기 시작하는데(진행률 창, 설정) 답할 자리가 없으면 서버가 그 자리에서 기다린다.

semantic token 은 그 문을 열지 않아도 된다. gopls v0.23.0 에서 조합을 다 재 보았다.

| client capabilities | `semanticTokens` 설정 | 결과 |
|---|---|---|
| 비움 | 끔(기본값) | provider 없음, 토큰 0 개 |
| 비움 | 켬 | **provider 옴, 토큰 698 개** |
| 알림 | 켬 | 같음 |

`initializationOptions` 에 `{"semanticTokens": true}` 한 줄이면 된다. 기본값이 꺼짐인 것은 `gopls api-json` 으로 확인했다. 능력은 그대로 비어 있다.

이름표(legend) 는 악수 응답의 `semanticTokensProvider.legend` 에서 읽어 둔다. 응답의 토큰은 번호로 오는데 그 번호는 이 표 안에서만 뜻이 있다. 받는 자리에서 곧바로 이름으로 바꾸면 표를 들고 다닐 필요가 없다.

## 3. 파일 전체가 아니라 창을 묻는다

`semanticTokens/full` 은 **큰 파일에서 조용히 빈 답을 준다.** 오류가 아니라 빈 배열이다. 재서 경계를 잡았다.

| 파일 크기 | full 응답 |
|---|---|
| 84 KB (6402 줄) | 토큰 14402 개 |
| 103 KB (8002 줄) | **토큰 0 개** |
| 213 KB (16002 줄) | 토큰 0 개 |

10 만 byte 언저리다. 그대로 쓰면 큰 파일에서 색이 이유 없이 사라지고, 사라진 자리가 오류를 남기지 않아 알아채기도 어렵다. `range` 는 같은 300 KB 파일에서 60 줄에 1 ms 였다.

창 단위는 우리 쪽 모양과도 맞는다. 담아 두는 것이 이미 「화면 맨 아래 줄까지」이고(ADR-0039 의 `lexSyntaxTo`) 값이 파일 크기가 아니라 화면 크기에 매인다.

**화면 위아래로 100 줄을 더 묻는다**(`semanticMargin`). 보이는 만큼만 물으면 한 줄만 굴려도 새로 보이는 줄이 답을 기다리는 동안 색이 튄다. 감싸는 머리줄이 화면 위의 줄을 그리는 것도(ADR-0049) 이 여유가 받는다.

## 4. 줄 통째로 갈아끼운다

`syntaxLine` 에 칸을 하나 더했다.

```go
type syntaxLine struct {
	tokens   []syntax.Token // lexer 의 답
	after    syntax.State
	semantic []syntax.Token // 서버의 답. 있으면 이쪽을 그린다
}
```

**둘을 섞지 않는다.** 서버가 그 줄에 무엇이든 말했으면 그 줄은 서버가 정한다. 섞으면 같은 글자에 두 갈래가 겹치고 어느 쪽이 이기는지가 글자마다 달라진다.

서버가 아무 말도 하지 않은 줄은 lexer 로 돌아간다. 문법이 깨진 동안 답에서 빠지는 줄이 그렇다. 재 보니 gopls 는 깨진 파일에서도 읽히는 만큼을 준다. **틀린 색이 아니라 빠진 색이 된다.**

**서버의 토큰은 줄을 넘지 않는다.** 여러 줄 raw string 과 여러 줄 block comment 도 줄마다 잘려서 온다. 규격이 그렇게 정해 두었고 재서 확인했다(`TestGoplsSemanticTokensDoNotSpanLines`). 우리 캐시가 줄 단위라 이것이 맞지 않으면 얹을 자리가 없었다.

## 5. 늦게 온 답은 버리고, 고친 줄만 lexer 로 돌아간다

답은 물은 뒤에 온다. 그 사이에 한 글자만 쳐도 줄 자리가 밀린다.

`syntaxCache` 에 `revision` 을 둔다. 내용이 갈린 횟수이고 `replace` 가 센다. 물을 때의 값을 답에 실어 보냈다가 돌아왔을 때 견주고, 다르면 통째로 버린다. 버려도 잃는 것이 없다. lexer 의 답으로 한 박자 남았다가 다음 tick 이 다시 묻는다.

**타이핑 중에 색이 통째로 깜빡이지는 않는다.** 편집이 지나는 자리(`replaceLines` → `syntaxCache.replace`) 가 **갈아끼운 줄의 `semantic` 만** 비운다. 나머지 줄은 자리가 밀린 만큼 같이 밀려서 그대로 남는다. 고치고 있는 줄만 잠깐 lexer 색이 된다.

이 값은 캐시를 버리는 갈래에서도 이어진다. 0 으로 돌아가면 지나간 답이 다시 맞아 보인다.

## 6. 묻는 자리는 「타이핑이 멎었을 때」 하나다

`editTickMsg` 다(ADR-0051 이 만든 자리). 이동 키도 그 tick 을 예약하므로 굴러간 창까지 같은 자리가 받는다. 새 예약 상태를 만들지 않았다.

**묻기 직전에 그 파일을 맞춘다.** 맞추는 일(`syncGopls`) 과 묻는 일이 각자의 goroutine 이라 순서가 정해져 있지 않다. 묻는 goroutine 이 스스로 `Sync` 를 한 번 지나면 그 뒤의 답은 반드시 지금 글의 것이다. 이미 맞았으면 아무것도 보내지 않는다.

오류는 알리지 않는다. 색이 lexer 의 답으로 남을 뿐이고, 서버가 죽은 것은 맞추는 자리가 알아채서 다시 띄운다(ADR-0092). 250ms 마다 같은 알림을 쌓을 일이 아니다.

## 7. 갈래 표

LSP 규격이 정한 이름을 우리 갈래로 옮긴다. gopls 말고 다른 서버가 붙어도 같은 표로 읽힌다.

| 서버가 말한 것 | 우리 갈래 |
|---|---|
| `type`, `typeParameter`, `namespace` | `KindType` |
| `function`, `method`, `macro` | `KindFunction` |
| `keyword` / `comment` / `string` / `number` | 같은 이름의 갈래 |
| `variable`·`parameter`·`property` + `readonly` | `KindConstant` |
| `variable`·`parameter`·`property` + `definition` | `KindVariable` |
| 그 밖(`operator`, `label`, 쓰는 자리의 이름) | 그리지 않는다 |

**package 이름도 type 색이다.** `syntax.State` 처럼 앞에 붙는 이름은 뒤의 type 과 한 덩어리로 읽힌다. lexer 도 그 자리를 이미 type 으로 칠하고 있었고(`goTypePosition` 의 `PERIOD` 갈래), 이제 `errors.New` 의 `errors` 도 같은 색이 된다.

**이름은 붙이는 자리만 칠한다.** `definition` 수식어가 그것을 가른다. 쓰는 자리까지 칠하면 Go 소스의 거의 모든 식별자가 한 색이 되어 색이 구조를 짚어 주지 못한다. 선언은 대개 파일에 한 번이라 「여기서 생겼다」를 짚는 자국이 된다.

**바뀌지 않는 이름은 상수다.** `nil`·`true`·`iota` 와 `const` 로 선언한 것이 여기 든다. lexer 가 이름 표로 잡던 것과 같은 갈래라 서버가 붙어도 색이 그대로다.

## 결과

잰 값이다(gopls v0.23.0, 이 저장소).

| 하는 일 | 걸린 시간 |
|---|---|
| 첫 요청 (서버가 모듈을 훑는다) | 약 1 초 |
| 그 뒤의 요청 | 1 ms |
| 편집 직후 | 10 ms |
| 300 KB 파일의 60 줄 | 1 ms |

앞에 적은 네 자리가 전부 색을 얻었다. `List[T]` 의 `T`, `func Map[T any]` 의 type 인자, `) Result` 의 결과 type, 그리고 덤으로 struct 필드 이름과 인자 이름이 선언 자리 색을 얻었다.

## 남는 것

- **gopls 가 없으면 lexer 의 어림이 그대로 보인다.** 이번 항목이 물은 generic 인자와 결과 type 은 그때 여전히 색이 없다. 서버가 뜨기 전 1 초 동안도 그렇다.
- **감싸는 머리줄이 창의 여유(100 줄) 밖이면 lexer 색이다.** 500 줄짜리 함수의 머리줄이 그렇다. 한 화면에 두 손이 섞여 보이는 자리다.
- **Go 말고는 서버가 없다.** js·python 에 서버를 붙이면 이 길이 그대로 열린다. 갈래 표가 규격의 이름이라 표를 다시 쓸 일은 없다.
