# ADR-0023: `ctrl+z` 로 셸에 내려가고, 올라올 때 git 은 다시 읽고 보고 있는 파일은 알리기만 한다

- 상태: 채택
- 날짜: 2026-08-13

## 맥락

`ctrl+z` 가 없었다. 셸에서 명령 하나를 돌려보려면 편집기를 끝내고(`ctrl+c` → 확인창) 다시 띄워야
했고, 그때마다 tab 구성과 트리를 펼친 상태와 undo 이력이 사라졌다. vim 을 쓰던 손은 여기서
`ctrl+z` 를 먼저 누른다.

두 가지가 같이 걸려 있다.

**첫째, 어느 mode 에서 받을지.** `ctrl+c`(전체 종료) 는 normal·insert·트리·확인창에 모두 달려
있지만, `ctrl+z` 는 그것과 성질이 다르다. insert mode 에서 누르면 글자를 치던 중에 화면이
사라진다.

**둘째, 올라올 때 무엇을 볼지.** 셸로 내려가는 이유의 대부분이 `git pull`·`git checkout`·포매터·
빌드다. 그 셋 모두 열어둔 파일을 밖에서 바꾼다. ADR-0015 는 "포커스가 돌아올 때 검사(vim 의
`checktime`)" 를 미뤄뒀고, ADR-0016 은 "다시 읽을 길이 생겼으니 그 알림에 붙일 수 있게 되었다"
고 적어 두었다. `ctrl+z` 는 그 "돌아오는 자리" 가 편집기 안에서 처음으로 확실해지는 지점이다 —
터미널 포커스와 달리 편집기가 스스로 내려갔다 올라온 것을 안다.

## 결정

**`ctrl+z` 는 `tea.Suspend` 를 낸다.** bubbletea 가 터미널을 돌려주고 프로세스 그룹에 `SIGTSTP`
를 보낸다. 셸의 job 이 되고 `fg` 로 올라온다. 올라오면 `tea.ResumeMsg` 가 내려간 그 mode 로 온다.

**normal mode 와 트리(sidebar) 에서만 받는다.** insert·명령줄(`:`)·검색(`/`)·팔레트·확인창에서는
지금처럼 아무 일도 하지 않는다 — 그 mode 들은 `Text` 가 빈 키를 이미 버리고 있어서 코드가
늘지 않는다.

**종료가 아니라 멈춤이므로 저장하지 않은 변경을 묻지 않는다.** `ctrl+c` 가 확인창을 띄우는 것과
갈리는 자리다. 잃는 것이 없으니 물을 것도 없다.

**올라올 때 보고 있는 tab 하나만 검사한다.** 파일을 다시 읽어 `diskHash` 와 맞춰 본다.
판정은 ADR-0015 와 같은 내용 해시다.

**알리기만 한다.** statusBar 아래 줄에 찍고 buffer 는 건드리지 않는다. 세 경우를 구분해서 말한다.

- 내용이 다르다 → `파일이 밖에서 바뀌었습니다. 다시 읽으려면 :e 입니다`
- 없던 파일이 생겼다 → `파일이 밖에서 새로 생겼습니다. 다시 읽으려면 :e 입니다`
- 있던 파일이 사라졌다 → `파일이 밖에서 사라졌습니다`

**트리에 포커스가 있었으면 파일을 검사하지 않는다.** 화면만 되살아난다.

> ADR-0031 이 트리에서도 보게 했다. 알림을 놓을 자리가 없다는 것이 이 예외의 이유였는데,
> statusBar 의 `[!]` 마커가 mode 와 무관한 그 자리다. 셸 복귀는 여기 적힌 그대로 두었다.

**git 상태는 두 mode 모두에서 다시 읽는다.** ADR-0009 가 정한 갱신 시점(편집기를 열 때·파일을
열 때·저장할 때) 에 "셸에서 올라올 때" 를 더한다.

> ADR-0030 이 이것을 되물렸다. 5 초마다 도는 갱신이 생겨서 올라오는 자리에서는 읽지 않는다.
> 파일이 밖에서 바뀌었는지 보고 알리는 것은 그대로다.

**판정과 문구를 가른다.** `Buffer.checkOutside` 가 `outsideChange`(같다/바뀌었다/생겼다/사라졌다)
를 주고, 문구는 부르는 쪽이 만든다. `checkNotChangedOutside`(저장) 는 `:w!` 를, 복귀 검사는
`:e` 를 붙인다.

## 근거

### 왜 normal 과 트리만인가

**insert mode 는 글자를 치는 중이다.** 그 중간에 화면이 사라지는 것은 놀랍고, 셸에 갈 생각이
있으면 `esc` 를 먼저 누르는 것이 vim 을 쓰는 손의 순서다. 한 키를 아끼려고 놀라움을 사지 않는다.

**명령줄·검색·팔레트는 치던 문자열을 들고 있다.** 내려갔다 올라오면 그 문자열이 화면에 그대로
남는데, 그 사이에 셸에서 무엇을 했는지에 따라 이어 치는 것이 맞는지 알 수 없다. 버리면 버린
것이 아깝고 남기면 어긋난다. 판단할 근거가 생기기 전에는 키를 먹지 않는다.

**확인창은 답을 기다리는 중이다.** 여기서 내려가면 올라와서 무엇을 묻고 있었는지부터 다시 읽어야
한다. `ctrl+c` 도 여기서는 취소로만 동작한다.

**트리는 normal 과 같은 "쉬고 있는" 상태다.** 파일을 고르다가 셸에 다녀오는 것은 자연스럽고,
포커스를 그대로 두고 올라오면 하던 일을 잇는다.

### 왜 보고 있는 tab 하나만인가

**여러 tab 을 검사하면 알림이 목록이 된다.** statusBar 아래 줄은 한 줄이다. `git checkout` 뒤에
세 파일이 바뀌었으면 세 줄을 어디에 띄울지부터 정해야 하고, 그것은 알림 자리를 새로 만드는
결정이다(`docs/tasks.md` 의 confirm 창 개선 항목과 같은 자리다).

**보고 있지 않은 tab 은 아직 위험하지 않다.** 그 tab 으로 `gt` 하기 전에는 편집도 저장도
일어나지 않고, 저장하는 순간에는 ADR-0015 가 막는다. 안전망은 이미 있고 여기서 더하는 것은
편의다. 편의는 지금 보고 있는 것부터 준다.

**읽는 파일이 하나라 값이 싼 것도 맞다.** 다만 이유의 순서는 값이 아니라 알림 자리다.

### 왜 알리기만 하는가

**자동으로 다시 읽으면(vim 의 `autoread`) undo 이력이 조용히 사라진다.** 다시 읽기는 undo 이력을
버리는 일이다(ADR-0016). 사용자가 시킨 일이 아닌데 이력이 사라지는 것은 `ctrl+z` 한 번의 대가로
너무 크다. `dirty` 하지 않은 buffer 로 한정해도, 방금까지 `u` 로 되돌려 보고 있었을 수 있다.

**확인창으로 물으면 올라오자마자 y/n 이 뜬다.** 셸에서 무엇을 했는지에 따라 답이 갈리는데,
그 판단을 하기 전에 화면이 확인창으로 덮인다. 편집기가 어떤 상태였는지 눈으로 확인하고 나서
결정하는 쪽이 낫다.

**알림 한 줄이면 다음 걸음이 사용자 손에 남는다.** 가져올 것이면 `:e`, 아니면 무시하고 계속
편집한다. 이 편집기의 다시 읽기는 이미 `:e`·팔레트 두 길이 있고(ADR-0016, ADR-0021) 둘 다
잃을 것이 있으면 묻는다. 알림이 그 길을 가리키기만 하면 된다.

### 트리에서 검사하지 않는 이유

**보고 있는 것이 파일 내용이 아니다.** 트리에 포커스가 있으면 statusBar 아래 줄은 고른 항목
이름이고, 커서도 트리 위에 있다. 거기에 파일 알림을 끼우려면 `viewSidebar` 에 `message` 자리를
새로 만들어야 하는데, 그 알림이 가리키는 `:e` 는 트리에서 바로 칠 수 없다(먼저 편집 영역으로
나와야 한다).

**트리에서 셸에 다녀오는 것은 파일을 고르러 온 흐름이다.** 곧 파일을 열 것이고, 열면 그때
디스크에서 새로 읽는다. 알릴 것이 없다.

**놓치는 자리는 남는다.** 트리에서 내려가 파일을 고친 뒤 올라와 `ctrl+w ctrl+w` 로 돌아오면
알림 없이 옛 내용을 본다. 저장할 때 막히므로 잃는 것은 없고, 알림 자리를 새로 만드는 값보다
싸다고 봤다.

### git 은 트리에서도 읽는 이유 — 파일 검사와 갈리는 자리

**셸에서 올라오는 것은 git 값이 바뀌었을 가장 확실한 자리다.** 내려가는 이유의 상당수가
`commit`·`checkout`·`pull` 이다. ADR-0009 가 파일 열기를 갱신 시점으로 삼은 근거("바깥에서
`commit`/`checkout` 을 하고 돌아온 직후일 때가 많다") 가 여기서는 추측이 아니라 사실이다.

**알림을 띄울 자리가 필요하지 않다.** statusBar 오른쪽의 git 표시는 mode 와 무관하게 늘 그
자리에 있어서, 값을 바꿔 넣으면 그것으로 끝이다. 파일 검사를 트리에서 빼는 이유가 "알림을 놓을
데가 없다" 였으니, 놓을 데가 이미 있는 쪽은 같이 뺄 이유가 없다.

**값은 조용히 바뀌어도 되는 것이다.** 다시 읽기와 달리 사용자가 편집한 무엇도 잃지 않는다.
편집기가 들고 있는 낡은 branch 이름을 맞는 것으로 바꾸는 일뿐이다.

**비용은 프로세스 세 개다.** `:w` 마다 이미 같은 값을 내고 있고(ADR-0009), 복귀는 저장보다
드물다. 큰 저장소에서 `git status` 가 느린 문제는 저장 쪽과 같은 건이라 같이 본다.

### 판정과 문구를 가르는 이유

**같은 사실에 붙는 다음 걸음이 자리마다 다르다.** 저장이 막힌 자리에서 알려야 하는 것은
`:w!` 로 빠져나가는 길이고, 복귀 자리에서 알려야 하는 것은 `:e` 로 가져오는 길이다. 문구를 한
벌로 합치면 "파일이 밖에서 사라졌습니다. 덮어쓰려면 `:w!` 입니다" 를 아직 아무것도 쓰려 하지
않은 자리에서 보게 된다.

**판정을 두 벌 두는 것이 더 나쁘다.** 파일을 읽고 해시를 맞추고 없는 파일과 새로 생긴 파일을
가르는 세 분기가 두 곳에 생기면, 한쪽만 고쳐서 저장과 복귀가 다른 판단을 하는 날이 온다.
`outsideChange` 는 그 분기를 한 곳에 두기 위한 型 이고 상태를 늘리지 않는다.

## 결과

좋은 점

- 셸에 다녀올 때 tab 구성·트리·undo 이력을 잃지 않는다. 이 변경의 전부다.
- ADR-0015 가 미뤄둔 `checktime` 이 가장 확실한 자리(스스로 내려갔다 올라온 것) 에서 먼저 켜진다.
  저장할 때까지 몰랐던 바깥 변경을 그 전에 한 번 알게 된다.
- 저장 쪽 문구와 복귀 쪽 문구가 갈리면서 판정은 한 곳에 모였다.
- 셸에서 `commit`·`checkout` 을 하고 올라오면 statusBar 오른쪽이 맞는 값이 된다. ADR-0009 가
  감수하겠다고 적은 "낡은 값" 중에서 가장 흔한 경우가 없어진다.

감수하는 것

- **insert·명령줄·검색·팔레트에서는 `ctrl+z` 가 먹지 않는다.** vim 은 insert 에서도 내려간다.
  `esc` 를 먼저 누르는 한 손이 더 든다.
- **보고 있지 않은 tab 은 여전히 저장할 때 알게 된다.** `git checkout` 으로 여러 파일이 바뀐 뒤
  알림은 한 파일에 대해서만 뜬다.
- **트리에 포커스가 있으면 알림이 없다.** 위에 적은 그대로다.
- **알림이 statusBar 폭을 넘으면 뒤가 잘린다.** 좁은 화면에서 `다시 읽으려면 :e 입니다` 가 먼저
  사라져서, 사실만 남고 다음 걸음이 안 보인다(`docs/tasks.md` 의 statusBar 표시 항목과 같은 건).
- **복귀할 때 파일을 한 번 더 읽고 git 프로세스 세 개를 띄운다.** ADR-0015 가 저장마다 읽는 것과
  같은 크기의 비용이다. 큰 저장소에서 `git status` 가 느리면 올라오는 것이 그만큼 늦어진다 —
  저장이 늦어지는 것과 같은 건이다(`docs/tasks.md`).
- **다른 터미널에서 한 `commit`·`checkout` 은 여전히 낡은 값으로 남는다.** 편집기를 띄워둔 채
  옆 창에서 하는 경우다. ADR-0009 가 감수한 그대로이고, 주기적 새로고침 결정으로 넘긴다.

## 대안

**`:suspend`·`:sus` 명령** — vim 에 있는 이름이다. 셸에 잠깐 다녀오는 것은 키 하나로 끝나야 하는
일이라 명령줄을 거치는 것은 결이 맞지 않는다. 나중에 별칭으로 더할 수 있다.

**모든 mode 에서 받기** — vim 에 가장 가깝고 규칙이 하나다("어디서든 `ctrl+z`"). insert 중에
화면이 사라지는 놀라움과, 명령줄·검색이 들고 있던 문자열의 처리를 정해야 한다.

**복귀할 때 아무것도 검사하지 않기** — 가장 단순하고, 안전은 ADR-0015 가 이미 지킨다. 셸에 내려가는
이유의 대부분이 파일을 바꾸는 일이라, 가장 알려주기 좋은 자리를 비워두는 것이 된다.

**열린 tab 전부 검사하기** — vim 의 `:checktime` 과 같다. 알림이 여러 줄이 되어 띄울 자리를
새로 만들어야 한다.

**dirty 하지 않은 buffer 는 자동으로 다시 읽기(vim 의 `autoread`)** — 손이 가장 덜 간다.
undo 이력이 조용히 사라지고, 커서가 선 자리의 내용이 말없이 달라진다.

**확인창으로 「다시 읽을까요」 묻기** — ADR-0016 이 예고한 형태다. 올라오자마자 화면이 덮이고,
여러 파일이면 여러 번 묻는 문제가 그대로 남는다.

**복귀할 때 git 을 읽지 않기** — ADR-0009 가 정한 갱신 시점을 늘리지 않는다. 셸에서 `commit`
하고 올라오는 것이 흔한데 statusBar 가 그것을 모른 채로 남는다. 갱신 시점을 늘리는 값이 프로세스
세 개보다 크다고 봤다.

**git 도 트리에서는 읽지 않기** — 복귀 처리를 normal 하나로 모아서 규칙이 한 줄이 된다. 트리
옆의 statusBar 도 같은 git 표시를 그리고 있어서, `ctrl+w ctrl+w` 로 나올 때까지 낡은 값이
보이는 이유를 설명할 수 없다.

## 이 ADR 이 정하지 않는 것

- 터미널 포커스가 돌아올 때(`tea.FocusMsg`) 도 검사할지. 진짜 `checktime` 은 그쪽이다
- 여러 tab 을 한 번에 검사·다시 읽는 것과 그 알림을 띄울 자리
- git 표시를 주기적으로 새로고침할지. 다른 터미널에서 한 `commit`·`checkout` 은 그쪽 결정이다 (ADR-0009, ADR-0030 이 정했다)
- 한글 입력 상태에서 `ctrl+z` 가 `ctrl+ㅋ` 로 오는 것. 터미널이 PC-101 자리를 같이 주면 되돌려
  받는다(ADR-0014) — `ctrl+p` 와 같은 문제이고 같은 해결이다
- `:!<shell command>` 로 셸 명령 하나만 돌리는 것. 셸로 내려가는 것과 목적이 겹치지만 별개다
