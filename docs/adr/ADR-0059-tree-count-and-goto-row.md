# ADR-0059 트리도 숫자 접두와 `G`·`gg` 를 받고, 처음으로 가는 키는 `gg` 다

- 상태: 채택
- 날짜: 2026-08-24

## 맥락

트리가 받는 이동 키가 `j`·`k`·`↑`·`↓` 넷뿐이었다. 파일 스무 개짜리 디렉터리를 펼치면 끝까지
가는 데 `j` 를 스무 번 친다. 편집 영역에서는 `20j` 로 끝나는 것이 그 옆에서는 안 된다.

파서가 그 자리를 미리 적어 두고 있었다.

> 이름만 주고 숫자를 주지 않아서 normal mode 처럼 동작 type 을 두지 않고 string 이다.
> 트리에는 아직 숫자 접두가 없다. `5j` 를 넣을 때 struct 가 된다.

그 「넣을 때」가 이 결정이다. 같이 정해야 하는 것이 셋 있다.

## 1. 동작은 이름과 숫자를 든 struct 다. type 을 만들지 않는다

`sidebarState.press` 가 `[]string` 대신 `[]sidebarAction` 을 준다. `sidebarAction` 은 이름과
count 둘뿐인 struct 다.

normal mode 처럼 동작마다 type 을 두지 않았다. **저쪽이 type 이 된 까닭은 operator 다.**
`d3w` 는 범위를 잡아 그 위에 지우기를 얹는 것이라 동작이 motion 과 count 를 들고 다녀야 했다
(ADR-0013). 트리에는 operator 가 없고, 동작 스무 개 중 숫자를 보는 것은 이동 넷(`j` `k` `G`
`gg`) 뿐이다. 그 넷 때문에 스무 개의 type 을 만들면 `run` 의 `switch` 가 이름 하나로 갈리던
것이 type 스무 개로 갈린다. 얻는 것이 없다.

`viewSidebar.run` 의 서명만 `string` 에서 `sidebarAction` 으로 바뀌었고, 숫자를 읽지 않는
동작은 그 필드를 그냥 보지 않는다. **그래서 `3md` 가 `md` 다.** normal 에서 `3i` 가 `i` 인
것과 같은 자리이고, 「숫자를 받는 키 목록」을 따로 들지 않아도 그렇게 된다.

`:jobs` 쪽 파서(`jobsState`) 는 그대로 `[]string` 이다. 받는 키가 전부 한 개짜리라 아직 들 것이
없고, 그쪽에 숫자가 올 때 이 struct 가 본이 된다.

## 2. `G` 와 `gg` 는 숫자를 되풀이가 아니라 행 번호로 받는다

`20j` 의 20 은 「스무 번」이고 `20G` 의 20 은 「스무 번째」다. vim 이 그렇고 편집 영역이
이미 그렇다(`motionToLastLine`).

그래서 **count 를 1 로 메워 받지 않는다.** `G` 는 숫자가 없는 것과 있는 것을 가려야 하고
(없으면 마지막 행, 있으면 그 행) 1 로 메우면 그 둘이 같아져서 `G` 가 첫 행으로 간다.
`sidebarAction.count` 의 0 이 「대지 않았다」이고, 그것을 아는 곳은 `run` 의 `G` 자리뿐이다.

행 번호는 **보이는 행**을 1 부터 센 것이다. 접힌 디렉터리 안쪽은 세지 않는다. 트리가 화면에
늘어놓은 것이 `rows()` 이고 `j`·`k` 가 이미 그 기준으로 센다. 파일 시스템의 무엇을 세는
번호가 아니라 「화면에서 몇 번째 줄」이라, 접었다 펴면 같은 번호가 다른 파일을 가리킨다.
그것을 받아들인다. 눈으로 세는 번호라야 `20G` 를 칠 수 있다.

범위를 넘는 번호(`99G`) 는 거절하지 않고 마지막 행에 선다. `scrollTo` 가 이미 `selected` 를
행 수 안으로 당기므로(트리가 줄어드는 것을 다루려고 있던 것이다) 뛰는 쪽은 계산만 하고
가두는 것은 한 곳에 남는다. `20j` 가 트리 끝에서 멈추는 것도 같은 자리다.

## 3. 처음으로 가는 키는 `gg` 다. 목록 판들의 `g` 를 따르지 않는다

`:messages` 와 `:registers` 는 `g` **하나**로 처음, `G` 로 끝으로 간다(ADR-0053, ADR-0058).
트리도 목록이므로 그쪽을 따르는 것이 자연스러워 보인다. **따르지 않았다.**

**트리는 읽는 판이 아니라 머무는 곳이다.** `:messages` 는 열어서 보고 `q` 로 닫는 판이라
그 안에 있는 시간이 짧고, 그동안 다른 키를 쓰지 않는다. 트리는 포커스를 옮겨 두고 파일을
오르내리며 만들고 지우고 이름을 바꾸는 자리다. `mc`·`md`·`mm` 이 여기 있는 이유가 그것이고
(ADR-0054), 편집 영역과 `ctrl+w` 로 오가는 사이에 손버릇이 갈리면 안 된다. 편집 영역에서
`gg` 로 파일 처음에 가던 손이 트리에서 `g` 를 치면 그 사이에 아무 일도 나지 않는다.

값을 치른다. **`g` 의 뜻이 판마다 갈린다.** 트리에서는 접두 키이고 목록 판들에서는 그
자체로 동작이다. 그래도 갈리는 자리를 「편집기 안(normal·트리)」과 「열었다 닫는 판」으로
그을 수 있고, 그 선은 `q` 로 닫히는지로 이미 그어져 있다.

`g` 가 접두 키가 되면서 트리의 접두 키가 `ctrl+w`·`m` 에서 셋이 되었다. 짝이 없는 조합
(`gx`) 은 이름이 되어 `run` 에서 버려진다. `m x` 가 그렇던 것과 같다.

한글로는 `gg` 가 `ㅎㅎ` 다. **`G` 는 한글 상태에서 낼 수 없다.** 두벌식에 `ㅎ` 의 shift
자리가 없어서 대문자 키와 구분되지 않는다(hangul-key.go). 새로 생긴 제약이 아니라 편집
영역의 `G` 가 이미 그렇고, 이 결정이 그것을 트리로 넓히지도 좁히지도 않는다.

## 결과

**상태가 둘에서 셋이 되었다.** `sidebarCount` 가 늘었고 `sidebarPending` 이 숫자를 들고
다닌다(`20gg`). 숫자가 뜻이 없는 접두 키(`m`·`ctrl+w`) 앞에서는 모으던 숫자를 버린다.
normal 에서 `3ctrl+w` 가 `ctrl+w` 인 것과 같다.

**`0` 은 숫자의 첫 자리가 될 수 없다.** 편집 영역에서 줄 시작으로 가는 키라 비워 둔 자리인데
(`normalStart`), 트리에서는 `0` 이 아무 일도 하지 않으므로 숫자로 받을 수도 있었다. 받지
않았다. 한쪽에서만 숫자가 되면 손이 그 키의 자리를 두 벌로 기억한다.

**showcmd 가 모으던 숫자도 보인다.** `20g` 까지 치면 그것이 그대로 오른쪽 끝에 보인다.
접두 키만 보이던 자리에 `countString` 을 앞에 붙인 것이 전부다. 편집 영역이 쓰는 것과
같은 함수다.

**시험 두 개가 뒤집혔다.** 「숫자는 count 가 아니다」와 「숫자 뒤의 키를 삼키지 않는다」가
그 규칙을 붙잡고 있었다. 뒤집는 것이 이 결정이므로 같은 자리에 `3j`·`20j`·`20G`·`20gg` 를
넣었다.

## 이 ADR 이 정하지 않는 것

- `ctrl+d`·`ctrl+u`(반 화면) 와 `H`·`M`·`L`(화면 위·가운데·아래). 뛰는 것이 `20j` 로 되므로
  급하지 않다. 뒤 셋은 `top` 을 기준으로 세는 첫 이동이라 규칙이 하나 는다
- `zz`·`zt`·`zb`(고른 항목을 화면 가운데·위·아래로). 지금은 `scrollTo` 가 최소한으로만 굴린다
- `/` 로 트리 안에서 이름을 찾는 것. 팔레트(`ctrl+p`) 가 그 자리를 겸하고 있다
- 이름 첫 글자로 뛰는 것(파일 관리자들이 하는 것)
- `:jobs` 목록의 숫자 접두. §1 을 보라

## 관련

- ADR-0005 sidebar 파일 트리: 트리가 받는 키를 정한 자리
- ADR-0006 normal mode 키 상태 기계: 숫자 접두와 접두 키의 규칙이 여기서 왔다
- ADR-0013 `d` operator: normal 의 동작이 type 이 된 까닭
- ADR-0008 입력줄이 없는 mode 는 한글을 되돌린다: `ㅎㅎ` 가 `gg` 인 자리
- ADR-0053 알림 목록, ADR-0058 register 목록: §3 이 따르지 않기로 한 `g`
- ADR-0054 트리에서 파일 만들고 지우고 이름 바꾸기: `m` 접두 키와 「트리에 머문다」
