# ADR-0028: 터미널의 ambiguous 폭을 재서 박스 문자를 고른다

- 상태: 채택
- 날짜: 2026-08-14

## 맥락

화면에 그려지는 박스 그리기 문자는 여덟 개다.

| 문자 | 코드포인트 | 자리 |
|---|---|---|
| `│` | U+2502 | sidebar 구분선(모든 행), tabline 의 tab 사이, 팔레트 좌우 |
| `─` | U+2500 | 팔레트 가로선 |
| `┌ ┐ └ ┘ ├ ┤` | U+250C, 2510, 2514, 2518, 251C, 2524 | 팔레트 모서리와 갈림 |

여덟 개가 전부 East Asian Width 가 **Ambiguous** 다(`golang.org/x/text/width` 로 확인).
Ambiguous 는 이름 그대로 폭이 정해져 있지 않다 — "ambiguous 를 두 칸으로" 설정(iTerm2·Windows
Terminal 에 있다) 이나 그렇게 도는 CJK 로케일에서는 두 칸으로 그려진다. 터미널마다 정하는 방식이
달라서(tmux 는 그런 옵션 없이 제 폭 표를 따른다) 설정을 읽어 아는 길은 없다.

우리 폭 계산(`clusterAt` → `charm.land/x/ansi`) 은 한 칸으로 본다. 두 칸으로 그리는
터미널에서는 이렇게 어긋난다.

- **sidebar 구분선은 매 행에 있다.** 한 칸씩 밀린 것이 행마다 쌓여 편집 영역 전체가 오른쪽으로
  밀리고 화면 끝이 흘러넘친다.
- **팔레트 테두리가 깨진다.** 각 행이 정확히 `paletteWidth()` 칸이라는 전제가 무너진다.

ADR-0020 에서 공백 마커를 고를 때 같은 문제를 만나 `·`(Ambiguous) 를 `⋅`(Neutral) 로
바꿨다. 그때는 "박스 문자는 대체할 Neutral 글자가 없다" 고 적고 `docs/tasks.md` 로 미뤘다.

다시 재보니 그 전제가 반은 틀렸다. U+2500 블록 128 자 중 16 자가 Neutral 이다 —
점선 `╌╍╎╏`(254C–254F) 와 반쪽선 `╴╵╶╷╸╹╺╻╼╽╾╿`(2574–257F). 세로선과 가로선은 갈아치울 수
있다. 하지만 **모서리는 Neutral 이 하나도 없다.** 블록 원소도 `▐`(2590) 와 `░`(2591) 만
Neutral 이고 `▌`·`▏`·`█` 은 전부 Ambiguous 다.

## 결정

**시작할 때 터미널이 Ambiguous 글자를 몇 칸으로 그리는지 재고, 한 칸으로 확인된 터미널에서만
유니코드 박스를 쓴다.** 두 칸이거나 재지 못하면 ASCII `| - +` 로 내린다.

**재는 방법은 커서 위치 되묻기다.** 줄 맨 앞으로 가서(`\r`) `│` 를 하나 찍고 `ESC[6n`(DSR 6)
을 보낸 뒤 답(`ESC[행;열R`) 의 열에서 1 을 뺀다. 답을 받으면 `\r ESC[K` 로 찍은 글자를 지운다.
alt screen 에 들어가기 전이라 이 글자는 셸이 쓰던 화면에 찍힌다 — 지우지 않으면 편집기를 끝낸 뒤
그 줄이 그대로 남는다.

**`tea.NewProgram` 보다 먼저 잰다.** 나중이면 bubbletea 가 이미 stdin 을 읽고 있어서 답을
그쪽이 가져간다.

**못 재면 ASCII 다.** tty 가 아니거나, 100ms 안에 답이 없거나, 답을 알아볼 수 없을 때다.

**고른 글자는 `editor.boxChars` 에 `boxSet` 값으로 들어간다.** `boxSet` 은 여덟 자리에 이름을
붙인 struct 값이다. 어느 쪽을 쓸지는 `core.Run` 이 재본 뒤 한 번 넣어주므로 편집기 안에는
"ASCII 인가" 를 되묻는 자리가 없다. `viewPalette` 는 `*editor` 를 들고 있어 그대로 읽고,
`sidebar.cells` 와 `treeRow.cell` 은 인자로 받는다.

**zero value 는 글자가 빈 `boxSet` 이다.** 그러므로 화면을 그리는 테스트는 편집기를 만드는
자리(`newTestEditor`·`newTabsEditor`·`newTreeEditor`) 에서 `boxUnicode` 를 넣는다.

**이번에 물러서는 것은 테두리·구분선뿐이다.** 파일 내용의 폭 계산(`clusterAt`) 은 건드리지
않는다.

## 근거

### 왜 그냥 ASCII 로 통일하지 않는가

**대부분의 터미널은 한 칸으로 그린다.** 다수가 멀쩡한데 소수 때문에 모두가 `+---+` 를 보는
것은 손해다. 재는 값이 있으면 양쪽을 다 만족시킬 수 있고, 재는 비용은 시작할 때 한 번
왕복 한 번이다.

### 왜 Neutral 점선(`╎` `╌`) 이 아니라 ASCII 인가

세로·가로는 갈아치울 수 있지만 **모서리가 안 된다.** 결국 모서리는 `+` 가 되고 선 두 종류가
섞인 테두리가 나온다. 그리고 ambiguous 를 두 칸으로 잡는 환경은 대개 CJK 로케일인데,
그 폰트가 `╎`(U+254E) 글리프를 갖고 있으리란 보장이 없다 — 두부(`□`) 가 되면 폭은 맞아도
읽을 수 없다. **물러서는 자리에서는 확실한 쪽이 낫다.** `| - +` 는 Narrow 이고 글리프가
없는 폰트도 없다.

### 왜 bubbletea 의 `RequestCursorPosition` 을 쓰지 않는가

그것은 bubbletea 가 **자기 프레임에서 커서를 놓은 자리**를 되묻는 것이다. 우리가 알아야
하는 것은 "방금 찍은 글자 뒤" 인데, 화면은 bubbletea 가 그리고 커서 자리는 `view.Cursor` 가
정하므로 프로브 글자 바로 뒤에 커서를 둘 수가 없다. 그래서 bubbletea 가 시작하기 전,
날 것의 터미널에 직접 묻는다.

### 왜 goroutine 이 아니라 cancelreader 인가

답하지 않는 터미널에서 읽기를 **끊을 수 있어야** 한다. goroutine 에 읽기를 맡기고
`time.After` 로 넘어가면 그 읽기는 살아남아, 나중에 사용자가 처음 친 키를 한 개 집어삼킨다.
`muesli/cancelreader` 는 bubbletea 가 이미 쓰는 의존성이고 darwin·linux 의 차이를 덮어준다.

### 왜 `map[string]rune` 이나 interface 가 아닌가

`map` 은 키 오타가 컴파일에서 잡히지 않는다. interface 는 구현이 둘뿐이고 동작이 없는 —
글자 여덟 개를 내놓는 것이 전부인 — 자리라 CLAUDE.md 의 "필요하기 전에는 도입하지 않는다" 에
걸린다. 이름 붙은 필드를 가진 struct 값 하나면 컴파일러가 다 잡아준다.

### 왜 zero value 가 ASCII 가 아닌가

"못 재면 ASCII" 는 **실제로 재본 결과**에 대한 결정이고, zero value 는 **재본 적이 없다**는
뜻이다. 둘은 다른 상황이다. 재본 적 없는 곳은 테스트뿐이고, 거기서 유니코드가 기본이어야
기존 화면 문자열 assert 열네 자리가 그대로 뜻을 유지한다.

### 왜 파일 내용의 폭 계산은 건드리지 않는가

**범위가 다르고 위험이 다르다.** 테두리는 우리가 그리는 것이라 글자를 갈아 끼우면 끝이지만,
폭 계산은 커서 이동·줄바꿈·마우스 클릭·검색 강조가 전부 매달린 자리다. `clusterAt` 이
`ansi.GraphemeWidth` 대신 `displaywidth` 의 `EastAsianWidth` 옵션을 타야 하고, 테스트가 두
모드를 다 돌아야 한다.

미루는 값이 크지 않다. **재는 값은 이미 손에 있으므로** 넓히기로 하면 그 값을 그대로 쓰면
된다. `docs/tasks.md` 에 남겼다.

## 결과

좋은 점

- ambiguous 를 두 칸으로 잡는 터미널에서 sidebar 아래가 밀리지 않고 팔레트가 깨지지 않는다.
- 멀쩡한 터미널은 지금 그대로 유니코드 박스를 본다. 잃는 것이 없다.
- "이 터미널은 ambiguous 를 두 칸으로 본다" 는 사실을 편집기가 알게 됐다. 파일 내용까지
  넓힐 때 다시 잴 필요가 없다.

감수하는 것

- **시작할 때 왕복이 한 번 붙는다.** 답하는 터미널에서는 눈에 띄지 않고, 답하지 않는
  터미널에서는 100ms 늦다.
- **재는 동안 터미널을 잠깐 raw mode 로 바꾼다.** 답을 읽으려면 echo 와 줄 단위 입력을 꺼야
  한다. 끝나면 되돌리지만, 그 사이에 사용자가 친 키는 답 앞에 섞여 버려진다.
- **답하지 않는 정상 터미널은 이유 없이 ASCII 를 본다.** DSR 은 오래된 표준이라 드물 것으로
  본다.
- **파일 내용은 여전히 어긋난다.** 재고도 쓰지 않는 자리가 생겼다.
- **테두리 글자가 두 벌이 됐다.** 화면 문자열을 글자 그대로 확인하는 테스트는 어느 벌을
  쓰는지 밝혀야 한다.

## 대안

**그대로 안고 가기** — 아무것도 안 한다. 문제가 나는 환경이 소수라는 판단인데, 그 소수에서는
편집기가 못 쓸 정도로 깨진다.

**늘 ASCII** — 확실하고 코드가 가장 적다. 대신 멀쩡한 터미널을 쓰는 다수가 이유 없이 투박한
화면을 본다.

**Neutral 점선 + `+` 모서리로 통일** — 재지 않아도 되고 ASCII 보다 낫다. 선이 두 종류로
섞이고, 정작 문제가 나는 CJK 환경의 폰트가 그 글자를 가졌는지 보장할 수 없다.

**문자를 버리고 배경색으로 가르기** — 공백은 Narrow 라 폭 문제가 원천적으로 사라지고,
statusBar 의 반전 관용구(ADR-0004) 와도 결이 같다. 하지만 256색 배경을 새로 정해야 하고
팔레트 경계가 흐려진다. 폭이 아니라 **보이는 모양**을 바꾸는 결정이라 이 자리에서 같이
정하기에는 범위가 크다.
