# ADR-0046: 줄 범위는 토큰이고, 그 갈래는 끊은 쪽이 붙인다

- 상태: 채택
- 날짜: 2026-08-21

## 맥락

`:1,5d` 로 줄을 지울 길이 없었다. 지우는 것 자체는 이미 있다. `Buffer.deleteLines(from, to, width)`
가 줄 단위 register·커서 규칙·되돌리기 묶음까지 다 한다(ADR-0013, ADR-0017). 없던 것은
**"어느 줄인가" 를 명령줄에서 받는 길**이다.

ADR-0045 가 `:!` 를 넣으면서 파싱을 상태 기계 둘로 세우고, 범위가 올 자리를 적어 두었다.
*"범위 문법(`:1,5d`) 은 commandName 앞에 상태가 하나 더 붙는 자리다"*.

그 자리를 열면서 걸리는 것이 셋이다.

1. **범위는 이름 앞에 오는데 토큰이 문자열이었다.** `1,5d` 를 tokenize 하면 토큰 하나(`1,5d`)다.
   범위를 따로 끊어야 하고, 끊은 뒤에는 **뒤쪽 기계가 그것이 범위임을 알아야** 한다.
   `:e 1,5` 의 `1,5` 는 파일 이름이고 글자가 똑같다. 문자열만 보고는 가를 수 없다
2. **어디까지의 문법을 받을 것인가.** vim 은 주소에 숫자·`.`·`$`·`%`·`+N`·`-N`·마크(`'<`)·
   검색(`/pat/`) 을 다 받는다
3. **어느 명령이 범위를 받는가**

## 결정

### 토큰이 자기 갈래를 들고 다닌다

`tokenize` 가 `[]string` 이 아니라 `[]token` 을 준다.

```go
type token struct {
	text string
	kind tokenKind
}

const (
	tokenKindWord  tokenKind = iota // 여느 토큰. 이름이거나 인자다
	tokenKindRange                  // 이름 앞의 줄 범위(`1,5`, `%`, `.,+3`)
	tokenKindShell                  // 이름 자리의 `!` 뒤를 뜯지 않은 한 줄
)
```

**어디서 끊겼는지는 끊은 쪽만 알 수 있다.** 글자 단위 기계는 "맨 앞에서 숫자를 만났다" 를 알고
있었고, 그 사실을 문자열에 담을 방법이 없어서 버리고 있었다. 갈래를 실어 보내면 토큰 단위 기계가
문자열을 보고 갈래를 되짚는 자리가 없다. ADR-0034 가 지운 「파싱이 세 겹」이 범위에서 되살아나지
않는다.

이 덕에 ADR-0045 에 남아 있던 마지막 문자열 비교(`token == "!"`) 도 같이 없어졌다.

### 이름 자리의 `!` 에 `tokenKindBang` 을 두지 않은 이유

처음에는 `!` 를 자기 토큰(`tokenKindBang`) 으로 두고 뒤쪽을 셸 토큰으로 줬다. 범위를 넣자마자
그것이 깨졌다. `:1,5!sort` 에서 `!` 는 **줄 맨 앞이 아니고**, 범위 토큰을 내보내는 자리에서
토큰 둘(`Range` 와 `Bang`) 을 한꺼번에 낼 수 없다.

되짚어 보니 `!` 가 뜻을 갖는 자리는 줄 맨 앞이 아니라 **이름 자리**였다. 그래서 `!` 는 토큰을
내지 않고 상태만 바꾸고, 뒤쪽 한 줄이 `tokenKindShell` 토큰으로 나온다. 이름 자리는 두 곳이라
(`tokenHead`, 그리고 범위가 끝나는 `tokenRange`) 둘 다 `!` 를 그렇게 읽는다.

`:!` 만 쳤을 때 빈 셸 토큰이 남아야 명령이 이름을 잃지 않으므로, "빈 토큰은 버린다" 는 규칙에
셸 줄만 예외를 둔다(`keepToken`). 비어 있다는 것도 결과다.

### 범위 토큰 안쪽은 parseLineRange 하나가 읽는다

글자 단위 기계가 붙여주는 갈래는 **"이것이 범위다"** 까지다. 그 안의 주소 둘과 자리 옮김은
범위 자신의 문법이라 `parseLineRange` 가 읽는다. 주소를 토큰으로 더 잘게 끊지 않은 것은,
그러면 범위 문법이 두 기계에 나뉘어 앉고 `,` 한쪽이 빈 것(`:,5d`) 을 다루는 자리가 늘기 때문이다.

### 받는 문법은 숫자·`.`·`$`·`%` 와 자리 옮김이다

```
:5d          5 줄
:1,5d        1 부터 5 줄
:.d          커서 줄
:.,$d        커서 줄부터 끝까지
:%d          파일 전체 (= `1,$`)
:.,+3d       커서 줄부터 아래 3 줄
:-2,.d       위 2 줄부터 커서 줄
:$-1,$d      끝에서 두 줄
:,5d         커서 줄부터 5 줄 (쉼표 한쪽이 비면 커서 줄이다)
:+3d         커서 아래 3 줄 하나 (base 를 안 쓰면 커서 줄에서 옮긴다)
```

마크(`'<,'>`) 와 검색(`/pat/`) 은 넣지 않는다. `'<,'>` 는 visual 을 나갈 때 확정된 범위를
남기는 결정(ADR-0037 이 보류해 둔 것) 이 먼저다.

### 줄 번호는 세지 않고 들고 있는다

`lineAddress` 는 뜯은 그대로다. base(숫자·커서·마지막) 와 자리 옮김이다. 줄 번호로 바꾸는 것은
실행할 때(`resolve`) 다. `.` 와 `$` 가 몇 번째 줄인지는 buffer 를 봐야 알고, 파싱은 buffer 를
모른다. `:5,1d` 처럼 뒤집힌 것을 바로잡는 자리도 여기다.

**`lineRange` 의 zero 가 "치지 않았다" 다.** 그래서 명령마다 범위 없이 칠 때의 기본값을 스스로
정하고(`:d` 는 커서 줄), 범위를 받지 않는 명령은 붙은 것을 알아채고 거절한다. 이것을 위해
`addressBase` 의 zero 를 `addressNone` 으로 두었다. `.` 는 그것과 다른 값이다.

### 없는 줄은 거절한다. 뒤집힌 것은 바로잡는다

`:1,500d` 를 파일 끝으로 잘라 주지 않는다. 조용히 잘라 주면 손이 미끄러진 것과 시킨 것을 가를 수
없다. vim 도 여기서 거절한다(E16).

뒤집힌 범위(`:5,1d`) 는 되묻지 않고 바로잡는다. vim 은 확인창을 띄우지만, `:5,1d` 가 뜻할 수 있는
것은 1 부터 5 줄 하나뿐이고 잘못 쳤으면 `u` 로 되돌린다.

### 범위를 받는 것은 `:d`·`:y` 와 이름 없는 것

- **`:[범위]d`**
	- `Buffer.deleteLines` 를 그대로 부른다. 지운 줄 수를 알린다.
	- 키로 치는 `dd` 는 글자가 사라지는 것이 화면에 보여서 알리지 않는데(ADR-0017), 손으로 친
	  범위는 화면 밖일 수 있어서 무엇이 사라졌는지 볼 길이 없다. vim 이 `5 fewer lines` 를
	  찍는 이유다.
- **`:[범위]y`**
	- 파일을 건드리지 않으므로 **커서도 움직이지 않는다.** motion 쪽은 이동이 잡은 범위라 커서가
	  따라가야 하지만(`yb` 는 앞으로 간다) 손으로 친 줄 번호에는 따라갈 이동이 없다.
	- 알림 문구는 `y` 가 쓰는 `copiedMessage` 를 그대로 쓴다. 세는 법이 두 벌이 되면 `5y` 와
	  `:.,+4y` 가 같은 일을 하고 다르게 말한다.
- **`:[범위]`**
	- 이름 없이 범위만 친 것이다. 그 줄로 간다(`:5`). 두 자리면 뒤쪽이다.
	- 칸은 첫 비공백이라 `gg`·`G` 와 같다.

나머지 명령에 붙은 범위는 거절한다(`이 명령은 줄 범위를 받지 않습니다`). 조용히 버리면
`:1,5w` 가 그 줄만 쓴 것처럼 보인다. `:1,5!sort`(vim 의 filter) 도 여기서 걸린다. 아직 없는
명령이라는 것을 그 자리에서 알린다.

## 근거

### 왜 `:5` 로 뛰는 것까지 넣었는가

넣지 않으면 `:5` 가 「이 명령은 줄 범위를 받지 않습니다」로 끝난다. 범위를 뜯어서 그 줄을 알고
있는데 거절하는 것이고, vim 에서 가장 많이 치는 범위 형태가 이것이다. 있는 것으로 넉 줄이면 된다.
`moveLineFirstNonBlank` 와 `scrollToCursor` 가 이미 하는 일이다.

### 왜 범위 글자로 시작하는 이름을 걱정하지 않는가

숫자·`.`·`$`·`%`·`,`·`+`·`-` 로 시작하는 명령 이름이 없다. `:e 1,5` 처럼 **인자** 로 오는 것은
맨 앞이 아니라서 글자 단위 기계가 이미 갈라 준다. 나중에 그런 이름이 생기면 그때 부딪히는데,
vim 에도 그런 이름은 없다.

### 왜 상대 지정(`+3`) 까지 넣었는가

`:.,+3d` 는 "여기서 네 줄" 이고 `4dd` 와 같은 일이다. 그런데 `.`·`$` 만 있으면 그 흔한 것을
줄 번호를 세어 쳐야 한다. 뜯는 값은 부호 하나와 숫자 하나이고, `resolve` 에서 더하기 한 번이다.

## 결과

좋은 점

- 화면 밖의 줄을 지우고 복사한다. 커서를 옮겨 세지 않아도 된다
- 한 번의 `u` 로 범위 전체가 돌아온다. `deleteLines` 의 되돌리기 묶음을 그대로 쓴 덕이다
- `:5` 로 줄을 찾아간다
- 토큰이 갈래를 들고 다니게 되어 문자열을 되짚는 자리가 파싱에 하나도 없다
- 범위가 붙을 다음 명령(`:%s` 치환, `:w` 일부 쓰기, filter) 은 `cmd.lines.resolve` 한 줄이다
- `:1,5!sort` 가 「범위를 받지 않는다」로 걸려서, filter 를 넣을 자리가 코드와 문구에 다 남았다

감수하는 것

- **마크(`'<,'>`) 와 검색(`/pat/`) 주소가 없다.** visual 로 고른 범위를 명령줄에서 쓸 수 없다
- **`;` 구분자가 없다.** vim 의 `:1;+3` 처럼 앞자리를 커서로 옮겨 세는 것은 안 된다
- **`:d 3` 처럼 뒤에 붙는 count 가 없다.** 인자로 읽혀 「알 수 없는 명령」이 된다
- **범위 글자로 시작하는 이름을 앞으로도 쓸 수 없다.** 맨 앞의 그 글자는 범위다
- **없는 줄을 거절한다.** `:1,500d` 로 "끝까지" 를 뜻할 수 없고 `:1,$d` 나 `:%d` 를 쳐야 한다
- **`:y` 가 커서를 안 움직이는 것이 vim 과 다를 수 있다.** vim 의 ex 명령은 대개 마지막으로
  건드린 줄로 커서를 옮긴다. 파일을 건드리지 않는 명령이 커서를 옮길 이유가 없다고 봤다

## 대안

- **범위를 문자열로 두고 `commandRange` 가 첫 토큰을 들여다보기**
	- 토큰 type 을 안 바꾼다.
	- `:e 1,5` 의 인자와 `:1,5d` 의 범위를 가를 수 없어서 "맨 앞이었나" 를 다시 세게 된다.
- **주소·쉼표를 각각 토큰으로 끊기**
	- 범위 문법까지 상태 기계가 된다.
	- 문법이 두 기계에 나뉘어 앉고, `,` 한쪽이 빈 것과 빈 토큰을 버리는 규칙이 부딪힌다.
- **상태가 `*command` 를 들고 채우기(기계 하나)**
	- 토큰이라는 개념이 없어진다.
	- `tokenize` 가 명령줄 전용이 되고, 따옴표·`\` 규칙을 다른 곳에서 쓸 길이 막힌다.
- **`%` 를 주소로도 받기(`:%,5d`)**
	- 규칙이 하나가 된다.
	- `%` 는 주소가 아니라 범위 전체라서 `:%,5d` 가 무엇인지 정해야 하는데 vim 도 이것을 거절한다.
- **없는 줄을 파일 끝으로 자르기**
	- `:1,500d` 가 "전부" 로 편하게 읽힌다.
	- 손이 미끄러진 것과 시킨 것을 가를 수 없다.
- **`:5` 를 거절하기**
	- 이 결정을 지우기·복사에만 묶는다.
	- 범위를 뜯어 놓고 가장 흔한 형태를 거절하게 된다.

## 이 ADR 이 정하지 않는 것

- `'<,'>`(visual 로 고른 범위) 와 `gv`. visual 을 나갈 때 확정된 범위를 남기는 것이 먼저다 (ADR-0037)
- `/pat/` 주소와 마크 주소
- `:[범위]!cmd`(filter) 와 `:[범위]w <파일>`(일부 쓰기)
- `:%s/a/b/g` 치환. 범위를 받는 자리는 이 결정이 만들었고 치환 문법은 그쪽이다 (ADR-0010)
- `:d x` 처럼 register 를 이름으로 고르는 것 (ADR-0017)
