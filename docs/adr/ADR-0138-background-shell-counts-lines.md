# ADR-0138: `:!&` 는 셸을 작업으로 돌리고 줄 수만 센다

- 상태: 채택
- 날짜: 2026-09-07
- 관련: ADR-0045(`:!`), ADR-0027(작업 관리자), ADR-0072(폭 눈금), ADR-0139(끝난 목록)

## 맥락

`:!` 는 터미널을 셸에 통째로 넘기고 **편집기가 멈춘 채** 기다린다(ADR-0045). `make dev-run` 처럼 오래 사는 것에는 쓸 수 없어서 `ctrl+z` 로 내려가 셸에서 돌리는 것이 유일한 길이었다.

ADR-0045 는 「셸 명령을 `:jobs` 에서 보고 취소하는 것. **비동기 실행을 정할 때 같이 본다**」로 이 자리를 열어 두었다. 그때 작업으로 돌리지 않은 까닭이 셋이었다.

1. 출력을 담을 화면을 새로 만들어야 한다
2. 대화형 명령이 통째로 빠진다
3. 출력의 색 escape 를 우리가 해석하게 된다

**1 번이 가장 컸는데 이번에는 그 화면을 만들지 않기로 했다.** 바라는 것이 「기다리지 않고 계속 고치기·끝나면 알리기·도는 것 죽이기」 셋이고, 그 셋 가운데 출력을 보는 화면을 요구하는 것이 없다.

## 결정

### 1. 문법은 `:!& <셸 명령>` 이고 `:!` 는 그대로 둔다

접두 두 글자만 우리가 떼고 뒤는 뜯지 않는다. **`:!` 의 「셸 줄은 우리가 뜯지 않는다」가 상하지 않는 것이 이 문법을 고른 까닭이다.** 끝에 붙는 `&` 를 우리가 읽는 길(`:!cmd &`) 은 셸에 넘길 줄에서 글자 하나를 가로채는 일이 된다.

글자 단위 기계에 `!` 를 먹은 다음 자리 상태 하나를 끼우고 `tokenKind` 를 하나 더한다. `tokenRest` 는 셸 줄과 정규식이 함께 쓰는 상태라 **끝에서 낼 갈래를 필드로 받게** 했다. `command` 에 필드는 늘지 않는다. background 인지는 이름(`!&`) 에 들어 있다.

경계가 이렇게 갈린다.

| 친 것 | 이름 | 셸 줄 |
|---|---|---|
| `:!& make` | `!&` | `make` |
| `:!&` | `!&` | 비어 있다. 「셸 명령이 없습니다」 |
| `:!&&make` | `!&` | `&make`. 첫 `&` 만 우리 것이고 나머지는 셸이 읽는다 |
| `:! &make` | `!` | ` &make`. 접두는 정확히 `!&` 두 글자다 |
| `:1,5!&sort` | `!&` | 「줄 범위를 받지 않습니다」 |

**앞뒤 공백은 뗀다. `:!` 는 떼지 않는다.** 셸이 하는 일은 그대로인데(`sh -c " make"` 와 `sh -c "make"` 가 같다) 이 줄이 **작업의 신원**이라 떼야 한다. 안 떼면 `:!& make` 와 `:!&make` 가 서로 다른 작업이 되어 `make dev-run` 이 둘 뜬다. `:!` 에는 신원이 없어서 그 자리가 없었다.

### 2. 출력을 담지 않는다. 줄 수와 마지막 비어 있지 않은 줄만 든다

`:jobs` 에 `200,000` 으로 도는 것이 보이고, 끝나면 요약이 `200,000 줄` 이며, 실패 이유가 마지막 출력 줄이다. **새 화면이 하나도 늘지 않는다** — `job` 의 `done`·`summary`·`err` 세 칸에 그대로 들어간다.

**실패 이유가 사용자가 얻는 전부다.** 출력을 보는 화면이 없으므로 그 한 줄에 값이 다 실린다. 끝에 빈 줄을 붙이는 명령이 흔해서 비어 있지 않은 줄을 든다.

**그 줄을 그대로 화면에 얹을 수 없다.** statusBar 알림과 `:jobs` 의 상태 칸으로 가므로 색을 켜는 escape 가 섞이면 우리 화면에 새고 제어문자가 있으면 커서가 움직인다. `ansi.Strip` 을 걸고 제어문자를 버린다. 편집기가 파일 안의 `\x1b` 를 `^[` 로 그리는 것과 같은 자리다(ADR-0118).

**한 줄에 상한을 둔다(8KiB).** `\n` 없이 계속 오는 출력(`base64 -w0`, `\r` 로 덮어쓰는 진행 막대, minify 된 한 줄) 이 있어서 없으면 그 크기를 우리가 든다. **읽기를 멈추는 것이 아니라 기억만 자른다** — 멈추면 pipe 가 차서 자식이 write 에서 막힌다. 닿으면 조용히 자르지 않고 요약에 적는다(ADR-0077 §7).

### 3. 출력은 exec 가 쥔 pipe 로 받는다. `StdoutPipe` 로 직접 읽지 않는다

이것이 이 결정에서 가장 미묘한 자리다.

```go
cmd.Stdout = counter        // 우리 io.Writer
cmd.Stderr = cmd.Stdout     // 같은 값이면 fd 하나를 쓴다. 순서가 섞이지 않는다
cmd.WaitDelay = shellWaitDelay
```

`StdoutPipe()` 는 `c.Stdout` 에 `*os.File` 을 넣고(`exec.go:1089`), `writerDescriptor`(`exec.go:590`) 는 `*os.File` 이면 그것을 그대로 쓰고 **복사 goroutine 을 만들지 않는다.** 그러면 `WaitDelay` 가 pipe 를 닫아 주는 길이 잠긴다.

그 결과가 이렇다. 손자가 pipe 를 물려받고 직계 자식만 끝나면 EOF 가 오지 않고, **작업 goroutine 이 채널을 닫지 못해 `:jobs` 의 그 줄이 영원히 「도는 중」으로 남는다.** Go 주석이 그 경우를 그대로 적어 두었다.

```
// If WaitDelay is zero (the default), I/O pipes will be read until EOF,
// which might not occur until orphaned subprocesses of the command have
// also closed their descriptors for the pipes.
```

`io.Writer` 를 주면 복사 goroutine 이 생겨 `WaitDelay` 가 제 일을 한다. 대가가 둘이다.

- **`counter` 에 잠금이 필요하다.** 복사 goroutine 이 쓰고 작업 goroutine 이 읽는다
- **`Wait` 가 `exec.ErrWaitDelay` 를 준다.** 명령이 성공했는데도 err 이 non-nil 이 되므로(`exec.go:296`) 따로 잡아 성공으로 읽는다. 안 그러면 성공한 `make build` 가 「실패 exec: WaitDelay expired…」로 남는다

`WaitDelay` 값은 `saveHookTimeout`(2 초) 과 같은 자리다. 둘 다 「여기까지 왔으면 그 판이 무언가 잘못된 것」을 재는 시간이다. **근거 없는 상수가 아니라 막히는 자리가 확인된 상한이다**(ADR-0093).

### 4. 세션을 가른다(`Setsid`). 죽이기 때문이 아니라 신호 때문이다

`SysProcAttr{Setsid: true}` 면 자식이 새 세션 리더가 되고 제어 터미널이 없다. pgid 는 그대로 자기 pid 라 `kill(-pid, …)` 도 그대로 된다.

- **`:!` 중에는 `ctrl+c` 가 진짜 SIGINT 이고 foreground 프로세스 그룹 전체에 간다.** 안 가르면 `:!` 를 끊으려 누른 한 번이 돌던 `make dev-run` 까지 죽인다
- **`ctrl+z`(`tea.Suspend`) 는 `syscall.Kill(0, SIGTSTP)` 로 그룹 전체를 멈춘다**(`bubbletea/v2@v2.0.9/tty_unix.go:44`). 안 가르면 빌드까지 정지하고, 정지한 자식은 `Wait` 가 안 돌아와 작업이 얼어붙는다
- **제어 터미널이 없으면 `/dev/tty` 열기가 실패한다.** `sudo` 가 화면 한가운데에 「Password:」를 찍거나 SIGTTIN 으로 조용히 정지하는 대신 「sudo: a password is required」로 곧 끝난다. 재서 확인했다

`stdin` 은 세우지 않는다. nil 이면 자식이 `/dev/null` 을 읽어 즉시 EOF 다. **대화형 명령은 이 길로 돌 수 없고 그 사실이 마지막 줄에 남는다.** 그것이 필요하면 `:!` 다.

### 5. 죽이는 것은 `cmd.Cancel` 한 곳에서만. `x` 는 SIGTERM, `X` 는 SIGKILL

`exec.CommandContext` 의 기본값은 직계 자식만 죽인다(`exec.go:490`). 그것을 그룹 kill 로 덮는다.

**`Cancel` 안에서만 pid 를 읽으면 경쟁이 없다.** exec 은 `Start` 가 실패하면 `Cancel` 을 부르지 않고 감시 goroutine 은 `Start` 의 끝에서 뜨므로 그 시점에 `Process` 가 이미 차 있다. 밖에서 pid 를 들고 다니면 그것을 읽고 쓰는 자리가 갈려 경쟁이 생긴다.

**`pid <= 1` 을 반드시 확인한다.** `kill(-0, …)` 은 우리 프로세스 그룹 전체(편집기와 그 터미널의 모든 것) 이고 `kill(-1, …)` 은 보낼 수 있는 모든 프로세스다. 방어가 아니라 필수다 — 이 문서를 쓰다 손으로 재던 중에 실제로 자기 그룹을 쏴서 셸이 죽었다.

키를 둘로 나눈 까닭은 **ctx 를 한 번만 끊을 수 있어서**다.

- **`x`**: 지금 그대로 `cancelJob`. ctx 가 끊기고 `cmd.Cancel` 이 그룹 SIGTERM 을 보낸다. 서버가 소켓·pid 파일을 치울 틈이 있다
- **`X`**: 들고 있던 그룹에 곧바로 SIGKILL. ctx 와 무관한 길이라 이미 `x` 를 누른 것에도 듣는다. 죽일 프로세스가 없는 작업(grep·트리 읽기) 에서는 `x` 와 같이 동작한다

「안 죽네」를 본 사람이 더 세게 누르는 것이라 타이머도, 숨은 goroutine 도, 「몇 초 뒤에 올린다」는 상수도 없다.

그룹 번호는 `editor` 가 셸 줄로 찾는 표에 든다. **작업 목록에 담지 않는다** — 실행기는 진행률만 알고 결과 모양은 작업이 정한다는 규칙이라(ADR-0025), 프로세스를 아는 것도 그 일을 하는 쪽이다. 지우는 자리는 `jobDoneMsg` 하나다. 끝났든 실패했든 취소됐든 그곳을 지나므로 지우는 곳이 하나로 남고, 남겨 두면 그 pid 가 돌아 쓰일 때 남을 죽인다.

### 6. 취소한 뒤에는 조각을 보내지 않는다

`cancelJob` 이 `context.Canceled` 를 **미리** 적어 두는데, 그 뒤 runner 가 err 을 실은 조각을 보내면 `updateJob` 이 그것을 덧칠한다. 그러면 그만하라고 한 사람에게 `signal: terminated` 가 실패로 뜨고 「취소는 알리지 않는다」(ADR-0027) 가 깨진다.

**err 을 보고 가릴 수도 없다.** 신호로 죽은 프로세스의 `Wait` 는 `context.Canceled` 가 아니라 `*ExitError`(`signal: terminated`) 를 준다. 그래서 **우리가 끊었다는 사실만 본다** — `ctx.Err() != nil` 이면 그대로 물러난다.

### 7. 진행 조각은 ticker 로 모은다

**줄마다 보내지 않는다.** 20 만 줄을 뱉는 명령에 Update 와 View 가 20 만 번 돌고, 채널에 버퍼가 없어서 편집기의 그리는 속도가 자식의 속도를 잡는다.

**줄 수로 모으지도 않는다.** 「N 줄마다」는 조용한 쪽에서 깨진다. `make dev-run` 은 석 줄 뱉고 몇 시간 조용한데, 그러면 그 석 줄이 상한에 닿지 못해 화면에 영영 오르지 않는다. 안 보고 있던 것을 위한 기능인데 정작 볼 것이 비어 있게 된다.

줄은 채널로 받고 ticker 가 울릴 때 바뀐 것이 있으면 한 조각을 보낸다. 간격은 `editIdleDelay`(250ms) 와 같은 자리다. 그것이 이미 「손이 멈춘 것을 알아보고 화면을 다시 맞추는」 간격이라 화면을 다시 그리게 하는 리듬을 하나로 둔다. 재보니 20 만 줄이 2 초에 쏟아지는 동안 편집기가 키를 그대로 먹었다.

### 8. 성공도 알린다

`finishJob` 은 실패만 알리는데(ADR-0027) 이 작업은 **안 보고 있던 것이 요점**이라 끝난 것을 말해야 한다. 마지막 조각의 `apply` 안에서 알린다 — 설치 작업이 같은 자리에서 성공을 알린다.

```
셸 명령이 끝났습니다: make build (1,204 줄)
셸 명령 make build 실패: make: *** [build] Error 1
```

같은 줄이 이미 돌고 있으면 `startJob` 이 조용히 nil 을 주는데, **프로세스를 띄우는 자리가 그 안이라** 먼저 물어야 한다. 묻지 않으면 갈 곳 없는 셸이 하나 뜬다. 조용히 물러나지 않고 알리는 것은 사람이 방금 친 것이기 때문이다.

### 9. 나가는 길은 끊고 나서 직접 죽인다

**`tea.Quit` 은 ctx 를 끊지 않는다.** 받은 것을 그대로 넘기면 `q` 로 끝냈을 때 도는 작업의 ctx 가 살아 있고, 그러면 조각을 받는 쪽이 없어져 작업 goroutine 이 `select` 에 갇힌다. `defer` 도 `cmd.Wait` 도 kill 도 돌지 않는다.

두 겹으로 막는다.

1. **작업용 ctx 를 루트에서 한 겹 갈라 두고 나가는 길에 끊는다.** 프로세스를 띄운 작업(`gopls 설치`) 이 편집기보다 오래 사는 것은 지금도 있는 병이라 이것이 같이 고친다
2. **background 셸은 그룹째 동기로 죽인다.** ctx 를 끊어도 신호를 보내는 것은 exec 의 감시 goroutine 이고, `main` 이 먼저 반환하면 그것이 돌지 않는다. 여기서 직접 그룹에 보내면 커널이 그 자리에서 배달한다

**`signal.NotifyContext` 에 `SIGHUP` 을 더한다.** 터미널 창을 닫으면 오는 신호이고, 듣지 않으면 defer 가 하나도 돌지 않는다. 커널은 hangup 을 foreground 그룹에만 보내므로 세션을 갈라 둔 자식은 신호를 받지도 못한다. `SIGINT` 와 달리 ADR-0045 의 결정을 건드리지 않는다.

`q` 확인창은 손대지 않는다. 「죽이고 나간다」로 정했으므로 묻지 않는다.

### 10. statusBar 진행 표시가 가장 나중에 시작한 것을 가리킨다

예전에는 맨 앞, 곧 가장 먼저 시작한 것을 가리켰고 그 까닭이 「끝날 때까지 가리키는 것이 바뀌지 않아야 눈이 따라간다」였다. **그 전제가 수명이 비슷한 작업들을 깔고 있었다.** 몇 시간 도는 셸 명령이 맨 앞을 차지하면 그 뒤 git 갱신·인덱싱·검색이 영원히 `(+N)` 으로만 보인다.

눈이 따라가는 값은 잃는다. 대신 **지금 무엇이 도는지**를 늘 답한다. 오래 도는 것은 시작한 사람이 이미 알고 끝나면 알림이 오므로 statusBar 가 그것에 붙어 있을 이유가 없다.

### 11. `:jobs` 가 열려 있는 동안만 경과 시간을 다시 그린다

이 판은 진행 msg 가 올 때만 View 를 지나므로, 조용한 작업 하나만 돌면 경과 시간이 `0:03` 에 얼어붙는다. 도는 것과 멈춘 것이 화면에서 구별되지 않는다.

**판이 tick 을 낸다. 작업이 내지 않는다.** 작업이 heartbeat 를 보내면 `:jobs` 를 열지도 않은 사람에게 1 초마다 Update 와 View 왕복이 생긴다. 판이 내면 다음 tick 을 거는 자리가 이 판의 Update 뿐이라 **닫는 순간 비용이 0 이다.** 간격은 1 초다 — 경과 칸이 `분:초` 라 초가 이 판이 보여줄 수 있는 가장 작은 단위다.

### 12. unix 전용으로 정한다

`SysProcAttr{Setsid}` 와 `syscall.Kill` 은 windows 에 없다. `GOOS=windows go build ./...` 가 **이 변경 전에는 통과했고**(재봤다) 이것이 그것을 처음으로 깨뜨린다.

**build tag 를 들이지 않는다.** 짓는 목표에 windows 가 없고(`scripts/makefile.d/build.mk` 에 `GOOS` 가 없다), 이 저장소에 build tag 가 하나도 없다는 것 자체가 결정이었고, 가르면 **돌려본 적 없는 windows 경로**가 영구 부채로 남는다. `:!` 가 `$SHELL`·`sh` 를 부르는 것도 이미 windows 에서는 뜻이 없다.

## 감수하는 것

**스스로 그룹을 새로 만든 자식은 놓친다.** `kill(-pgid)` 는 그 그룹에만 간다. 재서 확인했다 — `make dev-run` 의 `watcher` 가 자기 자식(`make test run`) 을 새 그룹에 넣어서, `x` 로 그룹을 죽인 뒤 그것이 고아로 남았다. **사용자의 본보기가 하필 이 경우다.** 세션으로 죽이려면 프로세스 전부를 훑어 세션 번호를 견줘야 하는데 그 목록을 얻는 길이 GOOS 마다 달라 두지 않았다(`docs/tasks.md`).

**출력을 다시 볼 길이 없다.** 줄 수와 마지막 한 줄이 남는 전부다. 실패한 빌드의 오류를 보려면 `:!` 로 다시 돌린다. 되찾는 길은 출력을 담을 화면이고 그것을 만들지 않은 것이 이 ADR 이다.

**대화형 명령이 빠진다.** ADR-0045 가 든 까닭 둘째가 그대로 남는다. `Setsid` 로 매달리는 대신 곧 실패하게 만든 것이 답이고, 그 명령은 `:!` 로 돌린다.

**거두어진 pid 를 쏠 좁은 창이 남는다.** Go 에 그룹 kill 의 pidfd 상당물이 없다. `Getpgid(pid) == pid` 확인이 창을 좁힌다.

**windows 를 짓지 못한다.** 위 12 번의 대가다.

**statusBar 가 가리키는 것이 오다마다 바뀐다.** 10 번의 대가다.

## 대안

- **`:!cmd &` 로 끝의 `&` 를 우리가 읽기** — 셸에 넘길 줄에서 글자 하나를 가로챈다. 「뒤를 뜯지 않는다」가 상한다
- **셸에 맡기기(`:!cmd &` 를 그대로 셸에)** — `sh -c` 가 곧 끝나 고아가 되고 줄 수도 못 세고 `:jobs` 에도 안 뜬다
- **출력을 담을 화면 만들기** — ADR-0045 가 잰 그 값이 그대로다. 필요해지면 `docs/tasks.md` 의 항목이다
- **`StdoutPipe` 로 직접 읽기** — 3 번에 적은 대로 손자가 pipe 를 붙들면 작업이 영원히 안 끝난다
- **줄 수로 조각을 모으기** — 7 번. 조용한 명령의 꼬리를 잃는다
- **SIGTERM 뒤 타이머로 SIGKILL 올리기** — 「몇 초 뒤」라는 근거 없는 상수와 자는 goroutine 이 하나 늘고, 그동안 pid 재사용 창이 넓어진다. `X` 가 그 자리를 사람 손으로 대신한다
- **`_unix.go`·`_windows.go` 로 가르기** — 12 번

## 결과

- `:!& make dev-run` 을 치면 편집기가 멈추지 않고 `:jobs` 에 `셸 명령` 이 선다
- 끝나면 성공도 실패도 알리고, 실패 이유가 마지막 출력 줄이다
- `x` 로 그룹 SIGTERM, `X` 로 그룹 SIGKILL. 손자까지 죽는다(스스로 그룹을 만든 것은 뺀다)
- 편집기를 끄면 도는 셸이 같이 죽는다. 터미널 창을 닫아도 그렇다
- `:!` 는 그대로다. `ctrl+c`·`ctrl+z` 가 background 를 건드리지 않는다
- 시험은 `internal/core/shell-background_test.go` 와 `command-parser_test.go` 다
