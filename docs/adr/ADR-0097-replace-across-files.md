# ADR-0097 여러 파일 치환은 찾은 목록을 확정하는 것이고, 되돌리기는 git 이 받는다

- 상태: 채택
- 날짜: 2026-08-28
- 관련: ADR-0084(`:s` 의 문법), ADR-0077·ADR-0078(여러 파일 검색과 그 판), ADR-0067(rename 이 디스크에 쓰는 손), ADR-0075(작업의 이름과 인자), ADR-0089(고른 범위 안의 치환)

## 맥락

`docs/tasks.md` 의 v1.1 에 마지막으로 남은 기능이다.

> 여러 파일 replace. 한 파일 안의 치환은 `:s` 가 답했고(ADR-0084) 여기서 새로 오는 것은 작업(job)·열려 있지 않은 파일의 저장·되돌리기 셋이다

**적어 둔 셋 중 둘은 이미 답이 있었다.** 코드를 읽고 재 보니 이렇다.

- 작업은 `:grep` 이 냈다. `grepFiles` 가 파일 열거(`.gitignore` 포함)·이진 판정·크기 상한·진행도·취소를 다 들고, 고치던 buffer 를 얹는 `dirtyOverlay` 까지 있다
- 열려 있지 않은 파일의 저장은 rename 이 냈다. `applyRenameTo` 가 「열린 tab 은 buffer 를 고쳐 `Save`, 아닌 것은 `OpenBuffer` → 고침 → `write()`」로 답했다(ADR-0067)
- 되돌리기만 진짜로 남았다. rename 도 풀지 못하고 git 을 안전망으로 두었다

치환 알맹이도 그대로 쓴다. `substitution.applyRange(line, from, to)` 가 **줄 하나를 받아 바꾼 줄과 바꾼 수를 주는 함수**라 파일과 무관하다.

그래서 이 결정이 새로 정하는 것은 배관이 아니라 **손**이다. 어느 문으로 부르는가, 무엇을 묻는가, 되돌리기를 어떻게 하는가 셋이다.

## 1. 문은 둘이고 끝나는 자리는 하나다

`:replace/a/b/g` 로 부르면 **먼저 찾아 판을 연다.** 곧바로 바꾸지 않는다. 그리고 `:grep` 으로 이미 열려 있는 판에서도 같은 자리로 들어온다.

찾기와 바꾸기를 나눈 것이 요점이다. 한 명령이 찾자마자 써 버리면 **무엇이 바뀔지 보기 전에 저장소가 바뀐다.** 되돌리기가 약한 이 기능에서 그것은 감당할 수 없다(§4). 판은 이미 「둘러보고 확정하는」 손을 들고 있어서(ADR-0078) 미리보기를 새로 만들 것이 없다.

이름은 `:replace` 다. 찾기가 `:grep` 이라 바꾸기가 `replace` 인 것이 짝으로 읽힌다. 구분자 문법은 `:s` 와 같고 파서도 그쪽 겹(`takesDelimitedArgument`) 을 그대로 쓴다. `parseSubstitute` 가 통째로 재사용된다.

## 2. 바꾸는 단위는 줄이다

`grepLines` 가 **줄마다 첫 매칭만 담는다**(ADR-0077). 목록에 같은 글이 두 줄 서면 훑는 데 방해가 되어서 그렇게 정한 것인데, 그 덕에 여기서 「하나씩」의 단위가 저절로 정해진다. 목록의 한 줄이 곧 물어볼 한 자리다.

그래서 바꾸는 것도 줄 단위다. 고른 줄에 `applyRange(line, 0, len(line))` 를 건다. `g` 가 있으면 그 줄의 매칭이 다 바뀌고 없으면 첫 하나다. **목록에 안 보이던 같은 줄의 둘째 매칭이 `g` 로 같이 바뀌는 것**이 이 규칙의 결과이고, 그것이 옳다 — `:s///g` 가 한 파일에서 하는 일과 같아야 한다.

## 3. 자리는 다시 맞춘다. 담아 둔 col 을 믿지 않는다

`grepHit` 은 `col`·`end` 를 들고 있다. 그것으로 바로 잘라 붙이면 빠르지만 **틀린다.**

찾은 순간과 바꾸는 순간 사이에 파일이 움직인다. fsnotify 가 밖의 변경을 물어오고(ADR-0093), 사람이 판을 열어 둔 채 편집할 수 있고, 판은 열려 있는 동안 계속 산다. 담아 둔 byte 자리로 잘라 붙이면 그 사이에 밀린 만큼 **글자 가운데를 자른다.**

그래서 **적중은 「어느 파일 어느 줄인가」만 정한다.** 바꿀 때 그 줄을 다시 읽어 그 자리에서 다시 맞춘다. 다시 맞춰서 안 걸리면 그 줄은 건드리지 않고 세어 둔다 — 「목록에는 있었는데 지금은 아닌」 줄이 몇인지 알리는 것이 조용히 지나가는 것보다 낫다.

값도 싸다. 어차피 파일을 열어야 쓸 수 있고, 다시 맞추는 것은 그 줄 하나에 정규식 한 번이다.

## 4. 되돌리기는 git 이 받는다

`u` 는 buffer 안의 일이라 디스크에 쓴 것을 못 돌린다. 이것이 rename 이 부딪힌 벽 그대로이고(ADR-0067) 여기서도 답이 같다.

**두 갈래가 갈리는 것을 그대로 둔다.** 열려 있는 tab 은 buffer 를 고쳐 저장하므로 `u` 가 산다. 열려 있지 않은 파일은 git 만 받는다. 한 번의 치환이 두 가지 되돌리기에 걸리는 셈인데, 이것을 맞추려면 길이 둘이다.

- **바꿀 파일을 전부 tab 으로 연다.** 그러면 `u` 가 전부 산다. 그런데 한 번의 치환에 tab 이 스무 개씩 열리고 나면 그 뒤로 편집기를 쓸 수가 없다. ADR-0067 이 rename 에서 같은 까닭으로 물린 길이다
- **buffer 밖의 되돌리기 이력을 새로 만든다.** 편집기가 처음으로 파일 밖의 이력을 들게 된다. 그것을 어디에 얼마나 두는지가 통째로 새 결정이고, 이 기능 하나를 위해 열 문이 아니다

그래서 **무엇을 바꿨는지 알리는 것으로 대신한다.** rename 과 같다. 바꾼 파일 수와 줄 수를 알림에 적고 `:messages` 에 남긴다.

## 5. 묻는 것은 한 번이고, 고르는 것은 셋이다

찾은 뒤 아래 줄이 묻는다.

```
파일 12 개 87 줄을 바꿉니다   a 전부  y 하나씩  q 그만
```

**`a` 와 `y` 를 둘 다 둔다.** 넓게 치는 치환은 목록을 보고 한 번에 확정하는 것이 손에 맞고, 좁게 치는 치환(같은 낱말이 주석에도 있고 문자열에도 있는 자리) 은 하나씩 봐야 한다. 하나만 두면 다른 쪽이 못 쓰게 된다.

**`c` flag 를 치면 묻지 않고 곧바로 하나씩 간다.** `:replace/a/b/gc` 다. `:s///c` 가 이미 쓰는 글자라 새로 외울 것이 없고 `parseSubstitute` 가 이미 읽고 있다. flag 를 아는 사람은 한 걸음을 아끼고, 모르는 사람은 확인창에서 고른다.

**`a` 에도 물음을 남긴 것이 이 절의 요점이다.** rename 은 묻지 않고 바로 쓰는데(ADR-0067) 그쪽은 언어 서버가 「이 이름이 가리키는 자리」를 답한 것이라 사람이 고른 범위가 이미 좁다. 치환은 정규식이라 `.` 하나로 저장소 전체가 온다. 되돌리기가 약한 것을 이 한 걸음으로 갚는다.

## 6. 하나씩은 판에서 훑는다

`c` 로 가는 자리는 `:s///c` 의 편집 화면 물음(view-editor-substitute.go) 이 아니라 **판이다.** 키는 같다(`y` 바꾸기, `n` 넘기기, `a` 남은 것 전부, `q` 그만).

까닭은 보여줄 것이 파일을 넘나들기 때문이다. `:s///c` 는 한 buffer 안이라 커서를 옮기는 것으로 「지금 물어보는 자리」가 드러나는데, 여기는 자리마다 파일이 달라서 tab 을 옮겨 가며 물어야 한다. 그 손을 판이 이미 들고 있다 — `previewSession` 이 둘러보며 연 tab 을 뒤에 정리한다(ADR-0071, ADR-0078).

## 밖에 둔 것

- **되돌리기.** §4 대로 git 이 받는다
- **팔레트 항목.** 「프로젝트 검색」으로 찾은 뒤 `r` 로 넘어가는 길이 이미 있다. 따로 두려면 `/a/b/g` 를 통째로 받는 박스가 하나 더 생기는데, 찾을 것과 바꿀 글을 한 줄에 치는 것은 명령줄의 손이지 박스의 손이 아니다
- **파일 이름 바꾸기·만들기·지우기.** 치환은 내용만 건드린다
- **범위를 경로로 좁히는 것.** `:grep` 이 아직 못 하는 것이라(docs/tasks.md) 여기만 먼저 낼 자리가 아니다
- **포매터.** 걸지 않는다. 치환 하나에 남의 파일이 통째로 다시 포맷되면 그 diff 가 무엇 때문인지 알 수 없다. rename 이 같은 까닭으로 뺐다(ADR-0065, ADR-0067)
