# ADR-0027 작업 관리자 — 취소, 목록, 결과

## Status

Accepted

ADR-0025 의 바탕 위에 얹는다. "실행기는 진행률만 안다" 는 선은 결과 쪽에서 그대로 두고,
수명(취소) 쪽에서만 실행기가 관여하도록 넓힌다.

## Context

ADR-0025 의 실행기는 진행률만 추적하고 실행에는 관여하지 않았다. `go` 를 부르는 것은 작업 자신이고
실행기는 채널만 받는다. 그래서 셋이 없었다.

- **취소.** 멈추라고 말할 대상을 안 들고 있었다. 십오만 개짜리 디렉터리에서 팔레트를 닫아도 인덱싱은
  끝까지 돌고, `git ls-files` 는 `exec.Command` 라 프로세스를 죽일 길조차 없었다.
- **돌고 있는 것 보기.** statusBar 는 맨 앞 하나와 `(+N)` 만 찍는다. 둘째가 무엇인지 알 수 없었다.
- **끝난 것 알기.** `jobProgress` 에 오류 자리가 없어서 실패한 작업은 조용히 사라졌다.
  팔레트가 비어 있어도 실패한 것인지 파일이 없는 것인지 갈리지 않았다.

## Decision

### 실행기가 수명을 쥔다 — context 로

`editor` 가 `core.Run` 이 받은 루트 ctx 를 들고, `startJob` 이 작업마다 `WithCancel` 로 나눠 넘긴다.
`cancel` 은 job 에 들고 있다가 `:jobs` 의 `x` 가 부른다.

- `gitFiles` 는 `exec.CommandContext` 다. 큰 저장소에서 가장 오래 걸리는 자리가 취소로 죽는다.
- `walkFiles` 는 콜백이 `ctx.Err()` 를 돌려주어 `WalkDir` 를 멈춘다.
- 조각을 보낼 때 `select` 로 `ctx.Done()` 을 같이 본다. 취소된 뒤 아무도 받지 않는 채널에 막혀
  goroutine 이 남던 것이 이것으로 닫혔다 — ADR-0025 가 "프로세스가 끝나면서 사라진다" 고
  감수했던 자리다.
- 편집기를 끝내면 루트가 끊겨 도는 것이 전부 정리된다.

`context` 를 struct(`editor`) 에 두는 것은 Go 관례에서 벗어난다. 다만 이것은 요청 단위 ctx 가 아니라
편집기 프로세스의 수명 그 자체이고, 팔레트처럼 작업을 시작하는 자리는 인자로 받아올 길이 없다.
비어 있으면 `context.Background()` 로 돈다 — 테스트가 `editor` 를 직접 만든다.

### 취소했다는 것은 실행기가 적는다

작업이 알려주기를 기다리지 않는다. 조각을 보내다 끊긴 작업은 아무 말 없이 채널만 닫으므로,
그것을 기다리면 취소한 작업이 목록에 「끝남」으로 남는다. `cancelJob` 이 `err` 을
`context.Canceled` 로 적고 나서 `cancel()` 을 부른다.

목록에서 바로 빼지는 않는다. 언제 진짜 끝났는지는 작업이 알고, 채널을 닫으면 `jobDoneMsg` 가 와서
나머지는 끝난 작업과 같은 길로 흐른다.

### 결과 모양은 여전히 작업이 정한다

`jobProgress` 에 `summary`(끝나며 남기는 한 줄) 와 `err`(실패한 이유) 를 더했다. 마지막 조각만 채운다.
실행기는 이 둘을 목록에 옮겨 적기만 하고 무엇인지 읽지 않는다 — ADR-0025 가 그은 선이다.
인덱싱은 `"151,933 개"` 를 남긴다.

이 자리에 `apply` 처럼 함수를 두지 않은 것은, 이 둘이 실행기가 **화면에 그려야 하는** 값이기
때문이다. `apply` 는 editor 어딘가를 고치는 것이고 이것은 목록에 찍히는 글자다.

### 끝난 작업은 최근 스무 개를 남긴다

`editor.finished` 에 최근 것부터 쌓고 스무 개를 넘으면 오래된 것부터 버린다. 조용히 실패한 것을
나중에 찾을 수 있을 만큼이면 되고, 그보다 오래된 것은 볼 일이 없다.

> ADR-0030 이 이것을 바꿨다. 주기적으로 도는 작업(git 갱신) 이 생겨서 스무 개 자리를 한 이름이
> 다 차지하게 되었다. 지금은 이름당 마지막 결과 하나이고 개수 상한은 없다.

### 목록은 별도 mode 다

`:jobs` 와 팔레트의 「작업 목록」이 같은 화면을 연다(ADR-0011 의 짝 명령과 같다).

- 팔레트 접두로 두지 않았다. 팔레트는 "고르고 닫는" 자리인데 이 목록은 실시간으로 자라고 줄어든다.
- 하단 pane 으로 두지 않았다. register 보기·quickfix 까지 걸린 큰 결정이고, 편집 영역 높이와
  포커스를 다시 정해야 한다. `docs/tasks.md` 에 남겼다.
- 팔레트처럼 박스로 얹지 않는다. 아래 화면이 비치면 무엇이 움직이는 것인지 읽기 어렵다.
- **tabline 과 sidebar 까지 덮는 전체 화면이다.** 처음에는 편집기 틀(`renderScreen`) 위에 목록만
  갈아끼웠는데, 트리와 tab 이 그대로 있어서 "파일을 보고 있는 화면" 으로 읽혔다. 그러면 여기서 치는
  키가 편집기 키인 줄 알게 된다. 맨 위 제목줄(`작업  도는 중 2 · 끝난 것 3`) 이 tabline 자리를
  대신하고, 목록은 화면 왼쪽 끝에서 시작한다.
- statusBar 만 남긴다. mode 와 git, 알림이 늘 같은 자리에 있어야 한다. 다만 트리를 덮었으므로
  트리가 없는 것으로 치고 그린다 — 목록은 왼쪽 끝인데 statusBar 만 32 칸 밀리면 화면이 반쪽만
  바뀐 것처럼 보인다.
- 터미널 설정(대체 화면, mouse, 키 확장) 은 `render` 에서 `screenView` 로 빼서 나눠 쓴다.
  편집기 틀을 쓰지 않는 화면도 이 설정만은 같아야 대체 화면이 어긋나지 않는다.
- 키는 vim 식이다. `j`/`k`·화살표 이동, `x` 취소, `q`·Esc 닫기. `x` 는 normal 의 "지우기" 와 같은
  결이라 목록에서도 "없앤다" 로 읽힌다. 이 화면에만 있는 키라 안내를 화면에 둔다 —
  statusBar **안**이 아니라 그 바로 위 줄에, 팔레트가 항목 설명에 쓰는 흐린 회색(244)으로.
  statusBar 아래 줄은 다른 mode 와 같이 알림 자리로 비워 두어서, 취소가 안 되는 것을 알릴 때
  안내가 밀려나지 않고 나란히 보인다.

### 실패만 statusBar 아래 줄로 알린다

성공은 조용히 사라지고 취소도 알리지 않는다 — 그만하라고 한 사람이 결과를 이미 안다.
실패는 목록을 열어 보기 전에는 아무 일도 없던 것처럼 보이므로 아래 줄에 적는다.

그러려면 알림이 mode 밖에 있어야 한다. 작업 msg 는 어느 mode 에서든 도착하는데 `message` 는
`viewEditorNormal` 의 필드였다. `editor.message` 로 옮기고 `messageOr(fallback)` 하나로
"알림이 있으면 그것이 먼저" 규칙을 모았다. normal·insert·트리·목록이 이것을 쓰고,
명령줄·검색은 그 줄을 자기 입력에 쓰므로 부르지 않는다.

## Consequences

좋은 점

- 큰 디렉터리에서 시작한 인덱싱을 `:jobs` 에서 `x` 로 멈출 수 있다. `git` 프로세스까지 죽는다.
- 남아 있던 goroutine 누수가 닫혔다. 편집기를 끝내면 도는 작업이 전부 정리된다.
- 조용히 실패하는 작업이 없어졌다. 아래 줄이 알리고 목록에 이유가 남는다.
- 알림이 `editor` 로 올라와서 어느 mode 에서 일어난 일이든 같은 자리에 뜬다.
- 다음 작업(여러 파일 검색·치환) 은 `ctx` 를 받고 `summary` 를 남기기만 하면 목록·취소가 따라온다.

감수하는 것

- **`editor` 가 ctx 를 든다.** Go 관례에서 벗어난 자리이고, 테스트에서 비어 있을 때를 위한
  `rootContext()` 한 겹이 생겼다.
- **취소가 즉시가 아니다.** `x` 는 "그만하라" 까지이고 목록에서 사라지는 것은 작업이 채널을 닫은
  뒤다. 오래 걸리는 한 걸음 안에 있으면 그만큼 늦는다.
- **`:jobs` 는 실시간이지만 스스로 다시 그리지 않는다.** 진행 msg 가 올 때마다 갱신되므로 도는
  작업이 있으면 저절로 움직이지만, 도는 것이 없으면 경과 시간이 멈춘 것처럼 보인다.
- **끝난 작업의 산출물로 들어갈 길이 없다.** 이 목록은 상태만 보여준다. 여러 파일 검색의 적중
  목록 같은 것은 quickfix 결정으로 남겼다.
- **인덱싱에는 실패 경로가 사실상 없다.** git 이 없으면 walk 로 넘어가고 읽지 못한 디렉터리는
  지나간다. 실패 표시는 다음 작업들을 위해 먼저 만들어 둔 것이다.

## Alternatives

**취소 채널(`chan struct{}`)** — context 의존이 없다. 다만 `exec` 로 도는 외부 프로세스를 끊으려면
결국 직접 다뤄야 하고, `exec.CommandContext` 가 이미 하는 일을 손으로 옮기게 된다.

**작업이 스스로 취소를 알리게 하기** — `cancelJob` 이 표시하지 않고 작업이 `err: ctx.Err()` 를 보내는
방식. 조각을 보내다 끊긴 작업은 그 조각조차 보낼 수 없어서 「끝남」으로 남는다.

**하단 pane** — register·quickfix 와 목록 자리를 공유한다. 방향은 맞지만 편집 영역 높이·포커스·mode
를 한 번에 정해야 해서 이번 결정에 얹지 않았다.

**끝난 작업을 남기지 않기** — 가장 단순하다. 실패 알림이 다음 키에 사라지고 나면 무엇이 실패했는지
다시 볼 길이 없어진다.
