# ADR-0120: 렌더는 두 패스로 두되 화면 버퍼는 두지 않는다

## 맥락

ADR-0119 로 `internal/lines` 를 물린 뒤 「그러면 렌더 순서를 어떻게 세울까」가 남았다. 나온 제안은 이랬다.

> 화면 렌더링을 두 단계로 한다. 제어문자와 tab 을 마커·빈 칸으로 전환하고 폭에 따라 재단해 화면 행을 만드는 component 와, 파일 내용을 파싱해 색을 입히는 component 를 둔다. 둘 다 index 는 파일 기준으로만 한다. 그러면 화면에 색과 cell 들이 생긴다.

**두 패스라는 것은 이미 그렇다.** 재보니 이렇게 서 있었다.

| | 무엇 | 화면을 아나 |
|---|---|---|
| A | `wrapOffsets` → `expandRow` | **안다.** 폭으로 재단하고 tab 을 편다 |
| B | `rowHighlight.segments` | **모른다.** 줄 안 offset 구간에 색을 매긴다 |
| 엮는 곳 | `renderRow` | B 가 낸 구간마다 A 를 부르며 `col` 을 이어간다 |

`syntax.Token{Start, End}` 도 줄 안 offset 이고 화면 폭이 바뀌어도 그대로다. 「색을 입히는 쪽은 화면 행을 모른다」는 요건이 이미 성립한다.

정할 것은 **cell 배열(화면 버퍼) 을 둘 것인가** 하나였다.

## 1. 중복 계산이 아니었다

cell 을 도입하는 첫 근거로 「색 구간이 n 개면 `expandRow` 를 n 번 돌리니 줄을 n 번 훑는다」를 들었다. **틀렸다.**

```go
// segments 는 이 행을 빈틈 없이 덮는 구간들이다. 앞에서부터 겹치지 않게 늘어선다.
for _, segment := range hl.segments(row.start, row.end) {
	put(segment.end, segment.style)   // put 은 offset..end 만 훑는다
}
```

구간이 겹치지 않고 빈틈 없이 덮으므로 **합치면 줄을 딱 한 번 지난다.** 늘어나는 것은 함수 호출과 `parts` slice 할당뿐이고, cell 배열로 가면 그 할당은 오히려 는다.

**성능이 근거가 아니었다.**

## 2. 남는 값이 하나였고 그것은 더 싸게 막힌다

cell 이 실제로 사는 것은 **grep 목록이 A 를 쓰지 못한다**는 것 하나였다. `expandRow` 는 색을 입힐 조각(`[]screenPart`) 을 내는데 grep 은 문자열 하나와 **옮겨진 매칭 자리**가 필요해서, `grepExpandScreen` 이라는 다른 길을 간다. ADR-0118 에서 제어문자가 그 길에만 빠져 있던 것이 이 갈림의 대가였다.

cell 이면 둘 다 그것을 쓸 수 있다. 각 cell 이 「이 칸이 줄 안 어느 byte 에서 왔나」를 들기 때문이다.

**그런데 그 하나 때문에 화면 버퍼를 도입하는 것은 값이 안 맞는다.** 빈틈은 이미 `screenText` 로 규칙을 한 자리에 모아 막았고(ADR-0118 §6), 다시 벌어지는 것은 **시험이 지킨다.**

```go
// TestGrepAndEditorExpandAlike
parts, _ := expandRow(line, 0, len(line), 0, markWhitespace(line), defaultTabWidth)
grep, _, _ := grepExpandScreen(text, 0, 0)
assert.Equal(t, 이어붙인(parts), grep)
```

tab·ESC·NUL·DEL·색 escape·한글 여섯 가지로 견준다. 마커는 들여쓰기와 줄 끝에만 붙는 편집 영역만의 것이라(ADR-0020) 그것이 없는 줄로 본다.

## 3. 그래서 경계만 못 박는다

구조는 그대로 두고 세 자리를 코드에 적었다.

- `expandRow` 머리글에 A·B·엮는 곳의 표를 둔다. **`col` 을 이어받는 것이 이 구조의 값**이라는 것도 같이 적는다 — tab 이 미는 폭이 시작 칸에 달려 있어서, 구간을 각각 0 칸부터 세면 들여쓰기가 어긋난다
- `grepExpandScreen` 머리글에 「길이 둘인 것을 그대로 둔다」와 그 까닭, 그리고 시험이 지킨다는 것을 적는다
- 엮는 것은 `renderRow` 하나다. 거기 말고 `col` 을 이어가는 자리가 생기면 그것이 신호다

## 언제 다시 볼까

**화면 버퍼가 실제로 필요해지는 자리가 둘 보인다.**

- **화면 분할.** 같은 파일을 두 폭으로 그리게 되면 「이 칸이 어디서 왔나」를 자주 묻는다
- **가로 스크롤.** 지금은 줄바꿈으로 대신하는데(ADR-0001), 가로로 밀면 화면 칸과 파일 offset 의 매핑이 화면 상태가 된다

그때는 cell 이 사는 값이 생긴다. **지금 안 하는 것은 「나중에도 안 한다」가 아니라 「지금은 살 것이 하나뿐이다」이다.**

## 되짚은 것

**cell 을 밀 뻔했다.** 구조가 깔끔해 보였고 「두 패스를 독립시킨다」는 말이 맞아 보였다. 그런데 근거로 든 성능 이야기가 코드를 다시 읽자 틀린 것이었다 — 구간이 빈틈 없이 덮는다는 주석이 바로 그 자리에 있었는데 안 읽고 말했다.

ADR-0119 가 「이 덩어리가 무엇을 결정하고 있나를 먼저 적는다」로 닫았는데, 여기서는 그 앞이 문제였다. **바꾸자는 근거부터 코드에서 확인해야 했다.** 재보니 남은 근거가 하나였고, 그 하나는 시험으로 막혔다.
