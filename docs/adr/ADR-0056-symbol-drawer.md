# ADR-0056 특수문자를 하단 drawer 에서 이름으로 찾아 넣는다

## 맥락

`▲` 하나를 넣으려면 편집기를 벗어나 다른 곳에서 복사해 와야 했다. `docs/tasks.md` 가
「unicode 이모지, 특수 문자 입력창 / 검색도 가능하고 list 도 보여줌 / command palette 로 접근」
으로 이 자리를 열어 두고 있었다.

두 문서가 서로 다른 것을 가리켰다. tasks.md 는 팔레트라고 적었고, `docs/spec.md` 는 「하단
drawer」를 statusBar 바로 위·편집영역 아래에 두는 것으로 명세만 해 두고 구현이 없었다.
`docs/tasks.md` 의 "하단 목록 pane 을 둘지 정한다" 도 미결이었다.

**팔레트는 여는 길이고 고르는 곳은 drawer 다.** 팔레트의 중심 규칙은 「맨 앞 글자가 갈래를
정한다」 인데(ADR-0011), 격자와 이름줄을 가진 화면은 그 규칙에 들어갈 자리가 없다.
`runJobs`·`runMessages`·`runGotoDefinition` 이 이미 팔레트 항목에서 다른 화면을 여는 길이고
(ADR-0051, ADR-0053), 이것도 그 길을 탄다.

> **`:symbols` 를 뒤늦게 붙였다 (2026-08-27).** 여는 길이 팔레트 하나뿐인 채로 남아 있었다.
> 이 문단이 「팔레트가 여는 길」이라고 적은 것을 「팔레트**만**」으로 굳혀 읽은 것이지 그렇게
> 정한 적은 없다. 짝이 되는 `:` 명령을 두는 것이 이 저장소의 규칙에 가깝다: 하단 drawer 를
> 여는 다른 둘(`:registers`·`:jumplogs`) 도 판과 명령 둘 다로 열리고, 팔레트 표의 `alias` 칸이
> 그 짝을 적는 자리로 이미 있었다. 줄임말은 두지 않았다. vim 에 없는 명령이라 따를 것이 없다.

정해야 하는 것들:

## 1. 얹지 않고 편집 영역의 행을 가져간다

팔레트는 `lipgloss.NewCompositor` 로 편집 화면 **위에** 얹는다. drawer 를 그렇게 하면
**넣는 자리인 커서가 판 밑에 가려진다.** 파일 끝에서 열면 늘 그렇게 된다.
연속으로 넣는 것이 이 mode 의 쓰임새라(§4) 결과가 안 보이는 것은 치명적이다.

그래서 `textHeight()` 에서 뺀다. 그러면 `scrollToCursor` 가 그대로 커서를 살려 준다.
드러난 자리 하나를 고치니 스크롤·커서 좌표·wrap 계산이 전부 따라왔다.

`paneHeight()` 를 새로 두고 편집 영역과 drawer 가 그것을 나눠 쓴다.

```go
func (e editor) paneHeight() int { return max(0, e.height-tablineHeight-statusBarHeight) }
func (e editor) textHeight() int { return max(0, e.paneHeight()-e.drawerHeight) }
func (e editor) sidebarHeight() int { return tablineHeight + e.paneHeight() }
```

`sidebarHeight` 는 빼지 않는다. 폭이 편집 영역과 같아서(spec.md) sidebar 옆을 지나가지
않기 때문이다. drawer 를 열어도 트리 높이는 그대로다. 이 값은 오늘의
`tablineHeight + textHeight()` 와 한 칸도 다르지 않다.

**그리는 것은 여전히 합성이다.** `textHeight()` 가 줄어든 만큼 `renderScreen` 이 아래를 빈
행으로 채우므로 그 빈 자리에 얹는다. `renderScreen` 에 손대지 않았다.

**drawer 를 일반 장치로 만들지 않았다.** spec.md 는 register 보기·상세 오류도 같은 자리를
쓴다고 적었지만 지금 쓰는 곳은 하나다. 두 번째 쓰임이 올 때 가른다.

## 2. 이름은 큐레이션 한국어 표 + 훑어서 얻은 영문

유니코드 공식 이름은 영문뿐이라(`BLACK UP-POINTING TRIANGLE`) `삼각형` 으로는 걸리지 않는다.
셋을 재고 갈랐다.

| | `삼각형` | 표 관리 | 바이너리 |
|---|---|---|---|
| 큐레이션만 | 표에 적은 것만 | 우리가 적는다 | +수십 KB |
| **큐레이션 + 영문 보조** | **표에 적은 것만** | **우리가 적는다** | **+1.12 MB (재봤다)** |
| CLDR 한국어 생성 | 이모지 전부 | 생성 스크립트와 원본 갱신 | +수백 KB |

**CLDR 을 생성하지 않는다.** 이모지 한국어 이름이 공식 표기라는 것이 매력이지만, 생성
스크립트와 원본 갱신을 떠안게 된다. 이 저장소에는 아직 생성 데이터도 `go:embed` 도 없다.
첫 사례로 만들 만큼의 값은 아니었다.

영문 보조는 `golang.org/x/text/unicode/runenames` 다. `x/text` 는 이미 간접 의존이라
새 라이브러리는 아니고 직접 의존으로 올라갈 뿐이다. 대신 이름 표 때문에 바이너리가
**23.4 MB 에서 24.6 MB 로, 1.12 MB(5.0%) 늘었다.**

ADR-0039 가 chroma 를 6MB 로 기각했던 자리와 견준다. 그때는 늘어난 것의 대부분이 우리가 쓰지
않는 언어 279 개였고 골라 담을 수도 없었다. 이쪽은 늘어난 것이 곧 이 기능 자체다.
「이름으로 찾는다」 가 기능의 절반이고, 그 절반을 유니코드 전체로 넓히는 값이 이 1.12 MB 다.

큐레이션 표는 1307 줄이고 `paletteCommands` 와 같은 방식이다. **새 글자는 한 줄이 는다.**

## 3. 글자와 숫자는 훑기에서 뺀다

`runenames` 는 낱개 조회만 주므로 한 번 훑어서 목록을 만든다. 그대로 담으면 한글 음절과
CJK 만 10 만 개가 넘어 목록이 그것으로 뒤덮인다. `A`·`가`·`漢` 은 특수문자 입력창이
찾아줄 것이 아니다. 빼고 나면 12,265 개다.

큐레이션 표에 일부러 담은 그리스 문자와 원문자는 표가 앞이라 이 규칙에 걸리지 않는다.

보이지 않는 글자(`NO-BREAK SPACE`) 는 큐레이션 표에 넣지 않았다. 격자에서 빈 칸으로 보여
서로 구별되지 않는다. 훑기에는 들어오므로 영문 이름으로는 찾을 수 있다.

훑기는 백그라운드 작업이고(ADR-0027) 프로세스에 한 번뿐이다. 유니코드 표는 도중에 바뀌지
않는다. 열 때마다 다시 읽는 파일 목록과 다른 점이다(ADR-0011). 여는 순간 큐레이션 표를
곧바로 쓰므로 훑기를 기다리지 않는다.

## 4. 커서 뒤에 넣고, 연속으로 넣는다

`a` 와 같은 자리다. `enter` 를 쳐도 판이 닫히지 않아서 같은 갈래에서 몇 개를 잇달아 넣을 수
있다. `삼각형` 을 한 번 치고 `▲▽▲` 를 넣는 것이 이 mode 를 만든 까닭이다.

`endEdit` 을 부르지 않아서 연달아 넣은 것이 `u` 한 번에 통째로 돌아온다. insert mode 에서
이어 치는 것과 같은 단위다.

`esc` 는 insert mode 의 `esc` 와 똑같다. 넣은 것이 있으면 마지막 글자 위에 서고, 아무것도
안 넣었으면 `a<Esc>` 처럼 열기 전 자리로 돌아온다. 언제나 normal 로 나간다.

## 5. `ctrl+p` 를 insert 에서도 받는다. ADR-0011 을 고친다

ADR-0011 은 「`ctrl+p` 는 normal 과 sidebar 에서 받는다」 였다. 글을 쓰다 기호가 필요한
순간이 잦은데 그때마다 `esc` 를 한 번 거치게 할 이유가 없다.

**「어디서 열렸는지 기억하지 않는다」 는 그대로 지킨다.** 기억하는 대신 여는 쪽에서 커서를
normal 자리로 맞춰 놓고 넘긴다. insert 의 `esc` 가 하는 것과 같다. drawer 가 `a` 처럼 한 칸
오른쪽으로 되돌리므로 치던 자리가 그대로다.

**커서가 줄 맨 앞(0 칸) 일 때만 한 칸 오른쪽에서 시작한다.** `i<Esc>a` 가 그 자리에서
한 칸 움직이는 것과 같은 이치이고, 되돌리려면 어디서 열렸는지 기억해야 해서 두었다.

## 6. Ambiguous 폭은 시작할 때 잰 값을 쓴다

`→ ± × °` 는 East Asian Width 가 Ambiguous 라 터미널마다 한 칸이기도 두 칸이기도 하다.
폭 계산(`clusterAt`) 은 늘 한 칸으로 세는데, 두 칸으로 그리는 터미널에서는 격자가 통째로
밀린다. 특수문자 입력창에서 그 갈래가 절반이라 그냥 둘 수 없었다.

`probeAmbiguousWidth()` 가 시작할 때 이미 재고 있었고 `boxChars` 를 고른 뒤 버렸다.
그 값을 `editor.ambiguousWidth` 에 남겨 격자만 쓴다. 판정은 `golang.org/x/text/width` 다.
`runenames` 로 이미 들이는 모듈이다.

**재지 못했으면(0) 두 칸으로 본다.** 좁게 잡으면 행이 넘쳐 그 아래가 통째로 밀리고, 넓게
잡으면 칸 사이가 조금 벌어질 뿐이다. 재지 못한 터미널이 테두리를 ASCII 로 내리는 것과
같은 태도다(ADR-0028).

## 7. 못 그릴 화면에서는 열지 않는다

격자가 한 행도 안 나오거나 편집 영역에 세 줄이 안 남으면 열지 않고 알린다. 열려 있는 동안
좁아지면 빠져나온다. 보이지 않는 mode 에 갇히면 키를 쳐도 아무 일이 안 난다.
팔레트의 `paletteFits` 와 같은 방어다(ADR-0011).

## 관련

- ADR-0002 mode 를 model 교체로
- ADR-0008 입력줄이 있는 mode 는 한글을 되돌리지 않는다
- ADR-0011 command palette: §5 가 그 규칙 하나를 고친다
- ADR-0026 editor 를 포인터로
- ADR-0027 백그라운드 작업
- ADR-0028 Ambiguous 폭 재기: §6 이 그 값을 이어 쓴다
- ADR-0039 바이너리 크기를 근거로 chroma 를 기각한 자리
