# ADR-0067 이름 바꾸기는 저장까지 하고, 되돌리기는 git 이 맡는다

- 상태: 채택
- 날짜: 2026-08-24

## 맥락

`\gd`(ADR-0051) 와 자동완성(ADR-0066) 이 놓은 gopls 연결 위에 남은 것이 이름 바꾸기였다
(`docs/tasks.md`). 재 보고 시작했다. 빈 `capabilities` 로도 `textDocument/rename` 이 되고,
`fitTip` 하나를 바꾸는 데 **664ms 에 세 파일**이 왔다. 그중 둘은 **열려 있지 않은 파일**이었다.

**그 둘이 이 결정의 전부다.** 지금까지 zn 이 고치는 것은 언제나 「열려 있는 buffer 하나」였고,
저장은 `:w` 하나였고, 되돌리기는 그 buffer 안의 일이었다. 이름 바꾸기는 셋 다 넘는다.

## 1. 열려 있지 않은 파일은 디스크에 바로 쓴다

세 가지 길을 놓고 골랐다.

- **바뀌는 파일을 다 tab 으로 연다.** 파일마다 `u` 가 남고 저장도 사람이 한다. 그런데 이름
  하나에 tab 이 열 개씩 열리면 그 뒤로 편집기를 쓸 수가 없고, 한꺼번에 저장할 `:wa` 도 없다.
- **열린 tab 만 고친다.** 안전하지만 나머지 참조가 옛 이름으로 남아 **빌드가 깨진다.**
  rename 이라고 부를 수 없는 것을 넣는 셈이다.
- **열린 tab 은 buffer 에서, 나머지는 디스크에서 고친다.** 이것을 골랐다.

열린 tab 을 디스크에서 다시 읽지 않는 것은 저장하지 않은 편집이 사라지기 때문이다.
열려 있지 않은 파일을 tab 으로 만들지 않는 것은 위의 까닭이다.

**한 파일 안에서는 편집을 뒤에서 앞으로 적용한다.** 서버가 준 편집은 한 파일의 여러 자리를
가리키는데, 앞에서부터 고치면 옛 이름과 새 이름의 길이가 달라 **뒤 편집의 열이 밀린다.**
뒤에서부터 고치면 아직 안 건드린 앞쪽 자리가 그대로라 자리를 다시 셀 일이 없다.

## 2. 고친 것은 그 자리에서 저장한다

**「저장은 `:w` 로만」이 여기서 뒤집힌다.** `.editorconfig` 가 저장하는 자리에서 규칙을 뒤집은
것과 같은 종류다(ADR-0052).

열려 있지 않은 파일은 buffer 로 들고 있을 자리가 없어서 쓰는 것 말고는 길이 없다. 그러면
열린 tab 만 저장하지 않은 채 남는데, 그것이 더 나쁘다. **한 번의 이름 바꾸기가 저장소를 한
상태로 만들어야 한다.** 절반은 디스크에, 절반은 buffer 에 있으면 그 사이에서 빌드도 git 도
무엇을 보고 있는지 알 수 없다.

대가는 **저장하지 않은 내 편집도 같이 쓰인다**는 것이다. 그 파일은 어차피 이름이 바뀌어야
하므로 따로 남겨 둘 수 없다.

포매터는 걸지 않는다(`Save` 에 hook 이 nil 이다). 이름을 바꾸다가 남의 파일이 통째로 다시
포맷되면 그 diff 가 무엇 때문인지 알 수 없다(ADR-0065).

## 3. 되돌리기는 git 이 맡는다

`u` 는 buffer 안의 일이라, 열려 있지 않은 파일에 쓴 것을 되돌릴 자리가 없다.
**한 번의 `u` 로 전부 되돌리는 길은 만들지 않았다.** 만들려면 편집기가 「파일에 쓴 것」을 되돌릴
기록을 따로 들어야 하는데, 그것은 buffer 와 다른 새 개념이고 그 기록이 어디까지 살아 있어야
하는지(편집기를 껐다 켜면?) 부터 정해야 한다.

대신 **무엇을 바꿨는지 반드시 적는다.** `Hello (으)로 바꿨습니다: 3 개 파일 7 곳` 이다.
git 이 안전망이다. 이 저장소가 위 줄에 git 상태를 늘 띄워 두는 것(ADR-0009, ADR-0030) 이
여기서 값을 한다. 바꾸기 전에 dirty 인지 보이고, 바꾼 뒤에 `git diff` 로 확인할 수 있다.

열린 tab 은 그래도 `u` 가 듣는다. 한 덩어리로 담기므로(`replaceAll`) 한 번이면 돌아온다.

## 4. 편집기를 연 자리 밖이면 아예 하지 않는다

**직접 겪어서 넣은 가드다.** zn 을 저장소 A 에서 띄우고 저장소 B 의 파일을 열어 이름을 바꾸면,
gopls 의 뿌리가 `os.Getwd()`(A) 라 B 의 다른 파일을 찾지 못한다. 그때 rename 은 **그 파일
안에서만** 일어나고 나머지 참조가 옛 이름으로 남아 조용히 빌드가 깨진다. 시험 삼아 해 보고
그렇게 되는 것을 보았다.

그래서 파일이 뿌리 아래가 아니면 거절하고 어디서 열었는지를 알린다. **반쪽짜리 rename 보다
안 하는 것이 낫다.** 정의로 가기는 같은 상황에서 「못 찾았습니다」로 끝나서 이 가드가 없었다.

## 5. 새 이름은 커서 옆 창에서 받는다

부르는 문은 셋이다.

- `\rn`: leader 키다. `\gd` 와 같은 자리이고 vim 세계에서 `<leader>rn` 이 가장 흔한 자리다
  (Neovim 0.10+ 의 내장 기본값은 leader 없는 `grn` 인데, 이 편집기는 정의로 가기부터 leader 를
  쓰고 있어서 그쪽을 따랐다)
- 팔레트의 「이름 바꾸기」
- `:rename`: 이름을 대면 곧바로 바꾸고, 대지 않으면 아래의 창으로 온다

**셋 다 커서 옆에 뜨는 창으로 모인다**(`view-rename-input.go`). 처음에는 명령줄에 `:rename `
을 채워 주는 것으로 두었는데, **바꾸는 것은 커서 자리에 있는데 받는 곳이 화면 맨 아래라**
눈이 거기까지 내려갔다 와야 했다. 자동완성이 목록을 커서 옆에 띄우는 것과 같은 까닭이다
(ADR-0066).

창은 **옛 이름으로 채워져 있다**(`Greet → Greet`). 한 글자만 고치거나 앞에 무언가를 붙이는
것이 이 동작의 거의 전부라 빈 칸에서 시작하면 매번 다시 쳐야 한다. 트리의 이름 고치기가
지금 경로로 채워져 있는 것과 같다(ADR-0054). 옛 이름 그대로 `enter` 를 누르면 아무 일도 하지
않는다.

**창을 열 때 커서를 그 이름의 첫 글자로 옮긴다.** 서버에 묻는 자리가 커서라, 옮겨 두면 화면에
보이는 것과 묻는 자리가 같아진다. 커서가 낱말 위가 아니면 그 줄의 첫 낱말을 잡는다.
`*` 가 쓰는 `wordUnderCursor` 를 그대로 쓴다(search.go).

창은 model 이다. 자동완성 목록이 mode 를 만들지 않은 것과 갈리는데(ADR-0066), 그쪽은 치는
동안 곁들여 뜨고 이쪽은 **키가 전부 이 창의 글자**라서다. insert 의 키 규칙이 남아 있을
자리가 없다.

**폭은 고정이고 넘치면 왼쪽부터 접는다.** 치고 있는 것이 뒤쪽이라 오른쪽부터 자르면 방금 친
글자가 보이지 않는다. 처음에 그렇게 두었다가 긴 이름에서 드러났고, **창 밖으로 나간 커서가
화면 끝에서 다음 줄로 감겨 엉뚱한 자리에 서기까지 했다.** 접는 규칙은 `GOTO` 목록이 경로를
접는 것과 같고(`trimLeftToWidth`), 그리는 글과 커서 칸을 한 함수에서 같이 내어 둘이 갈릴 수
없게 했다. 커서가 설 한 칸은 늘 남긴다.

**적용 전에 다시 묻지 않는다.** 확인창을 하나 더 두는 대신 결과를 아래 줄에 적는다. 물어야 할
만큼 위험한 자리는 4 절의 가드가 이미 막고 있고, 나머지는 git 이 받는다.

## 이 ADR 이 정하지 않는 것

- 여러 파일에 걸친 되돌리기. 편집기가 「파일에 쓴 것」의 기록을 들어야 한다(3 절)
- 바뀔 자리를 미리 보여주는 화면. `GOTO` 목록(ADR-0051) 을 쓰면 되는데, 그 목록을 「적용
  버튼」으로 쓰는 쓰임새가 새로 생긴다
- 파일 이름까지 같이 바꾸는 것(`documentChanges` 의 create·rename·delete). 지금은 걸러 낸다
- gopls 의 뿌리를 파일마다 모듈로 잡는 것. 지금은 편집기를 연 자리 하나다(ADR-0051)
- Go 밖의 언어. 언어 서버가 gopls 하나다
