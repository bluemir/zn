# ADR-0118: 파일에 든 제어문자는 `^[` 로 보이게 그린다

## 맥락

ADR-0117 로 폭을 재는 함수를 정리하다가 물음이 하나 나왔다. **`lines.ColAt` 과 `widthOf` 가 ANSI escape 를 반대로 다루는데 그것이 맞나.**

설계상 이유는 있었다. `ColAt` 은 파일에서 온 줄을 재고 `widthOf` 는 화면에 지은 글을 재므로, 같은 `\x1b` byte 를 앞에서는 내용으로 뒤에서는 색으로 읽는다. 그 갈림이 `internal/lines`(파일) 와 core(화면) 의 경계와 겹친다.

**재보니 그 전제가 실제로는 깨져 있었다.**

```
파일:   esc \x1b[31mRED\x1b[0m here     (21 byte)
화면:   esc RED here                     (12 칸)
```

파일의 escape 가 화면으로 그대로 새어 나가 **터미널이 그것을 색 명령으로 먹었다.** 그런데 `ColAt` 은 그 byte 들을 글자로 세고 있었다.

그 줄에서 `0` 과 `$` 를 눌러 쟀다.

| | 줄 시작 | 줄 끝 |
|---|---|---|
| tmux 가 보는 커서 | 32 | 50 |
| statusBar | `2:1` | `2:19` |

편집기는 18 칸 갔다고 믿고 커서를 거기 놓는데 눈에 보이는 글자는 12 칸뿐이었다. **커서가 글자 끝에서 6 칸 뒤에 떠 있었다.** 사라진 `[31m`(4) 와 `[0m`(3) 에서 ESC 두 개를 뺀 7 칸이 유령으로 세어진 것이다.

색을 끄는 `\x1b[0m` 이 없는 파일이면 그 뒤 화면이 통째로 물든다.

## 1. 편집기는 터미널 흉내가 아니다

정할 것은 「파일에 든 제어문자를 어떻게 보일까」다. 셋이 있었다.

| 길 | 결과 |
|---|---|
| 지금대로 흘려보낸다 | 터미널이 먹는다. 화면 0 칸, 계산은 글자. **어긋난다** |
| 지워서 안 보이게 한다 | 화면과 계산은 맞는다. 그런데 **파일에 있는 것을 못 보고 못 고친다** |
| **`^[` 로 보이게 그린다** | vim 이 그렇게 한다. 보이고, 세어지고, 고칠 수 있다 |

셋째를 골랐다. **여기는 텍스트 편집기이지 터미널 에뮬레이터가 아니다.** 파일에 든 `\x1b` 는 색을 켜라는 명령이 아니라 **고칠 수 있어야 하는 내용**이다. 로그를 열어 escape 를 걷어내는 일이 실제로 있고, 그러려면 그것이 보여야 한다.

## 2. tab 과 같은 규칙의 다른 사례다

새 개념이 아니다. `GlyphAt` 이 `(size, width)` 둘을 돌려주는 까닭이 이미 그것이었다.

| | size (파일 byte) | width (화면 칸) |
|---|---|---|
| ASCII | 1 | 1 |
| 한글 | 3 | 2 |
| tab | 1 | 1~4 (시작 칸에 따라) |
| **제어문자** | **1** | **2** |

파일의 1 byte 가 화면의 여러 칸으로 펼쳐지는 것이 tab 에서 이미 하던 일이고, 제어문자는 그 표에 줄이 하나 는 것이다.

**그래서 고칠 자리가 둘뿐이었다.** `GlyphAt` 이 폭 2 를 주고, `expandRow` 가 그 자리에 `^[` 를 쓴다. `ColAt`·`OffsetAtCol`·`WrapOffsets`·커서·줄바꿈은 전부 `GlyphAt` 위에 서 있어서 저절로 따라온다.

## 3. 보이는 글자와 세는 폭은 한 자리에서 나온다

`ControlText` 를 `internal/lines` 에 두었다. 「`^[` 두 글자로 보인다」와 「2 칸이다」가 갈라지면 이 결정이 고치려던 어긋남이 그대로 다시 생긴다. 폭을 정하는 `GlyphAt` 이 그 함수를 불러 판정한다.

```go
if ControlText(line[offset]) != "" {
	return 1, 2
}
```

**표현을 정하는 일이라 core 가 맞지 않나** 물을 수 있는데, 그 반대다. 여기서 정하는 것은 **폭이 먼저**이고 글자는 그 폭에 맞춰 고른 것이다. 폭은 좌표 변환의 일부라 `lines` 의 말이다(ADR-0117).

무엇을 제어문자로 볼지는 vim 을 따랐다. `^` 다음 글자는 그 byte 에 `0x40` 을 더한 것이고(ESC 0x1b → `^[`), DEL 은 `^?` 다. **tab 은 들지 않는다** — 그것은 칸으로 펴는 쪽이다. 줄바꿈은 줄 안에 없다(splitLines 가 뗀다).

## 4. 고치고 나서 다시 쟀다

```
화면:   esc ^[[31mRED^[[0m here
```

| | 줄 시작 | 줄 끝 |
|---|---|---|
| tmux 가 보는 커서 | 32 | 54 |
| statusBar | `2:1` | `2:23` |

둘 다 22 칸이고, 화면 글자를 세어도 23 칸이다(`esc ` 4 + `^[` 2 + `[31m` 4 + `RED` 3 + `^[` 2 + `[0m` 3 + ` here` 5). **어긋남이 사라졌다.**

`^[` 위에서 `x` 를 치면 그 1 byte 만 지워진다. `GlyphSize` 가 1 을 주기 때문이고, 커서 이동·삭제·복사가 전부 그 위에 서 있어서 따로 손댄 자리가 없다.

## 5. 색은 공백 마커와 반대로 간다

`^[` 를 본문 색으로 두면 **진짜 두 글자인 `^` `[` 와 구별되지 않는다.** 그러면 이 결정이 사려던 「파일에 무엇이 들었는지 보인다」가 반쪽이 된다.

공백 마커와 정반대 방향이다.

| | 색 | 까닭 |
|---|---|---|
| 공백 마커 `»`·`⋅` | 흐린 회색 240 | **늘 있는 것이라 물러나야 한다.** 코드를 읽는 데 끼어들면 안 된다 |
| 제어문자 `^[` | **분홍 205** | **드물게 나타나 알리는 자리다.** 흐리면 알릴 것을 못 알린다 |

진단의 빨강(1)·노랑(11) 은 피했다. **제어문자가 든 것은 오류가 아니라 사실이다.** 로그 파일에 escape 가 있는 것은 정상이고, 편집기는 그것을 보여 주기만 하면 된다. 문법 색 아홉과도 겹치지 않는다.

**조각의 갈래가 셋이 되었다.** `screenPart` 가 `marker bool` 을 들고 있었는데 그것으로는 셋을 못 가른다.

```go
type partKind int

const (
	partText    partKind = iota // 파일에 든 그대로의 글자
	partMarker                  // 공백을 보이게 한 `»`·`⋅` (ADR-0020)
	partControl                 // 제어문자를 보이게 한 `^[`
)
```

갈래는 **글자가 무엇인지가 아니라 그 자리가 무엇을 나타내는지**다. 파일에 든 `»` 는 본문이고 마커로 그린 `»` 는 마커다. 같은 글자가 갈래가 다르다.

### `^[` 만 칠하고 `[31m` 은 본문이다

`\x1b[31m` 을 통째로 칠하지 않는다. **편집기가 escape sequence 를 해석하지 않기 때문이다.** `[31m` 은 진짜 ASCII 네 글자이고 지우면 네 번 지워진다. 제어문자 하나가 갈래이지 sequence 가 갈래가 아니다.

vim 도 같다. 여기서 sequence 를 알아보기 시작하면 §1 에서 「터미널 흉내가 아니다」라고 정한 자리로 되돌아간다.

## 6. 변환하는 자리가 둘이라 하나가 빠져 있었다

고치고 나서 「이 변환을 어디서 하나」를 훑었더니 자리가 둘이었다.

| 함수 | 어디 | tab | 제어문자 |
|---|---|---|---|
| `expandRow` | render-row.go (편집 영역) | 공백으로 편다 | `^[` 로 편다 |
| `grepExpandTabs` | view-grep.go (grep 목록) | 공백으로 편다 | **안 했다** |

**grep 목록에서는 escape 가 그대로 새고 있었다.** 그리고 편집 영역보다 나빴다.

```
a.txt:1   hit ^[[31mRED^[[0m ^[[38;5;16m^[[48;5;220mtarget...
              └ 파일에서 온 escape        └ 매칭 강조
```

파일의 `\x1b[0m` 이 목록의 반전과 매칭 강조 색까지 꺼버린다. **파일 내용이 UI 를 오염시킨다.**

바꿀 글자를 `lines.ScreenText` 로 모았다. 폭을 정하는 `GlyphAt` 바로 옆이라 둘이 갈릴 수 없고, 그리는 두 자리가 같은 함수를 부른다. `grepExpandTabs` 는 tab 만 펴는 함수가 아니게 되어 `grepExpandScreen` 이 되었다.

### 공백 마커는 옮기지 않았다

`»`·`⋅` 도 「화면에 무엇으로 보이나」이니 같이 갈 것 같지만 성격이 다르다.

| | 그대로 그리면 | 폭 | 껐다 켤 수 있나 |
|---|---|---|---|
| tab | **사라진다** | 1 byte → 1~4 칸 | 아니오 |
| 제어문자 | **터미널이 먹는다** | 1 byte → 2 칸 | 아니오 |
| 공백 마커 | **맞게 그려진다** | 1 칸 → 1 칸 | **예**(`whitespaceMark`) |

**앞의 둘은 「이대로는 못 그린다」는 사실이고 마커는 「이렇게 보여주자」는 선택이다.** 그래서 마커만 껐다 켤 수 있고, 어디에 찍을지(들여쓰기와 줄 끝만) 도 편집기의 판단이다(ADR-0020).

그리고 `ScreenText` 가 폭과 글자를 한 몸으로 책임지는 까닭이 §3 의 「갈리면 어긋난다」인데 마커에는 그 위험이 없다. 1 칸을 1 칸으로 바꾸기 때문이다.

**다만 처음 모을 때 한 자리가 샜다.** tab 이 마커로 찍히는 줄에서 core 가 여전히 손수 펴고 있었다.

```go
// 처음
case char == '\t' && isMarker:
	text.WriteString(markerTab)
	text.WriteString(strings.Repeat(" ", width-1))   // ← core 가 tab 을 편다
```

「마커는 core, 펴기는 lines」로 갈랐다면서 **마커가 붙는 tab 만 펴기까지 가져가고 있었다.** 편 것에서 첫 칸만 바꾸도록 고쳤다.

```go
// 지금
screen := lines.ScreenText(line, offset, col, tab)   // "    "

case char == '\t' && isMarker:
	text.WriteString(markerTab)
	text.WriteString(screen[1:])                      // 첫 칸만 마커로 바꾼다
```

이제 core 에는 tab 을 펴는 코드가 한 줄도 없다. core 가 아는 것은 「첫 칸만 마커로 바꾼다」뿐이다.

경계를 말로 적으면 이렇다.

> `internal/lines` 는 **옮기지 않으면 틀리는 것**을 옮긴다.
> core 는 **맞게 그려지는데 일부러 다르게 보여주는 것**을 얹는다.

## 그래서 `ColAt` 과 `widthOf` 는 무엇이 다른가

이 결정 뒤에 둘의 차이가 더 선명해졌다. **입력의 출처가 다르고, 그것이 ESC 의 뜻을 가른다.**

| | `lines.ColAt(line, offset, tab)` | `widthOf(text, ...)` |
|---|---|---|
| 무엇을 받나 | **변환 전.** 파일에서 온 줄 | **변환 후.** 화면에 지어 놓은 글 |
| 무엇을 묻나 | 이 byte 자리가 화면 몇 칸째인가 | 이 글이 통째로 몇 칸인가 |
| `\x1b` 는 | **내용.** 앞으로 `^[` 로 보일 것이라 2 칸 | **색.** lipgloss 가 붙인 것이라 0 칸 |
| 사는 곳 | `internal/lines` | core (width.go) |

**진짜 갈림은 변환 전이냐 후냐다.** 같은 byte 가 변환 전에는 고칠 수 있는 내용이고 변환 후에는 색이다. `ColAt` 은 §2 의 변환 규칙을 알고 그것을 적용해서 재고, `widthOf` 는 그 변환이 이미 끝난 것을 잰다.

```
ColAt("\x1b[31mab", 7, 4) = 6    // ^[(2) + [31m(4) ... 화면에 그렇게 그려진다
widthOf("\x1b[31mab")     = 2    // ab 만 자리를 차지한다
```

**둘 다 자기 입력에 대해 맞는 답이다.** 그리고 이제는 `ColAt` 의 답이 화면과 실제로 일치한다. 전에는 그 6 칸을 화면이 그리지 않아서 계산만 그렇게 믿고 있었다.

같은 byte 열을 두 겹이 다르게 읽어야 하므로 이 둘은 합칠 수 없다. **어느 쪽인지는 byte 를 봐서는 알 수 없고 「이 글이 어디서 왔나」로만 갈린다.** 그 물음의 답이 곧 패키지 경계라, 함수가 사는 곳이 그 답을 말한다.

## 남는 것

- insert 모드로 제어문자를 **넣는** 길은 없다. vim 의 `Ctrl-V` 다. 보고 지우는 것이 먼저 필요했던 것이라 그것만 했다
