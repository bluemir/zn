# ADR-0141 커밋 기록의 그래프는 git 의 알고리즘을 그대로 옮긴다

- 상태: 채택
- 날짜: 2026-09-13
- 관련: ADR-0115(커밋 기록 화면, 이 결정이 §5 와 §1 을 되집는다), ADR-0028(ambiguous 폭에서 물러설 글자), ADR-0042(go-git)

## 맥락

「backmerge 가 잘 안 보인다」에서 시작했다. 대각선으로 그리면 나아지겠다는 물음이었는데, 재현해 보니 **모양의 문제가 아니었다.** 그 선이 아예 안 그려지고 있었다.

`emit` 이 merge 의 둘째 부모를 이렇게 다루고 있었다.

```go
// merge 의 나머지 부모다. 이미 서 있는 열이 있으면 그리로 붙고, 없으면 열을 연다.
for _, hash := range parents[1:] {
	if slices.Contains(w.lanes, hash) {
		continue          // 「그리로 붙고」가 주석에만 있다
	}
	w.lanes[w.freeLane()] = hash
}
```

backmerge 는 둘째 부모가 늘 「이미 다른 열이 기다리는 커밋」이라 언제나 이 길로 빠진다. `graphRow` 가 `before`·`after`·`lane` 셋만 들고 있어서 **열이 늘지 않는 연결은 적어 둘 자리가 없었다.** 부모 둘인 커밋이 부모 하나인 커밋과 화면에서 구별되지 않았다.

## 0. 대각선을 우리 방식으로 넣어 보고 물렸다

먼저 열 배치는 그대로 두고 글자만 모서리에서 대각선으로 바꿨다. 갈래가 하나뿐인 자리는 `git log --graph` 와 같아졌는데, **갈래가 둘 이상 살아 있는 저장소에서 읽을 수 없게 되었다.**

```
●          Merge branch 'a2'
│╲
● │        Merge branch 'a1'
│╲│─       ← `╲` 가 가리키는 `│` 는 a2 의 열이고, 진짜 목적지는 그 너머다
│ ● │      a2
│ │ ●      a1
│╱──       ← 가로선이 어디서 시작하는지 눈이 잇지 못한다
●          Merge branch 'a2'
```

**대각선은 바로 옆 열을 가리키는 글자다.** 열이 둘 이상 떨어져 있으면 그 옆 열은 남의 갈래이고, 뒤에 가로선을 붙여도 한 선으로 읽히지 않는다. 모서리(`│─┐`)는 꺾이는 자리가 목적지 열에 있어서 이 문제가 없었다. ADR-0115 §5 가 모서리를 고른 것은 결과적으로 이 구조에 맞는 선택이었다.

그러면 왜 git 은 대각선으로도 읽히는가. **글자가 아니라 열을 움직이기 때문이다.**

```
* |   af4e077
|\ \            ← 새 열을 커밋 바로 옆에 끼우고 나머지를 오른쪽으로 민다
| |/            ← 한 칸 당긴다
|/|             ← 또 한 칸 당긴다
| * 78baadc
|/
```

새 열이 늘 커밋 **바로 옆**에 열려서 여는 선이 한 칸이고, 그다음 몇 행에 걸쳐 왼쪽으로 당겨 붙인다. 대각선이 언제나 옆 열을 가리키는 것이 이 둘 덕이다.

**열을 안 움직이면 git 의 그림이 나오지 않는다.** 그래서 알고리즘째 옮긴다.

## 1. git 의 상태 기계를 옮긴다

`graph.c` 의 구조를 그대로 가져왔다. 열 배치(`columns`·`newColumns`), 칸마다 갈 자리를 적은 `mapping`, 그리고 상태 다섯이다.

| 상태 | 내는 행 |
| --- | --- |
| `preCommit` | octopus 가 설 자리를 넓힌다 |
| `commit` | 커밋이 선 행 |
| `postMerge` | merge 가 연 열들이 뻗는 행 |
| `collapsing` | 열을 왼쪽으로 **한 칸** 당기는 행. 제자리에 다 앉을 때까지 되풀이한다 |
| `padding` | 낼 것이 없다. 커밋 하나가 끝난 자리 |

**핵심은 `mapping` 이다.** 커밋 행 직후에는 열이 제자리에 있지 않고(`mapping[i] != i/2`), 당기는 행이 한 번에 한 칸씩 옮겨 맞춘다. 새 열을 늘 왼쪽부터 끼우므로 **열이 가야 할 자리는 언제나 지금 자리이거나 그 왼쪽**이고, 오른쪽으로 옮길 일이 없다는 것이 이 되풀이를 단순하게 만든다.

**칸을 이어 붙이며 그린다.** 절대 자리로 쓰면 octopus 가 옆으로 펴는 `-`·`.` 가 뒤따르는 열과 자리를 다툰다. git 이 이어 붙이는 모양이라 그 자리 셈이 아예 없다.

## 2. 맞는지는 진짜 git 이 판정한다

`git log --graph` 를 돌려 그래프 칸만 뽑고 **글자 단위로 견주는** 시험을 두었다. 저장소 여섯이다. 갈래 하나, backmerge, 갈래 둘을 번갈아 합치는 것, octopus, 갈래 넷, 그리고 이 저장소 자체다.

**이것이 이 기능의 기준선이다.** 옮겨 온 것이 git 의 알고리즘이므로 「git 과 같은가」가 곧 맞는지다. 눈으로 읽는 그림을 기대값으로 적어 두면 틀린 그림을 굳히게 된다. 실제로 이 시험이 잡아 준 것이 넷이다.

- octopus 의 `-`·`.` 를 두 칸씩 띄워 그리던 것
- merge 가 연 선 뒤에 사이 칸을 넣어 `|\` 가 `| \` 가 되던 것
- 커밋 오른쪽으로 밀린 열을 `|` 로 그리던 것
- 부모가 하나인 커밋까지 「연 열」로 세어, merge 바로 다음 커밋의 옆 열이 `\` 로 그려지던 것

## 3. 차례는 커밋한 때 그대로다

`git log --graph` 는 `--topo-order` 를 함의한다. 갈래의 커밋을 붙여 놓아 섞이지 않게 하는 차례다. 우리는 커밋한 때 내림차순이고, 그것은 git 의 `--date-order` 와 같다.

**그래서 시험도 `--date-order` 로 견준다.** 그 차례에서는 여섯 저장소가 한 글자도 다르지 않다.

`--topo-order` 를 넣지 않은 것은 **조금씩 읽기와 부딪히기 때문이다.** 그 차례를 내려면 범위 안 모든 커밋의 자식 수를 먼저 세야 하는데(git 의 `sort_in_topological_order`), 그러면 여는 순간 저장소를 통째로 읽게 되어 ADR-0115 §3 이 정한 것이 무너진다. git 도 commit-graph 파일의 세대 번호가 있을 때만 이것을 게으르게 한다.

`docs/tasks.md` 에 열어 두었다.

## 4. 커밋 하나의 높이가 고정이 아니다

ADR-0115 §1 이 `git graph` alias 에서 가져온 「커밋 하나가 두 줄」을 되집는다. 열을 당겨 붙이는 행이 붙으면 그만큼 는다.

**바닥은 여전히 둘이다.** git 은 커밋 하나를 한 행으로 낼 수도 있는데 우리 형식은 이름 줄과 제목 줄 둘이다. 모자란 자리는 그리는 쪽이 채운다.

**채우는 행을 훑기가 같이 준다**(`graphRow.pad`). 그 행은 살아 있는 열을 그대로 내려 긋는 것이라 빈 칸으로 두면 지나가던 갈래의 선이 한 행 끊긴다. 그리는 쪽이 열을 다시 세지 않게 훑기가 얹어 준다.

**첫 커밋은 여전히 커밋 단위다.** 화면 행으로 굴리면 커밋이 위에서 반쪽만 잘린 채 서는데, 그 커밋이 목록에 있는지가 갈리지 않는다. 「반쪽 커밋은 그리지 않는다」를 그대로 지킨다.

**한 화면에 담기는 커밋 수를 세어서 낸다.** 나눗셈 한 번으로 나오던 값(`listHeight / 2`) 이 이제 보고 있는 자리에 따라 달라진다.

**커서는 커밋이 선 행이다.** octopus 가 자리를 넓히는 행이 그 위에 올 수 있어서 커밋의 첫 행이 아니다. 훑기가 몇 번째인지 같이 준다.

## 5. 글자는 그리는 쪽이 고른다

훑기가 내는 것은 칸마다 「무엇인지」뿐이다(`graphSymbol`). 어느 글자로 그릴지는 터미널에 따라 갈리는 판단이라 그리는 쪽이 안다. ADR-0115 §5 가 세워 둔 나눔을 그대로 지킨다(ADR-0028).

| 갈래 | git | 우리 |
| --- | --- | --- |
| 커밋 | `*` | `●` |
| 이어지는 열 | `\|` | `│` |
| 왼쪽 아래로 | `/` | `╱` |
| 오른쪽 아래로 | `\` | `╲` |
| 열을 건너는 선 | `_` `-` | `─` |
| octopus 의 끝 | `.` | `┐` |

**물러설 자리가 곧 git 이 쓰는 글자다.** `* | / \ _ - .` 는 전부 East Asian Width 가 Narrow 라 어느 터미널에서도 한 칸이고 폰트에 글리프가 없어 두부가 될 일도 없다.

## 결과

- backmerge 가 보인다. 부모 둘인 커밋이 부모 하나인 커밋과 갈린다
- 그래프가 `git log --graph --date-order` 와 **한 글자도 다르지 않다**
- 진짜 git 과 견주는 시험 여섯이 생겼다. 이 기능의 기준선이다
- `boxSet` 에 대각선 둘이 는다. 물러설 자리는 `\`·`/` 다
- `graphRow` 가 열 배치가 아니라 **다 그려진 칸**을 든다. 그리는 쪽이 표를 한 번 보는 일만 남았다
- 커밋 하나의 높이가 가변이다. 담기는 수가 나눗셈이 아니라 세어서 나온다
- `graphWalk` 에서 열을 다루던 코드(`lanes`·`freeLane`·`trimLanes`) 가 통째로 빠졌다

**대가**

- **차례가 git 과 다르다.** git 의 기본은 `--topo-order` 이고 우리는 커밋한 때다(§3)
- **훑기가 상태를 하나 더 들고 다닌다.** 앞 커밋에서 이어지는 열 배치 위에서만 다음 행이 나온다. 화면이 나중에 다시 그릴 수 있는 값이 아니다
- **옮겨 온 코드라 우리 판단이 적다.** git 이 그 글자를 왜 그렇게 두는지까지는 담지 않았다. 고칠 일이 생기면 git 의 `graph.c` 를 같이 봐야 한다
- **커밋마다 그려 둔 칸을 들고 있다.** 수만 커밋을 담는 자리라 그만큼 메모리를 쓴다. 커밋 하나에 행 두셋, 행마다 칸 몇이라 크지 않지만 0 은 아니다

## 대안

- **모서리를 그대로 두고 빠진 선만 그리기**
	- 고칠 것이 한 군데다. backmerge 가 보이는 것이 이 건의 값이고 그것만으로 답이 된다.
	- 옆 터미널과 문법이 갈린 채로 남는다. 기록을 보는 사람은 `git log --graph` 를 이미 눈에 익혀 두고 있다.
- **열을 고정해 두고 글자만 대각선으로 바꾸기**
	- 그리는 쪽만 고친다. 훑기가 그대로다.
	- 갈래가 둘 이상 살아 있으면 읽을 수 없다. 실제로 넣어 보고 물렸다(§0).
- **한 칸은 대각선, 여러 칸은 모서리**
	- 흔한 자리는 git 처럼 보이고 먼 자리는 안 헷갈린다.
	- 그림 문법이 둘이 된다. 그리고 열이 둘 떨어지는 것이 merge 가 잦은 저장소에서는 드문 일이 아니다.
- **열을 왼쪽으로 당겨 붙이지 않기**
	- 같은 갈래가 늘 같은 칸에 서서 세로로 훑기 좋다.
	- 그러면 대각선이 옆 열을 가리키지 못한다. git 이 당기는 행을 쓰는 까닭이 그것이다(§0).

## 이 ADR 이 정하지 않는 것

- **`--topo-order`.** `docs/tasks.md` 에 열어 두었다(§3)
- **갈래마다 색을 나누는 것.** git 은 `--color` 에서 열마다 색을 돌려 쓴다. 지금 그래프 칸은 색이 없다
- **`GRAPH` 에서 누르기로 고르는 것.** `DIFF`·`COMMIT` 만 받는다(ADR-0140 §1)
- **commit-graph 파일을 읽는 것.** 세대 번호가 있으면 topo 차례를 게으르게 낼 수 있는데, go-git 이 그것을 내주는지부터 재야 한다
