# ADR-0015: 저장 직전에 파일을 다시 읽어 내용 해시로 바깥 변경을 감지하고, `:w!` 로만 덮어쓴다

- 상태: 채택
- 날짜: 2026-08-13

## 맥락

`Buffer.Save` 는 `os.WriteFile` 하나였다. 파일을 연 뒤 그 파일이 밖에서 바뀌어도 저장은 그것을
모르고 통째로 덮어썼다. 실제로 밟는 자리가 여럿이다.

- 편집기를 띄워둔 채 다른 터미널에서 `git checkout`·`git pull`·포매터를 돌린 뒤 돌아와 `:w`
- 같은 파일을 두 tab 에 연 경우. tab 마다 Buffer 가 독립이라 한쪽 저장이 다른 쪽 편집을 지운다
  (`docs/tasks.md` 에 이미 열려 있는 항목이다)
- 열어둔 파일을 밖에서 지운 뒤 `:w`

셋 다 결과는 같다 — **남이 쓴 내용이 아무 표시 없이 사라진다.** 편집기 안에는 그것이 일어났다는
흔적조차 남지 않는다.

## 결정

**`Buffer` 가 `diskHash` 를 든다.** 읽은 시점(또는 마지막으로 쓴 시점) 파일 내용의 SHA-256 이다.
`nil` 은 "그때 파일이 없었다" 는 뜻이다.

**`:w` 는 쓰기 직전에 파일을 다시 읽어 해시를 맞춰 본다.** 다르면 쓰지 않고 statusBar 아래 줄에
알린다. 세 경우를 구분해서 말한다.

- 내용이 다르다 → `파일이 밖에서 바뀌었습니다. 덮어쓰려면 :w! 입니다`
- 없던 파일이 생겼다 → `파일이 밖에서 새로 생겼습니다. …`
- 있던 파일이 사라졌다 → `파일이 밖에서 사라졌습니다. 다시 만들려면 :w! 입니다`

**`:w!` 는 검사 없이 덮어쓴다.** `Buffer.Save` 와 `Buffer.SaveForce` 두 메서드로 가른다.
`!` 를 보고 둘 중 하나를 부르는 것은 명령줄 쪽이고, `:wq!`·`:x!` 도 같다.
검사하는 쪽이 그냥 `Save` 이므로, 나중에 저장하는 곳(`:wa` 같은 것) 이 늘어도 기본이 안전하다.

**쓰고 나면 방금 쓴 내용의 해시가 새 기준이 된다.** 이어지는 저장이 자기가 쓴 것을 남의 변경으로
보지 않는다.

**막힌 저장은 아무것도 바꾸지 않는다.** 파일도 그대로고 `dirty` 도 그대로다. `:wq` 는 저장이
막히면 tab 을 닫지 않는다(이름 없는 buffer 에서 이미 그렇다).

## 근거

### 무엇으로 판정하는가 — mtime+크기가 아니라 내용 해시

**mtime 은 내용이 같아도 자주 바뀐다.** `git checkout` 으로 같은 내용이 되쓰이거나, 포매터가
바꿀 것이 없어도 파일을 다시 쓰거나, 백업 도구가 건드리기만 해도 mtime 이 움직인다. 그때마다
경고가 뜨면 사용자는 곧 `:w!` 를 반사적으로 치게 되고, 그 순간 이 기능은 없는 것보다 나쁘다 —
정말 위험한 순간에도 손이 먼저 `!` 를 친다.

**내용 해시는 "진짜 달라졌을 때만" 운다.** 이 결정의 목적이 헛경고 없는 경고다.

**비용은 저장 한 번에 파일 하나를 더 읽는 것이다.** 이미 `:w` 마다 git 프로세스 세 개가 뜨고
있다(ADR-0009). 그 옆에서 파일 한 번 더 읽는 것은 눈에 띄지 않는다. 편집기가 다루는 파일 크기는
어차피 통째로 메모리에 올려두는 크기다(ADR-0001).

**mtime 으로 거르고 다를 때만 해시를 보는 절충도 있었다.** 헛경고도 없고 평소 비용도 없지만
상태가 둘(stat, 해시)로 늘고 분기가 는다. 지금 파일 크기에서 아낄 것이 없는 비용을 위해 코드를
늘리지 않는다. 큰 파일이 실제로 문제가 되면 그때 이 절충으로 옮긴다.

### 언제 보는가 — 저장 직전에만

vim 은 창에 포커스가 돌아올 때(`checktime`) 도 본다. 그쪽이 더 일찍 알려주지만, 알림을 띄울
자리와 "지금 다시 읽을까" 라는 두 번째 결정이 따라온다. **덮어쓰기를 막는 데는 저장 직전 한 번이면
충분하다.** 일찍 알려주는 것은 편의고, 안 덮어쓰는 것은 안전이다. 안전부터 한다.

### 어떻게 빠져나가는가 — `:w!`

**명령줄 parser 에 이미 `force` 가 있다.** `:q`/`:q!`, `:qa`/`:qa!` 와 같은 결이라 새로 배울 것이
없다. vim 에서 오는 사람에게도 `:w!` 는 이미 손에 익은 키다.

**확인창(y/n) 은 mode 를 하나 더 만든다.** 종료 확인창(`viewQuitConfirm`) 처럼 화면과 상태가
붙는다. 얻는 것은 "한 번 더 물어본다" 뿐인데, `:w` 가 실패로 끝나고 `:w!` 를 다시 치는 흐름도
똑같이 두 단계다. 더 싼 쪽을 고른다.

**빠져나갈 길을 아예 막지는 않는다.** 편집기 안에서 못 하면 밖에 나가서 파일을 옮기고 다시 여는
수밖에 없는데, 그 과정에서 잃는 것이 더 많다.

### 사라진 파일도 막는 이유

덮어쓸 내용이 없으니 "그냥 다시 만든다" 도 안전하기는 하다. 그래도 막는 쪽을 고른 것은
**"저장 시점 내용 == 읽은 시점 내용" 이라는 규칙 하나만 남기기 위해서다.** 예외가 생기면
"어떤 경우에 경고가 뜨는가" 를 매번 따로 기억해야 한다. `git checkout` 으로 파일이 사라진 것은
알아야 할 사건이기도 하다. 되살리려면 `:w!` 다.

## 결과

좋은 점

- 밖에서 바뀐 파일을 모르고 덮어쓰는 일이 없어진다. 이 변경의 전부다.
- 같은 파일을 두 tab 에 연 경우의 손실도 같이 막힌다. `:e` 로 여는 길(`docs/tasks.md`) 이
  생기기 전에 안전망이 먼저 깔린다.
- 내용이 같은 되쓰기는 조용히 지나간다. 헛경고가 없다.

감수하는 것

- **저장할 때마다 파일을 통째로 한 번 더 읽는다.** 지금 크기에서는 문제가 아니지만 공짜도 아니다.
- **다시 읽기(reload) 가 없다.** 충돌을 알려도 사용자가 할 수 있는 것은 `:w!` 로 덮어쓰거나
  포기하는 것뿐이다. 바깥 내용을 가져오려면 편집기를 나가야 한다(`docs/tasks.md`).
- **읽은 뒤부터 쓰기 전까지의 틈은 여전히 있다.** 검사와 `WriteFile` 사이에 남이 쓰면 덮어쓴다.
  atomic 하게 하려면 잠금이나 임시 파일 + rename 이 필요한데, 한 사람이 쓰는 편집기에서 그
  복잡도를 낼 이유가 없다.
- **`:w!` 를 습관적으로 치면 아무 소용이 없다.** 헛경고를 없앤 것이 그 습관을 막는 유일한 장치다.

## 대안

**mtime + 크기** — vim 이 하는 방식이고 비용이 파일 크기와 무관하다. 내용이 같은 되쓰기마다
경고가 떠서 `:w!` 가 습관이 된다.

**mtime 으로 거르고 다르면 해시 확인** — 헛경고도 없고 평소 비용도 없다. 상태와 분기가 는다.
큰 파일이 실제로 문제가 될 때 옮겨갈 자리로 남겨둔다.

**포커스가 돌아올 때 검사(vim 의 `checktime`)** — 더 일찍 알려준다. 알림 자리와 다시 읽기 결정이
따라온다. 저장 직전 검사와 배타적이지 않으므로 나중에 더할 수 있다.

**확인창으로 묻기** — vim 의 실제 동작에 더 가깝다. mode 가 하나 늘고, 단계 수는 `:w!` 와 같다.

**잠금 파일(`.file.swp` 같은 것)** — 두 편집기가 같은 파일을 여는 것 자체를 막는다. 편집기가
비정상 종료하면 남은 잠금을 치우는 문제가 따라오고, 편집기 밖에서 바뀌는 경우는 여전히 못 막는다.

## 이 ADR 이 정하지 않는 것

- 다시 읽기(`:e!`) 와 충돌 시 바깥 내용을 가져오는 방법
- 포커스 복귀 시 검사(`checktime`) 와 그 알림 형태
- 세 방향 병합이나 diff 표시. 이 편집기가 할 일인지부터 정해야 한다
- 같은 파일을 두 tab 에 열지 못하게 할지. 이 결정은 손실만 막고 여는 것은 그대로 둔다
- `:w <파일>` 로 다른 이름에 쓸 때의 검사 규칙. 그 명령이 아직 없다
