# ADR-0142 커밋 상세에 줄 수를 낸다. 재 보고 정했다

- 상태: 채택
- 날짜: 2026-09-13
- 관련: ADR-0115(커밋 기록 화면), ADR-0140(diff 판, 이 값을 낼 수 있게 한 셈이 거기서 왔다), ADR-0094(git 마커 색)

## 맥락

`COMMIT` 화면의 파일 목록이 이름까지만 적고 있었다. `git-commit.go` 가 그 자리에 이렇게 적어 두었다.

> 줄 수(`+12 -3`) 는 내지 않는다. blob 을 전부 풀어 diff 를 돌려야 나오는 값이고, 그 값이 필요해지는 것은 diff 화면과 함께다.

diff 판이 생기면서 그 셈이 생겼다(ADR-0140). 남은 것은 **값을 치를 만한가**였다.

## 1. 먼저 쟀다

이 저장소의 커밋 258 개로 쟀다.

| 재 것 | 평균 | 가장 큰 커밋(192 파일) |
| --- | --- | --- |
| 지금(tree 만 견줌) | 9.2ms | 126ms |
| 줄까지 세면 | 20.8ms | 288ms |
| **늘어나는 값** | **11.6ms** | 162ms |

**치를 만하다.** 읽는 일이 통째로 Cmd 안에서 돌아서(`readCommitDetail`) 그동안 화면이 멈추지 않는다. 평균 12ms 는 눈에 띄지 않고, 최악이 커밋 하나를 여는 데 0.16 초 더다. 그 자리에는 「읽는 중입니다」가 이미 서 있다.

**값이 드는 곳은 diff 가 아니라 blob 을 푸는 쪽이다.** 세기만 하는 길(줄 안 글자 diff 없이)을 따로 내서 재 봤는데 12.9ms 로 같았다. 잡음 범위다. 그래서 줄을 세는 자리를 둘로 가르지 않고 `buildDiffRows` 를 그대로 쓴다.

## 2. 맞는지는 진짜 git 이 판정한다

`git show --numstat` 과 경로별로 대는 시험을 두었다. ADR-0141 이 그래프에서 세운 것과 같은 손이다. 손으로 적은 기대값은 틀린 셈을 굳힌다.

**고친 줄은 양쪽에 한 번씩 든다.** 사람이 한 일은 하나인데 diff 는 지우기와 넣기 둘로 적기 때문이고, git 도 그렇게 센다. 우리 `diffRowChanged` 한 자리가 `+1 -1` 이다.

## 3. 수는 오른쪽 끝에 선다

```
 파일 13 개  +1,242  -287
 A  docs/adr/ADR-0141-graph-diagonals.md      +160    -0
 M  internal/core/render-graph.go              +39  -105
 M  internal/core/view-graph.go               +101   -31
```

**이름 앞이 아니라 오른쪽 끝이다.** 앞에 두면 자릿수가 파일마다 달라 이름이 들쭉날쭉해진다. 오른쪽에 세우면 수끼리 한 줄로 서서 세로로 훑을 수 있다. 트리가 `M`·`?` 를 오른쪽 끝에 세운 것과 같은 손이다(ADR-0094 §6).

**막대를 그리지 않는다.** git 의 `--stat` 은 `274 +++++---` 처럼 크기에 비례하는 막대를 그린다. 어느 파일이 큰지가 한눈에 보이는 대신 막대 폭을 배당하는 규칙이 새로 필요하고, 이름이 긴 파일에서 그 폭이 먼저 깎인다. 수만으로도 견줄 수 있다.

**이름이 길면 이름을 자른다.** 수는 늘 오른쪽 끝에 선다. 이름은 앞이 같은 것이 많아 뒤가 잘려도 어느 파일인지 남는데, 수는 잘리면 뜻이 없다.

**부호를 직접 쓴다.** `%+d` 는 0 에도 `+` 를 붙여서 지운 것이 없는 파일이 `+0` 으로 적힌다.

**색은 git 마커와 같다.** 넣은 수가 초록, 들어낸 수가 빨강이다(ADR-0094). 고른 줄에는 색을 얹지 않는다. 반전 위에 색을 얹으면 그 자리에서 반전이 끊긴다.

## 4. 합계는 목록 위다

`파일 13 개  +1,242  -287` 한 줄이다.

git 은 목록 **아래**에 적는다(`13 files changed, ...`). 우리는 위에 둔다. **목록이 길면 아래는 화면 밖이다.** 커밋 하나가 파일 스물을 건드리면 그 화면에서 합계를 보려고 끝까지 굴려야 하는데, 「이 커밋이 얼마나 큰가」는 목록을 훑기 **전에** 묻는 것이다.

## 5. 줄로 셀 수 없는 파일은 그렇다고 적는다

앞 8,000 byte 에 NUL 이 있으면 이진이다. git 이 쓰는 잣대와 같다. 통째로 훑지 않는 것은 큰 파일에서 그 훑기만으로 값이 들기 때문이다.

수 대신 `이진` 이라고 적는다. **비워 두면 안 바뀐 것처럼 보인다.** 그 줄은 수 칸에 맞추지 않고 오른쪽 끝에만 세운다. 수가 아니라 말이라 자릿수를 나눠 쓸 것이 없다.

`git show --stat` 은 `Bin 12 -> 34 bytes` 로 byte 수까지 적는데, 그 수로 할 일이 없어서 낸다는 사실만 적는다.

**submodule 은 빈 것으로 친다.** 파일이 아니라 커밋 해시라 풀 blob 이 없다. git 도 그 줄에는 수를 적지 않는다.

## 결과

- 파일마다 `+274  -12` 가 오른쪽 끝에 선다. `git show --numstat` 과 같은 셈이다
- 목록 위에 합계 한 줄이 선다
- `git show --numstat` 과 경로별로 대는 시험이 생겼다. 이 셈의 기준선이다
- `commitFile` 에 `added`·`removed`·`binary` 가 는다
- `git-commit.go` 가 「줄 수는 내지 않는다」로 적어 두었던 자리가 닫혔다

**대가**

- **커밋 상세를 여는 값이 두 배 남짓이다.** 평균 9ms 에서 21ms 로 는다(§1)
- **파일이 아주 많은 커밋에서는 0.3 초쯤 든다.** 그동안 「읽는 중입니다」가 선다
- **이름이 긴 파일은 이름이 잘린다**(§3)
- **`git diff --stat` 의 막대가 없다**(§3)

## 대안

- **그대로 두기**
	- 여는 값이 지금 그대로다.
	- 「이 커밋이 얼마나 큰가」를 화면에서 볼 길이 없다. 파일 이름만으로는 한 줄 고친 것과 통째로 새로 쓴 것이 같아 보인다.
- **세기만 하는 셈을 따로 내기**
	- 그리는 데 쓰는 줄 안 글자 diff 를 건너뛴다.
	- 재 보니 값이 같았다. 병목이 blob 을 푸는 쪽이다(§1).
- **고를 때 그 파일만 세기**
	- 여는 값이 지금 그대로이고, 훑어 내려가는 만큼만 든다.
	- 합계를 낼 수 없다. 그리고 `j` 를 누를 때마다 밀리초가 드는 것이 한 번에 몰아 드는 것보다 눈에 띈다.
- **막대까지 그리기(`git diff --stat` 과 같게)**
	- 어느 파일이 큰지가 한눈에 보인다.
	- 막대 폭을 배당하는 규칙이 새로 필요하고 이름 칸을 먼저 깎는다(§3).

## 이 ADR 이 정하지 않는 것

- **`GRAPH` 목록에도 줄 수를 적는 것.** 커밋마다 blob 을 푸는 일이라 값의 성격이 다르다. 그쪽은 1,000 개씩 읽는 자리다(ADR-0115 §3)
- **이진 파일의 byte 수**(§5)
- **`--stat` 의 막대**(§3)
