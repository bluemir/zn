# ADR-0121: 커서와 화면 자리는 viewport 가 든다. `Buffer` 는 글만 든다

## 맥락

ADR-0100 이 「커서와 스크롤은 tab 마다 유지하려고 여기 든 것이다. `Buffer` 의 본질이라서가 아니라 실용이고, 화면 분할이 오면 밖으로 빼야 한다」고 적어 두고 닫았다. ADR-0120 이 렌더 경계를 잡으면서 그 자리가 다시 나왔다.

가를 수 있는지 재기 전에 **무엇이 무엇을 만지는지** 부터 셌다. 메서드 128 개를 필드 묶음으로 갈랐다.

| 갈래 | 메서드 | 호출자리 |
|---|---|---|
| 글만 쓰거나 읽는다 | 62 | 271 |
| 커서를 쓰면서 글을 읽는다 | 41 | 166 |
| 커서만 읽거나 쓴다 | 24 | 67 |
| 글을 쓰면서 커서도 옮긴다 | **0** | 0 |
| 글을 쓰면서 커서를 읽는다 | 1 | 25 |

## 1. 마지막 줄이 요점이었다

**「글을 쓰면서 커서도 옮기는」 메서드가 하나도 없었다.** 예상과 달랐다 — ADR-0100 이 「편집이 만들어 낸 자리는 `Buffer` 가 둔다」며 열여섯을 남겨 두었기에 그것들이 얽혀 있을 줄 알았다.

까닭은 그 열여섯이 `lines` 를 **직접 쓰지 않기** 때문이다. `insert`·`pasteText`·`joinLines` 는 `replaceLines` 를 부르고 자기는 커서만 옮긴다. 그래서 「글을 고치는 겹」과 「커서를 옮기는 겹」이 이미 다른 자리에 있었다.

**가르는 데 새로 지어낼 규칙이 없었다.** 이미 있던 금을 따라간 것뿐이다.

얽힌 자리는 하나였다. `beginEdit` 이 되돌린 뒤 커서를 놓을 자리를 undo 항목에 담는다.

**옮기고 보니 그것도 저절로 풀렸다.** `beginEdit` 이 커서를 읽으므로 전이적 닫기에서 viewport 로 따라왔고, 인자로 받게 할 일이 없었다. `Buffer` 는 `edit` 을 담기만 하고 그 안의 커서를 해석하지 않는다 (ADR-0122).

## 2. embed 로 호출부를 지켰다

```go
type viewport struct {
	Buffer      // 글
	viewPlace   // cursorLine·cursorCol·top·topRow
	desiredCol int
	selection  selection
}
```

`editor.buffers` 가 `[]viewport` 가 되고 `activeBuffer()` 가 `*viewport` 를 준다. **`Buffer` 를 embed 하므로 `v.lines`·`v.insert`·`v.Save` 가 그대로 서고, 부르는 233 곳이 한 줄도 안 바뀌었다.**

바뀐 것은 메서드 88 개의 receiver 다. receiver **이름은 `buf` 로 두고 타입만 바꿨다** — 본문을 안 건드려 diff 가 작고, 되돌리기도 쉽다. 이름을 `v` 로 다듬는 것은 따로 볼 일이다.

옮길 메서드를 고르는 데도 자동을 썼다. 필드로 고른 65 개에서 시작해 **빌드 오류가 없어질 때까지 전이적으로 닫았다** — `Buffer` 메서드가 viewport 메서드를 부르면 그것도 viewport 여야 한다. 세 바퀴에 23 개가 더 따라왔다.

## 3. 컴파일러가 층을 지킨다

**`Buffer` 에 커서 필드가 없으므로 그 40 개는 커서를 만질 수 없다.** ADR-0117 이 패키지를 갈라서 얻으려던 것을 패키지 없이 얻었다. 같은 패키지 안이라도 type 이 갈리면 필드 접근은 막힌다.

| | 든 것 | 메서드 |
|---|---|---|
| `Buffer` | `data`·`lines`·`undo`·`redo`·`disk`·`git`·`syntax`·`diagnostics`·`indent`·`tab`·`path` | 40 |
| `viewport` | `Buffer` + 커서·`top`·`desiredCol`·`selection` | 88 |

## 4. 파일을 여는 함수가 창을 준다

`newBuffer`·`newEmptyBuffer`·`OpenBuffer` 가 `viewport` 를 돌려준다. 「글을 만드는 함수가 창을 준다」는 것이 어색해 보이지만, **지금은 tab 과 파일이 1:1 이라 「파일을 열면 그것을 볼 창이 하나 생긴다」가 사실이다.**

부르는 쪽이 `viewport{Buffer: newBuffer(...)}` 로 감싸는 길도 있었는데, 그러면 시험까지 243 곳이 바뀐다. 이름을 다시 보는 것은 화면 분할이 올 때 같이 한다.

## 남는 것

- **화면 폭(`width`) 인자.** 아직 메서드 예순 남짓이 받는다. 화면 행 이동과 `desiredCol` 이 줄바꿈에 걸려 있어서인데, 그 둘이 viewport 로 갔으므로 이 인자도 그쪽으로 모을 수 있다
- **receiver 이름.** 88 개가 `buf` 인 채로 viewport 다
- **화면 분할.** 그때 embed 를 `*Buffer` 로 바꾸면 창 여럿이 글 하나를 가리킨다. 이 결정이 그 길을 열어 둔 것이고, 지금 값 embed 인 것은 tab 과 1:1 이기 때문이다

## 되짚은 것

**세기 전에는 52 곳이 엉켜 있다고 보았다.** 「글+보는자리」를 같이 만지는 메서드가 52 개였기 때문이다. 그런데 그 52 를 읽기/쓰기로 한 번 더 가르니 「글을 쓰면서 커서도 옮기는」 것은 0 이었다.

**「같이 만진다」와 「얽혀 있다」가 다르다.** 커서를 옮기려고 줄 길이를 읽는 것은 얽힘이 아니라 아래 겹을 쓰는 것이다. 가를 수 있는지 물을 때는 **어느 쪽을 쓰는지** 까지 세야 한다.
