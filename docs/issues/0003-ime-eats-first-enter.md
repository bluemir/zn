# 0003: 한글로 검색어를 치면 첫 Enter 를 입력기가 먹는다

- 상태: **넘기지 않음** — 앱에 키가 오지 않아 앱에서 할 수 있는 것이 없다
- 난 곳: OS 한글 입력기(macOS) 와 터미널. 우리 코드가 아니다
- 날짜: 2026-08-31

## 증상

`/` 검색에서 **한글로** 찾을 것을 치고 Enter 를 누르면 아무 일도 없는 것처럼 보인다. mode 가 `SEARCH` 에 그대로 있고 아래 줄도 그대로다. 한 번 더 누르면 그때 검색이 돌고 normal 로 나온다.

영문으로 치면 한 번에 나간다.

## 재현

1. 한글 입력기를 켠다
2. `/` 를 누르고 `한글` 을 친다
3. Enter 를 한 번 누른다 — 그대로 `SEARCH` 다
4. Enter 를 한 번 더 누른다 — `한글` 로 검색이 돌고 normal 로 나온다

## 우리 코드가 아니라는 근거

**앱은 Enter 를 한 번만 받으면 한 번에 나간다.** 검색 mode 를 세우고 키를 먹여 재 보았다.

| 친 것 | 결과 |
|---|---|
| `/` `a` `l` `p` `h` `a` Enter | `viewEditorNormal`, 커서가 매칭으로 감 |
| `/` `한` `글` Enter | `viewEditorNormal`, 커서가 매칭 줄로 감 |

**Enter 가 다른 이름으로 올 길도 없다.** bubbletea 는 「Enter 같은 특수 키의 `Text` 는 비어 있다」고 문서에 못 박아 두었고(`key.go`), `KeyEnter`·CR(13)·keypad enter 셋 다 `String()` 이 `"enter"` 다. 우리 switch 는 그것을 받는다.

**조합 확정 글자는 제대로 온다.** 두 번째 Enter 로 돌아간 검색이 `한` 이 아니라 `한글` 을 찾는다. 그러니 확정된 글자가 버려지는 것도 아니다.

남는 설명은 하나다. `/한글` 을 친 시점에 마지막 `글` 은 아직 **입력기가 조합 중**이라 앱에 오지 않았고(우리 입력은 `한` 까지다), 화면에 보이는 `글` 은 터미널이 그린 조합 글자다. 이때 Enter 는 **조합을 확정하는 데 쓰이고 앱까지 오지 않는다.** 확정된 `글` 이 그제서야 앱에 닿아 입력이 `한글` 이 되는데, 화면에 보이던 것과 같아서 아무 일도 없는 것처럼 보인다.

같은 자리를 ADR-0008 이 normal mode 쪽에서 이미 적어 두었다 — 「마지막으로 누른 키는 입력기가 조합 중이라 편집기에 도착하지 않는다」. normal 에서는 **동작이 한 키 밀리는** 모습이고, 검색·명령줄에서는 **Enter 를 두 번 쳐야 하는** 모습이다. 같은 일이다.

## 지금 어떻게 넘겼는가

넘기지 않았다. 앱에 키가 오지 않으므로 앱에서 할 수 있는 것이 없다. 「조합 중인 글자가 있으면 Enter 를 한 번 더」가 이 터미널에서 한글로 쓰는 값이다.

vim 도 같은 터미널·입력기에서 같게 동작한다. 앱 위층의 일이다.

## 다시 나면 무엇부터 볼지

**검색이 무엇을 찾았는지 먼저 본다.**

- `한글` 을 찾았으면 이 문서의 일이다. 앱은 제 일을 했다
- `한` 만 찾았으면 **다른 일이다.** 확정 글자가 버려진 것이고, 그때는 조합 확정을 붙여넣기(`tea.PasteMsg`) 로 주는 터미널일 수 있다 — 우리는 그것을 insert mode 에서만 받는다(`view-editor-insert.go`)
