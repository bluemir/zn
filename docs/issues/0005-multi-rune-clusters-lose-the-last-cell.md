# 0005: 여러 rune 으로 된 글자가 든 격자 행이 마지막 칸을 잃는다

- 상태: **피했다** — spacing mark 는 목록에서 뺐고(452 개) ZWJ 이모지는 격자에 첫 rune 만 그린다. 본문에 그 글자가 들어오면 그대로 난다
- 난 곳: `ultraviolet` (bubbletea v2 의 렌더러). 여러 rune 으로 된 grapheme cluster 가 든 행의 마지막 칸을 그리지 않는다. **폭은 우리와 터미널이 같게 세는데도 난다**
- 곁들여 갈리는 것: `Emoji_Presentation=No` 인 이모지 5 개(우리 한 칸, 터미널 두 칸)
- 날짜: 2026-09-07

**진단을 두 번 고쳤다.** 처음에는 `Mc` 폭이 터미널과 갈리는 것으로 봤는데 재보니 `Mc` 폭은 tmux 와 일치했다. 그다음에는 결합 문자만의 문제로 봤는데 ZWJ 이모지에서도 났다. 아래는 마지막으로 잰 값에 따른 것이다. 무엇을 어떻게 갈랐는지가 이 문서의 값이다.

## 증상

특수문자 판에서 **격자 행의 오른쪽 테두리가 사라지고** 화면이 아래로 밀린다. 두 갈래에서 났다.

```
DEVANAGARI 로 걸렀을 때:
│ │  ि    ◌ु   ◌े   ो    ◌ऺ   ा    ी    ◌ू   ◌ै   ौ      ← 오른쪽 `│` 가 없다

사람 으로 걸렀을 때:
│ │  🧑  👨  👶  🧒  👩  🧚  👪  🧑‍🎓  💂  👦  🕵      ← 같다
```

## 재현

```bash
D=./.claude/skills/run-zn/driver.sh
ZN_WIDTH=80 ZN_HEIGHT=20 $D start docs/tasks.md
$D keys ':' s y m b o l s Enter
$D keys 사 람                         # 또는 D E V A N A G A R I
tmux capture-pane -t zn-driver -p | sed -n '13,16p'
```

나가는 바이트를 같이 받으면 원인이 바로 보인다.

```bash
tmux pipe-pane -t zn-driver -O 'cat >> /tmp/grid.log'
# ... 키를 넣고 ...
LC_ALL=C grep -o '\[7[0-9]G\|\[80G' /tmp/grid.log | sort | uniq -c
```

## 원인

**우리 계산은 맞았다.** 격자 한 칸이 전부 4 칸이고 행이 전부 80 칸이다. 유니코드 전체(12000 여 개) 를 칸에 넣어 재도 어긋나는 글자가 없었다. 칸을 이어 붙인 폭도 칸 폭의 합과 같다 — 칸 경계에서 클러스터가 합쳐지지도 않는다.

**터미널도 우리와 거의 같게 센다.** 큐레이션 표 1307 개를 하나씩 터미널에 찍고 커서 열을 물어(DSR 6) 우리 폭과 견줬더니 **어긋난 것이 5 개**였다.

| 글자 | zn | 터미널 | 비고 |
|---|---|---|---|
| `☝` U+261D | 1 | 2 | `Emoji_Presentation=No` |
| `✍` U+270D | 1 | 2 | 같음 |
| `✌` U+270C | 1 | 2 | 같음 |
| `🖐` U+1F590 | 1 | 2 | 같음 |
| `🕵` U+1F575 | 1 | 2 | 같음 |

### 렌더러가 마지막 칸을 그리지 않는다

그 행이 이렇게 끝난다.

```
│ │  ◌़   ꣹   𑬂   𑬉   ◌्   ः    ि    ◌ु   ◌े   ो    ◌॓\x1b[80G
                                                        ↑ 커서만 옮기고 아무것도 쓰지 않는다
```

정상 행은 `│\r\n` 으로 끝난다. 여기서는 `\x1b[80G` 나 `\x1b[79G` `\x1b[78G` 로 커서만 옮기고 오른쪽 테두리를 **그리지 않는다.** 한 행에 여러 rune 글자가 몇 개 있는지에 따라 열이 달라진다.

`ultraviolet` 이 셀 버퍼를 이전 프레임과 견주어 바뀐 셀만 그리는데, 여러 rune 클러스터가 든 줄에서 셀 대응이 어긋나 마지막 칸을 「안 바뀐 것」으로 본다.

**폭 문제가 아니라는 것을 세 번 갈라 확인했다.**

1. 위 다섯 개에 `U+FE0F`(VS16) 를 붙여 폭을 터미널과 맞췄다. 우리도 2, 터미널도 2 가 됐다. **그런데도 격자는 깨졌다**
2. 여러 rune 글자(ZWJ 6 개 + VS16 5 개) 를 목록에서 빼니 **격자가 완전히 정상**이 됐다. `\x1b[7xG` 가 사라지고 테두리가 다 살아났다
3. `◌֙`(`◌` + Mn, 2 rune, 폭 1) 만 든 격자는 처음부터 정상이었다. **폭 2 이면서 여러 rune 인 클러스터**가 조건으로 보인다

issue 0001 과 같은 부류다. 그쪽은 `DCH` 로 셀을 당기는 자리였고 이쪽은 셀 대응이다.

### 곁들여: 터미널이 더 넓게 그리는 글자

`mode 2027` 을 끄고 켜서 잰 값이다.

| 잰 것 | zn | Ghostty 1.3.1 | Ghostty + 2027 | tmux 3.6a |
|---|---|---|---|---|
| `space` + `ि`(U+093F, Mc) | 1 | **2** | **2** | 1 |
| `a` + `ि`(Mc) | 1 | **2** | **2** | 1 |
| `◌` + `ि`(Mc) | 1 | **2** | **2** | 1 |
| `space` + `֙`(U+0599, Mn) | 1 | 1 | 1 | 1 |
| `◌` + `֙`(Mn) | 1 | 1 | 1 | 1 |
| `🕵`(U+1F575) | 1 | 2 | 2 | **2** |
| `👨‍👩‍👧`(ZWJ) | 2 | **6** | 2 | 2 |

- **`Mc` 는 Ghostty 에서만 갈린다.** tmux 는 우리와 같다. `mode 2027` 로도 고쳐지지 않고 `◌` 에 얹어도 두 칸이다
- **`🕵` 갈래는 터미널 둘 다 두 칸이다.** 우리 쪽이 좁게 센다
- **ZWJ 는 `mode 2027` 로 고쳐진다.** 6 칸이 2 칸이 된다. 그 모드를 켤지는 `docs/tasks.md` 에 있다

## 우리 코드가 아니라는 근거

- 격자 한 칸과 행 폭을 우리 자로 재면 전부 맞는다. 유니코드 전체를 넣어 봤다
- 나가는 바이트에 `\x1b[80G` 가 있다. 우리는 그 escape 를 짓지 않는다. 우리가 넘기는 것은 80 칸 문자열 하나뿐이고, 셀로 옮기고 커서를 옮기는 것은 렌더러다
- 폭을 터미널과 맞춰도(VS16) 그대로 난다. 폭 어긋남으로 설명되지 않는다
- tmux 의 폭 계산이 우리와 같은데도 난다. 터미널이 폭을 다르게 세는 것만으로도 설명되지 않는다
- 여러 rune 글자를 빼면 없어진다

**우리가 폭을 고칠 수는 없다.** 폭 계산만 바꾸면 `ultraviolet` 은 여전히 `x/ansi` 로 세므로 어긋나는 자리가 옮겨갈 뿐이다. ADR-0072 가 그 이유로 프로세스를 다시 시작하는 길을 골랐는데, 여기엔 그런 손잡이(env) 가 없다.

## 어떻게 넘겼나

### 1. spacing mark(Mc) 를 목록에서 뺀다

`indexSymbols` 가 `unicode.Mc` 를 거른다. 452 개가 빠진다(12265 → 11813).

```go
if unicode.Is(unicode.Mc, r) {
	return false
}
```

**둘에 걸려서다.** 앞 글자에 결합해 여러 rune 클러스터를 만들고, Ghostty 에서는 폭까지 갈린다. 어느 쪽도 우리가 고칠 수 없다.

근거는 「**낼 수 없는 글자는 목록에 세우지 않는다**」다. 큐레이션 표가 `NO-BREAK SPACE`·`ZERO WIDTH SPACE` 를 넣지 않은 것과 같은 규칙이다(ADR-0056).

큐레이션 표에는 `Mc` 가 하나도 없어서 손으로 적은 글자는 그대로다. 시험이 `TestIndexSymbolsSkipsSpacingMarks` 다.

**대가: 인도계 모음 기호를 특수문자 판으로 넣을 길이 없어졌다.** 그 글자를 쓰는 사람은 입력기로 넣는 것이 정상이고, 우리 판은 그것을 낱개로 세울 수 없다.

### 2. ZWJ 이모지는 격자에 첫 rune 만 그린다

`symbolGlyph` 가 한다. `👨‍💻` 를 격자에는 `👨` 로 그리고 **넣는 것은 원래 글자다.**

```go
if runes := []rune(char); len(runes) > 1 {
	first := string(runes[0])
	if textarea.WidthOf(first) == textarea.WidthOf(char) {
		return first
	}
}
```

**폭이 줄지 않을 때만 그렇게 한다.** `👨‍💻` 는 첫 rune 도 두 칸이라 칸이 그대로다. `☝️`(글자 + VS16) 는 첫 rune 이 한 칸이어서 떼면 칸이 밀린다.

**임시로 피하는 것이다.** 렌더러가 고쳐지면 되돌린다. 격자에서 `👨‍💻` 와 `👨` 가 같은 모양으로 보이는 것이 대가이고, 무엇을 넣는지는 이름줄이 알려준다.

시험이 `TestSymbolGlyphDrawsFirstRuneOfZWJ`, `TestSymbolGlyphKeepsCharWhenFirstRuneIsNarrower` 다.

### 3. `☝` 갈래 다섯은 그대로 둔다

`VS16` 을 붙이면 폭은 맞지만 여러 rune 이 되어 1 번 문제에 걸린다. 떼면 폭이 갈린다. 둘 다 안 되므로 손대지 않고, **터미널이 우리보다 넓게 그리는 글자**로 남긴다 — `⬠`·`①` 과 같은 자리다(docs/issues/0004).

`🕵` 가 든 격자 행은 여전히 한 칸 밀린다.

## 남은 것

- **본문에 그런 글자가 들어오면 그대로 난다.** 목록에서 빼고 격자에서 다르게 그린 것은 판을 지킨 것이고 폭 문제를 푼 것이 아니다
- `🕵` 갈래 다섯이 든 격자 행은 아직 밀린다
- 고치는 길은 위(upstream) 에 있다
  - `ultraviolet` 의 셀 대응. 재현 절차와 나가는 바이트가 이 문서에 있다
  - `x/ansi` / `displaywidth` 의 클러스터 폭. spacing mark 를 세게 하는 손잡이가 열리면 우리 답을 Ghostty 에 맞출 수 있다

## 다시 나면

1. `tmux pipe-pane` 으로 나가는 바이트를 받아 **`\x1b[<n>G` 로 줄이 끝나는지** 본다. 있으면 렌더러가 마지막 칸을 빠뜨린 것이다
2. 우리 자로 그 행을 재본다. 80 칸이면 우리 쪽은 맞게 낸 것이다
3. **폭 어긋남인지 셀 대응인지 갈라라.** 폭을 맞춰 놓고도 나면 셀 대응이다. 여러 rune 글자를 빼서 없어지는지도 같이 본다
4. 터미널이 그 글자를 몇 칸으로 세는지는 글자를 찍고 `ESC[6n` 으로 커서 열을 물어 잰다. `mode 2027` 을 끄고 켜서 둘 다 재면 그 모드가 먹는지도 같이 나온다. 표 전체를 재는 것이 낱개로 짐작하는 것보다 빠르다
